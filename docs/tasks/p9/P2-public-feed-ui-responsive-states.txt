CLIENT ARCHITECTURE
Use a small same-origin JavaScript client served by the existing Express/static-resource boundary. Prefer one straightforward file such as:

`src/app/web/public/public-feed.js`

No bundler/transpiler/framework is required.

The client should derive the Publication slug from the canonical page URL and request:

`/api/publications/<encoded-publication-slug>/feed`

Use the existing API as the only authoritative data boundary. The client MUST NOT:
- duplicate public eligibility predicates;
- sort/re-rank feed rows differently from the server;
- infer Source trust/operational state;
- attempt Source collection;
- use another database/read path;
- substitute identity/canonical URLs for the supplied `originalUrl`.

PRESENTATION STATE MACHINE
Implement explicit observable states:

`loading -> populated | empty | unavailable | error`

Required semantics:
- loading is visible while the API request is unresolved;
- HTTP 200 + non-empty items -> populated;
- HTTP 200 + empty items -> empty, while still showing successful Publication identity;
- HTTP 404 -> generic unavailable/not-found state;
- any missing Publication and any non-public Publication MUST remain indistinguishable on the public page;
- HTTP 503/network/parse/unexpected response failure -> bounded generic dependency/error state;
- backend error text, stack traces, connection strings, and synthetic secret-like details must never be surfaced.

Do not invent automatic retry loops, offline persistence, stale cache fallback, or a second hidden fetch path in Phase 9.

PUBLICATION IDENTITY
On successful 200 responses:
- use the API-returned Publication name as the visible page identity;
- use API data rather than the URL slug as the display name;
- update the document title from successful Publication identity where appropriate;
- never hard-code the initial Publication/topic in shared UI source or tests except where a test is deliberately proving configuration-specific data remains data.

UNTRUSTED TEXT RENDERING
Publication name, headline, and Source display name are untrusted presentation data.

Render them with safe DOM text operations such as `textContent`/created text nodes. Do not use `innerHTML`, string-built HTML, script execution, or unsafe attribute interpolation for Source-provided content.

Browser tests MUST include markup-looking strings and prove they remain inert visible text rather than executable/interpreted markup.

ORIGINAL HEADLINE DESTINATION
Every populated headline link MUST use exactly the API-supplied stored `originalUrl` as the reader destination.

The Accepted ADR requires `original_url` as the primary public destination. Never substitute `canonical_identity_url`, a cleaned URL, a Platform-hosted redirector, or a reconstructed URL.

A defensive client presentation check that a link is an absolute `http:` or `https:` URL is acceptable, but it must not become a parallel Source-domain/eligibility policy engine. If an impossible/malformed API item is encountered, fail safely/generically rather than widening policy or navigating to an unsafe scheme.

External navigation must be understandable to keyboard/screen-reader users. If opening in a new tab is chosen, use the appropriate rel/security/accessibility behavior; opening in the same tab is also valid if implemented consistently. Do not contact external publishers from deterministic browser tests.

UTC DATE RULE
Until Publication presentation timezone/settings exist, derive the displayed calendar date from `effectiveFeedDate` in UTC.

Do not allow browser locale timezone defaults to shift the calendar date.

Implement a small explicit date formatter using UTC semantics. Locale may control textual month styling only if timezone is fixed to UTC and deterministic assertions do not depend on the test machine's local zone.

Browser coverage MUST include a timestamp near a UTC day boundary and execute the browser under a deliberately non-UTC timezone/context so viewer-local time would produce a different calendar day if the implementation were wrong.

Do not add a Publication timezone field or migration in Phase 9.

DESKTOP PRESENTATION
At representative desktop width the visible core feed must support the customer's concept:

`Date | Headline | Source`

Requirements:
- reverse chronological order remains exactly the server-returned order;
- headline is the dominant interactive element;
- Source identity is clear;
- dates are readable and UTC-stable;
- rows wrap rather than truncating important headline/source text into unusability;
- semantic structure is understandable without relying solely on visual column position.

A semantic list/grid is acceptable and may be preferable to a literal `<table>` if it enables accessible responsive transformation. Do not re-sort rows in CSS/JS.

MOBILE PRESENTATION
At representative mobile width do NOT compress the desktop three-column layout into an unreadable table.

Use a stacked item concept such as:

`AUG 6 · SOURCE NAME`
`Linked article headline`

Requirements:
- no horizontal page overflow caused by the feed layout;
- headline text wraps;
- Source/date identity remains visible;
- links remain usable/tappable;
- keyboard focus remains visible;
- the mobile layout represents the same item ordering/data as desktop.

Phase 9 requires sane basic mobile rendering, not final Phase 13 accessibility/responsive/theme polish.

ACCESSIBILITY BASELINE
Within Phase 9 scope provide basic semantic/accessibility behavior sufficient for the tech demo:
- one sensible primary heading;
- state changes exposed appropriately to assistive technology without noisy duplicate announcements;
- meaningful link text (the headline itself);
- visible keyboard focus;
- logical tab order;
- no pointer-only interaction;
- reasonable tap target/padding;
- accessible contrast for the chosen simple baseline palette.

Do not build a full design system or claim final WCAG/presentation completion.

BROWSER TEST COMPOSITION
Expand the P1 browser suite using the actual production Express app on an ephemeral local port with controlled injected `publicFeed.read` outcomes.

The browser suite must remain deterministic and must not require PostgreSQL or public internet access.

Required controlled cases include:
1. pending read promise -> loading state visibly persists;
2. successful populated feed -> Publication identity and ordered items render;
3. successful empty feed -> explicit empty state with Publication identity;
4. `undefined` for a missing-looking slug -> generic unavailable state;
5. `undefined` for a private-looking slug -> same generic unavailable state/text/structure as missing;
6. thrown error containing synthetic secret-like text -> generic error and no secret leak;
7. publication/headline/source strings containing markup-looking payloads -> inert text only;
8. `effectiveFeedDate` near UTC boundary under non-UTC browser timezone -> expected UTC calendar date;
9. original headline link href equals supplied `originalUrl` exactly;
10. clicking/interacting with the external link is observed through interception without sending a request to the real publisher;
11. keyboard tab reaches headline links with visible focus;
12. representative desktop viewport, approximately `1440x900`, shows usable Date/Headline/Source columns;
13. representative mobile viewport, approximately `390x844`, shows stacked items with no horizontal layout overflow.

Use resilient behavioral assertions. Avoid pixel-perfect screenshot baselines or implementation-private selectors unless no stable accessible selector exists.
