REQUIRED ARCHITECTURE
Use the existing Express Web/API process. Do not introduce a second frontend process or build server.

The preferred Phase 9 shape is a tiny server-delivered HTML/CSS/JS surface beside the existing JSON API. P1 should establish only the HTML/CSS/static-delivery foundation; P2 will add the feed client and rendering behavior.

The canonical page route is exactly:

`GET /publications/:publicationSlug`

The HTML shell MUST:
- be topic independent;
- work for an arbitrary syntactically valid slug without hard-coding the initial Publication;
- not query PostgreSQL merely to deliver the shell;
- not call `publicFeed.read()` merely to deliver the shell;
- not reveal whether the requested Publication exists or is private before the P2 client consumes the canonical API;
- preserve the existing JSON feed and health endpoints unchanged.

A fixed generic shell is intentional. Publication identity comes from the canonical public-feed API in P2.

STATIC RESOURCE BOUNDARY
Prefer a small explicit Web-owned resource surface such as:
- `src/app/web/public-feed-page.ts` for page response/template/header helpers;
- `src/app/web/public/public-feed.css` for the initial shell styling.

Do not add a bundler, transpiler, React, Vue, Svelte, Vite, Next.js, or another application framework.

Avoid inline script/style so the page can operate under a restrictive CSP. P1 does not need to create a placeholder/no-op JavaScript file solely because P2 will later add client behavior.

Static-resource routing MUST be narrowly scoped. Do not expose arbitrary repository paths or use a catch-all static directory that could serve source/config/test files.

CONTENT / SECURITY BASELINE
Collected content is untrusted even though P1 does not render feed items yet. Establish the page security boundary now so P2 does not need to weaken it.

At minimum the HTML response MUST use an appropriate restrictive Content-Security-Policy compatible with the planned same-origin CSS/JS/API client and external headline navigation. It should not permit arbitrary remote scripts, inline executable script, framing, form submission, plugin/object content, or base-URI rewriting unless a specific current requirement proves otherwise.

Also establish appropriate MIME-sniffing protection and explicit content types. Do not leak filesystem paths, stack traces, database details, or internal configuration in page/static failures.

Choose a simple explicit cache policy for the unversioned shell/static assets and test it. Do not invent a CDN/cache architecture in Phase 9.

BROWSER TOOLING DECISION
Add the Playwright library as a development dependency and keep the repository's existing `node:test` runner.

Do NOT introduce `@playwright/test` or a second test-runner architecture. Browser tests should be ordinary `node:test` files selected by the existing `scripts/run-tests.mjs` harness.

Add a substantive root script:

`test:browser`

following the established runner pattern over `test/browser/**/*.test.ts`.

The command MUST:
- select at least one substantive test;
- fail if no browser tests match through the existing runner behavior;
- fail clearly if the required Chromium executable/browser prerequisite is unavailable;
- never silently skip browser coverage and report green.

Chromium installation is an environment prerequisite, not a committed binary. Use the installed Playwright package's supported browser-install command during validation when needed (for example the equivalent of `playwright install chromium`); do not commit browser binaries or caches.

BROWSER TEST COMPOSITION
Browser tests should start the actual production Express application on an ephemeral local port using existing Web construction/server helpers.

For P1, inject a `publicFeed.read` dependency that would fail the test if called by page-shell delivery. This proves the shell is not a hidden second feed-query path.

The first browser suite must substantively prove at least:
- Chromium launches;
- direct navigation to `/publications/<generic-slug>` succeeds;
- the response renders the generic HTML shell;
- refreshing that page succeeds;
- the expected same-origin CSS is requested/applied;
- there is no initial-Publication/topic hard-coding in the visible shell;
- page navigation does not invoke the public-feed reader.

This is Level 6 foundation evidence only. It does not satisfy the complete Phase 9 browser exit gate; P2 expands the suite.
