SOURCE ENDPOINT TYPE / PROFILE REPRESENTATION
Extend canonical Source-endpoint persistence to support exactly the currently implemented types:
- `rss_atom`;
- `html_listing`.

Use the smallest coherent endpoint-owned durable representation. A JSONB profile column plus positive integer profile revision on `source_endpoints` is preferred if it cleanly satisfies current architecture and tests; do not create a separate profile subsystem/table without a concrete integrity/ownership reason.

Database/application invariants must guarantee:
- `rss_atom` has no HTML listing profile and no HTML profile revision;
- `html_listing` has a valid normalized HTML listing profile and a positive revision before it is collectable/persisted as supported configuration;
- endpoint type, profile, and revision are read/written as one coherent configuration snapshot;
- malformed persisted profile data fails mapping loudly rather than silently falling back to RSS or empty/default selectors;
- Source/endpoint ownership, URL uniqueness, config-key uniqueness, approval/lifecycle/operational state, domain policy, polling, Category defaults, conditional validators, and runtime timing remain unchanged.

Do not introduce Publication tenancy keys or adapter-specific Article persistence.

PROFILE REVISION SEMANTICS
Use deterministic prospective revision behavior:
- first persisted `html_listing` profile revision is `1`;
- replacing an HTML endpoint with a materially different normalized profile increments revision exactly once in the same endpoint-configuration transaction;
- replacing with a semantically identical normalized profile does not increment revision merely because JSON key order/whitespace differed at input;
- `rss_atom` → `html_listing` starts HTML profile revision `1`;
- `html_listing` → `rss_atom` clears HTML profile and revision;
- changing endpoint URL, polling, domain narrowing, Category default, approval, lifecycle, or operational state without changing the normalized HTML profile must not advance profile revision;
- profile edits are prospective and do not rewrite historical Articles, observations, or earlier Collection runs.

If the existing endpoint service transaction is the natural owner for no-op-aware replacement, expose repository primitives/read models needed by P4 rather than embedding admin command semantics inside low-level repository mapping.

- `SourceEndpointConfiguration` truthfully represents type/profile compatibility;
- all creation/bootstrap/admin callers can pass the P1 normalized profile through one canonical validation path;
- `PersistedSourceEndpoint` and `EndpointConfigurationAggregate` expose the HTML profile + revision only where valid;
- find-by-key/find-by-id/aggregate reads used by Worker jobs return the profile snapshot required by P3;
- create-if-absent bootstrap keeps existing no-overwrite behavior: an existing endpoint is not silently rewritten/revisioned by a bootstrap rerun.

Do not duplicate P1 selector/profile validation in repository code. Call the canonical normalizer at untrusted configuration boundaries and validate persisted JSON through the same contract when mapping database rows.

COLLECTION-RUN PARSER DIAGNOSTICS
Extend canonical Collection-run persistence with the smallest bounded fields required to explain parser execution across adapters.

Persist enough to identify for every parsed-content run where applicable:
- parser/adapter kind;
- parser implementation version;
- HTML profile revision used, nullable for RSS/Atom;
- bounded count of matched-item extraction failures/rejections where the adapter reports them;
- bounded parser diagnostic code/detail for successful-with-item-failures or terminal parser failure where existing generic run `error_code`/`error_detail` alone cannot truthfully represent the information.

Prefer a compact summary rather than storing one database row per malformed HTML item. Do not store raw response bodies, raw HTML samples, DOM fragments, stack traces, arbitrary parser objects, or unbounded diagnostic arrays.

Preserve existing run status/stage/outcome arithmetic, retry classification, response validators, duplicate effects, and runtime reconciliation semantics.

Run diagnostic constraints/mapping must distinguish:
- parser not run;
- RSS/Atom parser run without profile revision;
- HTML parser run with the exact positive profile revision snapshot used;
- parser success with zero or positive bounded item-failure count;
- terminal parser failure with safe bounded code/detail.

Do not invent HTML-specific run status values if the existing generic parser/run status vocabulary remains sufficient.
