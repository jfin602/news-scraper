GOAL
Extend the existing Source/endpoint administrator workspace so operators can configure `html_listing` endpoints through structured profile controls, safely preview a bounded operator-supplied HTML sample, inspect parser/profile diagnostics, and use the existing check-now workflow.

P5 is a thin functional consumer. Backend validation/persistence/parser/collection authority remains in P1–P4.

ENDPOINT TYPE UI
Add `HTML listing` as the second supported endpoint type beside `RSS / Atom`.

Required behavior:
- existing RSS/Atom endpoint create/edit workflow remains unchanged except for clearer admission-filter explanation where necessary;
- choosing `html_listing` reveals the structured HTML profile controls required by the actual P1/P4 API;
- choosing `rss_atom` hides HTML-only controls and the submitted payload does not carry stale HTML profile data;
- switching an existing endpoint between types requires the profile data appropriate to the new type and relies on server validation/revision semantics;
- immutable config key, URL, polling, default Category, domain policy, initial state, approval/operational/lifecycle actions remain integrated with the existing editor;
- no generic endpoint adapter JSON editor or arbitrary scraping script field is introduced.

STRUCTURED HTML PROFILE CONTROLS
Render explicit labeled controls for the actual normalized Phase 18 profile, expected to include:
- repeated item/root CSS selector;
- title selector/extraction fields;
- Article-link selector using the governed href extraction;
- optional published/update date selectors/extraction modes exposed by P1;
- optional author selector;
- optional summary selector;
- optional category-label selector.

Do not present XPath, regex, JavaScript, template/expression, browser automation, pagination, Article-page, or subresource controls.

Use clear help text that this is static HTML listing extraction and that Article links may be relative because canonical resolution happens during real collection.

Do not duplicate the complete selector parser/validation algorithm in JavaScript. Client-side required-field/basic input affordances are fine; server response remains authoritative for profile validity.

RSS/ATOM ADMISSION EXPLANATION
Update Source-level admission help so operators can understand the existing distinction:
- phrases affect RSS/Atom endpoints only;
- no phrases means all otherwise-valid RSS/Atom items are admitted;
- HTML listing profile selectors determine which HTML rows become Raw items;
- this is not an HTML keyword filter and not Relevance.

Do not move admission phrases into individual endpoint forms.

SAFE SAMPLE PREVIEW UI
Add a bounded sample-preview panel visible only for HTML listing configuration.

It should include:
- one clearly labeled textarea for operator-supplied HTML sample;
- a Preview button separate from Save endpoint and Check now;
- explicit help that preview parses only the pasted sample and performs no network request;
- loading/in-flight state that prevents duplicate preview submissions;
- success rendering of bounded extracted rows using the P4 response fields;
- safe rendering of parser/item diagnostics;
- empty/error/failure states that do not insert response data as HTML;
- recovery after validation/server errors without leaving controls permanently disabled.

Use `textContent`/safe DOM construction for all Source/parser/operator data. Never inject preview HTML through `innerHTML` or equivalent.

Preview must call only P4's protected preview API with the standard admin mutation header. Browser code must never fetch the configured publisher URL directly.

Saving an endpoint and previewing a draft are independent actions:
- Preview must not save/revision the profile;
- Save must not silently run Preview;
- Preview success must not imply endpoint collection succeeded;
- Check now remains the only real network-backed verification action after valid persisted configuration exists.

PROFILE REVISION / DIAGNOSTICS PRESENTATION
For an existing HTML endpoint, display the current persisted profile revision from P4 without calculating it client-side.

In recent Collection runs, render the P4 parser diagnostics when present, including:
- parser adapter/kind/version;
- profile revision used for the run;
- item/extraction failure count;
- bounded parser diagnostic code/detail.

Keep existing transport/run/status/count presentation intact. Do not expose raw response bodies or attempt to reconstruct them.

When a current endpoint profile revision differs from a historical run revision, the UI may simply display both truthful values; do not label the historical run as invalid or rewrite history.

CHECK-NOW WORKFLOW
Keep the existing Check now button and status behavior.

For an HTML endpoint:
- Check now queues the same P4/P3 durable job;
- accepted/queued UI copy must continue to say collection is queued/not yet finished;
- refreshing operational data shows resulting health/run diagnostics through the existing polling/manual refresh behavior;
- no HTML-specific direct fetch button or browser-side collection path is added.

STATE MANAGEMENT
Extend the existing admin client without duplicating backend/domain state.

At minimum handle correctly:
- new HTML endpoint draft;
- edit existing HTML endpoint;
- edit existing RSS endpoint;
- switch draft/edit type RSS↔HTML;
- select another Source/endpoint while a previous preview request is in flight;
- cancel endpoint edit after entering profile/sample data;
- failed preview followed by corrected preview;
- failed save followed by corrected save;
- endpoint save response with revised profile revision;
- refresh/reselect preserving only persisted state, not stale draft sample/profile fields;
- repeated Check now/refresh behavior already governed by current UI.

Use request sequencing/staleness protection consistent with existing admin patterns where asynchronous results could otherwise render into a newly selected endpoint.

ACCESSIBILITY / RESPONSIVE BEHAVIOR
Preserve the current admin interaction baseline:
- native labels/inputs/selects/buttons;
- logical keyboard order;
- visible focus indication from existing styles;
- preview status/error output with appropriate live-region/alert semantics;
- no color-only error/diagnostic meaning;
- long selectors/URLs/diagnostics wrap instead of causing horizontal page overflow;
- profile controls remain usable at representative desktop and mobile widths already used by the browser suite;
- do not perform unrelated UI-polish redesign work on `main`.
