GOAL
Create the complete pure, bounded, topic-independent static HTML listing profile and parser boundary that later Phase 18 prompts can persist, dispatch in the Worker, and expose through safe admin preview.

P1 owns parser/profile semantics and focused deterministic tests only. It does not persist endpoint profiles, perform network requests, change Worker dispatch, expose admin routes/UI, or create Collection-run database diagnostics.

DEPENDENCY / PARSER POLICY
Use the smallest maintained runtime dependency set that provides standards-aware inert HTML parsing and CSS selector evaluation. Prefer a mature static parser such as Cheerio or an equivalently maintained non-browser library. If structural selector validation requires the underlying selector parser/AST, use the smallest maintained direct dependency needed rather than validating selector grammar with ad-hoc regular expressions.

Do not use Playwright, Puppeteer, jsdom script execution, a headless browser, or any API that loads external resources. Parsing must remain in-process and inert.

GENERALIZE THE PARSER BOUNDARY
Refactor `src/collection/parsers/parser.ts` only as far as needed so RSS/Atom and HTML adapters can share one truthful parser result contract.

Preserve existing RSS/Atom behavior and tests. Do not make RSS/Atom pretend to have HTML profile semantics.

The shared result must support:
- adapter/parser kind and stable implementation version identity as needed by later run diagnostics;
- successful bounded `RawItem[]` output;
- safe bounded parser failure reason/detail;
- bounded nonterminal item/extraction diagnostic summary for adapters such as HTML where some matched rows may fail while valid rows continue.

Do not expose raw response bodies, DOM nodes, parser-library objects, stack traces, or unbounded diagnostics through the shared contract.

HTML LISTING PROFILE
Create one canonical endpoint-profile type and normalization/validation function under collection/parser ownership. It is inert declarative data and must be reusable by P2 persistence and P4 preview.

Use a small explicit structure equivalent to:
- required `itemSelector`;
- required title field descriptor;
- required Article-link field descriptor;
- optional `publishedAt` field descriptor;
- optional `updatedAt` field descriptor;
- optional author field descriptor;
- optional summary field descriptor;
- optional categories field descriptor.

The exact TypeScript names are implementation details, but the JSON-serializable normalized representation must be stable/deterministic for persistence equality and revision decisions in P2.

Field semantics:
- selectors are evaluated relative to each matched item root;
- title extracts bounded text;
- Article link extracts only an `href` value from the selected element;
- publication/update date may extract bounded text or narrowly allowlisted `datetime`-style attribute data;
- author and summary extract bounded text;
- categories may extract a bounded ordered list of text values from multiple matches;
- absent optional fields remain absent;
- P1 does not add image/language/body extraction beyond the contracted Phase 18 profile surface.

CSS SELECTOR SAFETY
Implement a deliberately small deterministic CSS-selector subset adequate for ordinary static listing pages. It may support ordinary element/class/id/attribute matching plus descendant/child composition where the chosen selector library supports them safely.

Reject unsupported or unnecessarily expensive/general selector behavior rather than silently accepting the entire selector engine. In particular, do not admit executable/custom pseudos, pseudo-elements, selector extensions that interpret arbitrary expressions, or unbounded selector nesting/complexity. If the chosen library supports advanced pseudos such as `:has()` or text-content extensions, reject them unless the current governing docs explicitly require them.

Define explicit constants for at least:
- profile serialized/structural size where applicable;
- selector length;
- selector token/AST complexity;
- input HTML bytes/characters;
- matched item count;
- title/URL/date/author/summary/category value sizes;
- categories per item;
- diagnostic detail length and diagnostic sample count.

Bounds must be substantive and testable, not comments only.

STATIC HTML PARSER
Implement a parser adapter, expected under `src/collection/parsers/`, that accepts fetched HTML plus a validated normalized profile and emits `RawItem` values.

Required behavior:
- parse only the supplied input;
- never execute scripts;
- never load scripts, stylesheets, images, iframes, embeds, Article pages, pagination, or any subresource;
- never perform DNS or network I/O;
- preserve extracted Article URLs as Source-shaped strings, including relative URLs, for later canonical normalization against the terminal fetched endpoint URL;
- never synthesize `RawItem.externalId` from title, selector position/path, hashes, DOM markup, or content fingerprints;
- map extracted title/url/date/author/summary/categories into the existing `RawItem` fields without performing Article-candidate normalization early;
- trim/normalize only enough to enforce the parser/profile contract; canonical Article normalization remains downstream;
- produce deeply deterministic/frozen output consistent with existing parser conventions where practical.

ITEM FAILURE SEMANTICS
For a document that parses successfully:
- zero item-root matches is a stable parser failure;
- each matched item missing/invalid/over-bound required title or Article URL is rejected as an item extraction failure;
- malformed optional fields should be omitted or counted diagnostically according to the normalized profile contract without fabricating values;
- valid rows continue when unrelated matched rows are invalid;
- if no matched row yields a valid required title + URL pair, return a stable parser failure rather than a successful empty list;
- successful output may carry a bounded summary of rejected/malformed rows for later Collection-run diagnostics.

SAFE PREVIEW PRODUCER
Expose a pure function/service boundary that accepts only:
- operator-supplied bounded HTML sample;
- draft profile input.

It validates the profile, invokes the exact same static parser implementation, and returns bounded preview rows/diagnostics suitable for P4. It must import no database, resolver, HTTP fetcher, job, endpoint-lock, scheduler, health, Article persistence, Relevance, or duplicate behavior.

Preview must not echo the raw HTML sample back in success or failure output.

FOCUSED TESTS
Add focused unit/collection tests and deterministic fixtures proving at minimum:
- valid profile normalization produces stable JSON-serializable output;
- malformed/unknown profile keys, missing required descriptors, invalid extraction modes/attributes, unsupported selectors, overlong selectors, and complexity-bound violations fail deterministically;
- valid static HTML produces multiple ordered `RawItem`s with required and optional fields;
- relative Article URLs remain relative Raw-item values;
- no HTML item receives a synthetic `externalId`;
- scripts and event-handler markup remain inert and cannot affect output beyond inert DOM text/attributes explicitly selected;
- zero matches and all-invalid rows are parser failures;
- mixed valid/invalid matched rows preserve valid output and bounded failure diagnostics;
- document, matched-item, categories, field, and diagnostic bounds are enforced;
- hostile/malformed input does not leak the response/sample body or secret sentinel values through diagnostics;
- repeated parsing is deterministic;
- RSS/Atom parser behavior and current RSS/Atom result semantics remain green after shared-interface generalization;
- the pure preview boundary has no network/database dependencies and returns only bounded extracted data/diagnostics.
