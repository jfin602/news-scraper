## `top-tag.php`

Add root-level customer-editable `top-tag.php` as the first-party fallback/reference presentation required by Project Contract Law 13.

Requirements:

- consume only the P3 stable customer local-read entrypoint;
- load/read normalized local state once, then let both presentation blocks consume that same normalized result;
- never require `src/bootstrap.php`, cache/manifests, `sync.env`, upstream URL, bearer token, or internal state-store classes;
- render useful server-side output when local state is usable/stale-usable;
- preserve canonical Article order exactly;
- headline anchors use exact stored normalized `originalUrl` values;
- escape all untrusted Publication/Profile/Article/Source/Category/digest generated text for HTML context;
- treat digest generated text as untrusted plain text, not trusted HTML/Markdown;
- handle empty Articles and unavailable/never-synced/disabled/stale-cutoff states safely and simply;
- do not filter, rerank, deduplicate, regroup, recategorize, reinterpret Source trust, or change destinations;
- no JavaScript required for the core content;
- no News Scraper/Gemini request on visitor render.

Keep the source intentionally editable: PHP and actual HTML elements should be laid out on separate readable lines. Do not build the entire table/page as one concatenated HTML string.

The file is instructional/customer-owned markup. Avoid framework-specific classes or customer-specific wording that makes it look authoritative.

## Locked presentation-block structure

`top-tag.php` must contain two clearly delimited customer-editable presentation blocks after the one normalized local-read setup:

```text
normalized local-read setup

OPTIONAL AI DIGEST SECTION

ARTICLE FEED SECTION
```

Use conspicuous source comments/headings around the two blocks so a customer editing PHP can immediately see where the optional digest markup starts/ends and where ordinary Article rendering starts. The exact comment decoration is implementation-owned; do not make runtime behavior depend on the comments.

The **AI Digest section must be self-contained as presentation markup** so a customer can copy, move, restyle, or remove that whole block without changing synchronization, LKG, local-read configuration, or Article rendering. It may read the already-created normalized local-read result; it must not initialize its own reader, reload configuration, open another state path, or define a second data authority.

The **Article Feed section is independent and unconditional with respect to digest existence**. The intended control flow is:

```text
if a normalized digest exists:
    render the optional digest block

render the Article Feed block using the normal Article path
```

Do not put ordinary Article rendering inside the digest condition, and do not create an alternate Article-rendering path for digest-null state. Removing the digest block from a customized copy of `top-tag.php` must leave ordinary Article behavior intact.

### Optional AI Digest block

When `LocalReadResult->digest` is non-null, render a compact semantic reference section containing:

- a plain reader-facing heading such as `AI News Summary` or an equally clear topic-independent label;
- an explicit indication that the summary is AI-generated;
- the digest generation date/time in a truthful human-readable form;
- a truthful freshness indication when useful, distinguishing `current` from `older` without inventing age-based staleness;
- the Overview text;
- each available Highlight title and explanation in canonical digest order;
- each Highlight's application-resolved Supporting Articles as ordinary anchors using their exact stored `originalUrl` destinations.

Do **not** display provider/model identity by default in the reader-facing reference markup. Those fields remain normalized data available to a customer who deliberately wants them, but the default template should not expose implementation/provider trivia such as a Gemini model name merely because it is present.

When the normalized digest is `null`, emit **no digest-section markup** and proceed directly to ordinary Article rendering. Do not show an AI error, placeholder, empty card, provider failure state, or visitor-time generation control.

Digest presentation must use only simple semantic markup and neutral optional classes such as `ns-digest`, `ns-digest-overview`, `ns-digest-highlight`, and similarly obvious descendants if classes are useful. Do not ship a digest visual design system, inline CSS, framework-specific classes, JavaScript behavior, or customer-specific theme assumptions. The customer owns styling.

Supporting links are a presentation of application-resolved governed Article references, not model-supplied destinations. Never trust or render a provider/model-generated URL as an outward Article destination.
