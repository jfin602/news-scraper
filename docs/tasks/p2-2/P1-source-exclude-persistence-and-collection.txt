
## Persistence contract

Use the smallest representation consistent with the existing Include table and repository conventions. The logical Source state must expose two independently bounded lists:

- Include: existing values and semantics preserved exactly;
- Exclude: new list, empty by default.

The database must enforce equivalent phrase integrity/bounds for Exclude as the existing Include representation: Source ownership, deterministic position/order, trimmed/nonblank safe bounded text, no control-character ambiguity, bounded count, and cleanup with Source lifecycle/deletion according to current relationship rules.

Supported production-forward upgrade must preserve every existing Include phrase/order and all other governed customer state. Do not migrate Include rows into a new representation merely for naming symmetry unless required for correctness; additive change is preferred.

Both lists use the same deterministic literal case-insensitive matching preparation already accepted for Include. Missing optional Source fields normalize to empty lists. Reuse one phrase-list normalizer/bounds owner rather than duplicating almost-identical Include/Exclude validation.

## Collection behavior

At the existing RSS/Atom-only stage after safe parse and before Article-candidate normalization:

1. evaluate Include against only the existing bounded Raw item editorial text fields: title, summary/content text, Source-provided category labels;
2. evaluate Exclude against those exact same prepared fields;
3. reject when Exclude matches regardless of Include result;
4. otherwise preserve current Include behavior;
5. when both lists are empty, collect all otherwise-valid parsed RSS/Atom items exactly as today.

Preserve:

- HTML listing endpoints bypassing this Source RSS/Atom filter entirely;
- Source/endpoint approval, lifecycle, operational, lock, fetch, redirect, network-safety, parser, Article-link, Relevance, identity/provenance, duplicate, and scheduling behavior;
- filtered Raw items terminating before candidate normalization;
- `source_item_filtered_count` accounting for either Include rejection or Exclude rejection;
- filtered items not becoming Relevance `excluded`, normalization failures, Articles, observations, or retroactive mutations;
- Source filter edits remaining prospective only.

Do not add separate counters for Include vs Exclude unless an already-governed observable contract requires them; one existing filtered-item count is authoritative.

## Bootstrap and repository compatibility

Repository reads must return frozen/immutable normalized Include and Exclude lists following existing Source model conventions.
