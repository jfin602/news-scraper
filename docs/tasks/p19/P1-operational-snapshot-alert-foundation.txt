GOAL
Create one canonical read-only operational snapshot for the installation and a protected admin API boundary that exposes truthful, bounded operational state and deterministic alert/status records.

P1 owns the operational semantics consumed by later Phase 19 UI work. The browser must not need to calculate health, queue delay, stale-work state, or alert severity itself.

IMPLEMENTATION BOUNDARY
Prefer a substantive `src/observability/` module boundary, with the smallest repository/query helpers necessary. Do not build a generic telemetry framework or vendor-specific metrics stack.

The snapshot should expose, at minimum, bounded installation-level facts for:
- endpoint counts by existing derived health (`unknown`, `healthy`, `delayed`, `degraded`, `unhealthy`);
- actionable endpoint rows for delayed/degraded/unhealthy states, with Source/endpoint stable identities and existing runtime timestamps/failure counters needed to diagnose them;
- queued and running endpoint-job counts;
- ready-now queued work versus future-scheduled queued work;
- oldest ready job age/queued-since timing when ready work exists;
- expired or suspicious running-job facts when this can be derived from existing lease fields without inventing a second recovery policy;
- current collection-capacity limits and Worker runtime timing values as configuration facts, not mutable dashboard controls;
- one deterministic server-side operational summary/status and bounded alert list sufficient for a later dashboard.

HEALTH / ALERT OWNERSHIP
- Reuse `deriveEndpointHealth`; do not duplicate its thresholds or reinterpret paused/disabled/archived states as health failures.
- Preserve separation between approval/lifecycle/operational state and derived health.
- Alert rules must be explicit, deterministic, topic independent, and based on existing persisted/runtime facts.
- Alerts are observability, not workflow authority: they must not mutate endpoints/jobs, enqueue work, recover leases, pause Sources, or change collection state.
- Do not persist alerts unless source inspection establishes a concrete contract need; P1 should prefer deriving bounded current alerts from durable facts.
- Do not treat an inactive Publication or intentionally paused/disabled Source/endpoint as an outage.
- Do not claim a healthy installation merely because the snapshot query succeeded when durable facts show delayed/unhealthy work.

DATABASE / QUERY RULES
- Keep queries bounded for the singleton installation and expected MVP scale.
- Avoid N+1 Source/endpoint/job lookups.
- Preserve real Source/endpoint/job relationships.
- Do not add a migration or index speculatively. Add an index only if an actual representative query plan/measurement demonstrates a need, and then include focused migration-from-zero/database proof.
- Snapshot reads must not hold locks that interfere materially with the Worker.

ADMIN API
Add the smallest Cloudflare-perimeter-protected admin GET surface needed for P2, registered through the existing admin router structure.

Requirements:
- read-only GET semantics;
- bounded JSON shape with stable machine-readable fields;
- no raw SQL errors, stack traces, database URLs, secrets, unbounded error details, or raw publisher content;
- ordinary dependency failure must return the established bounded admin error behavior rather than cached/fabricated green state;
- no native auth/session system.

TESTS
Add focused tests proving:
- endpoint-health aggregation uses the canonical health function/meaning;
- inactive/paused/disabled resources are not falsely reported as failed;
- queued ready versus queued future versus running work are distinguished correctly;
- oldest-ready timing is deterministic and absent when no ready work exists;
- expired/suspicious-running classification, if exposed, follows existing lease facts and does not mutate recovery state;
- alert ordering/severity/status are deterministic for representative combinations;
- zero/empty installation runtime state is safe and useful;
- snapshot/list sizes are bounded;
- database/query failure is bounded and secret-safe;
- admin route shape and error behavior are stable;
- real disposable PostgreSQL combinations of endpoints/jobs/runs produce the expected snapshot without changing rows.

Preserve all existing endpoint-health, scheduling, job, collection, public-feed, and admin tests.
