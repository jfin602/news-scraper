GOAL
Provide a safe operator-usable PostgreSQL backup, restore, verification, and backup-file retention path, then prove restoration with real PostgreSQL state. Documentation alone is not sufficient evidence.

DESIGN BOUNDARY
Prefer small Node operator modules/scripts that invoke PostgreSQL-native backup tools. Do not invent a custom SQL dump parser, proprietary archive format, or application-level row-by-row backup system.

Expected capabilities, with exact command names chosen consistently with repository conventions:
- create a database backup;
- produce bounded non-secret backup metadata/manifest sufficient to identify creation time/tool/source version where practical;
- restore a backup into an explicitly selected safe target database;
- verify restored schema/application readability;
- prune backup files according to an explicitly supplied retention policy;
- provide a specialized real-PostgreSQL recovery validation command/suite.

Likely package-script names are `db:backup`, `db:restore`, `db:backup:prune`, and `test:recovery`, but source conventions remain authoritative.

CREDENTIAL / PROCESS SAFETY
- Reuse `NEWS_SCRAPER_DATABASE_URL`/existing DB config parsing where appropriate without logging its value.
- Do not print passwords, database URLs, access tokens, environment dumps, or full child-process command lines containing secrets.
- Avoid placing secrets in process arguments where PostgreSQL tooling permits safer environment/native connection handling.
- Construct child-process environment narrowly and intentionally; do not blindly serialize all environment variables into artifacts.
- Capture/translate tool failures into bounded operator errors while preserving useful exit status/tool identity without echoing credentials.
- Validate file paths and required inputs. Do not overwrite an existing backup/restore target silently.

BACKUP SAFETY
A backup operation must:
- fail clearly when required PostgreSQL tooling is unavailable;
- create the output atomically enough that an interrupted/failed dump is not presented as a valid completed backup;
- avoid storing secrets in metadata;
- preserve a format suitable for deterministic restore verification;
- leave ordinary running application behavior unchanged except for the expected database workload of backup.

RESTORE SAFETY
Prefer restore into a fresh/empty explicitly selected database and validate it before any cutover. Do not make destructive in-place replacement of the currently configured database the default command behavior.

Fail closed when:
- target identity is missing/ambiguous;
- target is not safe for the supported procedure;
- backup is missing/corrupt/incompatible;
- restore tool exits unsuccessfully;
- post-restore schema/application verification fails.

Do not silently drop or recreate the configured current database.

REPRESENTATIVE DATA PRESERVATION
The recovery proof must seed and compare representative governed state sufficient to catch incomplete backup/restore, including where current schema supports it:
- singleton Publication configuration/presentation/public/collection state;
- Source/endpoint approval/lifecycle/operational/domain/parser configuration;
- Categories and Relevance rules/history/default references;
- Articles and Source-scoped identity fields;
- Article observations/provenance;
- Collection runs and bounded diagnostics;
- endpoint runtime/conditional validators;
- durable endpoint jobs/retry linkage/lease fields;
- duplicate candidates/groups/Primary/manual authority;
- Article moderation/visibility overrides and change history.

Use semantic assertions on relationships/state, not only row counts.

POST-RESTORE RECOVERY
Exercise realistic restored in-flight state without inventing a new state machine:
- queued jobs remain claimable according to existing policy;
- expired/unstarted running jobs reconcile through existing recovery behavior;
- started jobs/attached Collection runs reconcile without duplicate replay contrary to current contracts;
- interrupted Collection runs receive whatever existing reconciliation guarantees currently govern them;
- safe idempotent retry/replay remains possible because Article identity is Source-scoped/idempotent.

If source inspection shows some requested state is intentionally not recoverable through existing runtime semantics, document the exact limitation and stop if it violates Phase 19's exit gate rather than hiding it.

BACKUP RETENTION
Implement retention/pruning for backup artifacts, not wholesale application-data deletion.

Requirements:
- retention value/policy is explicit operator input or clearly documented deployment config rather than a silently invented universal production number;
- dry-run/list behavior is preferred when practical;
- only files proven to belong to the managed backup set may be deleted;
- path traversal/symlink/foreign-file cases fail safely;
- pruning is deterministic and reports bounded results;
- an invalid retention configuration deletes nothing.

Do not delete Article/provenance/run/moderation history merely to satisfy a retention deliverable unless an existing governing contract explicitly authorizes that data lifecycle.

RPO / RTO BOUNDARY
Do not hard-code arbitrary RPO/RTO targets in generic engine code. Provide enough observed backup/restore duration and procedure information that the actual reference deployment can record explicit targets/ownership in P6/P7.

REAL RECOVERY TEST
Add a specialized recovery suite that fails rather than skips when its declared PostgreSQL/tool prerequisites are missing.

At minimum it must:
1. create a disposable representative database using current migration/bootstrap paths;
2. seed governed representative state;
3. create a real backup with the same implementation/operator path;
4. mutate/destroy the disposable source/target state enough that successful restore is meaningful;
5. restore into a separate fresh disposable database;
6. verify migration ledger/schema plus semantic governed state/relationships;
7. start/use the appropriate repositories/services against restored data to prove application readability;
8. exercise post-restore queued/expired/in-flight recovery cases;
9. prove failed/corrupt restore cannot be mistaken for success;
10. clean up disposable databases/files without hiding test failures.

Do not connect destructive tests to the ordinary configured application DB or a non-disposable database.
