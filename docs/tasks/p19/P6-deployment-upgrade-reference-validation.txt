DEPLOYMENT PROCEDURE
Create/update the smallest authoritative operations/runbook documentation needed for an ordered deployment. Keep it specific enough to execute but not tied to an infrastructure product the repository has not adopted.

Cover, in order where applicable:
- identify exact source SHA and package version to deploy;
- confirm expected Node/npm/PostgreSQL/tooling prerequisites;
- verify required environment variables/secrets are present without printing them;
- verify a current tested backup exists or create one before risky schema work;
- determine whether Web/Worker must be quiesced for the planned schema change;
- run schema status/preflight;
- apply migrations with the existing migration engine;
- start/restart Web and Worker in safe order;
- verify Web readiness/public root/basic API;
- verify Worker readiness/scheduler/consumer/recovery diagnostics;
- verify protected admin surface from the authorized path;
- verify P1/P2 operational state is not showing unexpected backlog/failure;
- define explicit rollback decision points;
- use application/source rollback only when schema compatibility is safe;
- use P5 backup/restore rollback when the deployed schema/data cannot safely run with the prior application;
- record the exact deployed source/version/schema state for later Phase 20 baseline acceptance.

Do not implement an automatic zero-downtime deployment orchestrator unless current repository architecture already has one.

REFERENCE-DEPLOYMENT VALIDATOR
Add a small provider-neutral validation script/procedure for checks that can be automated safely against a supplied deployment configuration.

It may verify:
- canonical public root responds as expected;
- public API/readiness behavior is bounded;
- an unauthenticated request to the protected `/admin` surface is challenged/denied rather than returning the application admin UI directly;
- a supplied direct-origin candidate is not a successful bypass;
- results are bounded/machine-readable and never print Access tokens, cookies, database credentials, or full secret-bearing URLs.

The validator must distinguish observed HTTP outcomes from conclusions. It must fail clearly when required target inputs are absent instead of silently marking the check green.
