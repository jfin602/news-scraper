CURRENT SOURCE / IMPORTANT BASELINE
At expected P4 start:
- `createWebApp()` currently accepts only readiness and exposes `/health/live` + `/health/ready`;
- `main.ts` creates one application Database, wraps it in the readiness dependency, starts the Web server, and closes the database through the existing shutdown path;
- `server.ts` owns listener lifecycle and should not need feed-specific behavior;
- P3 exposes the complete read-side semantic boundary and returns `undefined` for both missing and private Publications.

WEB DEPENDENCY COMPOSITION
Move to one explicit Web dependency object rather than adding compatibility overloads, conceptually:

`createWebApp({ readiness, publicFeed })`

Exact names are implementation-owned.

Requirements:
- keep readiness as an injected boundary;
- inject a small public-feed reader interface/function from P3;
- do not pass raw SQL or route-owned database-query callbacks;
- do not keep both old/new `createWebApp` signatures for compatibility in this pre-production repository;
- update all current callers/tests to the one canonical composition.

MAIN PROCESS WIRING
`src/app/web/main.ts` should bind the P3 public-feed reader to the SAME Database instance already created for Web/API.

Database ownership remains singular:
- do not create a second Pool solely for the feed;
- do not make the feed reader close the shared database;
- preserve current startup failure redaction and graceful shutdown behavior;
- preserve readiness's migration-current check.

PUBLIC ROUTE
Add exactly:
- `GET /api/publications/:publicationSlug/feed`

The route must:
- require no reader authentication;
- pass the route slug to the injected P3 reader;
- never collect/fetch a Source inline;
- not accept search/filter/pagination/limit/cursor query parameters as Phase 8 behavior;
- serialize only the canonical P3 read model.

SUCCESS JSON CONTRACT
For a public Publication, return `200` with shape equivalent to:

{
  "publication": {
    "id": "...",
    "slug": "...",
    "name": "..."
  },
  "items": [
    {
      "articleId": "...",
      "effectiveFeedDate": "2026-08-10T12:00:00.000Z",
      "feedDateSource": "published_at",
      "headline": "...",
      "sourceName": "...",
      "originalUrl": "https://publisher.example/article"
    }
  ]
}

A public Publication with no eligible rows returns the same shape with `items: []` and HTTP 200.

SERIALIZATION
Convert `Date` values explicitly to canonical ISO-8601 strings at the HTTP boundary.

Do not rely on incidental Express/JSON Date serialization as the contract.

Do not add formatted display dates; Phase 9+ presentation owns display formatting.

NOT-FOUND / PRIVATE BEHAVIOR
When the injected P3 reader returns `undefined`, respond:
- HTTP `404`;
- one bounded generic body, expected equivalent to `{ "error": "not_found" }`.

Because P3 intentionally collapses private and missing, route code MUST NOT perform a secondary Publication lookup to distinguish them.

READ/DEPENDENCY FAILURE
If the feed reader throws/fails:
- catch at the public route boundary;
- respond HTTP `503`;
- use one bounded generic body, expected equivalent to `{ "error": "service_unavailable" }`;
- do not expose exception message/cause, SQL, connection detail, credentials, stack traces, raw DB rows, or Source/Article content.

Do not convert an actual read failure to 404/empty 200.

CACHE / HEADERS
Use safe explicit public-feed response headers consistent with current repository conventions. At minimum ensure error behavior is not accidentally cached in a way that would make private/missing/failure state misleading. Do not introduce a speculative caching subsystem; later scale work may add feed caching.

HEALTH ROUTE PRESERVATION
Existing behavior must remain unchanged:
- `/health/live` stays independent from database readiness and returns 200 while listener is responsive;
- `/health/ready` keeps checking the existing readiness dependency and returns deterministic 200/503 with `Cache-Control: no-store`;
- P4 feed failures must not break liveness handling.

PROCESS FAILURE / UNAVAILABLE DATABASE
Preserve the current Web process capability to listen with an unavailable database so:
- liveness still works;
- readiness is 503;
- feed request is bounded 503;
- synthetic database credentials never appear in process output or HTTP output;
- graceful termination still emits the established stopped event and exits cleanly.
