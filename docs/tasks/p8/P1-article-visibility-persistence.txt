MIGRATION
Add one new migration, expected as:
- `migrations/0006_article_visibility.sql`

Do NOT edit any previously committed migration file. Applied migration checksums are immutable history.

The migration should add `articles.visibility_state` with:
- `text NOT NULL`;
- baseline/default value `visible` so existing Phase 7 rows become `visible` and ordinary new inserts have a safe baseline;
- a database CHECK constraint allowing exactly `visible`, `hidden`, `archived`.

Use one canonical schema design. Do not add parallel booleans such as `is_visible`, compatibility aliases, duplicate-role fields, moderation audit tables, or speculative future state.

ARTICLE MODEL
Extend the production Article model with a typed visibility state, e.g.:
- `type ArticleVisibilityState = 'visible' | 'hidden' | 'archived'`
- `PersistedArticle.visibilityState`

Exact naming may follow repository conventions, but there must be one canonical representation.

Update as needed:
- `ArticleRow`;
- `ARTICLE_COLUMNS`;
- row mapping/validation;
- insert/update RETURNING shapes;
- test builders/fixtures whose typed shape legitimately includes persisted Article state.

SOURCE-DERIVED PERSISTENCE MUST NOT OWN VISIBILITY
This invariant is critical:
- new Article creation gets the baseline `visible` state;
- later unchanged observations MUST NOT reset a hidden/archived Article to visible;
- later material Source-derived Article updates MUST NOT reset a hidden/archived Article to visible;
- fallback promotion/strong-ID updates MUST NOT reset visibility;
- visibility is NOT part of the Source-derived `materialChange` comparison used to decide `updated` versus `unchanged`.

Do not add a P1 API to change visibility merely to test this. Database tests may deliberately set a valid non-visible state directly as fixture setup, then exercise the production persistence path and prove preservation.

- digest indexes;
- identity locks;
- one Article + successful observation atomic transaction boundary;
- endpoint/run provenance ownership constraints;
- first-seen/last-seen semantics;

FOCUSED DATABASE TESTS — LEVEL 4
