CANONICAL REPOSITORY MUTATION
Add one narrowly scoped repository operation for changing public status by stable Publication slug, e.g. conceptually:
- `setPublicationPublicStatus(executor, slug, publicStatus)`

Exact naming may follow current repository style, but the behavior must be singular and explicit.

Requirements:
- validate the requested state through the existing canonical public-status normalizer rather than introducing a second enum/parser;
- use a parameterized SQL UPDATE;
- identify the target by Publication slug;
- mutate only `public_status` and normal `updated_at` metadata;
- preserve Publication id/name/slug/`active_for_collection` and all owned Source/endpoint data;
- return the updated canonical `PersistedPublication` on success;
- represent a missing Publication predictably without inserting one;
- do not silently treat a missing Publication as success.

Do not add generic update-object merging, arbitrary Publication field mutation, aliases, or compatibility routes.

LOCAL OPERATOR COMMAND
Add the smallest generic local command, expected as:
- new `scripts/set-publication-public-status.ts`
- new npm script such as `publication:set-public-status`

Canonical invocation should be equivalent to:

`npm run publication:set-public-status -- <publication-slug> <private|public>`

The command must:
- require exactly the slug and desired public status;
- parse database config through the established shared database configuration boundary;
- use the shared Database implementation;
- invoke the narrow Publication repository mutation instead of embedding its own SQL;
- close the database cleanly on success/failure;
- emit bounded deterministic success output identifying the slug and resulting public status;
- emit bounded deterministic failure output for usage/validation/not-found/database failures;
- never print database URLs, credentials, SQL, stack traces, or arbitrary underlying database detail.

Follow existing repository operator-script conventions where applicable. Do not build a general command framework solely for this task.

BOOTSTRAP NO-OVERWRITE LAW
Ordinary `bootstrapPublicationTree()` MUST remain create-if-absent/no-overwrite.

Critical regression:
1. bootstrap a Publication whose config says `public`;
2. explicitly change its persisted state to `private` through the new production repository operation or operator mechanism;
3. rerun ordinary bootstrap;
4. persisted state MUST remain `private`.

Also prove the inverse direction as appropriate. Changing committed/bootstrap input is not a transition mechanism for an existing database.
