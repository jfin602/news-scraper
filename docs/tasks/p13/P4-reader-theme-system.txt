GOAL
Implement exactly three reader theme selections: `system`, `light`, and `dark`.

Theme is local presentation state only. It must never change Publication configuration, server-side state, Article eligibility/order, `/api/feed` parameters, root discovery URL state, cursor identity, or history semantics.

PRE-PAINT INITIALIZATION
Use a small explicit same-origin theme initializer so a saved Light/Dark choice can be applied before the main stylesheet paints.

Prefer a dedicated resource such as `src/app/web/public/public-theme.js`, served at an explicit `/public-theme.js` route with the same no-store and content-safety headers as existing public page resources. Load it early in `<head>` before normal page paint. Keep the current strict CSP compatible with same-origin external resources.

Do not introduce generic directory serving. Continue the existing pattern of enumerating only intended public assets.

LOCAL PREFERENCE CONTRACT
Use one stable topic-independent localStorage key.

Required behavior:
- no stored key means System;
- stored `light` means explicit Light;
- stored `dark` means explicit Dark;
- choosing System removes the fixed stored override;
- an unsupported/corrupt stored value falls back to System and is removed when possible;
- storage read/write/remove failure must not prevent the page or feed from starting and must fall back safely.

Do not use cookies, server sessions, query parameters, Publication persistence, IndexedDB, or reader accounts.

SELECTION VS EFFECTIVE THEME
Keep selected mode separate from effective color scheme:
- System follows `prefers-color-scheme` dynamically;
- Light remains light regardless of system preference;
- Dark remains dark regardless of system preference.

Use a simple document/root attribute or equivalent token strategy. Prefer no forced theme attribute for System, allowing CSS media queries to follow the browser/OS preference; explicit Light/Dark should set one canonical forced state.

Set `color-scheme` coherently so native controls match the effective presentation.

When System is selected and the system color preference changes while the page remains open, effective styling should follow without reload. Explicit Light/Dark must remain fixed until System is selected again.

THEME CONTROL
Expose all three choices explicitly. Do not reduce the contract to a binary sun/moon toggle.

Prefer native radio controls within a fieldset/legend that can be styled as a compact segmented control. A native select may be used on narrow layouts if that is materially cleaner and remains consistent with the approved design. Do not build a custom ARIA widget when native semantics suffice.

Requirements:
- keyboard operable;
- selected mode is understandable to assistive technology;
- selection updates presentation immediately;
- explicit Light/Dark survive reload;
- System resumes system following;
- theme interaction does not submit the discovery form or add browser history entries;
- theme control is independent of Publication/feed availability.

SEMANTIC THEME TOKENS
Establish the Phase 13 semantic token layer for effective light/dark values, including equivalents of:
- `--page-bg`;
- `--surface`;
- `--surface-subtle`;
- `--text-primary`;
- `--text-muted`;
- `--border`;
- `--link`;
- `--focus-ring`;
- `--brand-accent`;
- `--danger`;
- `--control-bg`.

P4 need not finish the editorial layout, but both themes must already be coherent enough for browser tests. Publication `accentColor` remains a restrained brand input and must not replace safe application-owned contrast-critical text/focus/error colors.

Do not add crossfade or large theme animation. Final motion/accessibility polish remains P5.

BROWSER TESTS — LEVEL 6
Using isolated Playwright contexts, prove at minimum:
1. no saved choice + light system preference -> System selected and effective light;
2. no saved choice + dark system preference -> System selected and effective dark;
3. System follows a live system color-scheme change without reload;
4. selecting Light while system is dark forces light and persists across reload;
5. selecting Dark while system is light forces dark and persists across reload;
6. selecting System after an explicit override removes the fixed override and follows system preference;
7. corrupt stored value falls back to System and feed startup still works;
8. unavailable storage access does not break theme/feed startup;
9. keyboard can traverse and activate the theme control;
10. theme changes do not change pathname/search, create discovery history, reset discovery controls, add/change criteria-bearing feed requests, or alter Article data;
11. theme behavior remains coherent across populated, empty, invalid, unavailable, and dependency-error states;
12. existing UTC date and same-context original publisher link behavior remains unchanged.

When asserting effective theme, inspect stable root state plus representative computed presentation values instead of checking only a class name.
