TASK: Correction 1 / P1 — Implement N6WD Article summary bound

CORRECTION SCOPE
This is the sole implementation prompt in correction `c1-n6wd`. It resolves the executable/data portion of known issue N6WD before the 3.0 Gemini roadmap is activated.

The owner-approved contract is already locked: normalized persisted `Article.summary` has a hard maximum of 4,000 characters after plain-text normalization; oversized summaries are truncated at the last usable complete-word boundary that permits exactly `...` while keeping the final value at or below 4,000 characters; when no usable word boundary exists, retain the first 3,997 characters and append `...`. Oversized Source description/content must not cause the Article to be rejected merely because it exceeds this normalized summary bound.

This correction owns the normalizer/persistence bound, additive production migration/data transformation, and focused/regression proof. It does not implement Gemini, URL Context, digest/chat behavior, roadmap activation, Source admission changes, public presentation changes, or unrelated cleanup.

GOVERNED N6WD INVARIANT
Implement exactly this topic-independent behavior:
- `Article.summary` remains nullable Source-derived metadata;
- Source description/content is converted through the existing deterministic plain-text normalization before the final summary bound is applied;
- a normalized summary of 1 through 4,000 characters is preserved unchanged;
- an empty normalized value remains absent under existing semantics;
- a normalized summary longer than 4,000 characters is truncated, not rejected;
- reserve exactly three characters for the literal ASCII suffix `...`;
- prefer the last complete word boundary that fits before that suffix;
- for this correction, a usable word boundary is deterministic normalized whitespace separation, not locale-dependent NLP segmentation; ordinary `collectionPlainText` output already collapses whitespace to single spaces;
- if the content that fits before the suffix ends at a complete word, preserve that complete word rather than unnecessarily backing up to an earlier word;
- if no usable word boundary exists before the 3,997-character content ceiling, retain the first 3,997 characters and append `...`;
- the final stored/normalized summary is never longer than 4,000 characters;
- do not split a Unicode character/surrogate pair while truncating;
- preserve the existing PostgreSQL `char_length` concept for the persisted summary invariant and make TypeScript summary-specific length/truncation behavior agree with that human-character/code-point boundary rather than accidentally relying on UTF-16 code-unit slicing for this field;
- do not change unrelated field limits or generic string-bound semantics solely to implement the summary correction.

Do not introduce Unicode word segmentation, stemming, tokenization, semantic summarization, HTML-aware truncation after the plain-text stage, or Source/topic-specific exceptions.

NORMALIZATION IMPLEMENTATION
The current summary limit is owned by `ARTICLE_CANDIDATE_LIMITS.summary` and `normalizer.ts` currently slices the normalized summary directly.

Change the summary limit to exactly 4,000 and replace the raw slice behavior with one small deterministic summary-specific truncation implementation.

The implementation must:
- call `collectionPlainText` first;
- make the <=4,000 and >4,000 decision using the same character semantics protected by the database summary constraint;
- preserve <=4,000 output byte-for-byte after normal plain-text normalization;
- calculate the maximum pre-ellipsis content as 3,997 characters;
- recognize whether the 3,997-character prefix already ends on a complete word before backing up to the previous whitespace boundary;
- remove the separating whitespace at a selected earlier boundary before appending `...`;
- return exactly one `...` suffix for truncated output;
- never emit a trailing space before `...`;
- remain deterministic across repeated normalization;
- not mutate the Raw item.

Keep ownership narrow. A summary-specific helper inside the existing normalization boundary is preferable to a generic new truncation framework unless current source clearly already has a reusable governed helper.

PERSISTENCE VALIDATION
Trace `src/articles/repository.ts` candidate validation. The persistence boundary must accept every valid normalized summary permitted by the new 4,000-character persisted invariant and reject malformed/out-of-bound direct candidates consistently.

Because generic TypeScript `.length` uses UTF-16 code units while PostgreSQL `char_length` counts Unicode characters, do not leave a summary-only runtime/database disagreement that would reject a valid 4,000-character normalized summary containing non-BMP characters or permit a value outside the database invariant.

Use the smallest summary-specific validation change needed. Do not globally reinterpret every existing field bound as part of N6WD.

Persisted Article create/update/idempotency/provenance behavior must otherwise remain unchanged.

ADDITIVE PRODUCTION MIGRATION
Add exactly one new migration after the current `0016_distribution_credentials.sql`:

`migrations/0017_article_summary_bound.sql`

Do not modify, squash, reorder, or checksum-change migrations `0001` through `0016`.

The migration must, transactionally through the existing migration runner:
1. transform only existing non-null `articles.summary` values longer than the new bound using the same visible N6WD semantics as runtime normalization;
2. preserve summaries already at or below 4,000 characters exactly;
3. for oversized multi-word summaries, preserve the longest complete-word prefix that fits with `...`;
4. use the 3,997 + `...` fallback when no usable boundary exists;
5. preserve valid Unicode text and use PostgreSQL character semantics consistently with the final constraint;
6. not change Article `updated_at`, identity fields, URLs, Source ownership, provenance, dates, moderation/visibility, Category membership/overrides, duplicate state, observations, audit state, or any other unrelated persisted value merely because the migration truncates `summary`;
7. replace the existing `articles_summary_shape_check` maximum of 32,768 with the new 4,000-character maximum while preserving its existing nullable/non-empty/trimmed shape semantics;
8. leave the database in a state where every existing Article satisfies the new constraint before the constraint is activated.

Use the existing constraint name when safely replacing the constraint so schema intent remains obvious. Do not edit `0001_initial_schema.sql` to make clean installs look simpler: supported migration history is immutable after the production baseline.

The migration is a one-time data correction, not permission to persist a second full Article body, AI text, or truncation provenance column.

RAW PARSER / SOURCE ADMISSION BOUNDARY
Do not reduce the existing RSS/Atom raw parser content limit merely because normalized summaries are now 4,000 characters. The larger Raw content/input ceiling is a separate ingestion-safety boundary.

Preserve current ordering:

`parse Raw content -> Source RSS/Atom admission matching -> Article normalization/4,000 summary bound -> Relevance -> persistence`

This means Source RSS/Atom admission filtering may continue to inspect the bounded Raw description/content it already owns before normalization. N6WD must not silently change admission semantics by truncating Raw content earlier.

Relevance `summary_contains` and outward Article summary consumers continue to consume the normalized Article summary and therefore naturally see only the governed bounded persisted value. Do not add compatibility access to discarded suffix text.
