GOAL
Create a durable PostgreSQL-backed queue specifically for endpoint collection attempts, with safe concurrent enqueue/claim/lease/ownership/terminal transitions and recovery primitives suitable for multiple Worker processes.

One `endpoint_collection_job` represents one collection attempt. A later retry is a new successor job, not another hidden attempt inside the same job record. This keeps job/Collection-run provenance auditable and follows the operations contract that each endpoint Collection run is an independent job.

P2 does not execute collection, schedule due endpoints, calculate retry policy, derive health, or start Worker loops.

DURABLE JOB MODEL
Create the first substantive `src/jobs/` capability and a dedicated durable table such as `endpoint_collection_jobs`.

Do not build a generic arbitrary job/workflow/plugin framework. The current job type is endpoint collection and its schema/API may say so directly.

Each job must persist enough state for deterministic diagnostics/recovery:
- stable UUID job id;
- `source_endpoint_id` foreign key;
- status;
- enqueue/availability timestamps;
- attempt number starting at 1;
- optional `previous_job_id` linking retry successors;
- claim owner/worker identifier;
- opaque claim token;
- claimed timestamp;
- lease expiration timestamp;
- optional linked Collection-run id, to be populated by P4;
- terminal timestamp;
- bounded terminal outcome/reason/error code/detail fields needed for diagnostics;
- created/updated timestamps if consistent with repository conventions.

Keep the schema minimal. Do not add Publication IDs, topic scopes, arbitrary payload JSON, priority/routing systems, cron expressions, or future job types.

STATUS MODEL
Use one clear state machine equivalent to:
- `queued` — durable, unclaimed, not terminal;
- `running` — owned by one active claim/lease;
- `succeeded` — terminal successful attempt;
- `failed` — terminal failed attempt;
- `skipped` — terminal non-attempt/blocked outcome where no Collection run occurred;
- `abandoned` — terminal interrupted attempt used by later crash reconciliation.

Exact names may follow existing conventions, but preserve the semantic distinction between a failed executed attempt, a blocked/skipped job, and a crash-interrupted/abandoned attempt.

Enforce status-dependent nullability/ownership invariants at the database boundary where practical:
- queued jobs have no active claim ownership or terminal timestamp;
- running jobs have claim token, worker id, claimed time, lease expiry, and no terminal timestamp;
- terminal jobs have a terminal timestamp and no active claim ownership;
- attempt number is a positive integer;
- `previous_job_id` cannot self-reference;
- a linked Collection run, when present, belongs to the same endpoint through the existing FK relationships and is unique to one job.

OUTSTANDING-JOB UNIQUENESS
Enforce at most one nonterminal queued/running job for a Source endpoint at a time with a real PostgreSQL uniqueness mechanism, preferably a partial unique index over the endpoint id for nonterminal statuses.

This is the race-safety backstop for competing schedulers and retries. Do not rely only on a pre-insert SELECT.

A terminal job must no longer block a later job for that endpoint.

ENQUEUE PRIMITIVE
Provide an idempotent/race-safe enqueue operation with caller-supplied `availableAt`, attempt number, and optional previous job id.

It should return whether a new job was created or an existing outstanding job prevented creation, without surfacing a normal duplicate-enqueue race as an unhandled exception.

Validate endpoint identity and timestamps. Do not contact Sources.

CLAIM PRIMITIVE
Provide an atomic `claimNext...` operation that:
- considers only `queued` jobs whose `available_at <= now`;
- orders deterministically by availability/enqueue time/stable id;
- safely supports multiple Worker processes using transaction row locking such as `FOR UPDATE SKIP LOCKED` or an equivalent PostgreSQL pattern;
- atomically changes exactly one selected job to `running` with worker id, fresh opaque claim token, claimed time, and lease expiry;
- returns no job when none is available;
- never allows the same job to be successfully owned by two workers.

Prefer claiming one job per call for a simple, reviewable API; later dispatch can repeat bounded claims as capacity permits.

CLAIM OWNERSHIP
All mutation of a running job after claim must be guarded by both job id and claim token, not job id alone.

Provide primitives for:
- renewing an active lease;
- attaching the actual Collection-run id once execution starts;
- terminalizing the current attempt;
- deferring/requeueing an unstarted claimed job safely when allowed by a later policy.

A stale/incorrect token must not renew, attach, complete, or otherwise steal ownership.

LEASE / RECOVERY PRIMITIVES
P2 establishes durable claim recovery but does not reconcile interrupted Collection runs yet.

Provide repository operations that let later P4/P7 recovery code:
- list expired `running` jobs in deterministic bounded batches;
- requeue an expired job only when no Collection run has been attached/started;
- distinguish expired jobs that already have a Collection run and therefore require execution-aware reconciliation rather than blind requeue;
- prevent a stale former owner from completing a job after its claim was recovered/reassigned.

Do NOT blindly requeue an expired job with an attached Collection run. P4 owns run-aware crash reconciliation so a single job cannot silently produce multiple Collection runs.

TERMINAL RESULT STORAGE
Persist bounded machine-readable outcome/reason/error information on terminal jobs so recent queue behavior is diagnosable without console logs.

Do not copy full HTTP bodies, Raw items, secrets, database messages, or unbounded exception strings into job rows.

Collection-run stage/counter detail remains owned by `collection_runs`; job rows are queue/retry/ownership diagnostics, not a duplicate run-accounting table.

RETRY CHAIN SUPPORT WITHOUT RETRY POLICY
Schema/API must support a later retry successor by storing:
- `attempt_number`;
- optional `previous_job_id`.

P2 must not choose retryability, max attempts, backoff, or jitter and must not enqueue automatic retries itself.

Later P5 will terminalize the current job and insert its successor in one transaction so the outstanding-job uniqueness constraint remains race-safe.

TRANSACTION BOUNDARIES
Queue state transitions must be atomic and fail closed.

Use `Database.transaction` for multi-statement transitions where necessary. Do not hold a database transaction open while collection HTTP work executes.

Job claim ownership is a durable lease, not an open transaction or process-local mutex.

REAL POSTGRESQL TEST MATRIX
Level 4 coverage is mandatory and should prove at minimum:
- migration from zero including P1 + P2;
- job FK to a real endpoint;
- enqueue creates one queued job;
- repeated/concurrent enqueue for one endpoint produces at most one outstanding job;
- different endpoints can each have an outstanding job;
- future `available_at` jobs are not claimable;
- deterministic claim ordering;
- concurrent independent claimers cannot own the same job;
- unrelated jobs can be claimed by separate workers;
- claim token is required for renew/attach/terminal transitions;
- lease renewal extends only the current owner;
- terminal job permits a later enqueue for the endpoint;
- retry linkage/attempt constraints reject invalid values;
- expired unstarted running job can be safely requeued;
- expired job with a linked run is not blindly requeued;
- former stale owner cannot mutate a recovered claim;
- transaction rollback leaves coherent queue state;
- bounded error/outcome fields reject unsafe/unbounded values.

Use controlled timestamps/barriers; avoid arbitrary sleeps.
