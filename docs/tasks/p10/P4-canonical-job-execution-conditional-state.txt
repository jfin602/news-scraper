SHARED EXECUTION SERVICE
Extract the production dependency composition currently embedded in the manual Worker command into one reusable collection service/module owned by the collection/Worker boundary.

The service should accept a Source endpoint identity and execution context, load the current endpoint aggregate, and invoke the existing `collectEndpoint` pipeline with the same production dependencies.

Support at least two trigger contexts:
- manual invocation;
- scheduled durable job.

Trigger context is operational telemetry, not a separate pipeline.

Manual command selection remains Source config key + endpoint config key as established by the singleton correction. Scheduled execution selects by `source_endpoint_id` from the durable job.

If a direct endpoint-id aggregate lookup does not yet exist, add the smallest canonical repository query for it. Do not reconstruct Source/Publication state manually in the job layer.

COLLECTION-RUN TRIGGER / EXECUTION CORRELATION
Persist enough bounded correlation to distinguish manual and scheduled runs and recover scheduled work safely.

Extend Collection-run persistence, if not already present, with:
- a trigger kind equivalent to `manual` / `scheduled`;
- a database uniqueness guarantee on `execution_id` so the same durable job execution id cannot create two Collection runs.

Manual runs continue to use fresh unique execution ids.

Scheduled jobs use their stable job id as the Collection-run execution id. This creates a durable one-job-attempt -> at-most-one-run correlation without adding Publication/job payload tenancy to the collection pipeline.

If the final post-correction schema/repository provides a safer equivalent correlation mechanism, use it, but preserve the one-attempt/one-run invariant.

JOB -> COLLECTION-RUN LINK
When scheduled execution starts an actual Collection run, attach that run id to the currently claimed P2 job using the current claim token.

Do this immediately after successful run creation, before outbound fetch proceeds when practical.

A failure to attach must fail closed rather than continuing untracked scheduled execution.

Do not attach a run for jobs blocked before Collection-run creation by current eligibility/lock behavior.

RETRY CLASSIFICATION PRESERVATION
The HTTP fetcher already distinguishes transient/permanent transport failure. `collectEndpoint` currently collapses that information at its outer result boundary.

Preserve the minimum canonical retry classification needed by P5:
- transient/permanent classification for transport failures;
- permanent classification for network-safety, parser-contract, normalization/link-policy, or deterministic processing failures that should not be automatically retried indefinitely;
- no retry classification for successful runs or ordinary pre-run blocking.

Persist retry classification on failed Collection runs when an actual run exists so crash recovery does not need to guess from free-form error text.

Do not implement the automated retry decision in P4.

CONDITIONAL FETCH INPUT
Before invoking the fetcher for an endpoint, load the persisted P1 ETag/Last-Modified validator state and pass it through the existing `FetchOptions.validators` path.

Do not create custom HTTP header code outside the fetcher boundary.

Preserve current header bounds/network-safety/redirect behavior.

CONDITIONAL VALIDATOR COMMIT RULE
Update persisted validators only after a successful canonical collection attempt:
- successful fresh content: replace the stored validator pair with the response's current bounded validator values; if a 200 content response omits a validator, clear the obsolete stored value for that validator;
- successful `304 Not Modified`: merge response validators, updating those present and preserving existing values for omitted validator headers;
- failed run: do not update stored validators;
- blocked/no-run result: do not update stored validators.

Critically, a 200 response whose parser/normalization/processing later fails must NOT commit new validators, otherwise the next request could receive 304 and make failed content unrecoverable.

ENDPOINT RUNTIME OUTCOME UPDATE
After an actual Collection run reaches a terminal persisted state, update the P1 endpoint runtime state from the final run and current endpoint poll interval.

Use the persisted run's finished time as authoritative when practical rather than an unrelated wall-clock read.

For successful content or not-modified runs:
- set `last_attempt_at`;
- set `last_success_at`;
- clear `last_failure_at` only if current semantics intentionally define it as latest failure absence; otherwise preserve historical latest-failure timestamp consistently;
- reset `consecutive_failure_count` to zero;
- clear cooldown;
- set `next_due_at = finished_at + poll_interval_seconds`;
- apply the validator commit rule above.

For a failed actual run:
- set `last_attempt_at`;
- set `last_failure_at`;
- derive/set the authoritative consecutive-failure count from persisted run history or an equivalently idempotent method rather than blindly double-incrementing on recovery;
- set a normal next due time from the poll interval;
- leave validators unchanged;
- do not apply P5 retry/cooldown policy yet.

State application must be idempotent/recovery-safe. Reapplying a terminal run after a crash must not double-increment failure count or move endpoint timing backward over a newer run.

Prefer deriving consecutive failures from actual terminal Collection-run history after the most recent success, or another equally robust transactionally proven approach.

BLOCKED / NO-LONGER-DUE JOBS
Scheduled jobs must re-read current endpoint state/eligibility before contact.

If the endpoint is no longer configuration-eligible, complete the job as a bounded skipped result with no Collection run and no endpoint attempt-state update.

Also avoid redundant scheduled work when a scheduler-root job became obsolete because another manual/scheduled run completed after enqueue and advanced `next_due_at` into the future. A first-attempt scheduler job may be skipped as `no_longer_due` (or equivalent stable job reason) when current endpoint state proves the scheduled work is no longer due.

Retry successor jobs introduced in P5 must not be suppressed solely by the ordinary `next_due_at` check; their own `available_at` controls retry timing.

ENDPOINT LOCK CONTENTION
The existing Phase 4 endpoint advisory lock remains mandatory.

If scheduled execution is blocked by `endpoint_locked`, do not count it as a failed Collection run or endpoint failure. Return a bounded non-attempt result so P5/P7 can defer/requeue it without consuming a retry attempt.

Manual execution preserves its current blocked result semantics.

JOB EXECUTION RESULT BOUNDARY
Create a bounded scheduled-job execution result that contains enough structured data for P5 policy without duplicating Collection-run accounting:
- job id/attempt;
- whether an actual Collection run occurred;
- Collection-run id if present;
- terminal collection success/failure/blocked category;
- stable outcome/reason;
- retry classification when failed;
- endpoint id;
- current claim ownership context as needed by the finalizer.

Keep queue completion/retry policy separate from the core `collectEndpoint` result.

P4 may provide a simple terminal finalization helper for tests, but design the execution result so P5 can atomically choose terminalization vs retry successor without rewriting the collection pipeline.

INTERRUPTED JOB/RUN RECONCILIATION
Implement execution-aware recovery for expired `running` P2 jobs.

For an expired job with no attached Collection run:
- use P2's safe unstarted-job recovery/requeue behavior.

For an expired job with a linked Collection run:
1. load the run and validate endpoint/job ownership;
2. if the run is already terminal, synthesize the same bounded job-execution result from persisted run state and retry classification; do not rerun collection;
3. if the run is still `running`, finalize/reconcile it as a failed interrupted run with a stable bounded reason such as `worker_interrupted` and transient retry classification while preserving whatever persisted stage/counter state is actually known;
4. produce a recoverable job-execution result for later P5 finalization/retry policy;
5. never create a second Collection run for that same job id/execution id.

Add a focused Collection-run repository operation for interrupted reconciliation rather than fabricating normal successful stage outcomes.

Recovery must verify preserved state, not merely throw an error.
