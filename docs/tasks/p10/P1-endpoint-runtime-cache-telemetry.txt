ENDPOINT RUNTIME STATE
Persist endpoint runtime state directly on the Source endpoint because the state belongs to that endpoint and is required by scheduler/job/health behavior.

Add the smallest coherent fields equivalent to:
- `next_due_at TIMESTAMPTZ NULL`;
- `last_attempt_at TIMESTAMPTZ NULL`;
- `last_success_at TIMESTAMPTZ NULL`;
- `last_failure_at TIMESTAMPTZ NULL`;
- `consecutive_failure_count INTEGER NOT NULL DEFAULT 0` with a nonnegative constraint;
- `cooldown_until TIMESTAMPTZ NULL`;
- persisted conditional-request validator values for ETag and Last-Modified, both nullable and bounded to the existing HTTP validator limits.

Use final repository naming conventions, but keep the semantic separation above.

Do NOT persist endpoint `health_state`. Health is derived in P5 from durable state/time and must not become a second stale authority.

Do not repurpose approval/lifecycle/operational state as health, due state, or failure state.

INITIAL / DUE SEMANTICS
A newly configured endpoint with no `next_due_at` is considered never scheduled and is eligible to be treated as due by the later scheduler when all collection eligibility gates pass.

P1 does not implement due selection, but persistence/mapping must preserve this null initial state unambiguously.

`poll_interval_seconds` remains the existing positive bounded configuration value and is not duplicated into runtime state.

CONDITIONAL VALIDATOR SAFETY
Use the existing fetcher header limits as the application-layer authority. Persisted validator values must remain bounded and must reject unsafe control characters/newlines rather than becoming a stored header-injection path.

Provide repository primitives that later execution code can use to:
- replace validators after a fully successful fresh-content response;
- merge validators after a successful `304 Not Modified`, preserving an existing validator when the 304 omits that header;
- leave validators unchanged after failed/blocked attempts.

P1 may expose explicit update primitives for these modes. Do not yet wire them into manual collection; P4 owns canonical execution integration.

ENDPOINT ATTEMPT STATE PRIMITIVES
Provide explicit repository operations needed by later Phase 10 tasks, with validation and immutable mappings consistent with current repository style.

They must support, without inventing retry policy:
- recording the completion time of an actual Collection run as `last_attempt_at`;
- recording successful completion and advancing `last_success_at`;
- recording failed completion and `last_failure_at`;
- setting/resetting `consecutive_failure_count` from caller-supplied authoritative accounting;
- setting `next_due_at`;
- setting/clearing `cooldown_until`;
- updating conditional validators with the safe replace/merge semantics above.

Prefer one coherent transaction-safe update boundary over many ad hoc SQL setters if that keeps invariants simpler.

Do not count eligibility/lock blocking as a Collection-run attempt; later callers update this runtime state only for actual persisted Collection runs.

P1 must not encode retry limits, exponential backoff, health thresholds, or scheduler jitter inside repository persistence.

COLLECTION-RUN TRANSPORT TELEMETRY
The canonical fetch path already returns redirect count and elapsed transport time in its bounded result metadata. Persist those values on Collection runs so recent transport behavior is diagnosable without console-only output.

Extend the canonical Collection-run schema/repository/result mapping with nullable bounded fields equivalent to:
- redirect count;
- transport elapsed milliseconds.

Preserve all existing Collection-run status/counter/accounting constraints and terminal-state behavior.

Update `collectEndpoint` finalization so the persisted run receives the same bounded redirect/elapsed metadata already exposed by the fetch result when available.

Do not invent parser/normalizer/identity timing columns in P1. The roadmap requires useful expanded telemetry, not speculative instrumentation for every future stage in one task.
