RETRY POLICY SCOPE
Automated retries apply only to scheduled durable jobs.

Do not automatically retry the manual CLI. Manual collection still uses the same canonical execution/cache/state path but returns its one result to the operator.

A scheduled attempt is retryable only when:
- an actual execution failure is classified `transient` by the P4 durable result; and
- the job has not reached the bounded maximum attempt count.

Do NOT automatically retry:
- successful runs;
- `304 Not Modified` success;
- current eligibility blocks;
- `no_longer_due`/superseded scheduler work;
- network-safety/configuration validation rejection;
- parser-contract failure;
- normalization/link-policy deterministic failure;
- permanent HTTP/client/TLS validation classifications;
- deterministic Article identity/provenance conflict;
- ordinary administrative paused/disabled/archived/unapproved state.

Infrastructure interruption explicitly recorded as transient by P4 recovery is eligible for retry.

BOUNDED ATTEMPTS
Use a small explicit baseline of three total attempts per scheduled chain:
- attempt 1 = scheduler-created job;
- attempts 2 and 3 = retry successor jobs;
- no attempt 4.

Keep this policy in one named module/constant so Phase 19 may tune it deliberately later.

Do not expose arbitrary admin configuration for retry count in Phase 10.

BACKOFF / JITTER
Implement a pure/injectable deterministic retry-delay function.

Use a conservative bounded exponential baseline equivalent to:
- retry after attempt 1 failure: nominal 30 seconds;
- retry after attempt 2 failure: nominal 60 seconds;
- cap nominal retry delay at 5 minutes for any future extension;
- equal jitter: actual delay is between 50% and 100% of nominal, selected with injected randomness.

Equivalent math is acceptable if the same properties are documented/tested:
- monotonic bounded backoff;
- no zero/negative delay;
- bounded maximum;
- deterministic under injected random input.

Do not use wall-clock sleeps in policy tests.

ATOMIC TERMINALIZE + RETRY SUCCESSOR
When P5 decides a transient failed attempt should retry, perform the durable transition atomically:
1. verify current job claim token/ownership;
2. terminalize the current attempt as failed/abandoned as appropriate with its bounded diagnostics;
3. insert exactly one successor job for the same endpoint with `attempt_number + 1`, `previous_job_id = current job id`, and `available_at = now + retry delay`;
4. release current claim ownership;
5. commit all steps together.

The P2 one-outstanding-job uniqueness constraint is the race-safety backstop.

There must never be a committed state where the current job was terminalized for retry but a competing scheduler won the endpoint slot before the successor was inserted. Use one database transaction.

If the retry successor cannot be inserted for an unexpected integrity reason, roll back the whole transition and surface a bounded error rather than silently losing retry work.

TERMINAL WITHOUT RETRY
For success, permanent failure, skipped/superseded work, or exhausted retry count:
- terminalize the current job once with bounded structured outcome/reason;
- do not create a successor retry job.

Preserve the distinction between failed, skipped, and abandoned/recovered attempts.

LOCK / CAPACITY DEFERRAL SUPPORT
Endpoint-lock contention is not a failed Collection attempt and must not consume a retry attempt.

Provide/complete a policy operation that can safely defer the SAME claimed job back to `queued` with a short future `available_at`, clearing its claim token but retaining its attempt number.

Use this non-attempt deferral for `endpoint_locked` and make it reusable by P6 for `collection_capacity_limited`.

A suitable baseline is a small 5-second bounded delay with injectable jitter/no sleep. This is contention deferral, not exponential failure retry.

Before executing a deferred scheduler-root job, P4's `no_longer_due` check must still be able to skip it if another run already satisfied the due work.

CONSECUTIVE FAILURE ACCOUNTING
P4 must already update endpoint consecutive failure state idempotently from actual terminal runs.

P5 should treat that persisted count as a derived/cache value backed by Collection-run history, not as a retry attempt counter.

Retries and consecutive failures are different:
- attempt number counts work within one retry chain;
- consecutive failure count spans terminal Collection runs until a successful run resets it.

Do not derive endpoint health from job attempt number.

COOLDOWN POLICY
Repeated failures must protect a persistently failing endpoint from immediate normal scheduler churn after a retry chain ends.

Apply cooldown only when the scheduled chain reaches a terminal failed state and the endpoint has at least three consecutive failed Collection runs.

Use a simple baseline:
- cooldown duration = max(endpoint `poll_interval_seconds`, 5 minutes);
- `cooldown_until = terminal run finished time + duration`.

Do not create an unbounded exponential circuit-breaker in Phase 10.

Retry successor jobs already queued within the current chain are governed by their own `available_at`; normal scheduler due selection remains suppressed by P3 while cooldown is active.

Any successful Collection run clears cooldown through the P4 success-state path.

DERIVED ENDPOINT HEALTH
Add a pure deterministic health derivation with the canonical states:
- `unknown`;
- `healthy`;
- `delayed`;
- `degraded`;
- `unhealthy`.

Use durable endpoint configuration/runtime state plus caller-supplied `now`. Do not persist the derived result.

Baseline precedence:
1. `unknown` when no actual Collection run has ever completed (`last_attempt_at` absent);
2. `unhealthy` when `consecutive_failure_count >= 3`;
3. `degraded` when `consecutive_failure_count` is 1 or 2;
4. `delayed` when the endpoint is currently schedule-eligible by configuration, has no current failure degradation, has a `next_due_at`, and `now` is later than `next_due_at + one poll interval`;
5. otherwise `healthy`.

For delayed evaluation, schedule-eligible means singleton collection is active and Source/endpoint are approved + active + enabled. Cooldown is not a lifecycle/operational state; a cooldown after failures will already be degraded/unhealthy by precedence.

A paused/disabled/archived/unapproved endpoint must not become `delayed` merely because time passes while it is intentionally non-collectable. If it already carried degraded/unhealthy evidence from prior failures, pausing it does not erase that history; health and operational state remain separately reportable.

If current source shape makes one minor naming/precedence refinement necessary, preserve the semantics above and document it rather than inventing competing health authority.

RETRY FAIRNESS
A retry job is simply another durable job with future `available_at`. It must not run in an in-process tight retry loop.

Therefore unrelated available endpoint jobs remain claimable while one endpoint waits for backoff/cooldown.

Add tests showing future retry jobs do not block another endpoint's ready job.

TIME / RANDOMNESS
All retry, deferral, cooldown, and health tests use injected/controlled time/randomness. No arbitrary sleeps.

REAL POSTGRESQL / INTEGRATION MATRIX
Prove:
- transient failed job + remaining attempts atomically terminalizes current and creates exactly one successor;
- competing scheduler cannot insert a duplicate outstanding job during that transaction;
- permanent failure creates no retry;
- attempt 3 failure creates no retry;
- retry successor points to previous job and increments attempt exactly once;
- endpoint-lock deferral requeues same job/token safely without consuming an attempt;
- former claim owner cannot mutate after deferral;
- future retry does not prevent another endpoint job being claimed;
- final repeated failure applies cooldown;
- scheduler respects cooldown through existing P3 query;
- later success clears cooldown/failure count and returns health to healthy when not delayed;
- interrupted transient run from P4 recovery follows the same retry policy without creating a duplicate run.
