SCHEDULER OWNERSHIP
Create the first substantive `src/collection/scheduler/` module.

Prefer a small split such as:
- due-endpoint persistence/query boundary;
- pure scheduling-jitter calculation;
- one scheduler-pass service that queries and enqueues.

Do not create a timer/process loop in P3. P7 owns runtime cadence.

DUE-ENDPOINT RULE
An endpoint is scheduler-due only when all scheduling/configuration gates are true:
- singleton Publication settings exist and `active_for_collection = true`;
- Source approval = approved;
- Source lifecycle = active;
- Source operational state = enabled;
- endpoint approval = approved;
- endpoint lifecycle = active;
- endpoint operational state = enabled;
- endpoint is not currently inside a persisted cooldown (`cooldown_until` absent or <= scheduler `now`);
- endpoint has never been assigned a due timestamp (`next_due_at IS NULL`) OR `next_due_at <= now`.

Do not perform DNS/address/network-safety checks in the scheduler. Those remain in the canonical endpoint execution path immediately before contact.

Do not make scheduler eligibility replace the canonical execution-time eligibility recheck. State may change between enqueue and execution.

An absent singleton Publication or inactive collection setting yields no scheduler work; there is no Publication selector or multi-Publication loop.

OUTSTANDING WORK
Do not intentionally enqueue another job when an endpoint already has a queued/running durable job.

The due query may exclude endpoints with outstanding jobs for efficiency, but P2's database uniqueness remains the final race-safety authority. Competing schedulers must be allowed to race and converge safely rather than depending on a process-local scheduler mutex.

DUE ORDER / BATCHING
Return due endpoints in deterministic oldest-due order with a stable endpoint-id tie breaker.

Treat a null `next_due_at` as initial due work and order it consistently rather than nondeterministically.

Scheduler pass size must be bounded with a small explicit default/limit suitable for MVP. Do not select an unbounded endpoint set into memory.

SCHEDULING JITTER
Add a pure deterministic/injectable jitter calculation used only when creating the queued job's `available_at`.

Use bounded jitter based on the endpoint poll interval, with a maximum no larger than a small fixed window. A suitable baseline is:
- maximum jitter = min(30 seconds, 10% of `poll_interval_seconds`);
- actual jitter chosen from 0 through that maximum by an injected random source.

Equivalent bounded math is acceptable if documented/tested and it cannot create negative or unbounded delays.

Do not mutate `next_due_at` merely because work was enqueued. Runtime outcome processing later owns the next due timestamp. This prevents lost jobs from falsely appearing successfully scheduled.

Scheduler randomness must be injectable/control-friendly for deterministic tests. Do not use unmockable global randomness inside assertions.

SCHEDULER PASS
Provide a service equivalent to:
1. capture/inject one scheduler `now`;
2. load a bounded due batch;
3. calculate each job's bounded jitter/`available_at`;
4. call P2 race-safe enqueue independently for each endpoint;
5. return bounded summary counts such as considered/enqueued/already-outstanding.

One endpoint enqueue failure caused by normal uniqueness contention must not abort enqueue of unrelated due endpoints.

A real database failure may fail the scheduler pass, but must not leave partially invented in-memory authority; durable rows already committed remain the truth and the next pass may retry remaining work safely.

Do not fetch publisher data or create Collection runs during scheduling.

SOURCE / PUBLICATION FAILURE ISOLATION
The scheduler must operate directly on installation endpoints. Do not introduce Publication ids/slugs into job rows or scheduler queries.

A bad/paused/archived/unapproved Source/endpoint is simply not selected; do not rewrite its lifecycle/operational/health state.

POLL INTERVAL
Use the existing persisted positive `poll_interval_seconds` only to bound scheduling jitter in P3. P4/P5 outcome processing determines future `next_due_at` from the interval.

Do not add a second poll cadence field.

REAL POSTGRESQL TEST MATRIX
Level 4 tests must prove:
- singleton Publication inactive/absent => no due work;
- approved/active/enabled Source + endpoint with null due timestamp is selected;
- due timestamp <= now is selected;
- future due timestamp is not selected;
- future cooldown excludes an otherwise due endpoint;
- expired cooldown no longer blocks due selection;
- unapproved/archived/paused/disabled Source and endpoint cases are excluded;
- deterministic due ordering and bounded batch size;
- an existing queued/running job suppresses duplicate scheduling;
- competing scheduler passes racing on the same due endpoint create at most one outstanding job due to P2 uniqueness;
- unrelated due endpoints continue enqueueing when one race loses;
- terminal prior jobs do not prevent a new due enqueue.

Use controlled clock/random values and database barriers where concurrency matters. Avoid arbitrary sleeps.

UNIT TEST MATRIX
Pure tests should prove jitter immediately below/at meaningful bounds, including:
- small poll interval produces <=10% jitter;
- large interval is capped at the fixed maximum;
- deterministic 0/maximum random cases;
- invalid injected random values are rejected or normalized according to one explicit contract.
