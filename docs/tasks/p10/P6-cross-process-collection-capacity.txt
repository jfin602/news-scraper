GOAL

- global installation capacity;
- per Source capacity;
- per destination host capacity.

P6 does not start the background Worker loop; P7 owns runtime orchestration.

CAPACITY COORDINATION MODEL
Use PostgreSQL session-level advisory locks as fixed concurrency slots, not a new durable capacity-lease table.

Rationale/invariants:
- all Worker processes already share PostgreSQL;
- advisory locks are cross-process for the installation;
- a dropped/crashed database session releases its capacity automatically;
- capacity is ephemeral coordination, unlike durable job ownership/state;
- this avoids a second stale-lease/recovery state machine solely for concurrency.

Do not replace the durable P2 job lease with advisory capacity. They solve different problems:
- durable job lease = who owns the queued attempt;
- capacity advisory slots = whether that owner may execute collection now;
- endpoint advisory lock = whether this exact endpoint may overlap another execution.

BASELINE CAPACITY LIMITS
Use one explicit small installation baseline, kept in a named module/constants for Phase 19 tuning later:
- global collection executions: 4;
- per Source: 2;
- per destination host: 2.

Do not add admin/runtime environment configuration in P6 merely to make the numbers configurable. Multiple Worker processes must share the same effective limits, and fixed Phase 10 constants make that invariant deterministic. Phase 19 may deliberately introduce tuning/configuration later.

If current contracts/source reveal a concrete reason these exact baseline values are unsafe, choose equally conservative documented fixed values while preserving all three scopes and explain the deviation.

ADVISORY SLOT KEYS
Create deterministic 64-bit advisory-lock keys using a namespaced hash strategy equivalent to the existing endpoint lock.

Use separate namespaces for:
- global slot index;
- Source id + slot index;
- normalized host + slot index.

The same Source/host across different Worker processes must resolve to the same slot key set.

Host keying must use the canonical normalized hostname already parsed from the configured endpoint URL. Do not key by full URL/path/query, raw unnormalized text, IP selected after DNS, or Publication identity.

ACQUIRE ALL SCOPES OR NONE
A collection execution may proceed only after one slot is acquired in each required scope: global, Source, and host.

Use one dedicated database session to hold all acquired capacity locks for the duration of the wrapped collection work.

Acquisition should be nonblocking (`pg_try_advisory_lock` or equivalent) and deterministic:
1. global slot;
2. Source slot;
3. host slot.

For each scope, try slots in deterministic index order unless a tested fairness strategy is simpler.

If any scope cannot acquire a slot:
- release every slot already acquired in reverse order;
- return a bounded blocked result identifying the limiting scope (`global`, `source`, or `host`);
- do not invoke the collection pipeline;
- do not create a Collection run;
- do not update endpoint attempt/failure state;
- do not consume a retry attempt.

No partial capacity ownership may leak after a failed acquisition.

RELEASE SAFETY
Release every acquired advisory lock on success, ordinary collection failure, thrown work error, and cancellation/shutdown paths where the session remains available.

Reuse the endpoint lock's defensive pattern:
- validate release result;
- discard the database session when lock state becomes uncertain;
- if work and release both fail, preserve both failures coherently rather than hiding lock-release failure;
- never return a pooled connection with uncertain advisory-lock ownership.

A process/database-session crash must be proven to release capacity from the perspective of another connection when practical in Level 4 tests.

INTEGRATION WITH CANONICAL EXECUTION
Place the capacity wrapper around the same shared endpoint collection service used by manual and scheduled work.

The required order is conceptually:
1. load/revalidate current endpoint aggregate and current Source/host identity;
2. acquire global/Source/host capacity;
3. invoke the canonical endpoint service;
4. canonical service rechecks eligibility and acquires the existing per-endpoint advisory lock before any Collection run/fetch;
5. release capacity when the service returns/throws.

Do not move network safety out of the canonical service. Capacity acquisition is not destination approval.

Do not remove or merge away the endpoint lock. Capacity >1 means two jobs could still target the same endpoint, and the Phase 4 endpoint lock remains the contractually established overlap authority.

MANUAL PATH
The manual Worker command must use the same capacity wrapper so manual/check-now style execution obeys the same baseline concurrency/rate-limit boundary as scheduled work.

For a manual command that cannot acquire capacity, return a bounded machine-readable blocked/error result without pretending a Collection run occurred.

Do not automatically retry the CLI.

SCHEDULED JOB PATH
When a claimed scheduled job cannot acquire capacity:
- use P5's same-job contention deferral operation;
- return that SAME job to queued with a short future `available_at`;
- preserve attempt number and retry-chain linkage;
- do not terminalize as a failed attempt;
- do not create a successor retry job;
- clear current claim ownership safely.

When it later becomes available, P4's `no_longer_due` logic must still be able to skip obsolete root scheduled work if another run already satisfied the due endpoint.

FAILURE ISOLATION
Capacity enforcement must not serialize the entire installation unnecessarily.

Prove behavior such as:
- two jobs for Source A may run up to the per-Source limit;
- an additional Source A job is blocked/deferred even when global capacity remains;
- Source B on another host may still proceed while Source A is at its Source cap;
- two Sources sharing one host are jointly bounded by the host cap;
- other hosts can proceed while one host is saturated;
- global cap eventually limits the aggregate across otherwise independent Sources/hosts.

One slow/failing Source must not prevent unrelated work except where the explicit global cap is legitimately exhausted.

No in-process semaphore alone satisfies this requirement because the architecture supports multiple Worker processes.

FAIRNESS / STARVATION BOUNDARY
Phase 10 requires bounded concurrency and failure isolation, not a sophisticated fair-queuing scheduler.

Use short durable deferral for capacity-blocked jobs so they re-enter the P2 queue rather than spinning in process.

Do not busy-loop trying advisory slots and do not hold a job claim while sleeping for capacity.

P7 will repeatedly claim available work, allowing unrelated jobs to proceed between deferrals.

LEVEL 2 TESTS
Cover deterministic key/slot behavior:
- same scope identity/index -> same key;
- different namespaces/scopes -> distinct keys for representative values;
- normalized host identity behavior;
- invalid Source/host/slot inputs rejected;
- configured slot counts/ordering are bounded.

LEVEL 4 CROSS-PROCESS TESTS
Use independent database sessions/process-equivalent actors and barriers, not process-local mocks, to prove:
- global slots permit exactly the configured number and block the next actor;
- per-Source slots apply across independent database clients;
- per-host slots apply across different Sources sharing a host;
- unrelated Source/host work can proceed while one scope is saturated;
- failed acquisition releases previously acquired slots;
- success releases all slots and allows reacquisition;
- thrown collection work releases all slots;
- release failure discards the session/does not leak an uncertain pooled connection;
- closing/crashing the holder session makes its advisory capacity available to another client;
- existing endpoint lock still prevents same-endpoint overlap inside available capacity;
- capacity-blocked scheduled job is durably deferred without attempt increment or Collection run;
- a separate ready endpoint job remains claimable/executable while another is deferred.

Use controlled barriers/events. Avoid arbitrary sleeps.

POOL / CONNECTION PRESSURE
This design holds one capacity-lock session plus the existing endpoint-lock session while an endpoint executes. Inspect the current PostgreSQL pool defaults and test/runtime composition.

Do not silently introduce a pool deadlock where the global capacity exceeds usable connections needed by the endpoint lock/Article persistence path.

If necessary, choose the smallest safe implementation adjustment:
- lower fixed global capacity; or
- explicitly size the application pool through the existing database config boundary if that capability already belongs there.

Do not create a broad database-pool tuning subsystem in P6. Document/test the chosen bound so capacity cannot self-deadlock the Worker.

SECURITY / NETWORK PRESERVATION
Capacity code must never:
- resolve/fetch a hostname itself;
- weaken SSRF or approved-domain policy;
- use a selected IP as a host-rate identity instead of configured normalized host;
- log secrets/query strings;
- bypass Source/endpoint eligibility.
