WORKER RUNTIME OWNERSHIP
Refactor the current Worker runtime from a keep-alive shell into an explicit orchestrator with independently testable dependencies.

The Worker process remains separate from Web/API. Web/API must not start scheduler loops or collect Sources inline.

The runtime should own:
- one scheduler loop;
- one durable-job dispatcher/consumer loop;
- bounded local in-flight task tracking;
- job lease renewal for in-flight jobs;
- periodic stale-job recovery;
- shutdown coordination;
- final database close after work ownership is resolved as far as practical.

Preserve current `worker.ready`, `worker.stopped`, startup-failure behavior unless a small documented structured extension is needed.

Do not add a Worker HTTP server merely for health probes.

RUNTIME TIMING CONSTANTS
Use explicit small internal defaults rather than a broad configuration subsystem unless the existing runtime-config contract already provides the cleanest home.

Suitable Phase 10 baselines:
- scheduler pass interval: 15 seconds;
- idle job-poll interval: 1 second;
- job lease duration: 2 minutes;
- lease renewal interval: 30 seconds;
- stale-recovery pass interval: 30 seconds.

These are process mechanics, not endpoint polling intervals. Endpoint `poll_interval_seconds` remains the configured collection cadence.

Keep timing values in one module and make clock/sleep/timer behavior injectable for tests. If implementation constraints justify modestly different fixed values, preserve the same relationships: renewal comfortably before lease expiry, bounded scheduler cadence, no busy loop.

Do not add admin UI/configuration for these mechanics in P7.

SCHEDULER LOOP
Repeatedly invoke the P3 scheduler pass.

Requirements:
- run once promptly after Worker becomes ready, then on bounded cadence;
- multiple Worker processes may run scheduler loops concurrently; P2/P3 database uniqueness/races make this safe;
- one scheduler-pass failure is logged safely and does not permanently stop job consumption or future scheduler passes;
- do not spawn overlapping scheduler passes within one Worker if a prior pass is still running;
- stopping the Worker prevents new scheduler passes.

Do not contact publishers from scheduler code.

DISPATCH LOOP
Maintain a bounded set of locally in-flight jobs, never exceeding P6's global fixed execution capacity.

The durable queue remains the authority; local in-flight tracking is only process orchestration.

Behavior:
1. while not stopping and local capacity exists, call P2 claim-next for available jobs;
2. if no job is available, sleep/wait through the injectable bounded idle mechanism;
3. for each claimed job, start one isolated async task;
4. execute through P6 capacity + P4 canonical job execution + P5 finalization/retry/defer policy;
5. catch per-job failures so one job task cannot terminate the dispatcher or unrelated jobs;
6. remove settled work from local in-flight tracking;
7. continue claiming when capacity returns.

Do not use unbounded `Promise.all` over the queue.

CAPACITY-BLOCKED JOBS
A job blocked by P6 capacity is immediately handed to P5 same-job deferral, releasing durable claim ownership. Do not hold claimed jobs sleeping while waiting for advisory capacity.

This lets other endpoints be claimed and preserves failure isolation/fairness.

LEASE RENEWAL
While a claimed job remains legitimately in-flight, renew its durable P2 lease before expiry.

Use the current claim token. A renewal failure/ownership loss must not be ignored.

If renewal fails:
- record a bounded structured diagnostic;
- do not later force terminal job mutation with a stale token;
- allow the current canonical endpoint execution/endpoint advisory lock to unwind safely if already running;
- let durable recovery reconcile the job/run state from P2/P4 rather than fabricating success.

Do not cancel network safety or release the endpoint lock incorrectly merely because queue ownership became uncertain.

STALE RECOVERY LOOP
Periodically inspect a bounded batch of expired running jobs and use the tested recovery chain:
- unstarted expired job -> P2 safe requeue;
- linked terminal run -> P4 synthesize/reconcile without rerunning;
- linked still-running run from dead owner -> P4 interrupt/reconcile as transient;
- recovered execution result -> P5 terminal/retry policy.

Recovery failures are isolated per job. One malformed/unrecoverable job must not stop later recovery passes or normal unrelated dispatch.

Never run the same job's collection again when an existing execution-id-correlated run already represents that attempt.

FAILURE ISOLATION
Explicitly preserve:
- one Source fetch timeout does not abort another job;
- one parser/persistence/job-finalization error does not stop scheduler/dispatcher loops;
- one capacity-saturated Source/host does not block unrelated jobs except under the real global cap;
- Web/API/public feed remains independently runnable/readable during Worker collection failures;
- a database-wide outage may make Worker work unavailable/readiness fail, but failures are bounded/redacted and recoverable state remains durable where already committed.

GRACEFUL SHUTDOWN
On SIGINT/SIGTERM or explicit runtime `shutdown()`:
1. transition runtime to stopping exactly once;
2. stop initiating scheduler passes;
3. stop claiming new jobs;
4. stop starting new recovery work;
5. continue necessary lease renewal for jobs already in-flight while they finish;
6. await existing in-flight job tasks and any active scheduler/recovery pass;
7. if a task cannot safely complete because dependency/ownership failed, leave durable job/run state recoverable rather than forging terminal success;
8. stop timers/listeners;
9. close the database once;
10. resolve `runtime.stopped` and emit existing stopped event.

Repeated/concurrent shutdown calls must be safe/idempotent.

Because actual fetch transport is bounded and durable stale recovery exists, do not add a complicated forced-cancellation protocol in Phase 10 unless required by a proven blocking case.

Remove the current `MessageChannel` keep-alive if timers/loops/in-flight work now naturally own process liveness. Do not retain it without an independent purpose.

STRUCTURED DIAGNOSTICS
Emit bounded structured events sufficient to correlate runtime activity without making logs the only durable authority.

Useful event classes include:
- scheduler pass completed/failed with counts;
- job claimed/started;
- job succeeded/failed/skipped/deferred/retry-scheduled;
- stale job recovered;
- lease renewal/ownership failure;
- shutdown begin/complete;
- worker ready/stopped.

Include safe identifiers such as endpoint/job/Collection-run ids where useful. Do not log:
- credentials/database URLs;
- authorization headers;
- Raw response bodies;
- unbounded parser content;
- secret query strings.

Persisted endpoint/job/run state remains the diagnostic source of truth for recent outcomes/failures.
