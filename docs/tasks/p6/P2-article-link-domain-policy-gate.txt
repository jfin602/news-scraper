CURRENT SOURCE / IMPORTANT BASELINE
At the P2 boundary:
- P1 should produce an absolute normalized original Article URL separately from canonical identity URL;
- Source approved-domain rules are the maximum trust boundary;
- endpoint domain rules may only narrow Source policy;
- `normalizeDomainHostname(...)`, `hostMatchesDomainRule(...)`, and `effectiveEndpointDomainRules(...)` already define generic normalized-host/domain-rule behavior;
- Phase 4 static/network destination safety also uses those helpers but adds fetch-specific scheme/port/DNS/address controls;
- Article-link acceptance must remain separate from pre-fetch safety and must not contact the Article URL.

MODULE BOUNDARY
Create one focused Article-link policy module, recommended:
- `src/collection/article-links/policy.ts`

A different small path under `src/collection/` is acceptable if it clearly communicates Article-link policy ownership and does not mix with Phase 4 network safety.

Do not create a general network-policy engine or duplicate Source configuration parsing.

INPUT / DECISION CONTRACT
The gate should consume:
- a normalized `ArticleCandidate` from P1;
- effective policy context containing Source domain rules and endpoint narrowing rules, or the existing `EndpointConfigurationAggregate` if that avoids duplicating policy shape without coupling to unrelated mutable runtime state.

Return a deeply immutable deterministic decision such as:
- accepted, preserving/returning the candidate or an acceptance marker;
- rejected with `stage: 'article_link_policy'` (or similarly explicit stage) and a stable bounded machine-readable reason.

Expected Source data rejection should not require callers to parse thrown errors. Internal programming/corrupt-policy failures may throw or fail explicitly according to existing repository style.

WHICH URL IS VALIDATED
Validate the candidate's preserved original resolved Article URL — the URL that is intended to remain the future public headline destination.

Do NOT validate only the cleaned canonical identity URL and do NOT replace the original destination with the canonical URL.

P1 already resolved relative input. P2 MUST NOT independently re-resolve the original Raw relative string against an endpoint URL.

STRUCTURAL ARTICLE URL RULES
For Article-link acceptance:
- parse through a standards-based `URL` representation;
- require absolute URL with hostname;
- permit only `http:` and `https:` Article destinations for the current MVP;
- reject username/password credentials;
- normalize hostname safely using the existing domain hostname authority;
- preserve URL path/query/fragment semantics; this gate is not canonical identity cleanup.

Stable rejection reasons should distinguish at least:
- invalid/malformed Article URL;
- unsupported Article scheme;
- credentials not allowed;
- Article domain not approved.

Recommended names include:
- `invalid_article_url`;
- `unsupported_article_scheme`;
- `article_url_credentials_not_allowed`;
- `article_domain_not_approved`.

Exact naming may vary only if it stays stable, bounded, machine-readable, and clearly separate from Phase 4 network-safety reason vocabulary.

DOMAIN POLICY
Reuse existing Source/endpoint domain authority.

Required semantics:
- Source domain rules define the maximum permitted Article destination boundary;
- endpoint domain narrowing, when configured, becomes the effective boundary for that endpoint;
- endpoint policy must never silently widen Source policy;
- exact-host and include-subdomains behavior must match the existing Source configuration contract;
- case-insensitive/IDN host normalization must use the existing generic hostname normalization rather than a new ad hoc implementation.

Do not hard-code Source names, known publishers, Publication topic terms, or site-specific aliases.

IMPORTANT SEPARATION FROM PHASE 4 NETWORK SAFETY
Article-link acceptance is NOT an outbound fetch authorization.

P2 MUST NOT:
- resolve DNS;
- classify public/private/special-use IP addresses;
- contact the Article;
- follow redirects from the Article;
- consume `ValidatedDestination` or require a resolver;
- apply the Phase 4 default-port-only server-fetch restriction as though the Platform were connecting to the Article;
- emit `network_safety` stage decisions.

A public Article link containing a non-default port may be unusual, but P2's contract is domain/link acceptance, not privileged server-side socket safety. Do not accidentally inherit fetch-only port restrictions by directly calling the Phase 4 static destination validator.

Likewise, accepting an Article link here does NOT authorize a later Worker to fetch that Article URL. A future collector/fetch of any URL would require its own pre-request network-safety gate.

NO NETWORK SIDE EFFECTS
The gate must be a synchronous/pure or otherwise deterministic computation from candidate + configuration.

No public DNS/network/database dependency is required for the decision.
