CANONICAL PHASE 6 ACCOUNTING
The persisted Phase 6 values are:

Normalization stage status:
- `not_run`
- `succeeded`
- `failed`

Counters:
- `normalized_candidate_count`
- `normalization_failure_count`
- `article_link_rejection_count`

Canonical meanings:
- `normalized_candidate_count` counts Raw items that completed normalization into an Article candidate BEFORE the separate Article-link decision;
- `normalization_failure_count` counts Raw items that could not produce an Article candidate because normalization failed or required candidate data was malformed/invalid/out of bounds;
- `article_link_rejection_count` counts normalized candidates rejected by the separate Article-link/domain policy gate;
- safe candidates for the next stage = `normalized_candidate_count - article_link_rejection_count`.

These are pre-persistence stage counters. Do not add or reuse Phase 7 processing outcomes such as `created`, `updated`, `unchanged`, `rejected`, `excluded`, or candidate-level `failed` outcome counters.

DATABASE CONSTRAINTS
Enforce durable invariants without making valid historical Phase 5 rows impossible.

At minimum:
- allowed normalization status vocabulary;
- all three counts are nonnegative;
- `article_link_rejection_count <= normalized_candidate_count`;
- `normalization_status = 'not_run'` requires all Phase 6 counters to remain zero;
- a normalization stage that is not `not_run` requires parser status `succeeded`;
- when normalization status is `succeeded`, `raw_item_count = normalized_candidate_count + normalization_failure_count`;
- a terminal run with `normalization_status = 'failed'` cannot report overall run status `succeeded`.

Do NOT require the Phase 6 arithmetic for historical Phase 5 rows where parser status is `succeeded`, Raw-item count may be positive, but normalization status defaults to `not_run` and Phase 6 counts are all zero.

Do not overconstrain future Phase 7+ outcome/effect additions. The DB should enforce timeless Phase 6 stage invariants, not every possible future pipeline combination.
