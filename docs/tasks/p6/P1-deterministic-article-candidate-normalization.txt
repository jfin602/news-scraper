Phase 6 — Article normalization.

GOAL
Create the generic deterministic Raw item -> Article candidate normalization boundary used by every later collection adapter.

P1 owns normalization only. It converts explicitly untrusted Source-shaped `RawItem` values plus explicit collection context into an immutable safe `ArticleCandidate` or a bounded item-level normalization failure.

P1 MUST NOT decide Source/domain Article-link approval, modify Collection-run persistence, invoke Worker collection, evaluate Relevance, persist Articles/observations, perform duplicate logic, or render public output.

CURRENT SOURCE / IMPORTANT BASELINE
At the Phase 6 baseline:
- `RawItem` is explicitly untrusted and currently exposes optional external ID, title, URL, raw publication/update timestamps, author, content, image URL, category labels, language, and diagnostics;
- parser output deliberately retains raw Source-shaped URL/date/content values;
- RSS/Atom parser limits are parser-owned defensive input/output limits and are not the canonical Article-candidate limits;
- `src/collection/normalization/` does not yet exist;
- the fetcher already returns terminal `finalUrl`, but P1 receives that value through an injected normalization context rather than changing fetch/Worker orchestration;
- Article identity/persistence is Phase 7 and does not exist in this task.

MODULE / TYPE BOUNDARY
Create substantive normalization ownership under the architecture-designated directory, recommended:
- `src/collection/normalization/article-candidate.ts`
- `src/collection/normalization/normalizer.ts`

Small focused helper files under `src/collection/normalization/` are allowed when they isolate meaningful behavior such as URL, date, or safe-text normalization. Do not create a speculative framework or generic plugin system.

Define an immutable `ArticleCandidate` representation suitable for Phase 7 downstream use.

The candidate should include, as applicable:
- optional opaque Source external identifier;
- required safe display/source title;
- required conservative normalized title representation;
- required original resolved Article URL;
- required canonical identity URL;
- optional safe author;
- optional bounded plain-text summary/excerpt derived from Raw `content`;
- optional resolved/structurally valid image URL;
- optional safe Source category labels, clearly distinct from Publication-owned canonical Categories;
- optional language;
- normalized publication/update date metadata;
- immutable provenance containing Publication ID, Source ID, endpoint ID, and Collection-run ID.

Do not add Article persistence state, first-seen timestamp, visibility/moderation, duplicate role, Relevance decisions, or Article-observation IDs to the candidate.

NORMALIZATION CONTEXT
Define an explicit context input rather than reading globals:
- `publicationId`;
- `sourceId`;
- `sourceEndpointId`;
- `collectionRunId`;
- `terminalFeedUrl`.

Validate/bound context enough that malformed programming/test input cannot silently become a candidate. P4 will later supply real persisted IDs and the fetcher's terminal `finalUrl`.

NORMALIZATION RESULT
Expected malformed Source data is ordinary item-level input failure, not an unbounded thrown exception contract.

Return a typed frozen result such as:
- success: candidate;
- failure: stable machine-readable reason + bounded safe detail.

Use a small stable normalization reason vocabulary. Exact names are implementation-owned, but they must distinguish at least unusable title and unusable Article URL and must not expose Raw feed bodies or stack traces.

Internal programming failures may throw; ordinary malformed/unusable Raw values should not require callers to parse thrown error strings.

REQUIRED CANDIDATE DATA
For the current headline/link product, a usable normalized candidate requires:
- a nonblank safe title;
- a structurally usable Article URL resolvable to an absolute URL.

A Raw item missing either required field, becoming blank after safe-text normalization, or exceeding a non-truncatable required bound is an item-level normalization failure.

Do not invent a title from author/content/ID and do not invent an Article URL from the feed endpoint.

CANONICAL NORMALIZATION LIMITS
Candidate limits are normalization-owned constants and MUST NOT import/reuse `RSS_ATOM_LIMITS` as shared semantic authority.

Use these planned Phase 6 maxima unless current governing docs have been deliberately changed before execution:
- external ID: 2,048 characters;
- display/source title: 2,048 characters;
- Article/original/canonical URL: 8,192 characters;
- author: 1,024 characters;
- summary/excerpt: 32,768 characters;
- image URL: 8,192 characters;
- language: 128 characters;
- Source category count: 64;
- Source category: 512 characters.

Behavior at bounds must be deterministic and directly tested below/at/above important limits.

Required fields must not be silently truncated into a different identity/title. Optional metadata may be omitted when malformed/oversized; the summary/excerpt may be deterministically bounded to its explicit excerpt limit because it is intentionally presentation metadata rather than identity.

SAFE TEXT / MARKUP
Collected text is untrusted.

For human-facing candidate metadata:
- strip/remove executable/non-content markup, including script/style element content;
- strip remaining HTML/XML-style tags rather than retaining rich markup;
- decode supported textual/numeric entities safely enough to preserve intended visible text;
- normalize line/space runs deterministically;
- trim outer whitespace;
- preserve intended human meaning rather than aggressively rewriting punctuation/wording;
- return plain text only.

Output-context escaping still belongs to the eventual renderer. P1 plain-text sanitization does not authorize rendering without escaping later.

Do not add a large HTML/browser DOM dependency merely for feed excerpt normalization unless the existing small deterministic approach cannot meet the tested contract. If a new dependency becomes materially necessary, justify it explicitly and inspect current security/maintenance state before adding it.

TITLE REPRESENTATIONS
Preserve two distinct title representations:
1. display/source title — safe human-facing plain text;
2. normalized title — conservative matching representation.

The normalized title should be deterministic and conservative:
- Unicode compatibility normalization is appropriate;
- case normalization/lowercasing is appropriate;
- whitespace normalization is appropriate;
- retain punctuation and semantic word content;
- do not implement fuzzy matching, stemming, token dropping, stop-word removal, punctuation erasure, or topic-specific rules.

Fuzzy-title similarity is not Article identity and must not be pulled into Phase 6.

ARTICLE URL RESOLUTION
Normalization owns relative Article URL resolution.

For Raw `url`:
- normalize conservative outer whitespace only where appropriate;
- resolve with a standards-based URL representation against `terminalFeedUrl`;
- `terminalFeedUrl` means the terminal successfully fetched feed URL after approved redirects;
- require a usable absolute URL with hostname for the candidate;
- reject credentials embedded in the Article URL as structurally unsafe candidate data rather than preserving them;
- preserve the resolved absolute Source-provided Article destination as `originalUrl`/equivalent.

P1 does NOT decide whether that hostname is approved. P2 owns the separate Article-link policy gate.

ORIGINAL DESTINATION VS CANONICAL IDENTITY URL
The original resolved Article destination is the future public destination and must remain separate from identity cleanup.

Derive the canonical identity URL from a separate URL object/copy.

Canonical identity rules are deliberately conservative:
- remove the fragment;
- strip only the exact recognized tracking parameter names:
  `utm_source`, `utm_medium`, `utm_campaign`, `utm_term`, `utm_content`, `utm_id`, `gclid`, `dclid`, `fbclid`, `msclkid`, `mc_cid`, `mc_eid`;
- preserve every other query parameter name/value;
- preserve repeated parameter multiplicity/order semantics produced by the standards-based URL representation;
- preserve path information;
- do not rewrite trailing slash semantics;
- do not sort arbitrary query parameters;
- do not collapse/guess redirect/canonical URLs;
- do not perform hostname/domain approval here.

The canonical identity URL MUST NOT silently replace the preserved original Article destination.

DATE NORMALIZATION
Dates must remain deterministic and distinguish Source claims from Platform observation.

For `publishedAtRaw` and `updatedAtRaw`:
- parse only recognized credible feed timestamp shapes suitable for RSS/Atom, including standards-style ISO/RFC dates used by the supported parser fixtures;
- reject/mark invalid locale-ambiguous or impossible timestamps rather than allowing machine-locale interpretation;
- convert valid parsed values to UTC ISO strings or another immutable deterministic UTC representation;
- preserve status/reason metadata distinguishing `parsed`, `missing`, and `invalid`;
- publication-date metadata must communicate the later `first_seen` fallback strategy when Source publication time is unavailable, without fabricating the fallback timestamp now;
- P1 MUST NOT manufacture `first_seen_at` or substitute Collection-run/start/current time as a Source publication timestamp.

Avoid mutable `Date` objects in the immutable candidate output when an immutable ISO UTC representation is sufficient.

EXTERNAL ID
Treat a Source external identifier as opaque identity evidence:
- conservative outer-whitespace normalization is acceptable;
- preserve case and internal content;
- do not lowercase, URL-decode, hash, or synthesize it;
- omit malformed/oversized optional ID rather than turning it into Article URL/title identity.

OPTIONAL IMAGE URL
If retained:
- resolve relative image URLs against the same terminal feed URL;
- require a structurally valid absolute HTTP/HTTPS URL with hostname and no embedded credentials;
- do not fetch/proxy it;
- do not apply Article-link domain policy to it in P1;
- omit malformed/oversized optional image metadata rather than rejecting an otherwise valid Article candidate.

SOURCE CATEGORY LABELS / LANGUAGE
Raw category labels are Source-provided metadata, not Publication-owned canonical Category decisions.

Normalize them as safe bounded plain-text labels while preserving order and meaningful content. Do not run categorization/Relevance rules or map them to persisted Categories.

Language remains bounded Source metadata. Do not invent language detection.

DIAGNOSTICS
Raw parser diagnostics are not automatically part of the canonical candidate.

Do not copy arbitrary diagnostic metadata through merely because it exists. Candidate provenance and normalization metadata should be explicit first-class fields. Preserve only a diagnostic field if a governing contract or concrete downstream consumer requires it.

IMMUTABILITY / DETERMINISM
Deep-freeze candidate/results and nested arrays/metadata consistently with current repository style.

For fixed Raw input + context:
- repeated execution must produce deeply equal output;
- no current clock, random UUID, environment, locale, DNS, network, database, or global mutable state may affect the result;
- input objects/arrays must not be mutated.
