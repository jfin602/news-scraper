CANONICAL P4 ORDERING
Preserve all Phase 4/5 ordering before parse.

For terminal content + successful parse:
1. freeze/capture the actual parsed Raw items;
2. normalize the complete Raw-item batch using P1 and explicit context;
3. count successful candidates vs item-level normalization failures;
4. only after the normalization pass completes, apply P2 Article-link policy to each successful candidate;
5. count ordinary policy rejections;
6. retain only link-accepted candidates for the next pipeline stage;
7. finalize the Collection run with truthful Phase 6 accounting;
8. return the bounded structured attempt result;
9. lock releases through the existing execution scope.

Use two explicit logical passes (normalization, then Article-link policy) rather than interleaving them per item. This makes `normalized_candidate_count` unambiguous and allows a fatal policy-stage execution error to preserve the truth that the normalization batch completed.

SUCCESSFUL CONTENT RESULT

The safe candidate count must equal:
`normalizedCandidateCount - articleLinkRejectionCount`.

NORMALIZATION ITEM FAILURES
Ordinary P1 item-level failures:
- increment `normalizationFailureCount`;
- do not increment `normalizedCandidateCount`;
- do not by themselves make the normalization stage failed;
- do not abort safe sibling Raw items;
- keep error/reason details bounded and do not aggregate unbounded per-item Source content into the Collection run.

A parsed batch where every item is an ordinary normalization failure may still have normalization stage `succeeded` because the bounded batch was completely processed. Overall run can remain `succeeded` at the pre-persistence Phase 6 boundary unless governing current contracts explicitly say otherwise; the key truth is counts and zero safe candidates.

ARTICLE-LINK ORDINARY REJECTIONS
Ordinary P2 rejected decisions:
- increment `articleLinkRejectionCount`;
- remain part of `normalizedCandidateCount` because normalization succeeded first;
- do not abort safe sibling candidates;
- do not make normalization stage `failed`;
- are not returned as safe downstream candidates;
- do not auto-widen Source/endpoint policy.

Do not rename these as Phase 7 `rejected` processing outcomes. P4 is still pre-persistence stage accounting.

STAGE-LEVEL NORMALIZATION FAILURE
Differentiate expected item-level failure from an unexpected failure that prevents the normalizer batch contract from completing.

If the normalizer dependency unexpectedly throws/fails outside its typed item-level result contract:
- transport status remains `succeeded`;
- parser status remains `succeeded`;
- normalization status = `failed`;
- overall run status = `failed`;
- `rawItemCount` remains the actual parsed count;
- do not fabricate completed candidate/failure arithmetic for an incomplete batch;
- use a stable bounded execution error such as `normalization_execution_failed`;
- do not run Article-link policy after the stage failure;
- finalize the run if persistence remains available;
- release lock;
- return a failed attempt rather than throwing Raw Source details.

P3 database/application invariants should allow truthful incomplete-stage accounting for `normalization_status = failed` without requiring succeeded-batch arithmetic.

ARTICLE-LINK POLICY EXECUTION FAILURE
Ordinary rejected decisions are not exceptions.

If the policy dependency unexpectedly throws/fails outside its decision contract after normalization completed:
- transport/parser remain `succeeded`;
- normalization status may truthfully remain `succeeded` because the complete normalization pass finished;
- overall run = `failed`;
- preserve the completed `normalizedCandidateCount` + `normalizationFailureCount` arithmetic;
- use a distinct stable bounded execution reason such as `article_link_policy_execution_failed`;
- do not miscount the unknown/uncompleted remainder as ordinary link rejections;
- release lock;
- do not report successful candidate handoff.

If P3 constraints do not yet permit this truthful state, make the smallest compatible correction with focused DB regression rather than mislabeling the failure as normalization failed. Explain the discovered contract/implementation mismatch.

FETCH/PARSE/NON-CONTENT PATHS
Preserve existing Phase 5 semantics:

Eligibility blocked:
- no run;
- no fetch/parser/normalization/policy.

Lock blocked:
- no run;
- no fetch/parser/normalization/policy.

Run creation failure:
- no network work;
- lock releases.

Network-safety block/fetch failure:
- parser/normalization/policy not run;
- normalization status not_run + zero counters.

304 not modified:
- run succeeded transport not_modified;
- parser/normalization/policy not run;
- Raw/candidate/failure/rejection counts zero.

Parser failure:
- normalization/policy not run;
- normalization status not_run + zero Phase 6 counts.

Unsupported/corrupted endpoint type:
- preserve predictable parser-stage failure behavior; do not fall through to normalizer.
