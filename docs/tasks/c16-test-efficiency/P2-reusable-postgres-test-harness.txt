GOAL
Introduce a test-only database scope that owns one unique disposable PostgreSQL database for one independently executed test file/equivalent scope, optionally migrates it once, resets mutable application state deterministically between test cases, and force-drops/verifies it once at file cleanup.

The existing `withDisposableDatabase()` behavior remains the canonical fresh-database slow path. Do not delete or repurpose it into a shared mutable singleton.

TARGET LIFECYCLE
Provide a small test-support abstraction with two modes:

- `migrated`: create one unique DB lazily, run the production migration path once, reuse schema between test cases, reset application rows between uses, and drop/verify once;
- `bare`: create one unique DB lazily without application migrations, reuse it between test cases where PostgreSQL itself is the behavior under test, and drop/verify once.

A name such as `createDatabaseTestScope()` is acceptable; prefer the smallest clear API consistent with existing test support. Do not expose this helper from production source.

The preferred migrated lifecycle is:

create unique DB -> migrate from zero once -> run case -> close case-owned resources -> reset mutable application state -> run next case -> ... -> force drop and verify once.

The scope SHOULD initialize lazily on first use so a mixed test file can retain independent fresh/uninitialized cases without paying for or forcing an eager migrated database.

STATE RESET CONTRACT
For migrated scope reuse:
- discover current public application base tables dynamically from PostgreSQL metadata rather than maintaining a hard-coded list that will drift as migrations change;
- exclude `news_scraper_schema_migrations` from reset;
- reset application tables with one deterministic `TRUNCATE ... RESTART IDENTITY CASCADE` operation or an equivalently safe current-PostgreSQL operation;
- quote discovered identifiers safely;
- preserve all schema objects, indexes, constraints, functions/extensions, and migration-ledger rows;
- perform reset only after the previous case callback has returned and its owned pools/clients/processes have been closed;
- a bare scope with no application tables must remain valid and need no fake schema/reset work.

Do not delete/reinsert rows manually table-by-table unless current PostgreSQL behavior proves dynamic truncate unusable.

RESOURCE / FAILURE SAFETY
The scope must fail visibly rather than hanging or silently sharing state.

Required behavior:
- exactly one active scope callback at a time; overlapping calls on one scope fail clearly rather than sharing mutable state;
- every parallel test file will later own its own physical DB; never introduce a process-global shared mutable test DB;
- use the existing safe admin URL/create/drop boundary and preserve explicit prerequisite failure;
- final cleanup uses FORCE drop/connection termination and verifies database absence, matching the existing disposable helper's safety expectation;
- reset uses a bounded PostgreSQL lock timeout or equivalent bounded mechanism so a leaked open transaction produces an actionable failure instead of another multi-minute hang;
- callback failures propagate truthfully;
- reset/cleanup failures are not swallowed as success;
- if both callback and cleanup fail, preserve useful causal information without leaking credentials;
- do not wrap all test cases in one outer transaction as a reset shortcut.

The last rule is mandatory: current DB tests intentionally use independent pools/backends/processes, advisory locks, committed transactions, and backend termination. A single rollback transaction would change what those tests prove.

DISPOSABLE HELPER FACTORING
If the new file scope needs lower-level create/drop ownership that `withDisposableDatabase()` does not expose, factor the existing helper minimally so both APIs share the same safe create/force-drop/verify implementation.

Requirements:
- preserve all current observable `withDisposableDatabase()` behavior;
- `test/database/disposable-database.test.ts` must continue to prove unique DB creation, independent state, cleanup after callback failure, and forced cleanup of leaked connections;
- do not duplicate admin SQL/create/drop logic across two helpers;
- do not move test-only code into production database modules.

HARNESS TESTS — REAL POSTGRESQL
Add focused test-support coverage proving at minimum:
1. one scope physically reuses the same database across multiple sequential callbacks;
2. two independent scopes receive different database names/physical databases;
3. migrated scope has the current migration ledger/schema on first use and retains that ledger across resets;
4. application rows written by one case are absent from the next case;
5. identity/sequence state is reset where current schema uses identity/sequence behavior;
6. schema/index/constraint objects remain after reset;
7. bare scope does not run application migrations and can reuse ordinary PostgreSQL state after deliberate cleanup/reset appropriate to bare mode;
8. overlapping callbacks on one scope fail safely;
9. callback failure does not make later sequential use observe the failed case's application rows once case-owned resources are correctly closed;
10. a deliberately blocking/leaked transaction causes a bounded reset failure rather than an indefinite wait;
11. final scope cleanup removes the physical database;
12. existing fresh disposable-database tests remain green.

If useful, a small injected migration callback/observer MAY be used inside test support to prove migrated initialization runs once, but do not create a generalized dependency-injection framework solely for this assertion.
