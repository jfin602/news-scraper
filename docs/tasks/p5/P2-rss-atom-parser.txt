RAW-ITEM CONTRACT
Create a topic-independent Raw-item representation, recommended:
- `src/collection/raw-item.ts`

The type must represent minimally interpreted Source-shaped values and remain explicitly untrusted.

Recommended fields, all optional except where the parser can truthfully provide a stable collection context field:
- Source-provided identifier/external ID;
- title;
- URL/link string;
- raw published timestamp string;
- raw updated timestamp string;
- author string;
- summary/excerpt/content string;
- image URL string where directly available;
- category label strings;
- language string;
- bounded diagnostic metadata for source/parser-specific details that are useful to later diagnosis but do not deserve first-class fields.

Do not attach Publication/Source/endpoint/Collection-run provenance to each Raw item in P2 unless current architecture clearly requires it at this boundary; Phase 6 owns candidate provenance attachment. The parser may receive source context only if needed for deterministic parsing/diagnostics, but parser output should remain reusable and topic independent.

IMPORTANT RAW-ITEM SEMANTICS
- Dates remain raw strings. Do not parse to `Date`; Phase 6 owns date parsing/confidence.
- URLs remain Source-shaped strings. Do not resolve relative URLs or strip tracking/fragments; Phase 6 owns URL normalization and post-parse Article-link policy.
- HTML/content remains untrusted text. Do not sanitize into final display text; Phase 6 owns sanitization/stripping.
- Do not reject an item merely because later normalization may reject it. The parser should preserve minimally interpretable items when structurally recoverable.
- Do not invent missing titles/URLs/IDs from unrelated fields unless there is an explicit dialect-standard fallback.
- Keep Raw-item fields bounded enough to prevent parser output from becoming an unbounded memory/logging object. The full response body is not Raw-item diagnostic metadata.

PARSER ADAPTER
Create a reusable parser interface, recommended:
- `src/collection/parsers/parser.ts`

The adapter should accept bounded fetched content plus minimal response/parser context and produce one of:
- successful parse result containing the detected dialect and immutable Raw items; or
- typed parser failure with stable machine-readable reason and bounded safe detail.

Do not make expected malformed/unsupported feed content require callers to scrape arbitrary thrown error text. Internal programming/infrastructure failures may still throw.

Recommended parser result concepts:
- `dialect: 'rss' | 'atom'`;
- immutable `items`;
- optional bounded feed-level metadata only when genuinely useful;
- failure reasons such as malformed XML, unsupported feed document, or parser limit/security rejection.

Do not create Article outcomes or Collection-run persistence in the parser.

RSS / ATOM IMPLEMENTATION
Create the first production structured-feed parser, recommended:
- `src/collection/parsers/rss-atom-parser.ts`

Support the initial practical dialects:

RSS 2.0:
- `<rss>` / `<channel>`;
- `item` collection;
- `guid` as Source identifier when present;
- `title`;
- `link`;
- `pubDate`;
- `dc:creator` and/or standard author-like field where directly available;
- `description`/content-style field as raw summary/content;
- repeated `category` labels;
- channel/item language where straightforward;
- common media/enclosure image metadata only when unambiguous and bounded.

Atom 1.0:
- `<feed>`;
- `entry` collection;
- `id` as Source identifier when present;
- `title`;
- preferred `link rel="alternate"` href, with sensible standard fallback if relation omitted;
- `published`;
- `updated`;
- `author/name`;
- `summary` or `content` as raw untrusted text;
- repeated category `term` values;
- feed language where straightforward.

Do not implement HTML collectors, JSON Feed, custom publisher adapters, browser automation, or topic-specific parsing.

DIALECT DETECTION
Endpoint configuration remains `rss_atom`; P2 must inspect the XML document and determine RSS vs Atom.

Expected behavior:
- supported RSS root/document -> RSS parser path;
- supported Atom root/document -> Atom parser path;
- valid XML that is neither supported RSS nor Atom -> typed `unsupported_feed`/equivalent parser failure;
- malformed XML -> typed malformed-parser failure;
- empty/whitespace body -> parser failure rather than synthetic empty feed.

Do not require an operator to classify RSS vs Atom separately.

XML LIBRARY SELECTION / SECURITY
Use a maintained lightweight XML parser rather than hand-rolling XML tokenization.

Planned library family: `fast-xml-parser` 5.x.

Execution-time requirement:
- check the current 5.x release/security state before adding the dependency;
- use a patched release at or above the latest known safe floor at execution time;
- as of prompt planning, 5.10.1 was the minimum known patched floor because 2026 releases addressed entity-expansion/DOCTYPE denial-of-service issues;
- do not pin to a historically vulnerable version merely because this prompt names a floor;
- do not add a package lockfile.

Configure the library defensively:
- do not enable unnecessary DTD/custom entity capabilities;
- reject or safely bound hostile entity/DOCTYPE constructs according to the actual library semantics;
- keep parser input already bounded by caller contract, while still ensuring XML structure cannot trigger uncontrolled expansion/resource consumption;
- avoid executing/translating XML content into code/configuration;
- do not expose parser stack traces/raw bodies as error detail.

If the chosen current parser library cannot provide an acceptable secure configuration or deterministic hostile-input behavior, stop and report the concrete blocker rather than silently weakening input safety.

NAMESPACE / SHAPE HANDLING
Do not overfit fixtures to one exact object shape.

Create small helper functions that:
- distinguish singleton vs repeated XML elements predictably;
- preserve text content deterministically;
- handle common namespace-prefixed fields such as `dc:creator`;
- avoid converting arbitrary tag names into executable behavior;
- tolerate optional metadata absence.

Do not build a generic XML-to-domain abstraction beyond what RSS/Atom needs.

RAW-ITEM BOUNDS
Establish conservative explicit limits for parser-output fields/collections, suitable for untrusted feeds.

Examples that need explicit decisions/tests:
- maximum item count per parsed response;
- maximum title/URL/ID/author/language lengths;
- maximum summary/content length retained in one Raw item;
- maximum category count and per-category length;
- maximum diagnostic metadata size/keys.

When a feed exceeds a parser-owned structural bound, prefer a typed bounded failure or deterministic truncation only if contracts make truncation semantics explicit. Do not silently drop arbitrary items without reporting why.

P2 does not own HTTP response-size limits; P3 will add those. Parser-side structure/field bounds still matter after decompression.
