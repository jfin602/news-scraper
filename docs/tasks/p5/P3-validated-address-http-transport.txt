TASK: Phase 5 / P3 — Validated-address one-hop HTTP transport

ROADMAP PHASE
Phase 5 — RSS/Atom transport, parsing, and minimal Collection runs.

MINIMUM MODEL / EFFORT
- Minimum recommended rating: `Sol High`.
- A stronger model/effort tier may be used.
- Do not lower this rating without explicit repository-owner direction.
- Rationale: this task crosses the highest-risk Phase 4 network-safety boundary into real HTTP/TLS behavior. It must preserve DNS-rebinding resistance, hostname/TLS semantics, timeout/size/compression limits, and safe error classification without creating redirect or scheduling behavior prematurely.

DEPENDS ON

GOAL
Implement the first production publisher HTTP(S) transport as a single-hop primitive that can contact only a previously Phase-4-validated concrete destination while preserving the configured hostname for HTTP Host/TLS certificate verification.

P3 owns one request/response hop, transport limits, conditional-request protocol support, response decoding, content-type handling, transport metrics, and typed transport outcomes. It deliberately does NOT follow redirects. P4 owns redirect orchestration and per-hop revalidation.

CURRENT SOURCE / IMPORTANT BASELINE
At the P3 boundary:
- `ValidatedDestination` already contains `requestUrl`, `protocol`, normalized `hostname`, default `port`, and immutable validated public-unicast addresses;
- safety rejects any DNS answer set containing unsafe/special-use destinations;
- Phase 4 outbound boundary currently invokes an injected callback with `ValidatedDestination` but performs no actual network request;
- no production `node:http`, `node:https`, fetch/undici, redirect loop, compression handling, or HTTP cache logic exists yet;
- `test:collection` exists from P2 and is deterministic;
- ordinary tests must not require public publisher network or weaken SSRF/whitelist policy.

CORE SECURITY INVARIANT — NO SECOND UNCHECKED DNS DECISION
Transport MUST NOT perform an independent hostname resolution after Phase 4 approved the destination.

The actual socket connection must be guaranteed to use one of the concrete addresses carried by the supplied `ValidatedDestination`.

Preserve the original validated hostname for:
- HTTP `Host` semantics;
- HTTPS SNI/servername;
- TLS certificate hostname validation.

Do not satisfy address binding by replacing the request URL hostname with a raw IP and thereby losing hostname verification semantics.

Do not:
- call global `fetch()` against the hostname with its normal resolver behavior;
- call `http.request()`/`https.request()` in a way that silently re-resolves hostname independently;
- set `rejectUnauthorized: false`;
- disable certificate hostname checks;
- introduce an environment/test bypass around production SSRF validation.

TRANSPORT IMPLEMENTATION APPROACH
Prefer Node's built-in `node:http` / `node:https` request stack with a carefully controlled resolver/lookup binding, unless another smaller standard-library-compatible approach is demonstrably safer.

Recommended production ownership:
- `src/collection/fetchers/fetcher.ts` — generic adapter/result contracts;
- `src/collection/fetchers/http-transport.ts` — one-hop implementation.

The transport may provide a custom `lookup`/connection selection function that returns only supplied validated addresses while the request options retain the original hostname/servername.

ADDRESS SELECTION
`ValidatedDestination.addresses` may contain multiple approved IPv4/IPv6 answers.

Define deterministic, bounded address-attempt behavior without re-resolving DNS.

Requirements:
- every attempted address must come from the supplied validated set;
- do not silently add addresses from system DNS;
- failure of one approved address may permit trying another approved address within the same total deadline if implemented cleanly;
- address retry/fallback is transport connection behavior, not Phase 10 application retry scheduling;
- bound the number of address attempts to the validated set and total deadline;
- transport metrics/error detail should not expose unsafe secrets.

If Node's chosen request API makes safe multi-address fallback impractical without significant complexity, selecting one deterministic validated address is acceptable for P3 provided the actual connection is proven bound to it and later extension remains possible. Do not compromise rebinding safety to implement Happy Eyeballs early.

GENERIC FETCHER CONTRACT
Create a reusable fetcher adapter contract suitable for future HTML/custom adapters, recommended in `src/collection/fetchers/fetcher.ts`.

Inputs should minimally support:
- one `ValidatedDestination`;
- connect timeout;
- total timeout/deadline;
- maximum wire/compressed response bytes;
- maximum decompressed response bytes;
- identifiable User-Agent;
- optional conditional validators: ETag and Last-Modified.

Use explicit validated configuration/defaults. Do not add Source/endpoint persistent timeout configuration in P3 unless it already exists in current persisted configuration; roadmap/domain docs list such endpoint fields as future logical state, not permission to front-load schema.

OUTPUT / RESULT TYPES
The one-hop transport should return typed outcomes rather than require P4/P5 to inspect arbitrary exceptions/status strings.

Recommended outcome categories:
1. terminal content response;
2. `not_modified` for HTTP 304;
3. redirect response carrying bounded `Location` and response metadata but NOT followed here;
4. expected transport failure with stable machine-readable reason, retry classification, bounded detail, optional HTTP status/metrics.

Unexpected programming/invariant failures may throw.

Do not convert Phase 4 safety blocks into transport failures; P3 only accepts already validated destinations.

HTTP METHOD / REQUEST SHAPE
Phase 5 structured feeds use GET.

Require:
- GET only;
- no request body;
- configured recognizable User-Agent;
- `Accept` values suitable for RSS/Atom/XML without claiming unsupported formats;
- `Accept-Encoding` limited to encodings P3 safely decodes;
- conditional headers only when caller supplies validators;
- no Authorization/Cookie forwarding mechanism in MVP P3;
- no arbitrary operator header injection in this task.

Do not send secrets from environment implicitly.

CONDITIONAL REQUEST SUPPORT
Implement protocol support for:
- request `If-None-Match` from caller ETag;
- request `If-Modified-Since` from caller Last-Modified;
- response ETag capture;
- response Last-Modified capture;
- 304 terminal `not_modified` outcome with no parser body.

CRITICAL DEFERRED BOUNDARY
Do NOT persist ETag/Last-Modified to `source_endpoints` or a new cache table in P3.

Phase 10 explicitly owns conditional-fetch state persistence when automated polling/scheduling exists. Phase 5 only needs fetcher protocol support when metadata is available from a caller/test/live single execution.

TIMEOUTS
Implement both:
- connect timeout: bounds establishment of the underlying connection;
- total timeout/deadline: bounds complete one-hop operation including connection + headers + response body + decompression.

Requirements:
- use timers/AbortSignal or socket/request controls with deterministic cleanup;
- timeout always destroys/aborts pending network work;
- no dangling sockets/listeners/timers after completion/failure;
- classify connect vs total timeout distinctly if implementation can do so reliably;
- timeout detail remains bounded.

Use conservative explicit defaults in one place. Do not pull timeout fields into endpoint persistence in P3.

RESPONSE SIZE LIMITS
Enforce a maximum received/wire/compressed byte count while reading the response stream.

Requirements:
- fail as soon as limit is exceeded;
- do not buffer beyond the configured bound;
- boundary behavior tested below/exactly/above limit;
- if `Content-Length` already proves the response exceeds the wire limit, fail without unnecessarily buffering the body, while still not trusting it as the only enforcement;
- no response body is written to logs/errors.

DECOMPRESSION
Support built-in content encodings deliberately, recommended:
- identity;
- gzip;
- deflate;
- Brotli (`br`) if supported cleanly by the Node baseline.

Requirements:
- a separate decompressed-size limit is enforced after decoding;
- a tiny compressed body expanding beyond the decompressed limit must fail safely;
- malformed compressed content yields typed bounded failure;
- unsupported content encoding yields typed bounded failure;
- do not automatically recurse/multiply decode arbitrary encoding chains unless explicitly supported and bounded;
- clean up decoder/request streams after errors.

CONTENT TYPE
Validate terminal content responses sufficiently for Phase 5 structured feeds.

Accept common XML/feed media types such as:
- `application/rss+xml`;
- `application/atom+xml`;
- `application/xml`;
- `text/xml`;
- compatible XML content-type parameters/charset.

Be deliberate about generic `text/plain`/`application/octet-stream` tolerance. If compatibility with real approved feeds requires a narrow fallback later, encode it explicitly with tests rather than accepting arbitrary types by default.

Redirect responses are not terminal feed bodies and need not pass terminal content-type validation.

HTTP STATUS CLASSIFICATION
Define predictable status behavior.

At minimum:
- 2xx content -> terminal content candidate after content-type/encoding/size handling;
- 304 -> `not_modified`;
- supported redirect statuses -> redirect outcome, Location handled/bounded but not followed;
- other statuses -> typed HTTP failure with status and safe retry classification.

Safe retry classification should distinguish broadly transient vs permanent/manual without implementing retry loops. Examples:
- common 5xx / 408 / 429 may be transient;
- ordinary permanent 4xx generally non-transient;
- parser/content-type failures are not transport retry loops in P3.

Do not build Phase 10 backoff/retry behavior.

REDIRECT STATUS SUPPORT FOR P4
P3 should recognize and surface standard redirect statuses needed by P4:
- 301;
- 302;
- 303;
- 307;
- 308.

P3 does not resolve or contact `Location`.

Bound the Location header value before returning it as diagnostic/input. A missing Location should be represented in a way P4 can classify cleanly; it is acceptable for P3 to return a redirect result with absent Location and let P4 own the redirect-semantics failure.

TRANSPORT METRICS
Return only metrics available reliably at this stage, for example:
- start/finish or elapsed milliseconds;
- HTTP status;
- wire bytes read;
- decompressed bytes produced;
- possibly selected validated address/family for diagnostics.

Keep metrics generic/topic independent and bounded.

Do not add endpoint health or persisted run writes here.

CONTROLLED HTTP TEST SERVER
Add a deterministic controlled HTTP fixture-server harness under test support, recommended:
- `test/support/collection/http-fixture-server.ts`

Important: local loopback fixture infrastructure must NOT require production network-safety policy to approve loopback.

P3 tests can directly exercise the one-hop transport with a synthetic `ValidatedDestination` whose address points at the controlled fixture only because the test is validating the transport primitive after the safety boundary. Do not modify production safety rules or add a test-only safety exemption.

P4/P5 tests of the full safety + transport path should continue to inject/compose safety separately so loopback does not masquerade as an approved public destination.

The fixture server should:
- bind only locally;
- use ephemeral ports for test reliability, but note production policy allows only default 80/443 at the Phase 4 safety boundary; direct P3 transport tests are intentionally post-validation primitive tests;
- provide deterministic routes for headers, statuses, compression, slow/stalled response, resets, and limits;
- close cleanly after tests;
- avoid arbitrary sleeps when barriers/events can control behavior.

HTTPS / TLS TESTING
The critical production requirement is hostname/TLS semantics without unchecked DNS.

Provide focused proof at the lowest reliable level:
- unit/component tests of request option construction/lookup binding;
- if a controlled HTTPS fixture can be implemented cleanly with test-owned synthetic certificates without committing secrets, test SNI/hostname behavior;
- otherwise retain TLS behavior through Node's standard verification path and prove structurally/component-wise that hostname/servername is preserved and `rejectUnauthorized` is never disabled.

Do not weaken TLS merely to make a test easy.
