CANONICAL COLLECTION-RUN OWNERSHIP
A Collection run represents one attempt to collect exactly one Source endpoint.

P1 must preserve these invariants:
- every run belongs to one existing Source endpoint;
- a run is created only by later collection execution after eligibility + lock ownership have succeeded;
- `started_at` records run creation/start;
- a running run is unfinished;
- a terminal run has a finish time;
- transport/parser state reflects only stages that actually exist in Phase 5;
- bounded structured errors are retained without storing response bodies/secrets;
- Phase 5 does not use post-Article-persistence processing outcome names such as `created`, `updated`, `unchanged`, `rejected`, `excluded`, or `failed` as candidate counters;
- later phases may extend the same run model rather than replace it.

MIGRATION
Add exactly one new production migration, recommended:
- `migrations/0002_collection_runs.sql`

Do not modify the checksum/content of `0001_publication_source_configuration.sql`.

The Phase 5 Collection-run schema should minimally represent:
- `id` UUID primary key;
- `source_endpoint_id` UUID NOT NULL FK to `source_endpoints(id)`;
- bounded nonblank `execution_id`/worker-correlation identifier;
- `started_at` timestamptz NOT NULL, defaulting to current database time unless there is a strong existing project reason to inject it;
- nullable `finished_at` timestamptz;
- run status with the minimal vocabulary `running`, `succeeded`, `failed`;
- transport status with minimal vocabulary `not_run`, `succeeded`, `not_modified`, `failed`;
- parser status with minimal vocabulary `not_run`, `succeeded`, `failed`;
- nullable HTTP status code when a transport response supplied one;
- nonnegative transport/wire byte count when known;
- nonnegative decompressed byte count when known;
- nonnegative Raw-item count;
- nullable bounded machine-readable error code;
- nullable bounded human-safe error detail.

Choose concrete column names consistently with existing snake_case SQL conventions.

Do NOT add normalization fields yet. Phase 6 owns normalization stage accounting.

Do NOT add:
- Article-processing counters/effects;
- Article/observation foreign keys;
- endpoint last-attempt/last-success/next-due state;
- ETag/Last-Modified endpoint cache columns;
- health/failure counters;
- scheduling/job IDs;
- Publication/Source duplicate foreign keys that can be derived through the endpoint relationship;
- arbitrary raw response/body storage.

DATABASE CONSTRAINTS
Use PostgreSQL constraints for durable shape/state invariants where they remain valid as later phases extend the row.

At minimum enforce:
- allowed status vocabularies;
- nonnegative counts/byte values;
- valid HTTP status range when non-null;
- execution identifier length/nonblank shape;
- error-code/detail bounds;
- a `running` run has `finished_at IS NULL`;
- a terminal `succeeded`/`failed` run has non-null `finished_at`;
- terminal finish time is not earlier than start time.

Avoid over-constraining cross-stage combinations in SQL if that would make legitimate Phase 6+ extension difficult. For example, do not encode every possible future parser/normalization sequence as an irreversible database truth when application lifecycle validation is a cleaner owner.

Use `ON DELETE` semantics that preserve provenance. Do not cascade-delete Collection runs merely because an endpoint is retired; current configuration law favors archival and retained provenance. A normal FK without delete cascade is preferred unless current contracts clearly require another behavior.

REPOSITORY
Create a focused production repository, recommended:
- `src/collection/runs/repository.ts`

The repository should depend on `QueryExecutor` and expose a narrow lifecycle rather than general-purpose mutation.

Recommended capabilities:
1. `startCollectionRun(...)`
   - validates/bounds application input;
   - creates a UUID run;
   - stores endpoint + execution identifier;
   - persists initial state: run `running`, transport `not_run`, parser `not_run`, zero Raw items;
   - returns an immutable mapped persisted object.
2. `finalizeCollectionRun(...)`
   - accepts terminal Phase 5 stage data;
   - performs a guarded update only while the row is still `running`;
   - sets finish time and terminal statuses/counts/metadata/errors;
   - returns the resulting immutable persisted object;
   - exact same finalization call should not silently rewrite already-terminal provenance.
3. `findCollectionRunById(...)`
   - focused read boundary for orchestration/tests/diagnostics.

A dedicated `CollectionRunPersistenceError` or similarly scoped error is appropriate if consistent with current repository patterns.

Do not expose a generic `updateCollectionRun(partial)` API that permits arbitrary state rewriting.

ROW MAPPING / VALIDATION
Treat database output as untrusted enough to validate shape, as existing repositories do.

Map:
- required strings/UUID-like identifiers;
- timestamps to `Date`;
- exact status vocabularies;
- nullable bounded values;
- integer counts/status codes.

Return immutable objects consistent with existing repository style.

Do not move generic Phase 3 configuration mapping helpers solely to reuse private implementation details unless a clearly shared helper is justified without increasing coupling. Small run-owned validators are acceptable.

FINALIZATION SEMANTICS
The repository must prevent accidental double terminal mutation.

Prefer a guarded SQL update conceptually equivalent to:
`UPDATE ... WHERE id = $id AND run_status = 'running' RETURNING ...`

If no row is returned, distinguish at least:
- nonexistent run; or
- run no longer mutable/terminal.

It is acceptable to report both through one bounded persistence error if callers do not yet require separate domain behavior, but do not silently succeed.

Do not invent crash reconciliation or abandoned-run recovery in P1. Production recovery belongs to later operational/scheduler work. A row left `running` after a catastrophic process/database failure is more truthful than falsely marking it successful.

APPLICATION-LEVEL FINALIZATION INPUT
Define a small terminal input type that can represent P5 mappings later:
- terminal run status;
- transport status;
- parser status;
- optional HTTP status;
- byte counts;
- Raw-item count;
- optional structured error.

P1 does NOT own the policy deciding whether a network-safety rejection maps to transport `not_run`, whether a parser failure maps the run to `failed`, etc. P5 orchestration owns those mappings. P1 owns validation + persistence of a valid terminal record.

BOUNDED ERRORS
Use conservative explicit bounds in schema/application validation.

Requirements:
- machine-readable error code must be bounded and safe for structured logging/inspection;
- human detail must be bounded and must not contain unbounded response bodies;
- no database URL, authorization header, token, credential, or environment secret should be required/stored;
- do not store arbitrary thrown stack traces as run detail.
