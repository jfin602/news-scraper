CANONICAL ENDPOINT SERVICE
Create one production service, recommended:
- `src/collection/collect-endpoint.ts`

The service should accept explicit dependencies rather than create hidden global singletons, with a production factory/composition layer as needed.

Conceptual input:
- endpoint aggregate already loaded or explicit endpoint key request handled by a thin caller;
- database/query executor needed for Collection-run persistence;
- endpoint lock runner;
- resolver/fetcher;
- parser;
- execution identifier provider;
- bounded fetch configuration (timeouts/limits/User-Agent) from one canonical configuration/default source.

Do not make the core service parse CLI arguments or process environment directly.

REQUIRED ORDER
The exact ordering is contract critical.

1. Load one endpoint aggregate outside or immediately before core execution.
2. Evaluate Publication/Source/endpoint collectability.
3. If ineligible, return the existing stable block decision and do NOT create a run.
4. Acquire the shared per-endpoint lock.
5. If lock is contended, return `endpoint_locked` and do NOT create a run.
6. Once lock ownership begins, create the Collection run immediately before network safety/fetch.
7. Run initial destination safety and P4 HTTP fetch/redirect orchestration.
8. Map transport/safety outcome to truthful run stage state.
9. Only when terminal content exists, invoke the RSS/Atom parser.
10. Persist terminal run state/counts/error information.
11. Return a bounded structured collection result suitable for CLI/testing/future scheduler consumption.
12. Release endpoint lock through the existing Phase 4 callback scope regardless of success/failure.

Do not move Collection-run creation before lock acquisition. An ineligible or lock-contended endpoint is not a real fetch attempt and must not create misleading run provenance.

Do not delay run creation until after network safety. Once an eligible endpoint owns execution and begins the real collection attempt, a safety rejection/fetch failure must have truthful persisted run history.

RUN ACCOUNTING — CANONICAL P5 MAPPING
P5 owns the policy mapping from execution outcomes to P1 run fields.

Required mappings:

A. Eligibility blocked
- no Collection run;
- return existing Phase 4 eligibility block reason.

B. Endpoint lock contended
- no Collection run;
- return existing `endpoint_locked` result.

C. Network-safety block after run creation
- run status: `failed`;
- transport status: `not_run`;
- parser status: `not_run`;
- Raw-item count: 0;
- bounded error code = the existing Phase 4 safety reason;
- preserve stage/context in returned result/diagnostics if useful without inventing another reason vocabulary.

D. Transport/fetch failure
- run status: `failed`;
- transport status: `failed`;
- parser status: `not_run`;
- Raw-item count: 0;
- persist available HTTP/byte metadata when truthful;
- persist the fetcher’s stable bounded error code/detail.

E. 304 Not Modified
- run status: `succeeded`;
- transport status: `not_modified`;
- parser status: `not_run`;
- Raw-item count: 0;
- persist available HTTP/transport metadata;
- return a successful no-change result.

F. Content response + parser success
- run status: `succeeded`;
- transport status: `succeeded`;
- parser status: `succeeded`;
- Raw-item count = actual parsed Raw-item count;
- persist HTTP/byte metadata;
- return immutable Raw items + run identity/summary.

G. Content response + parser failure
- run status: `failed`;
- transport status: `succeeded`;
- parser status: `failed`;
- Raw-item count: 0 unless parser contract explicitly provides a complete trustworthy count on failure (default should be zero);
- persist parser stable error code/detail and HTTP/byte metadata.

Do not use candidate processing outcomes (`created`, `updated`, `unchanged`, `rejected`, `excluded`, `failed`) in Phase 5 run accounting. Those arrive only when Article persistence exists.

RUN FINALIZATION FAILURE
If Collection-run terminal finalization itself fails:
- do not report the collection as successfully persisted/completed;
- propagate/surface the persistence failure to the caller;
- the endpoint lock must still release;
- do not issue a second broad update that fabricates terminal success;
- a retained `running` row after database failure is more truthful than silent success.

If both the collection work and run finalization fail, preserve the most useful bounded error/aggregate failure without losing the fact that persistence was not completed. Do not overwrite the original failure with a misleading normal state decision.

RUN CREATION FAILURE
If run creation fails after lock acquisition:
- no HTTP/DNS safety/fetch/parser work should proceed;
- release the endpoint lock;
- surface the database failure;
- do not return a normal transport/safety reason.

PARSER DISPATCH
Phase 5 has one endpoint type: `rss_atom`.

Required:

- after a fetch/parser failure the lock can be reacquired;
- another endpoint can be executed independently;
- one command invocation does not start a batch that aborts unrelated endpoints.

Do NOT invent a batch executor merely to demonstrate isolation. Sequential independent service calls/tests are sufficient.

ACCEPTANCE CRITERIA
P5 is complete only when:
- `package.json` is exactly `0.5.5`;
- one canonical endpoint collection service exists and is reusable by future phases/scheduler;
- configured endpoint loading, eligibility, lock, run creation, safety, fetch/redirect, parse, run finalization occur in the required order;
- ineligible/locked endpoints create no Collection run;
- once an eligible lock-owning attempt starts, safety/transport/parser failures create truthful persisted terminal run history;

- manual collection is owned by Worker command/process, not Web/API;
- existing Worker readiness/lifecycle behavior remains green;
