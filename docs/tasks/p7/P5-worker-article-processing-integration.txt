CANONICAL CONTENT-BATCH ORDER
For each successfully parsed content response:

1. normalize every Raw item using existing Phase 6 isolation/accounting;
2. run Article-link policy for every successfully normalized candidate;
3. map each Article-link rejection immediately to canonical processing outcome `rejected` and DO NOT invoke Relevance or identity for that candidate;
4. for each link-accepted candidate, invoke P1 Relevance;
5. Phase 7 default Relevance must return `include`; only an included candidate may reach P3 identity/persistence;
6. obtain one explicit observation time for the candidate and invoke P3;
7. map P3 success to `created`, `updated`, or `unchanged`;
8. map P3 expected bounded item-level identity failure to processing outcome `failed` and continue with unrelated candidates;
9. after the bounded candidate batch is completely accounted, finalize the Collection run with exact processing status/counters;
10. release endpoint lock through the existing execution boundary.

The ordering `Article-link policy -> Relevance -> identity` is contract-critical. Add tests that fail if identity is called before Relevance or if Relevance is called for a rejected Article link.

CANONICAL PROCESSING OUTCOME ACCOUNTING
Every successfully normalized candidate receives exactly one Phase 7 processing outcome:
- Article-link rejected => `rejected`;
- link accepted + Relevance excluded => `excluded` (not expected under Phase 7 default configuration, but the orchestration may preserve this typed branch if P1's contract is later extended);
- included + P3 new Article => `created`;
- included + P3 material change/promotion => `updated`;
- included + P3 no material Source change => `unchanged`;
- included + expected item-level P3 conflict/failure => `failed`;
- candidate prevented from normal processing by a stage-level Relevance/persistence execution failure => `failed` for exact run accounting.

Always preserve:

`created + updated + unchanged + rejected + excluded + failed = normalized_candidate_count`

For the Phase 7 default evaluator:
- `excluded_count` MUST be zero in real integrated success/failure tests unless the test intentionally injects a non-production fake evaluator to exercise branch mechanics;
- under the production Phase 7 path, `rejected_count` MUST equal `article_link_rejection_count` because Article-link policy is the only implemented candidate rejection path.

Normalization failures remain outside the processing equation.

PROCESSING STATUS SEMANTICS
- `processing_status = succeeded` when the bounded Article-processing loop completes normally, EVEN if one or more candidates returned expected item-level `failed` outcomes.
- `processing_status = failed` only when a stage-level evaluator/clock/persistence infrastructure failure breaks the normal bounded processing contract.
- stage-level processing failure implies overall `run_status = failed`.
- ordinary item-level identity conflicts may leave overall run/status succeeded if all remaining candidates are safely processed and finalization succeeds.

STAGE-LEVEL FAILURE ACCOUNTING
A stage-level failure MUST NOT create partial/missing canonical outcome accounting.

If an unexpected Relevance evaluator failure, observation-clock failure, or unexpected P3 persistence exception occurs after some normalized candidates have already been accounted:
- preserve outcomes for all candidates already processed/committed;
- preserve `rejected` outcomes already established by Article-link policy;
- classify the candidate at which the stage failed AND every remaining normalized candidate that has not yet received an outcome as `failed`;
- set `processing_status = failed`;
- set overall `run_status = failed`;
- finalize the Collection run with the complete exact six-counter distribution and a bounded stable error code/detail;
- do not attempt Article persistence for the remaining candidates after the stage becomes unsafe.

This preserves the contract that every normalized candidate has one canonical processing outcome while honestly distinguishing stage-level failure from ordinary item failure.

Do not include normalization-failed Raw items in this bulk `failed_count` adjustment because they never became Article candidates.

PER-CANDIDATE TRANSACTION / FAILURE ISOLATION
P3 owns one transaction per included candidate. P5 MUST NOT wrap the full feed batch in a database transaction.

Consequences:
- a successful Article from candidate A may commit before candidate B fails;
- an expected candidate B identity conflict does not roll back A and does not stop candidate C;
- an unexpected stage-level database failure stops remaining processing for safety, but already committed A remains;
- Collection-run finalization happens after candidate transactions and cannot roll them back retroactively.

If run finalization itself fails after Articles/observations committed, preserve the existing `CollectionRunFinalizationError` pattern or an equivalently explicit bounded error. Tests must prove already committed Article state is not falsely described as rolled back.

Do not use Collection-run start time as Source publication time.
