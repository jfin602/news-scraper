ADD PROCESSING STAGE STATE
Add a processing-stage status with exactly:
- `not_run`
- `succeeded`
- `failed`

Recommended persisted column: `processing_status`.

Semantics:
- `not_run`: the Article-processing stage did not execute for this Collection run;
- `succeeded`: the bounded Article-processing stage completed its candidate batch contract, even if one or more candidates ended in ordinary item-level `failed` outcomes;
- `failed`: a stage-level execution/infrastructure failure prevented normal per-candidate processing from completing, but every normalized candidate is still assigned one canonical processing outcome for truthful run accounting.

Do not use `failed` merely because `failed_count > 0`. Ordinary isolated candidate identity conflicts are item-level outcomes and do not by themselves mean the processing stage failed.

ADD CANONICAL OUTCOME COUNTERS
Persist nonnegative integer counters:
- `created_count`
- `updated_count`
- `unchanged_count`
- `rejected_count`
- `excluded_count`
- `failed_count`

Do not add generic `accepted`, `skipped`, `persisted`, or competing outcome fields.

EXACT ACCOUNTING INVARIANT
Once Article processing runs (`processing_status` is `succeeded` OR `failed`), EVERY successfully normalized candidate MUST have exactly one canonical processing outcome.

Therefore enforce:

`created_count + updated_count + unchanged_count + rejected_count + excluded_count + failed_count = normalized_candidate_count`

This invariant applies even when `processing_status = failed`.

If a stage-level processing failure occurs after some candidates committed, P5 will classify the current/unprocessed normalized candidates as `failed` so the run remains arithmetically complete while preserving already committed successes. Do NOT create a partial-accounting state where normalized candidates disappear from the canonical outcome taxonomy.

`normalization_failure_count` remains outside this equation because those Raw items never produced Article candidates.

ARTICLE-LINK REJECTION RELATIONSHIP
`article_link_rejection_count` remains Phase 6 stage telemetry and those SAME normalized candidates map to processing outcome `rejected` once processing accounting runs.

Database validation may enforce, when `processing_status != 'not_run'`:
- `rejected_count >= article_link_rejection_count`.

Do NOT require permanent equality at the database layer because future pipeline stages may add other canonical rejection reasons. P5 Phase 7 behavior should prove equality under the currently implemented pipeline.

RELEVANCE EXCLUSION RELATIONSHIP
Do NOT enforce `excluded_count = 0` in the schema. Phase 7 runtime behavior has zero exclusions because the empty-rule evaluator defaults to include, but Phase 11 already has contracted exclusion semantics and must be able to extend the existing accounting rather than replace the schema.

STATUS CONSISTENCY
Database and repository validation must preserve these truths:

1. `processing_status = 'not_run'` => all six processing counters are zero.
2. `processing_status IN ('succeeded', 'failed')` => `normalization_status = 'succeeded'` because only successfully normalized candidate batches can enter Article processing.
3. For either terminal processing status, exact six-counter arithmetic equals `normalized_candidate_count`.
4. `processing_status = 'failed'` => overall `run_status = 'failed'`.
5. Overall `run_status = 'succeeded'` MUST NOT coexist with `processing_status = 'failed'`.
6. `processing_status = 'succeeded'` may coexist with `failed_count > 0` because ordinary item-level failures are isolated outcomes, analogous to Phase 6 ordinary normalization/link rejections.
7. Earlier transport/parser/normalization stage failures and `not_modified` attempts remain `processing_status = 'not_run'` with zero processing counters.

Do not invent a second run lifecycle vocabulary.
