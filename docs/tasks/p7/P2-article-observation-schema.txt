Use database checks so Source-date status/timestamp pairs cannot contradict each other:
- `parsed` requires a timestamp;

`first_seen_at` and `last_seen_at` are Platform observation times, not Source dates. Require `last_seen_at >= first_seen_at`.

PUBLICATION / SOURCE OWNERSHIP
The database should structurally prevent an Article from pairing a Publication with a Source belonging to another Publication.

Add only the minimal composite uniqueness/reference support required to express that invariant. For example, adding a unique `(publication_id, id)` or equivalent key to `sources` is acceptable when needed for a composite foreign key. Do not redesign Source identity or existing configuration semantics.

ARTICLE IDENTITY INDEXING
The database must support the Phase 7 identity invariants without placing arbitrary maximum-length identities directly into B-tree unique keys.

Current candidate bounds are too large to assume a normal B-tree entry can always store the full indexed text. Use fixed-size SHA-256 identity digests for indexed lookup/uniqueness while retaining the complete external ID/canonical URL in their ordinary columns.

Constraints/indexes must support:
1. no duplicate Article for one strong external ID within the same Source;
2. no duplicate canonical-fallback Article for the same Publication/Source canonical identity when `external_id IS NULL`;
3. multiple Articles with DIFFERENT strong external IDs may legally share the same canonical URL;
4. P3 must be able to look up all Article rows with a matching canonical digest, including strong-ID-backed Articles.

Recommended design direction:
- fixed-size digest generated columns or expression indexes derived from the full identity using PostgreSQL core SHA-256 support;
- partial unique Source + external-ID-digest identity when external ID is present;
- partial unique Publication/Source + canonical-digest identity only for fallback rows where external ID is null;
- a non-unique canonical-digest lookup index across all Articles.

Do not install a database extension solely for hashing if PostgreSQL core functions suffice.

Hash values are an indexing/serialization aid, NOT semantic identity. P3 must compare the complete stored text after digest lookup before treating a row as an exact identity match. A digest collision may produce a conservative persistence conflict, but MUST NEVER cause silent merging of distinct full values.

ARTICLE-OBSERVATION SHAPE
Create `article_observations` or an equivalently clear table representing endpoint/run provenance for a persisted Article or candidate outcome.

Required logical columns:
- observation ID UUID primary key;
- Publication ID;
- Source ID;
- Source endpoint ID;
- Collection run ID;
- nullable Article ID;
- observation timestamp;
- processing outcome constrained to the canonical vocabulary: `created`, `updated`, `unchanged`, `rejected`, `excluded`, `failed`;
- nullable observed external ID preserving the complete value when present;
- observed canonical identity URL where available/required for the candidate being represented;
- optional bounded machine-readable reason/detail only if needed to preserve a stable outcome reason without storing unbounded source/database text.

P2 does not require runtime code to write rejected/excluded/failed observations. The schema MUST merely permit pre-identity terminal outcomes to have no Article ID, because the governing domain contract allows that. P3 will require successful `created`/`updated`/`unchanged` observations to reference an Article.

OBSERVATION PROVENANCE INVARIANTS
Use database constraints/composite foreign keys where practical so independently valid UUIDs cannot be combined into false provenance.

Enforce structurally:
- the Collection run belongs to the referenced endpoint;
- the endpoint belongs to the referenced Source;
- the Source belongs to the referenced Publication;
- when Article ID is non-null, that Article belongs to the same Publication/Source;
- `created`, `updated`, and `unchanged` observations MUST have a non-null Article ID;
- do not cascade-delete retained Article/observation provenance merely because Source configuration is later archived/removed through a future administrative operation.

Adding minimal composite unique keys to existing tables solely to support these foreign keys is allowed. Do not change the logical identity of those existing records.

BOUNDS / SHAPE CHECKS
Mirror current normalized candidate bounds where persisted Source-derived text is stored so database rows cannot exceed the accepted candidate contract. Preserve trimmed/nonblank constraints where values are semantically required.

Do not silently truncate required identity/title/URL values in SQL. Application normalization already owns bounded input; the database should reject contradictions rather than alter data.
