TASK: Correction 1 / P1 — Complete digest lifecycle producer handoff

CORRECTION SCOPE
This is the sole implementation prompt in correction `c1-digest-lifecycle-handoff`.

Phase 1 roadmap prompts P1 (`2.1.1`) and P2 (`2.1.2`) are already implemented. Phase 1 P3 correctly stopped with `Planning needed` before changing files because the P1 digest repository did not expose the complete producer contract P3 was instructed to consume.

The observed handoff gaps are bounded and already required by the governing Phase 1 contract:

- P1 has database-enforced scheduled-slot idempotency and one-running-attempt-per-Profile protection, but no producer API to read the current running attempt;
- P1 has stale-attempt recovery that requires a running attempt id, but no producer read seam that safely supplies that id;
- P1 has no normal `running -> completed` attempt-finalization API, so a successful/failed/skipped execution cannot release its running claim through the repository boundary;
- P1 exposes active-digest read/activation but no explicit active-reference suppression/clear primitive for disabled, zero-input, no-overlap, or canonical-invalidation cases;
- later protected admin status requires a bounded latest-attempt read rather than direct AI-table SQL;
- the current attempt terminal-outcome constraint has no truthful disabled-skip category even though Phase 1 P3 requires a disabled digest evaluation to finish as a bounded skip without calling Gemini.

This correction completes that producer boundary at unchanged package version `2.1.2`. It does not implement P3 scheduling/generation/freshness behavior itself, does not call Gemini, and does not consume roadmap version `2.1.3`.

CORRECTION GOAL
Leave one complete repository/application producer boundary that lets existing Phase 1 P3 implement its state machine without importing raw AI table names or writing repository-owned SQL.

Conceptually:

```text
claim running attempt
-> read current running attempt when recovery/status requires it
-> resolve input / call provider outside DB transaction
-> caller-owned bounded transaction
     -> persist successful digest when applicable
     -> activate or suppress active reference when applicable
     -> complete the exact running attempt
-> running claim released truthfully
```

The correction owns only the durable primitives and their validation. P3 still owns when to claim, when an attempt is stale, when to generate, how P2 failure categories map to bounded attempt diagnostics, semantic `current | older | null`, scheduler timing, canonical invalidation policy, and Worker integration.

RUNNING-ATTEMPT READ BOUNDARY
Add a validated repository read operation for the currently running attempt for one Profile, exact name implementation-owned, conceptually:

```ts
findRunningDigestAttempt(executor, profileKey)
  -> PersistedDigestAttempt | undefined
```

Requirements:

- resolve Profile ownership through the repository's existing config-key validation/lookup path;
- return at most the one row protected by the database partial-unique invariant;
- map through the same persisted-attempt validation as claim results;
- return `undefined` only when there is no running attempt for that Profile;
- never return another Profile's attempt;
- do not expose raw row/table shape;
- do not acquire/hold a long-lived transaction merely to read status;
- do not infer stale status here. P3 owns the timeout/cutoff policy.

This operation is the producer seam P3 uses to obtain the exact attempt id/start time before invoking stale recovery. The later recovery mutation must still revalidate state under transaction/lock; a prior read is never authority that the row is still running.

NORMAL ATTEMPT COMPLETION / FINALIZATION
Add a validated terminal-completion mutation for a claimed running attempt, with both caller-owned-transaction and convenience transaction forms where useful.

The core producer must support conceptually:

```ts
completeDigestAttemptInTransaction(executor, input)
completeDigestAttempt(database, input)
```

Exact type/function names are implementation-owned, but downstream behavior is not.

The completion input must identify at least:

- Profile config key;
- exact attempt id;
- terminal outcome;
- completion timestamp;
- nullable/required `digestInputIdentity` and input Article count as appropriate to the terminal path;
- nullable bounded failure category;
- nullable bounded provider/model identity;

Required state transition:

```text
same Profile + same exact attempt + state=running
-> one validated terminal update
-> state=completed
-> completed_at set
-> one truthful terminal_outcome
-> bounded metadata recorded
```

A completed/abandoned/nonexistent/wrong-Profile attempt MUST NOT be mutated by normal completion.

The completion operation MUST NOT silently complete whichever running attempt happens to exist. The caller must supply the exact claimed attempt id.

PER-PROFILE LIFECYCLE SERIALIZATION
