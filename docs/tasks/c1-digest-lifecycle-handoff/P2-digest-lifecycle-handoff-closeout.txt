## D. Exact-attempt completion

Trace normal completion from exported API to SQL mutation.

Verify:

- completion requires Profile identity and exact attempt id;
- mutation is conditional on `state='running'` or an equally strong invariant;
- wrong Profile cannot complete another Profile's attempt;
- an already completed/abandoned attempt cannot be silently rewritten;
- normal completion never means "complete whichever attempt is running";
- one successful completion sets completed state/timestamp and truthful terminal outcome;
- the one-running-attempt constraint becomes available to a later claim only after truthful completion;
- ordinary completion cannot manufacture `abandoned`; stale recovery remains the only owner of that transition unless current code has an equivalently explicit protected path.

Inspect application-level terminal metadata validation for:

- `success`;
- `skipped_disabled`;
- `skipped_no_input`;
- `skipped_unchanged`;
- `failed`;
- stale-recovery `abandoned`.

The state model must not allow impossible combinations such as a skipped attempt with provider retrieval facts, no-input with nonzero input count, a running row with completed timestamp, or a failed row carrying unbounded raw provider error text.

## E. Per-Profile lifecycle locking

Require the same lock discipline for:

- claim;
- stale recovery/reclaim;
- normal completion;
- active activation/replacement;
- active suppression.

Verify:

- stale recovery locks before changing the running attempt to abandoned;

- activation/suppression lock in the caller-owned transaction;
- different Profiles remain independently concurrent;
- unique constraints remain authoritative backstops;
- no transaction/advisory lock survives across provider I/O;
- reentrant use within one PostgreSQL transaction is safe.

## F. Active digest suppression

- removes only `distribution_profile_active_digests` state for the requested Profile;

- cannot affect another Profile;
- participates in the same lifecycle lock;
- has caller-owned transaction composition available to P3.

No "suppression" implementation may delete the immutable digest simply to hide it.

## G. Activation alignment

- generation exists completely before active pointer switch;
- prior generation remains immutable history;
- cross-Profile pointer remains impossible/rejected;
- existing convenience `persistAndActivate...` semantics are not weakened;
- P3 can still use lower-level caller-owned transaction primitives when it needs attempt completion in the same transaction.

## H. Atomic P3 composition proof

Require real integration/database evidence for the exact downstream handoff, not just isolated methods.

The tests must prove P3 could do all of these with exported producer operations only:

1. successful path:
   - claim attempt;
   - later transaction creates immutable digest;
   - activates that digest;
   - completes that exact attempt as success;
   - commit exposes all three coherent effects;
2. rollback path:
   - force a failure after one or more of create/activate/complete inside the same transaction;
   - none of the partial new state survives;
   - prior active digest/history remains correct;
3. suppression path:
   - suppress active reference + complete exact skip/failure attempt in one transaction;
   - rollback preserves prior state;
4. failed provider path:
   - exact attempt completes as failed with bounded diagnostics and no new digest;
5. skip paths:
   - disabled/no-input/unchanged finish without provider-state fabrication.

If the tests only prove each repository function independently but not caller-owned transaction composition, the P3 producer handoff is still incomplete.
