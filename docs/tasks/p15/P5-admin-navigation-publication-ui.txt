GOAL
Turn the Phase 14 Source-only `/admin` page into a compact multi-workspace control plane and add the operator-facing singleton Publication editor.

P5 owns admin navigation/shell composition plus Publication UI. It must preserve the complete existing Source/endpoint administration experience and must not implement Category/Relevance editing yet.

ROADMAP VS UI-WORKSTREAM BOUNDARY
This is versioned roadmap implementation on `main` because it exposes governed Phase 15 Publication behavior and API state. Do not move it to `ui-polish`, remove its version change, or create a `docs/design/tasks` prompt.

Presentation should extend the established admin visual language. Do not invent or modify durable design guidance unless execution discovers a real ambiguity that invalidates the prompt; in that case stop and report planning drift.

ADMIN INFORMATION ARCHITECTURE
Replace the page's Source-only top-level framing with a clear singleton admin shell that has at least:
- Publication workspace;
- Sources workspace;
- a place for the upcoming Editorial workspace if needed for P6, without implementing fake Category/Relevance behavior in P5.

A deployed installation contains exactly one Publication/topic, so there is no Publication switcher, tenant selector, slug selector, or list of Publications.

Use semantic navigation controls with clear current-state indication and keyboard operation. Preserve dedicated Source/endpoint nested navigation inside the Sources workspace.

Do not introduce a frontend framework solely for tabs/navigation. Keep the implementation dependency-light and consistent with the existing static admin assets unless the current source demonstrates a concrete need otherwise.

PUBLICATION WORKSPACE
Expose all P2 fields:
- name;
- `activeForCollection`;
- `publicStatus`;
- description;
- logo path;
- accent color;
- presentation timezone.

The UI should explain the two global state controls accurately:
- collection active controls whether eligible Sources/endpoints may run;
- public/private controls whether the public feed is exposed;
- neither silently changes the other.

For presentation timezone:
- empty/unset means UTC calendar-date presentation;
- configured value is an IANA timezone identifier;
- do not offer locale/date-template/time-format configuration;
- do not imply timezone changes Article timestamps or feed order.

Use appropriate native form controls. Keep existing safe validation/server error behavior; server remains authoritative.

CLIENT STATE / MUTATION BEHAVIOR
On Publication workspace entry/load:
- fetch the canonical P2 Publication read model;
- distinguish loading, ready, and error states;
- populate current values without exposing internal IDs.

On save:
- send one same-origin JSON mutation through the established admin helper/header contract;
- disable duplicate submission while the mutation is in flight;
- preserve useful unsaved values when validation/API failure occurs;
- render bounded server errors as text, never HTML;
- refresh/reconcile from the canonical saved response after success.

Do not perform optimistic state changes that bypass server validation.

SOURCE / ENDPOINT PRESERVATION
The existing Source administration client currently owns substantial state for:
- Source list/create/edit;
- Source approval/lifecycle/operational actions;
- Source admission phrases;
- endpoint list/create/edit;
- endpoint approval/lifecycle/operational actions;
- health/recent runs;
- check-now.

Preserve all of it. Navigation between Publication and Sources must not corrupt selected Source/endpoint state, leave hidden forms active unexpectedly, or cause duplicate listeners/fetch loops.

A minimal internal client refactor is allowed if it reduces duplication and keeps behavior obvious, but do not perform unrelated wholesale frontend restructuring.

SECURITY
Preserve:
- `/admin` no-store/security headers and restrictive CSP;
- state-changing same-origin requests using `X-News-Scraper-Admin-Request: 1` through the established helper;
- no credentials/Cloudflare tokens stored in browser storage or markup;
- no native login/session/role implementation;
- bounded text rendering for server values/errors.

ACCESSIBILITY / RESPONSIVE BASELINE
Maintain or improve the existing admin baseline:
- semantic landmarks/headings/navigation/forms/labels;
- keyboard-operable workspace navigation and controls;
- visible focus in all tested states;
- coherent focus placement after workspace changes and save/error actions where practical;
- no information conveyed solely by color;
- long Publication names/descriptions/logo paths/timezones/errors wrap safely;
- no horizontal document overflow at representative 390x844 mobile width;
- usable layout at representative 1280x900 desktop width;
- practical touch targets.

Do not let arbitrary Publication accent color restyle admin security/error/focus semantics unless the existing admin design explicitly supports it safely.
