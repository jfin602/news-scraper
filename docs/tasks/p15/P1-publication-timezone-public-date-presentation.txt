GOAL
Add optional singleton Publication `presentation_timezone` configuration and use it only for public calendar-date presentation.

Absent configuration preserves the existing UTC calendar-date fallback. A configured valid IANA time-zone identifier may change which calendar date is displayed for a timestamp near a zone boundary, but MUST NOT change persisted Article timestamps, effective-feed-date calculation, feed eligibility, chronological ordering, keyset cursors, routing, or Publication identity.

PERSISTENCE AND CONFIGURATION
Extend the existing singleton Publication model rather than creating a separate settings object or tenant entity.

Add the next migration in the current chain to persist nullable `presentation_timezone` on `publication_settings` or the current canonical singleton table. Do not rewrite historical migrations.

Configuration behavior:
- optional/absent value is canonical no-timezone configuration and means UTC presentation;
- configured value must be a trimmed valid IANA time-zone identifier supported by the runtime's standard timezone data;
- reject invalid/unsupported identifiers with the existing bounded `ConfigurationValidationError` pattern;
- keep validation topic independent;
- do not introduce locale, arbitrary date template, time format, offset-only, or general presentation-format configuration;
- prefer standard Node/ECMAScript `Intl`/ICU validation and formatting; do not add a timezone dependency unless the existing runtime demonstrably cannot satisfy the contract;
- persist and read the value through the canonical Publication repository and reject malformed database values rather than silently coercing them.

Preserve existing `name`, `activeForCollection`, `publicStatus`, `description`, `logoPath`, and `accentColor` validation and serialization behavior.

BOOTSTRAP
Extend the explicit Publication bootstrap document to accept optional `presentationTimezone` alongside existing optional presentation fields.

Preserve ordinary bootstrap create-if-absent/no-overwrite semantics exactly:
- omitted timezone remains absent/UTC;
- initial configured timezone is persisted when the singleton is first created;
- rerunning bootstrap MUST NOT overwrite a later operator-managed timezone or any other existing Publication setting.

PUBLIC READ MODEL / API
Expose the optional timezone through the existing canonical public Publication presentation read model returned by `GET /api/feed`, using the repository's current JSON naming convention (normally `presentationTimezone`).

Do not create a second feed endpoint/query or require a Publication selector.

The database Article query/order/cursor path must remain based on the existing UTC instants and order tuple. `presentation_timezone` belongs in Publication presentation metadata, not in Article ordering SQL, cursor payloads, candidate normalization, Article persistence, or Collection-run state.

PUBLIC BROWSER PRESENTATION
Update the root public client so calendar-date labels use:
- configured Publication timezone when present;
- UTC when absent.

Keep the established date presentation shape and accessibility behavior unless the current Phase 13 implementation requires a minimal compatible adjustment. Formatting must be deterministic for the configured zone and independent of the viewer machine's local timezone.

Do not alter headline destinations, Source labels, discovery/search/filter state, load-more behavior, theme selection, pending/loading behavior, or routing.
