GOAL
Complete the Phase 15 editorial control surface by adding practical Category and Relevance-rule administration to the protected `/admin` application.

P6 consumes the P3/P4 APIs. It must not reimplement their domain rules in browser code or turn the existing bounded Relevance model into a generic rule builder.

EDITORIAL WORKSPACE
Add/complete a top-level Editorial workspace in the P5 admin navigation.

The workspace should make two related but distinct resources understandable:
- Categories;
- Relevance rules.

The exact visual layout may be compact, but list/selection/editor state must remain clear on desktop and mobile. Do not add a Publication/topic selector.

CATEGORY UI
Support:
- list existing Categories;
- create Category with immutable config key + display name;
- select/read Category;
- edit display name only after creation;
- remove an unreferenced Category;
- display a clear bounded conflict when removal is blocked because the Category remains in use.

Requirements:
- config key field is editable only during create and clearly described as immutable afterward;
- server remains authoritative for relationship/deletion validation;
- a blocked delete MUST NOT optimistically remove the Category from client state;
- use a clearly named destructive action and require enough UI intentionality to avoid accidental activation, without inventing a new authentication/approval flow;
- do not expose Category archive/lifecycle controls because none exist.

CATEGORY CHOICE SYNCHRONIZATION
The managed Category set is also consumed by:
- existing Source default-Category selector;
- existing endpoint default-Category selector;
- Relevance `categorize` target selector.

After successful Category create/update/delete, refresh/reconcile the canonical Category choice state so every workspace uses current server data.

Preserve existing selected Source/endpoint default values when still valid. If a Category was successfully deleted, it was unreferenced by contract, so no existing persisted Source/endpoint default should point to it.

Do not move Source/endpoint default mutation ownership into Editorial UI unless the existing Source/endpoint editor already owns those controls; P6 only keeps their choices synchronized.

RELEVANCE RULE UI
Support:
- list/select rules;
- create rule;
- edit rule configuration;
- enable/disable rule;
- remove a genuinely unreferenced rule;
- display retained-history conflict when removal is blocked.

Expose only the canonical fields:
- immutable `configKey` on create;
- predicate: `title_contains`, `summary_contains`, `source_category_equals`;
- literal pattern;
- action: `include`, `exclude`, `categorize`;
- integer priority;
- enabled state through the dedicated enable/disable operation;
- reason/explanatory label;
- scope: installation-wide or one real Source;
- Category target only when action is `categorize`.

Use operator-readable labels while sending/storing canonical enum values.

CONDITIONAL RULE FORM BEHAVIOR
Keep conditional fields deterministic:
- installation-wide scope means no Source config key is sent;
- Source-scoped means one current real Source choice is required;
- `categorize` shows/requires a current Category target;
- `include`/`exclude` hide/clear Category target and MUST NOT send one;
- predicate/action changes do not silently rewrite unrelated values such as priority/reason/pattern;
- disabled is not archive/deleted.

Client-side form guidance may prevent obvious invalid combinations, but server validation remains authoritative and server errors must preserve useful unsaved form state.

DETERMINISTIC PRECEDENCE EXPLANATION
Provide concise operator guidance that accurately reflects the existing Phase 11 behavior. It must not become a second evaluator.

Explain at least:
- all applicable enabled literal rules are evaluated deterministically;
- include/exclude precedence follows the existing priority/scope/action/final immutable-key tie rules already implemented/tested;
- all matching `categorize` rules can add Categories and are not reduced to one winner;
- if no categorize rule assigns a Category, endpoint default wins over Source default;
- rule edits are prospective and do not automatically rescan historical Articles.

Derive wording from the governing contract/current evaluator tests rather than inventing simplified semantics that are false.

SOURCE CHOICES
Relevance Source scope should use bounded current Source choices from an existing protected admin read model. Do not expose internal Source UUIDs.

Prefer reusing `GET /api/admin/sources` data already available to the admin client. Do not create a duplicate Source directory API merely for the rule form.

DELETE / ERROR STATES
For Category/rule delete:
- render bounded `in use`/retained-provenance conflicts clearly;
- do not expose SQL/constraint names;
- keep the selected item/editor coherent after failure;
- after success, remove/reload canonical server state and choose a predictable next/empty selection.

For all create/update mutations:
- prevent duplicate concurrent submits;
- send the canonical same-origin JSON mutation header;
- preserve user input on validation/API failure;
- reconcile with server response after success;
- never render server-provided content as HTML.

ADMIN CODE STRUCTURE
The existing admin client is large. You MAY split it into a few focused same-origin static modules/resources if the current CSP/router can support that cleanly and the refactor directly improves Phase 15 maintainability.

If splitting:
- preserve restrictive CSP and no inline script requirements;
- keep dependencies local/no new frontend framework;
- preserve all Phase 14/P5 behavior and tests;
- avoid speculative generic state libraries/components unrelated to this phase.

A simple extension of the current file is also acceptable if it remains understandable and regression-safe.
