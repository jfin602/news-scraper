GOAL
Expose the existing installation-wide Category model through the protected admin API and add physical removal only when the Category is genuinely unreferenced.

P3 does not create a Category archive state, does not perform Article moderation/recategorization, and does not redesign Source/endpoint default Category semantics.

EDITORIAL ADMIN BOUNDARY
Create or establish a focused editorial administration service/router under the current `src/admin/` and Web/API ownership structure. P3 owns the Category portion; P4 extends the same boundary with Relevance-rule administration.

Do not embed SQL transaction orchestration directly in Express handlers.

CATEGORY IDENTITY / READ MODEL
Use immutable installation-wide Category `config_key` as the operator/API identity. Do not expose internal UUIDs in normal admin URLs or require Publication IDs/slugs.

Read models should contain only bounded operator-relevant fields, at minimum:
- `configKey`;
- `displayName`.

Retain the existing Category display-name bounds and normalization. `configKey` is accepted only on create and remains immutable afterward at both application and database levels.

CATEGORY COMMANDS
Support:
- list Categories;
- create Category;
- get Category by config key;
- update mutable display label;
- physically remove Category only when no retained relationship references it.

Recommended protected API:

`GET    /api/admin/categories`
`POST   /api/admin/categories`
`GET    /api/admin/categories/:categoryKey`
`PUT    /api/admin/categories/:categoryKey`
`DELETE /api/admin/categories/:categoryKey`

Small route-shape adjustments are allowed only to fit established admin conventions without changing semantics.

The existing `GET /api/admin/categories` contract used by Phase 14 Source/endpoint editors must remain compatible. Transfer that route from Source administration to the editorial registrar/service rather than leaving duplicate route ownership.

CREATE / UPDATE
Reuse canonical Category normalization/repository functions. Exact-key request validation must reject unknown fields.

Create accepts `configKey` + `displayName` and returns a stable conflict for duplicate config key.

Update accepts only mutable fields, currently `displayName`; it must never accept or rewrite `configKey`.

GUARDED PHYSICAL REMOVAL
No Category archive/lifecycle field is introduced.

A DELETE may succeed only when the Category is transactionally unreferenced by every retained relationship that requires it, including at least:
- `relevance_rules.category_id` for `categorize` targets;
- `sources.default_category_id`;
- `source_endpoints.default_category_id`;
- `article_categories.category_id` current Article membership;
- `article_observation_category_reasons.category_id` retained provenance/reasons;
- any equivalent retained Category reference already present in the final schema.

The command MUST NOT make deletion succeed by:
- cascading dependent rows;
- nulling Source/endpoint/rule references automatically;
- deleting Article Category memberships;
- deleting/re-writing observation reasons or provenance;
- bulk recategorizing Articles.

Prefer the existing restrictive PostgreSQL foreign keys as the final integrity authority and translate expected referential-conflict results into one bounded stable application error such as `category_in_use`. If a preflight relationship check is useful for deterministic UX, deletion must still remain safe under races by relying on the database constraint/transaction outcome.

Deleting an actually unreferenced Category should remove exactly that Category and no unrelated data.

ERROR SHAPING
Provide bounded stable errors for at least:
- invalid request/configuration;
- category not found;
- config-key conflict;
- category in use.

Do not leak PostgreSQL constraint names, SQL, stack traces, UUIDs, or database internals.

SOURCE / ENDPOINT DEFAULT INTEGRATION
Preserve Phase 14 default-Category controls without moving their mutation ownership into P3.

After P3:
- Source/endpoint admin code still resolves existing Category config keys through the canonical Category repository/service boundary;
- endpoint default overrides Source default during collection;
- defaults apply only when no categorize rule assigns a Category;
- Source priority remains Phase 14-owned;
- deleting a Category referenced by either default is rejected until the operator explicitly clears/changes that default through the existing Source/endpoint administration surface.
