GOAL
Expose the existing bounded Relevance-rule model through the protected admin API without changing Relevance semantics.

P4 owns rule list/detail/create/update/enable-disable/guarded removal. It does not build the browser rule editor, add predicates/actions, perform historical reprocessing, or alter the evaluator's deterministic precedence/default behavior.

RULE IDENTITY / READ MODEL
Use immutable installation-wide Relevance-rule `config_key` as the API/operator identity. Do not expose a Publication tenant key or require internal UUIDs in normal URLs.

A bounded admin rule read model should expose:
- `configKey`;
- `predicateType`;
- `pattern`;
- `action`;
- `priority`;
- `enabled`;
- `reason`/explanatory label using the existing canonical field;
- optional `sourceConfigKey` for real Source scope;
- optional Category target identity/config key only for `categorize`.

Do not expose internal database IDs or historical observation payloads merely because they exist.

SUPPORTED RULE MODEL
Preserve exactly the existing vocabulary:
- predicates: `title_contains`, `summary_contains`, `source_category_equals`;
- actions: `include`, `exclude`, `categorize`;
- deterministic literal matching only;
- optional Source scope referencing one real Source;
- Category target required for `categorize`;
- Category target forbidden for `include` and `exclude`;
- existing priority, Source-scope specificity, action precedence/tie behavior, rule-key tie-break, additive categorization, and endpoint-default then Source-default fallback.

Do not add regex, glob, fuzzy, stemming, semantic/AI, compound Boolean expressions, ranking/boost, or arbitrary metadata predicates.

ADMIN COMMANDS
Extend the P3 editorial admin service/router with operations equivalent to:

`GET    /api/admin/relevance-rules`
`POST   /api/admin/relevance-rules`
`GET    /api/admin/relevance-rules/:ruleKey`
`PUT    /api/admin/relevance-rules/:ruleKey/configuration`
`PUT    /api/admin/relevance-rules/:ruleKey/enabled`
`DELETE /api/admin/relevance-rules/:ruleKey`

Small naming adjustments are acceptable only when they better match current admin conventions without changing semantics.

Create accepts the immutable config key plus the complete canonical rule configuration.

Configuration update must not accept a replacement config key. Prefer requiring the complete canonical mutable rule representation so Source scope/action/target changes are validated coherently.

Keep enable/disable as a narrow ordinary non-destructive operation using/reusing the existing `setRelevanceRuleEnabled()` boundary rather than pretending disabled is an archive state.

RELATIONSHIP VALIDATION
All multi-resource mutations must validate real relationships and roll back invalid combinations:
- named Source scope must resolve to an existing Source config key;
- named Category target must resolve to an existing Category config key;
- `categorize` requires that target;
- `include`/`exclude` reject a Category target;
- missing Source/Category produces bounded stable admin errors;
- no Publication selector/foreign key is involved.

Reuse canonical normalization/repository functions and database transactions. Do not reproduce the evaluator's business rules in Express handlers.

GUARDED PHYSICAL REMOVAL
Enable/disable is the default retirement mechanism. If physical DELETE is exposed, it may succeed only when no retained relationship/history references the rule.

At minimum inspect/protect:
- `article_observations.relevance_rule_id` retained winning/decision reason relationships;
- `article_observation_category_reasons.relevance_rule_id` retained categorization reasons;
- any equivalent retained rule reference in the current final schema.

A removal path MUST NOT cascade-delete, null, or rewrite historical observations/category reasons to make deletion succeed.

Prefer restrictive PostgreSQL foreign keys as final race-safe integrity authority and translate expected referential conflicts to a bounded stable error such as `relevance_rule_in_use`. A preflight check may improve deterministic UX but cannot be the sole concurrency guarantee.

Deleting a genuinely unreferenced rule removes only that rule.

PROSPECTIVE-ONLY EDIT SEMANTICS
Rule create/update/enable/disable/delete affects future candidate processing only.

Admin mutation MUST NOT:
- scan existing Articles;
- bulk hide/delete/recategorize Articles;
- rewrite existing `article_categories` membership;
- rewrite historical Article observations/reasons;
- run Article identity on previously excluded historical candidates.

A later normal admitted/included observation may use then-current Relevance/Category configuration through the ordinary Worker pipeline; that is not bulk reprocessing.

ERROR SHAPING
Provide bounded stable errors for at least:
- invalid request/configuration;
- rule not found;
- config-key conflict;
- Source scope not found;
- Category target not found;
- action/target incompatibility;
- rule in use/retained provenance prevents deletion.

Do not leak SQL, constraint names, stack traces, raw rows, or internal IDs.

- exact-key/unknown-field rejection;
