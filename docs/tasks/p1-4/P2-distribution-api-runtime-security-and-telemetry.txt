- Reasoning basis: high reasoning is justified by reverse-proxy trust, HTTPS termination, limiter lifetime, header provenance, secret-safe telemetry, dependency-failure mapping, and the need to prove the real runtime without changing Phase 2/3 semantics.

- Escalation target: `Sol Medium` for ambiguous cross-system security/architecture reconciliation; otherwise stop with `Planning needed` for owner-level contract/ADR work.
- Estimate confidence: `High`.
- Efficiency rationale: reuse the P1 route and Phase 2/3 factories directly, add only the smallest provider-neutral Web configuration/request-context boundary, and prove it through focused security plus real-PostgreSQL HTTP tests.

The assigned project version is `1.4.2`.

## Goal

Wire P1's versioned v1 distribution router into the real Web/API process using the existing Phase 2 Profile page service and Phase 3 credential authentication/request guard, while establishing the concrete trusted client-network/HTTPS boundary and structured redacted runtime telemetry required for production machine access.

Required production chain:

```text
HTTP request
-> trusted request context
-> one long-lived Phase 3 machine request guard
-> authenticated principal / bounded auth-rate outcome
-> Phase 2 DistributionProfilePageService
-> P1 v1 HTTP serializer/status/ETag logic
-> bounded structured distribution telemetry
```

P2 must prove that this chain works against real disposable PostgreSQL without reimplementing either producer.

## Real Web-process composition

Construct the real distribution dependencies once per Web process, not per request.

At startup/runtime composition:

- create one `DistributionProfilePageService` from the application database;
- create one distribution credential authentication repository from the application database;
- create one machine authenticator from that repository;
- create one machine request guard from that authenticator and the governed Phase 3 rate policy;
- register the P1 distribution API router exactly once on the Web app;
- provide one concrete trusted client-network resolver and one structured telemetry sink;
- keep these objects alive for the Web process lifetime so process-local rate state is meaningful.

Do not add a second limiter/authenticator inside the route or rebuild one for each request.

The distribution route is not controlled by `NEWS_SCRAPER_ADMIN_ENABLED`; human-admin enablement and machine API availability are separate boundaries.

Preserve Web/Worker process separation; no Source collection occurs inline.

## Trusted client-network identity

P2 owns the HTTP/proxy boundary intentionally deferred by Phase 3.

Implement the smallest provider-neutral, explicit trust policy sufficient to derive the invalid-auth network key safely.

Requirements:

- never trust `X-Forwarded-For`, `Forwarded`, `CF-Connecting-IP`, or another client-supplied forwarding header merely because it is present;
- use the immediate socket peer when no proxy trust is explicitly configured;
- if forwarded client identity is supported, it must be enabled only through bounded startup configuration that defines a trusted proxy boundary; untrusted direct clients cannot spoof the limiter key by supplying forwarding headers;
- normalize the resulting network identity into the bounded grammar already accepted by `normalizeInvalidAuthNetworkKey`, handling ordinary IPv4/IPv6/IPv4-mapped forms deterministically without retaining arbitrary header text;
- invalid/unusable request-network state fails boundedly without using bearer plaintext as a fallback key;
- do not create a persistent visitor/IP analytics store; the key exists only for request-abuse protection and bounded diagnostics where permitted;
- avoid provider-specific Cloudflare logic unless the existing managed architecture genuinely requires a tiny optional adapter; the core rule must remain usable without Cloudflare.

Prefer existing Express/Node trusted-proxy facilities when they can be configured safely and tested deterministically; do not hand-roll a broad proxy parser when a narrow existing facility is sufficient.

If the actual environment requires a materially more complex multi-proxy/CIDR trust architecture than current contracts settle, stop rather than guessing.

## Production HTTPS boundary

Production distribution credentials must not be accepted over an externally insecure transport.

Implement/document in code/configuration one explicit production behavior that works with the existing HTTP Node origin behind a trusted TLS-terminating reverse proxy without trusting arbitrary forwarding headers.

Requirements:

- development/test may continue using controlled local HTTP servers;
- production must either establish a trusted externally-HTTPS request context or fail closed before credential-bearing distribution traffic is served;
- do not silently infer HTTPS from an untrusted `X-Forwarded-Proto` header;
- do not add an ungoverned permanent API response class such as a new Profile-specific `403` merely to handle deployment misconfiguration;
- prefer startup/configuration failure or another bounded deployment-safe behavior over serving bearer credentials through a known insecure external boundary;
- do not require Node itself to terminate public TLS when the accepted managed deployment uses a trusted upstream terminator;
- keep the configuration minimal, typed, bounded, and covered by `web-config`/request-context tests.

Any new environment variable must have one clear purpose, safe default, bounded accepted values, and a `RuntimeConfigError` that does not echo secret/private values. Do not introduce a generic reverse-proxy framework.

Because roadmap scope explicitly requires documented HTTPS/configuration behavior, update only the narrow current operator-facing configuration/runbook text needed to explain any newly required non-secret Web/proxy setting. Do not redesign contracts/ADRs/roadmap state; post-closeout `/docs-review` will handle broader current-state alignment.

## Runtime telemetry

Supply P1's telemetry sink with the existing newline-delimited structured Web logging convention or the smallest coherent equivalent.

Emit one bounded event per distribution request with useful operational facts, such as:

- event name and API version;
- bounded Profile key when safely parsed/known;
- status/outcome/failure category;
- duration;
- item count and whether continuation remains, when applicable;
- non-secret authenticated credential ID/lookup identity only after authentication succeeds;
- rate-limit classification where applicable;
- bounded client/adapter version if P1 finalized such a field;
- no visitor/click/referral analytics.

Never log:

- raw Authorization header;
- bearer token or token fragment;
- verifier bytes;
- raw cursor payload;
- response Article payloads;
- database errors/connection strings;
- unbounded arbitrary request headers;
- machine secrets in startup/config errors.

If the logging sink itself throws/fails in a test seam, the route must preserve bounded response behavior rather than leaking sensitive state.

## Runtime route/security semantics

P2 must preserve P1's exact v1 contract rather than reserializing it in `main.ts` or middleware.

Verify the real route remains:

```text
GET /api/v1/distribution/{profile_key}
GET /api/v1/distribution/{profile_key}?cursor=...
```

and that:

- no machine credential is accepted from query/body/cookie/path;
- a valid instance credential can read any active Profile without Profile-specific permission rows;
- missing/draft/disabled/Profile cursor states still use P1's status/error mapping;
- `Retry-After` comes only from the long-lived Phase 3 guard;
- `ETag`/`304` remain P1/Phase 2 revision behavior;
- no permissive browser CORS is introduced by runtime middleware;
- existing admin mutation-integrity middleware does not become machine authorization;
- machine credentials do not make admin routes accessible when the admin perimeter is disabled or mutation integrity fails.

## Real PostgreSQL end-to-end proof

Add one focused Level 4 database-backed HTTP suite for the actual Phase 4 runtime composition. Use the existing disposable PostgreSQL harness and real migration chain; do not mock persistence for claims below.

Seed the smallest governed Publication/Source/Profile/Article/credential state needed to prove:

1. an issued persisted credential authenticates through the real repository/authenticator/guard and receives the active Profile `200` envelope;
2. reconstruction from persisted verifier state works without plaintext persistence beyond the test's immediate issued token variable;
3. exact stored `original_url`, moderated/effective outward fields, Categories, Profile selection, and chronological order come from the existing read producer;
4. a multi-page Profile traverses with the producer cursor and stable revision without repetition;
5. a relevant mutation between pages yields `409 snapshot_changed` rather than mixed pages;
6. revoked and expired credentials return the same bounded `401` class;
7. different valid credentials have independent authenticated rate buckets;
8. disabled Profile -> `409 profile_disabled`, while draft/nonexistent remain non-readable;
9. Publication `public_status` does not suppress active distribution output;
10. dependency failure is bounded and does not leak SQL/connection detail.

Use focused test helper seams only where needed to control time/rate thresholds. Do not create a test-only production bypass for auth/HTTPS/trust behavior.

No new migration should be necessary. If P2 discovers a persistence/schema change is required, stop with `Planning needed` because that is roadmap drift.

## Focused security/component proof

- request guard is constructed once and rate state survives repeated requests;
- immediate peer identity is used when proxy trust is absent;
- spoofed forwarding headers do not change network identity when the peer is untrusted;

- logs/events contain bounded non-secret IDs/statuses but never token/header/verifier/SQL secrets;
