GOAL
Create one canonical admin input-shape primitive for validating that an untrusted value is a plain request object with the allowed/required top-level keys, then migrate all duplicated admin-service copies to that primitive without merging their domain semantics.

SHARED PRIMITIVE BOUNDARY
Add the smallest module appropriate for admin-only structural input validation, for example `src/admin/input-validation.ts`.

It should own only concepts such as:
- input must be a non-null object and not an array;
- all required keys are present when a caller declares them;
- no keys outside required + optional/allowed keys are present;
- return of a `Record<string, unknown>` or an equivalent neutral success result.

Prefer a neutral failure representation (`undefined`, boolean/result type, or a small structural error) that lets each calling service retain its own `invalid_request` error class. Do not make the helper throw `ArticleAdministrationError`, `EndpointAdministrationError`, etc.

CALLER MIGRATION
Migrate the duplicated structural check in all currently relevant admin services, expected to include:
- `src/admin/source-administration.ts`;
- `src/admin/endpoint-administration.ts`;
- `src/admin/editorial-administration.ts`;
- `src/admin/publication-administration.ts`;
- `src/admin/article-administration.ts`;
- `src/admin/duplicate-administration.ts`.

Preserve each caller's current distinction between:
- required keys;
- optional/allowed-only keys;
- commands where all keys are optional and `{}` is valid;
- invalid extra fields.

Do not force all commands into one required-key signature for symmetry.

DO NOT CONSOLIDATE
Keep these authorities local unless an already-existing canonical helper is simply reused:
- UUID validation/normalization;
- config-key validation;
- page-size/cursor decoding/fingerprinting;
- Source/endpoint domain-policy/configuration errors;
- Publication field validation;
- Category/Relevance semantic normalization;
- duplicate review/group state validation;
- database constraint/error translation;
- persisted-row validation.

Those rules have different contracts/error semantics and are not P5 cleanup targets merely because their code looks similar.

SECURITY / REQUEST INTEGRITY
This is service-level shape validation, not a replacement for Web-layer JSON parsing or mutation request-integrity controls. Preserve:
- duplicate JSON object-key rejection;
- body/content-type bounds;
- admin request-integrity header policy;
- Cloudflare perimeter assumptions;
- generic secret-safe HTTP failures.

P5 must not move or weaken any of those server middleware responsibilities.
