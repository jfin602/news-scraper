GOAL
Replace the current two-authority `AttemptDraft { result, finalization }` construction with one canonical internal terminal-attempt representation from which outward attempt results and persisted finalization input are derived.

CURRENT PROBLEM
At planning time collection terminal branches separately construct:
- an outward `EndpointCollectionAttemptResult`-shaped result; and
- a `FinalizeCollectionRunInput` persistence structure.

The same run status, stage status, counts, outcome, retry/error facts, parser diagnostics, transport telemetry, validators, and duplicate effects are authored twice across several branches. `resultFromFinalized()` then performs a large field-by-field reconciliation because the two independently created representations can theoretically diverge.

The persisted consistency check is valuable. The duplicate construction that makes it necessary to compare two separately authored semantic authorities is not.

TARGET DESIGN
Introduce the smallest collection-owned internal representation that captures one terminal attempt truthfully. Exact type/name is implementation-owned, but it must have one canonical value for each governed semantic fact needed by both outward and persistence views.

From that single snapshot derive:
1. `FinalizeCollectionRunInput` for persistence;
2. the pre-finalization `EndpointCollectionAttemptResult` used for bounded caller/error reporting;
3. the expected state used to validate the returned `PersistedCollectionRun`.

After successful persistence, retain a strong consistency assertion that the database returned the same terminal state and correct Collection-run identity. Do not weaken it merely because internal duplication has been removed.

SIMPLIFICATION EXPECTATIONS
- Collapse repeated terminal branch construction where doing so improves clarity and one-owner semantics.
- Preserve useful small constants for stage-not-run/count-zero defaults if they remain clearer than generic builders.
- Prefer explicit discriminated terminal-state data over a highly generic fluent/builder abstraction.
- Do not create a universal state machine framework.
- Keep error/outcome vocabularies canonical and bounded.
- Keep parser diagnostics and transport metadata attached only when their stage actually ran/produced them.
- Keep outward-only data such as accepted candidate snapshots distinct from persisted-run fields when appropriate rather than forcing everything into persistence.

DUPLICATE EFFECT FIELD TIGHTENING
P2 establishes one canonical included-processing path. Revalidate all `FinalizeCollectionRunInput` callers and then make `duplicateReviewCreatedCount` and `duplicateGroupedCount` required terminal accounting fields if every supported finalization can explicitly supply zero/nonzero values.

Update direct tests/callers to pass explicit zero values rather than preserving optional/default compatibility solely for historical callers. Do not tighten unrelated nullable historical telemetry fields without the same source-backed justification.

PERSISTED RESULT CONSISTENCY
The finalization check must still reject inconsistent persisted terminal state including, as applicable:
- Collection-run/endpoint/execution identity;
- terminal run status;
- transport/parser/normalization/processing statuses;
- raw/filter/normalized/failure/link-rejection counts;
- Article created/updated/unchanged/rejected/excluded/failed counts;
- duplicate review/group effect counts;
- outcome code and retry classification;
- ETag/Last-Modified validators;
- transport HTTP/byte/redirect/elapsed metadata where represented;
- parser adapter/profile diagnostics where represented by the persisted model.

If current source intentionally does not compare a persisted field because it is not part of the outward result, preserve that distinction or make the comparison explicit only when it improves correctness; do not invent new API fields for symmetry.

FINALIZATION FAILURE
`CollectionRunFinalizationError` must retain a truthful attempted result built from the canonical snapshot. A database finalization failure must not fabricate a successful persisted run or lose the attempted stage/accounting/error facts.

INTERRUPTED RUNS / RECOVERY
Do not merge Worker interruption reconciliation into ordinary collector finalization. `worker_interrupted` remains recovery-owned terminalization of a run left `running`; preserve its distinct semantics and tests.
