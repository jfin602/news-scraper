ROADMAP PHASE

MODEL / REASONING / USAGE
- Recommended configuration: `Sol High`.
- Model-family basis: this terminal gate requires Sol's independent whole-codebase review capability and, unlike an ordinary closeout, begins with a fresh optimization/maintainability assessment of the post-P1-P7 tree before any closeout action is allowed.
- Reasoning basis: High reasoning is justified because the prompt must discover and classify newly exposed structural problems, distinguish justified architecture from accidental complexity, decide whether Phase 21 needs more implementation prompts, and only then perform integrated adversarial closeout validation.
- Complexity / quality floor: `Critical`.
- Estimated usage: `Very High`.
- Lower-cost alternative considered: `Sol Light`; it is the normal repository closeout baseline, but it is inadequate for the owner-requested fresh whole-tree optimization deep dive and candidate classification that now precedes closeout.
- Escalation trigger: the reassessment or later closeout passes expose difficult unresolved transaction/recovery/concurrency ownership, ambiguous production compatibility, architectural security uncertainty, or another problem requiring reasoning beyond the approved Phase 21 boundaries.
- Escalation target: `Sol Ultra` when stronger cross-system inference is required; use `Terra Ultra` when the dominant problem is deeper reasoning over explicit transaction/state interactions. Meaningful behavior-preserving refactors found after the pre-closeout gate use the normal Terra High remediation handoff.
- Estimate confidence: `High`.
- Efficiency rationale: spend the stronger final review once on the actual cleaned tree, then either stop early for more targeted prompts or run each final evidence set exactly once and close the roadmap.
- Plan delta: `Escalated` from the ordinary Sol Light closeout baseline after the repository owner added a mandatory fresh optimization reassessment before terminal closeout.

STAGE 0 DEEP-DIVE SCOPE
Perform a fresh whole-codebase investigation of the actual post-P1-P7 tree. Do not limit the review to files changed in Phase 21.

Actively look for:
- dead, unreachable, obsolete, redundant, and compatibility-only source/test/config paths;
- duplicate semantic authority or parallel implementations of one governed rule;
- unnecessary wrappers, adapters, indirection, orchestration layers, or control/data flow that no longer earn their complexity;
- test-only seams or test-support concerns leaking into production modules;
- weak TypeScript/API boundaries, permissive optionality retained only for superseded callers, or unsafe casts hiding contract mismatch;
- transaction ownership, connection/session release, locks, timers, listeners, process startup/shutdown, child processes, and resource lifecycle problems;
- Worker versus Web/API responsibility leakage;
- repository/query/SQL ownership, N+1 patterns, repeated reads, unnecessary sequential I/O, or real index/query bottlenecks;
- unnecessary production dependencies, duplicated utilities, stale feature bridges, or obsolete compatibility exports;
- test harness duplication, expensive obsolete suites, repeated setup, flaky timing assumptions, or validation work that can be simplified without reducing coverage;
- modules that remain poorly owned after P1-P7, including any new cyclic/cross-module coupling created by refactoring;
- startup/runtime/memory/DB/Worker/Web/scheduling inefficiencies for which materially comparable evidence can be obtained;
- stale comments/copy/contracts only when they misdescribe current behavior rather than as general prose polishing;
- topic-specific shared-engine behavior or production-compatibility drift introduced accidentally during cleanup.

Do not equate file size, line count, module count, or dependency count with a defect. Inspect ownership and behavior first.

STAGE 0 CANDIDATE REGISTER
For every meaningful candidate, record:

`observed problem -> concrete source/runtime evidence -> maintainability/correctness/operational impact -> smallest candidate remedy -> invariants to preserve -> likely validation blast radius -> include/defer/reject`

Reject/defer work when:
- no concrete problem is demonstrated;
- the improvement is cosmetic or primarily a line/file/module-count target;
- the abstraction would become more generic/speculative than the code it replaces;
- risk exceeds demonstrated benefit;
- it would flatten meaningful Source/endpoint/run/Article/observation/duplicate/security/transaction/process boundaries;
- it requires unjustified schema churn;
- it is actually a deferred feature/product enhancement rather than behavior-preserving cleanup.

PASS 2 — ERROR / EDGE-CASE ADVERSARIAL REVIEW
Independently generate failure hypotheses from the final implementation, not merely existing test names.

Challenge at minimum:

- Collection-run outward state diverging from persisted state after canonicalization;
- finalization failure losing attempted result or conditional/parser metadata;
- `304`, safety block, parser failure, normalization failure, policy failure, candidate failure, and Worker interruption accounting edge cases;
- batching losing Category order, active empty manual overrides, filtered Articles, duplicate-group member semantics, cursor/order behavior, or transaction-local locked reads;

- admin API security extraction changing middleware ordering, malformed/duplicate JSON handling, integrity/content-type/body bounds, error secrecy, CSP, no-store headers, or disabled-admin behavior;

- Operations -> endpoint navigation, Editorial -> shared Category choices, Sources -> Article filter choices, Publication switching, Article/review mutation refreshes;
- resource/connection/timer/listener leaks introduced by refactors;
- supported production state becoming unreadable despite no schema change;
- live approved Source collection or public/admin deployment behavior diverging from local fixtures.

Classify each finding:
1. protected by code + meaningful evidence;
2. clear governed behavior with weak coverage — add bounded regression/evidence if safe;
3. concrete bounded defect — repair minimally and rerun invalidated evidence;
4. meaningful behavior-preserving structural refactor — use the Terra High closeout remediation handoff below;
5. material ambiguity/new architecture/product decision — stop for escalation/replanning.
