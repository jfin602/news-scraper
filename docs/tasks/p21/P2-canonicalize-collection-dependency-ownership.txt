GOAL
Make the production collection dependency contract express exactly one supported included-Article processing authority and one canonical parser dispatch path.

CURRENT PROBLEM
At planning time `CollectEndpointDependencies` contains both:
- required plain `persistArticle`;
- optional `processIncludedArticle`;

and collection chooses `processIncludedArticle ?? persistArticle`.

That representable fallback can bypass duplicate-aware included-Article processing even though production wiring already provides the canonical processor. The same production dependency interface also carries optional `createHtmlListingParser` explicitly as a test seam while production otherwise constructs `HtmlListingParser` directly.

IMPLEMENTATION BOUNDARY
A. INCLUDED ARTICLE PROCESSING
- Remove `persistArticle` from the collection orchestration dependency surface.
- Make the duplicate-aware `processIncludedArticle` dependency required wherever `collectEndpoint` processes an included Article.
- Remove the collection-service `persistIncludedArticle` fallback/wiring if it exists only to populate that obsolete collector dependency.
- Do NOT delete or weaken legitimate lower-level Article persistence primitives used by `processIncludedArticle` or other real consumers.
- On successful included processing, duplicate effect counts remain explicit required outputs owned by `IncludedArticleProcessingSuccess`; failed persistence retains its existing failure result semantics.
- Simplify result validation/effect extraction so a successful included result cannot silently omit duplicate effect counts and be interpreted as zero.

B. HTML PARSER DISPATCH
- Remove `createHtmlListingParser` from the production `CollectEndpointDependencies` interface.
- Keep the production parser selection path canonical: `html_listing` configuration constructs/uses the static `HtmlListingParser` with the persisted normalized profile and existing adapter/version diagnostics.
- Adapt tests to exercise real parser behavior through controlled HTML/profile fixtures rather than replacing the parser constructor solely to force outcomes.
- Do not create a generic parser registry or dependency-injection framework merely to replace this seam.

C. SERVICE DEPENDENCY CLEANUP
- Tighten `EndpointCollectionServiceDependencies` only as far as justified by the canonical runtime path.
- Preserve useful high-level service injection used to isolate database/network/collection boundaries in tests; remove only compatibility alternatives that allow a supported production behavior to be bypassed or exist solely for unit convenience.

PRESERVED COLLECTION LAW
This refactor MUST NOT alter:
- singleton Publication collection-active gate;
- Source/endpoint approval, lifecycle, operational state, domain policy, or endpoint lock;
- pre-request and redirect network safety;
- fetch limits/retry/conditional-request semantics;
- RSS/Atom Source admission filtering before normalization;
- HTML items bypassing that RSS/Atom-specific admission filter;
- Raw item -> normalization -> Article-link policy -> Relevance/Categories ordering;
- Source-scoped Article identity/idempotency and retained observations/provenance;
- included Article + duplicate work sharing the existing per-candidate transaction;
- excluded Article observation semantics;
- duplicate review/group topology rules;
- Collection-run outcome/accounting semantics;
- durable job scheduling/capacity/health behavior.

TEST ADAPTATION RULE
Do not preserve a production test seam merely because existing tests use it. Rewrite tests around supported observable boundaries.

For parser failures, use a real bounded profile/input that naturally produces the required success/failure/diagnostic result. For included processing, inject the required canonical processor where a component test does not use the database, and use the real `processIncludedArticle` path in the database/integration coverage that proves transaction and duplicate behavior.
