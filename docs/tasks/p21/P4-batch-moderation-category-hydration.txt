GOAL
Replace per-Article Category hydration in moderation reads with one set-based Category-loading path whose query count does not grow with the number of returned Articles.

CURRENT PROBLEM
At planning time `readModeratedArticles()` executes one bounded Article query, then maps each returned row sequentially. `mapArticle()` executes one automatic Category query and one manual Category query for each Article. At the maximum page size of 100, a full page can therefore require approximately 201 sequential queries before other consumers do additional work.

The same list read is used by duplicate administration for bounded duplicate-group member detail, so this amplification affects more than one UI path.

TARGET DESIGN
Create one canonical moderation Category hydration primitive that accepts the returned Article IDs and loads all required Category membership in a bounded set-oriented operation.

A preferred shape is one query that returns:
- Article ID;
- membership kind (`automatic` or `manual`);
- Category config key;
- Category display name;

for all requested Articles, ordered deterministically, then groups rows in memory into immutable per-Article automatic/manual arrays. Equivalent set-based SQL is acceptable if it is clearer and equally bounded.

The important invariant is that Category hydration query count remains constant with respect to page size rather than issuing two queries per Article.

MAPPING OWNERSHIP
After batch hydration:
- Article row mapping should be synchronous/pure with respect to already-loaded Category data where practical;
- automatic and manual Category sets remain separate stored concepts;
- `manual_override_active = true` selects the manual set as effective even when that manual set is intentionally empty;
- absent manual override selects the automatic set as effective;
- Category order remains deterministic by `config_key`;
- single-Article/detail/locked reads should reuse the same Category-loading semantics rather than retain a second interpretation path;
- do not move Category-effective-value policy into Article administration or duplicate administration.

QUERY / SCHEMA RULES
- Do not change moderation search/filter/pagination SQL merely because Category hydration is being optimized unless a minimal adjustment is necessary for correctness.
- Do not add a migration or index unless a representative query plan/measurement proves the new set query needs one; default expectation is no schema change.
- Keep all reads bounded to the Article IDs already selected by the caller.
- Preserve transaction/executor ownership; locked moderation reads must remain compatible with the caller-owned transaction used for mutations.
