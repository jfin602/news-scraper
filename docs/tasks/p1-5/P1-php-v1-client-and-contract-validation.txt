
## Package boundary

```text

  src/
  tests/
```

Do not place the PHP adapter inside the Node aggregation-engine `src/` tree. It is a downstream consumer of the machine API, not another engine authority.

Keep the Phase 5 PHP core dependency-light and suitable for ordinary shared-host/server PHP deployment:

- use `declare(strict_types=1)` and a package namespace;
- do not introduce a framework or third-party Composer dependency merely for HTTP, JSON, validation, or testing behavior that can remain small and explicit;
- do not create `vendor/`, `composer.lock`, or a speculative packaging ecosystem in this prompt;

## Client configuration and request safety

Define one explicit immutable/bounded client configuration sufficient for Phase 5, including at minimum:

- News Scraper base URL;
- bearer credential supplied at runtime;
- bounded connection/request timeout(s) where the chosen native transport supports them.

Requirements:

- normal production configuration accepts only an absolute `https` base URL;
- reject embedded username/password, query, and fragment components in the configured base URL;
- do not provide an insecure TLS-verification-disable option;
- do not automatically follow redirects with the bearer credential; an unexpected redirect is a bounded transport/protocol failure rather than permission to forward Authorization elsewhere;
- bearer plaintext remains only in runtime client/config memory and the outgoing `Authorization: Bearer ...` header;
- never append the credential to path/query, persist it, include it in result objects, or echo it through exceptions/diagnostics;
- safely encode the Profile key as one path segment and the opaque cursor as the only optional query parameter;
- use the permanent route `/api/v1/distribution/{profile_key}` exactly;
- continuation requests use only the opaque cursor returned by the previous validated response;
- do not add Source, Category, q, limit, sort, Publication, or other selector parameters.

Use a production HTTP transport with bounded response handling. Do not create public-internet tests or weaken TLS merely to make the test harness easy.

## v1 typed outcome boundary

Expose one narrow client operation for an initial or continuation page that returns typed outcomes rather than raw transport details to P2.

The downstream boundary must distinguish at least:

- validated active `200` page;
- bodyless initial `304 not_modified`;
- `400 invalid_request`;
- generic `401 unauthenticated`;
- `404 not_found`;
- `409 profile_disabled`;
- `409 snapshot_changed`;
- `429 rate_limited` with validated positive `Retry-After` seconds;
- `503 service_unavailable`;
- bounded transport failure/timeout;
- bounded invalid/malformed upstream response.

Do not turn different `401` causes into different PHP public states. Do not invent a `403` Profile-authorization model.

Unexpected status codes, redirects, malformed JSON, oversized/unusable transport results, or a documented response class with the wrong body/header shape become a bounded client failure without including sensitive response data.

## Successful page validation

For each `200`, validate the required v1 envelope and item shape from `distribution-api-contract.md`:

```text
apiVersion
generatedAt
snapshotRevision
profile { configKey, displayName }
publication { name }
items[]
nextCursor
```

Each item requires:

```text
articleId
headline
originalUrl
effectiveFeedDate
feedDateSource
publishedAt
author
summary
imageUrl
source { configKey, displayName }
categories[] { configKey, displayName }
```

Requirements:

- require `apiVersion === "v1"`;
- require the response Profile `configKey` to equal the requested Profile key;
- require required strings/objects/arrays and explicit nullable fields with their governed types;
- validate required timestamp strings as usable absolute timestamps without rewriting them into a different business meaning;
- keep `snapshotRevision`, cursor, ETag, IDs, and other opaque values opaque;
- preserve Article array order exactly as received;
- preserve exact `originalUrl`; do not canonicalize, rewrite, follow, rank, filter, or reinterpret it;
- preserve safe nullable metadata and Categories as supplied;
- permit unknown additional fields so compatible additive `/api/v1` evolution does not break the client merely because a new field exists;
- do not expose internal raw JSON/headers as the ordinary typed result when the explicit validated shape suffices.

P1 validates shape/compatibility only. It does not decide Article eligibility, duplicate status, Source trust, Profile filtering, Category semantics, chronological ordering, or destination policy.

## ETag, conditional request, and Retry-After handling

Expose exactly the inputs later synchronization needs:

- capture the successful response ETag as an opaque bounded value when present;
- allow `If-None-Match` only on an initial request when P2 supplies an existing active ETag;
- never use conditional headers on cursor continuation;
- treat `304` as a valid typed outcome only for an initial conditional request; it carries no replacement payload;
- parse `Retry-After` for `429` as a positive bounded integer number of seconds and reject malformed/non-positive values as an invalid upstream response;
- do not sleep or retry in P1.

Do not derive a second revision identity from the ETag or inspect cursor/revision internals.

## Focused proof

Add focused PHP tests covering at minimum:

- exact initial URL/path construction and encoded Profile key;
- cursor appears only as the single continuation query value;
- Authorization bearer header is present in the outgoing request but absent from returned result/error text;
- production base URL rejects non-HTTPS, credentials-in-URL, query, and fragment forms;
- transport does not auto-follow redirects with Authorization;
- exact valid first-page schema including nullable fields, empty arrays, and null `nextCursor`;
- exact `originalUrl` and item order preservation;
- compatible unknown/additive fields are tolerated;
- missing/wrong-type required fields are rejected;
- wrong API version or wrong Profile key is rejected;
- invalid timestamps/JSON become bounded invalid-response outcomes;
- ETag capture and initial `If-None-Match` request behavior;
- `304` accepted only in the initial conditional context;
- `400`, generic `401`, `404`, both governed `409` outcomes, `429` plus positive Retry-After, and `503` mapping;
- malformed/missing Retry-After on `429` is rejected boundedly;
- redirects/unexpected statuses/transport timeouts fail without leaking token/body internals;
- no Source/Profile/Article business filtering or sorting appears in the PHP client.
