## Concrete local storage layout

Implement one dedicated filesystem-backed state store under the PHP integration package.

The production cache root MUST be explicitly configured and suitable for placement outside the customer's public document root. Do not hard-code a provider path, home directory, web root, or operating-system-specific customer location.

Requirements:

- require an absolute configured cache/state root;
- derive all per-Profile directory/file identities from a deterministic safe encoding or cryptographic digest of the Profile key rather than interpolating raw Profile text into a path;
- reject path traversal/symlink/file-type states that would make the package write outside the intended root or follow an unsafe existing path;
- create directories/files with restrictive permissions where the host supports POSIX permission control, and report limitations honestly rather than claiming a universal permission guarantee;
- never store the bearer token, Authorization header, environment secret values, raw exception dumps, or credential-bearing configuration in any cache/state file;
- do not make cache/state files web-addressable or create a public HTTP endpoint for them;
- keep each Profile's state independent.

Do not add SQLite, PostgreSQL, Redis, or another local service merely to implement Phase 5 state.

## Atomic generation + manifest model

Use one coherent single-commit-point design. The preferred shape is:

```text
profile-state/
  lock
  generations/
    <immutable-generation>.json
  manifest.json
  temporary/orphan files ignored until cleanup
```

Exact names/formats are implementation-owned, but preserve these semantics:

1. active snapshot payload is never edited in place;
2. write a complete candidate snapshot to a temporary file in the same filesystem/directory boundary;
3. flush/close it safely and atomically rename it to an immutable generation name;
4. write a complete new manifest to a temporary peer file;
5. atomically rename the manifest as the **single visibility/activation commit point**;
6. readers trust only a valid committed manifest pointing at a valid immutable generation;
7. keep the previously referenced valid generation until after the new manifest commit succeeds, and retain at least one recoverable prior valid generation where practical without allowing unbounded accumulation;
8. orphan candidate/temp/generation files that are not referenced by the committed manifest never become active and may be cleaned up only after safe lock ownership.

The manifest must carry enough synchronized state to keep active selection, lifecycle suppression, and health facts internally consistent, for example:

- local storage schema/version;
- Profile key or safe identity check;
- active generation reference when one exists;
- active API version/revision/ETag/upstream generatedAt;
- last successful local synchronization timestamp;
- last attempt/result/failure facts;
- disabled marker;
- page/item counts and bounded adapter version/health facts;
- any configured freshness facts that are deliberately persisted.

Do not split one logical public/local state transition across several independently authoritative mutable files when doing so creates a reader-visible contradiction window.

Atomic rename claims apply only within the same local filesystem. Do not claim cross-filesystem, distributed, or power-loss durability beyond what is actually tested/observed.

## Store read/validation and safe recovery

Implement the concrete P2 state-store port so loading local state validates the storage representation before trusting it.

At minimum:

- validate manifest shape/version, Profile identity, referenced generation path/name, and required metadata;
- validate referenced generation file shape and consistency with manifest Profile/revision/API identity;
- reject missing/truncated/malformed/mismatched active state rather than partly using it;
- ignore temporary/orphan generations that are not the committed manifest target;
- never scan for "newest file" and promote it merely because a manifest is broken;
- preserve/return a bounded safe unavailable/corrupt local-state result for operations instead of exposing raw JSON or filesystem diagnostics to customer-facing callers;
- do not silently promote the prior generation if doing so would contradict an authoritative committed disabled/current-state manifest; recovery promotion requires an explicit reviewed policy, not filename guessing.

A valid prior generation may remain available for operator recovery, but the ordinary reader follows the committed manifest only.

## Concrete activation and non-corruption guarantee

Bind P2's `activateCompleteCandidate`-equivalent port to the atomic generation + manifest commit protocol.

Prove these interruption/failure points:

- failure before candidate file completion leaves old manifest/active unchanged;
- failure after candidate generation rename but before manifest rename leaves an orphan generation and old active unchanged;
- failure writing the new manifest leaves old manifest/active unchanged;
- only successful manifest rename exposes the new generation;
- cleanup/pruning failure after successful activation does not roll back or corrupt the new active state;
- a failed activation is returned to P2 as failure and never reported as successful sync.

Use injectable/narrow filesystem seams only where needed to deterministically fault specific commit stages; do not place test-only branches in production behavior.

## Authoritative disabled state

Implement P2's disabled-state mutation as an atomic manifest transition that retains any valid active generation but marks it unusable for public/local presentation.

Requirements:

- authenticated `profile_disabled` from P2 sets the committed disabled marker without deleting the active generation;
- a later successful complete activation or valid unchanged `304` transition clears the marker atomically;
- ordinary upstream failures never set it;
- manifest write failure means the disabled/re-enabled state transition did **not** commit and must be surfaced as a local persistence failure;
- the local usability resolver below always gives committed `disabled` precedence over freshness/stale-valid state;
- no filename, Source state, Article content, or HTTP `404` inference may substitute for the governed disabled marker.

Do not invent an adapter-side Profile lifecycle beyond the states needed to represent the contract.

## Real cross-process per-Profile locking

Implement P2's lock port using a native host-local file lock such as an open lock file plus nonblocking `flock(LOCK_EX | LOCK_NB)` for the entire synchronization attempt, including bounded `snapshot_changed` restarts and store commits.

Requirements:

- the lock identity is derived from the safe per-Profile identity, never a raw unsafe path;
- keep the lock handle alive until release; do not acquire/release between pages;
- lock release is exception-safe;
- two real PHP processes targeting the same Profile cannot both enter synchronization ownership;
- two different Profiles use independent locks and can proceed independently;
- stale lock-file existence alone must not be interpreted as lock ownership; rely on the OS lock state;
- do not delete a lock file merely to "break" another process's lock;
- no process-global boolean or News Scraper database row replaces the file lock.

This is host-local coordination only. Do not claim cross-host/distributed lock support.

## Freshness, stale policy, and local usability

Implement one internal Phase-5 local usability resolver over committed state for use by P3 diagnostics and Phase 6.

It must distinguish at minimum:

- `never_synced` — no valid committed active generation;
- `disabled` — committed authoritative disabled marker, regardless of retained generation freshness;
- `usable` — valid committed active generation and not beyond any configured maximum stale age;
- `stale_usable` — valid committed generation is older than the normal sync cadence/expected freshness but no hard cutoff applies, or it remains below the optional configured maximum stale age;
- `stale_cutoff` / unavailable — valid committed generation exceeds an explicitly configured maximum stale age.

Requirements:

- **no maximum stale cutoff by default**; valid old data remains locally usable unless disabled;
- optional maximum stale age is a positive bounded customer configuration;
- compute stale age from the last successful local synchronization timestamp using an injectable clock, not from Article dates;
- normal sync cadence and hard maximum stale age are distinct settings;
- disabled takes precedence over otherwise fresh/stale data;
- never-synced/corrupt local state is not usable;
- clock skew/invalid future timestamps are handled boundedly rather than producing negative/unsafe stale ages;
- this resolver returns state/data facts only and emits no HTML.

Do not treat a generic upstream `401`, `404`, `429`, `503`, timeout, or malformed response as local `disabled` or immediate cache deletion.

## Configurable cadence and due behavior

Provide one simple generic way for a scheduler such as cron to run the PHP synchronizer at a frequent interval while the package itself applies the configured Profile cadence.

Requirements:

- default synchronization cadence is **15 minutes / 900 seconds**;
- allow an explicit positive bounded customer override;
- keep cadence configuration separate from optional maximum stale age;
- define and test one deterministic due calculation using committed local attempt/success facts; do not let a cron invocation trigger overlapping work simply because it fires frequently;
- provide an explicit `force`/manual synchronization path only if it remains bounded and still acquires the same per-Profile lock;
- an ordinary not-due invocation is a successful no-op with no upstream request and no mutation that corrupts health/freshness;
- cadence behavior is per Profile so one Profile's activity does not postpone another's;
- do not build an internal daemon, queue, general scheduler framework, or News Scraper-side job for the customer's PHP host.

Choose and document whether due cadence anchors to `lastAttemptAt` or another committed local operational timestamp. The choice must avoid accidental hammering after failures and be locked by tests; it must not redefine the upstream API contract.

## Deterministic focused and integration proof

Extend `npm run test:php` with real temporary-directory filesystem tests and real PHP-process lock tests where process coordination is the claim.

Cover at minimum:

### Atomic storage and recovery

- first complete activation creates one valid committed active state;
- second activation switches the manifest to the new generation without editing the old generation;
- exact complete ordered items and `originalUrl` survive round-trip storage;
- failure before generation completion preserves old active;
- orphan generation after pre-manifest interruption is ignored;
- manifest write/rename failure preserves old active;
- cleanup/prune failure after manifest commit does not invalidate new active;
- corrupted/truncated manifest is rejected boundedly;
- missing/corrupt/mismatched generation is rejected rather than partially loaded;
- temporary/orphan files are not auto-promoted;
- prior valid generation is retained according to the bounded recovery policy;
- stored files contain no synthetic bearer/header secret used by the tests.

### Cross-process locking

- two actual PHP processes contending for the same Profile prove only one lock owner at a time;
- another Profile lock can be acquired independently;
- releasing/terminating the owner permits later acquisition;
- mere stale lock-file presence does not block acquisition after OS lock release;
- no test deletes another process's lock as an unlock mechanism.

### Disable/re-enable and freshness

- disabled manifest transition retains active generation but usability becomes disabled;
- successful activation/unchanged state update clears disabled;
- failure to commit disabled/re-enabled manifest is surfaced and does not pretend success;
- never-synced is unavailable;
- no-max-stale default keeps valid old data stale-but-usable;
- configured max stale allows data before cutoff and rejects after cutoff;
- disabled beats freshness;
- stale age uses local successful-sync time, not Article timestamps;
- future/invalid clock data is bounded safely.

### Cadence/runtime/health

- default cadence is 900 seconds;
- configured cadence changes due behavior within bounds;
- not-due performs no HTTP request;
- forced/manual path still takes the same lock;
- failed attempt does not cause cron-frequency hammering under the chosen due-anchor semantics;
- separate Profile cadence state is independent;
- CLI configuration failure is non-zero and secret-free;
- sync/unchanged/not-due/already-running output is bounded and secret-free;
- upstream failure exits non-zero while preserving active state;
- health exposes required safe fields and never secret/raw payload/cursor internals;
- Phase 6 loader returns only validated committed state and never parses an orphan candidate.

Use deterministic clocks for freshness/cadence and controlled P1 client seams for API behavior. Use real filesystem/process behavior only for claims that require it. Do not contact public News Scraper or publisher endpoints in ordinary tests.
