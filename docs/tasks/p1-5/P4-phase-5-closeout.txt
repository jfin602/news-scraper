## P1 — Native transport, bearer safety, and v1 compatibility

Trace the concrete PHP client from configuration through production transport and typed outcome.

Verify:

- normal production base URL is absolute HTTPS and rejects userinfo/query/fragment misuse;
- there is no insecure TLS verification-disable option;

- timeouts and response-size/error handling are bounded;
- Profile key is safely encoded as one path segment and cursor is the only continuation query parameter;
- client accepts only the permanent `/api/v1/distribution/{profile_key}` contract, not `/api/feed` or arbitrary selectors;
- exact required v1 fields/types/null/empty shapes are validated;
- `apiVersion` and requested Profile identity are validated;
- additive unknown v1 fields are tolerated rather than making compatible additions breaking;
- timestamps are validated without changing business meaning;
- cursor, revision, ETag, IDs remain opaque;
- `200`, initial `304`, `400`, generic `401`, `404`, `409 profile_disabled`, `409 snapshot_changed`, `429` + valid positive `Retry-After`, `503`, transport failure, and invalid upstream response are distinguishable through one bounded typed client boundary;
- continuation never uses `304`/If-None-Match;
- no `403` credential↔Profile model was invented.

Inspect executed P1/P2/P3 PHP evidence for the native production transport itself, not only fake/scripted transport consumers. At minimum, deterministic controlled-local proof should exercise the concrete transport's status/header/body handling, redirect policy, bounds/timeouts where technically practical, and secret-safe failure behavior. ## P2 — Complete snapshot synchronization

Trace one real synchronizer attempt through P1 outcomes and the state/lock ports.

Verify:

- one per-Profile lock owns the entire attempt, retries, `snapshot_changed` restart sequence, and state commits;
- active ETag is used only for the initial conditional request;
- valid `304` requires an existing usable active snapshot, preserves payload/revision, updates successful unchanged facts, and can clear prior disabled state when governed;
- `304` without active state cannot create success;
- a `200` candidate begins separate from active state and traverses every opaque cursor until null;
- every page agrees on API/Profile/revision and other identity facts the typed page exposes;
- item order/content is appended exactly without filtering/sorting/deduplication;
- repeated cursor/page/item safety limits stop rather than truncate-and-activate;
- partial, malformed, mixed-revision, looping, interrupted, or otherwise invalid candidates never call active activation;
- transport/`503`/`429` retries are finite and deterministic;
- `Retry-After` is honored rather than under-waited; an excessive configured wait safely ends the run;
- terminal `401`/`400`/`404`/invalid response preserve active state and are not misclassified as disabled;
- `snapshot_changed` discards the whole candidate and boundedly restarts from the beginning without splicing pages;
- repeated snapshot churn eventually fails while preserving active LKG;
- activation is called only once for a complete candidate;
- activation failure preserves the previous active state;
- lock contention performs no upstream/state mutation and returns boundedly;
- lock release occurs on every success/error/exception path.

## P3 — Atomic LKG storage and recovery

Review the concrete filesystem store at the actual commit protocol, not just happy-path JSON writes.

Require one unambiguous visibility authority such as an atomic manifest/pointer over immutable snapshot generations.

Verify:

- candidate/active bytes are separate;
- active generation is never modified in place;
- candidate and manifest temporary files are written in the same filesystem boundary needed for atomic rename;
- only a successful manifest/pointer rename exposes a new generation;
- failure before generation completion, after generation rename but before manifest commit, or during manifest write/rename leaves old committed active state intact;
- orphan/temp generations cannot be discovered/promoted as active merely because they are newer;
- cleanup failure after a successful commit cannot corrupt the new active state;
- prior valid recoverable generation is retained where practical without unbounded growth;
- manifest and referenced generation are validated together for schema/Profile/API/revision consistency;
- corrupt/truncated/missing/mismatched local state fails boundedly rather than partially loading;
- path identity cannot escape the configured cache root through Profile text, traversal, unsafe symlinks, or crafted manifest generation paths;
- the configured state root is explicit and intended for non-public placement;
- no bearer credential, Authorization, secret environment value, raw error/body, or cursor payload is persisted;
- any POSIX permission claim is phrased/tested only to the extent the actual host/runtime supports it;
- cross-filesystem/distributed/power-loss guarantees are not overstated.

Do not accept a sequence that first deletes/replaces active and then writes the new candidate. The previous LKG must remain the committed authority until the new complete snapshot commit point succeeds.

## Cross-process per-Profile locking

Verify:

At minimum investigate the following classes.

## Transport/configuration attacks and malformed upstream input

- Profile keys containing slashes, percent-encoding, Unicode, dots, path-looking text, query delimiters, or very long values;
- base URLs with HTTP, userinfo, path ambiguity, query/fragment, strange ports, or redirect responses;
- redirect to same host versus different host and whether Authorization could be forwarded unexpectedly;
- TLS verification/configuration failure and accidental insecure fallback;
- missing/combined/malformed response headers;
- malformed JSON, invalid UTF-8, empty/truncated/oversized bodies;
- required fields absent, wrong type, null where not allowed, duplicate/malformed nested entries;
- additive unknown v1 fields;
- wrong API version/Profile key;
- invalid/extreme timestamps;
- unexpected status codes or error-body mismatch;
- `304` with a body or without prior active state;
- malformed/nonpositive/extreme `Retry-After`;
- transport exception containing request headers or URL secrets;
- native transport accidentally auto-following redirects even if client logic assumes it does not.

## Snapshot/traversal/retry failure sequences

- zero items, exactly page boundary, many pages, candidate safety limit edge;
- repeated cursor, A->B->A loop, cursor that never advances;
- continuation returns different revision/Profile/API identity without a 409;
- transport failure after one/many pages;
- `429`/`503` alternating with successful pages;
- retry exhaustion on initial versus continuation requests;
- excessive Retry-After and interruption while sleeping;
- `snapshot_changed` on first page versus late page;
- repeated snapshot churn exhausting restart budget;
- stale cursor accidentally reused after restart;
- partial old candidate retained/appended into restarted candidate;
- lock released between restart/pages;
- exception/fatal-style error path skipping lock release;
- store activation called before traversal is fully exhausted.

## Filesystem atomicity/recovery/path attacks

- cache root absent/unwritable/read-only;
- raw Profile key crafted for traversal/path collision;
- two Profile keys colliding under unsafe normalization;
- symlink replacing profile directory, manifest, generation directory, or temp target;
- lock/generation/manifest wrong file type;
- partial file writes / short writes / disk full;
- generation rename succeeds but manifest rename fails;
- process interruption before/after each rename boundary;
- orphan generation/temp files on next run;
- manifest references missing, malformed, traversal, or wrong-Profile generation;
- manifest valid JSON but internally inconsistent revision/API/Profile metadata;
- cleanup deletes current or prior committed generation due to wrong reference set;
- pruning races with another process despite lock assumptions;
- state reader scans newest timestamp/file instead of manifest authority;
- atomic rename accidentally crosses filesystems;
- permissions are assumed rather than checked/limited honestly;
- cache root placed under a public web root contrary to docs/config intent.

## Cross-process locking/race windows

- simultaneous cron invocations for same Profile;
- one process blocks versus nonblocking contract mismatch;
- stale lock file after crash;
- process exits while holding lock;
- lock handle garbage-collected/closed early;
- lock acquired on different path spellings for same Profile;
- one process cleans/prunes while another can read/write;
- unrelated Profiles incorrectly share one global lock;
- manual force path bypasses lock;
- already-running result mutates last-success/disabled/active unexpectedly.

## Disable/freshness/cadence transitions

- valid active -> disabled -> transient failures -> re-enabled success;
- disabled with no active generation;
- disabled state write fails;
- re-enable state write/304 health update fails;
- `401`/`404` incorrectly suppresses cache;
- stale valid no-cutoff accidentally becomes unavailable;
- max stale exactly at boundary;
- cadence and max-stale values confused;
- future last-success timestamp / clock jumps backward/forward;
- failed attempts reset freshness incorrectly;
- not-due invocation resets attempt timestamp and postpones forever;
- high-frequency cron + repeated failures hammers upstream;
- separate Profiles interfere with due state;
- never-synced incorrectly treated as empty successful feed.

## Secret/logging/CLI leakage

- bearer in CLI args/process listing;
- bearer in config example/cache JSON/manifest;
- bearer or Authorization in exception message from native transport;
- upstream body/cursor in health/log output;
- environment dumps in diagnostics;
- token-derived hash/path/lock key revealing stable credential information;
- response/error object broadly serialized to log;
- customer Article content accidentally logged as operational diagnostics.

## Preserved-surface and phase-boundary drift

- Node package scripts altered so existing deterministic tests stop running;
- PHP test command silently passes when PHP is absent or no tests match;
- package introduces Composer/framework/vendor state unnecessarily;
- customer-facing Article query/filter/search or rendering API pulled into Phase 5;

Record representative hypotheses and their dispositions in the durable closeout artifact; do not claim the adversarial pass happened merely because all existing tests passed.
