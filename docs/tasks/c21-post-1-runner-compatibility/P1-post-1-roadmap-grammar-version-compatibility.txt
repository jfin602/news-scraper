CURRENT PROBLEM
The current runner/parser is intentionally pre-1.0:
- roadmap folders are only `p<number>` with positive integer phases;
- roadmap TASK headers require positive integer `Phase <phase>` values;
- roadmap versions are reconstructed as `0.<phase>.<prompt>`;
- resume baseline/version expectations are reconstructed independently as `0.<phase>.<completedCount>`;
- correction folders/headers also reject phase 0.

The approved post-1.0 roadmap instead restarts roadmap phase numbering at Phase 0 on baseline `1.0.0` and assigns prompt versions as `1.<phase>.<prompt>`. Historical pre-1.0 stacks and existing correction history must remain interpretable and safe.

GOAL
Extend the existing shared plan/parser/version authority so it can unambiguously represent both retained historical pre-1.0 roadmap stacks and new post-1.0 roadmap stacks, including Phase 0, while preserving correction-stack fixed-version semantics and exact Git-history resume safety.

FINAL POST-1.0 ROADMAP GRAMMAR
Implement this canonical post-1.0 roadmap folder convention:

`p1-<phase>`

where `<phase>` is a canonical non-negative decimal integer with no leading zero except the single value `0`.

Examples:
- `p1-0` = post-1.0 Phase 0;
- `p1-1` = post-1.0 Phase 1;
- `p1-12` = post-1.0 Phase 12.

Inside those folders, keep the human-facing TASK header form:

`TASK: Phase <phase> / P<number> — <title>`

Prompt numbering remains one-based and MUST NOT permit P0.

The assigned roadmap version for post-1.0 prompts is exactly:

`1.<phase>.<prompt number>`

Examples:
- `p1-0` / P1 -> `1.0.1`;
- `p1-0` / P2 -> `1.0.2`;
- `p1-1` / P1 -> `1.1.1`.

HISTORICAL PRE-1.0 GRAMMAR MUST REMAIN VALID
Retain existing historical roadmap interpretation:
- folder `p<number>` where number is positive and canonical;
- TASK header `TASK: Phase <phase> / P<number> — <title>` matching that folder phase;
- assigned versions exactly `0.<phase>.<prompt number>`.

Do not reinterpret historical `p1`, `p2`, etc. as post-1.0 work. Do not rename/archive/rewrite historical task artifacts or commit history.

CORRECTION GRAMMAR
Preserve correction syntax:

`c<roadmap-phase>-<lower-kebab-slug>`

but allow `<roadmap-phase>` to be canonical non-negative decimal, including `0`, with no leading zero except the single value `0`.

Required examples:
- `c0-phase-zero-fix` -> valid after P1;
- `c10-single-publication` -> remains valid;
- `c00-x`, `c01-x`, `c-1-x`, uppercase or malformed slugs -> invalid.

Correction TASK headers remain `TASK: Correction <phase> / P<number> — <title>`, must match the folder numeric component, retain one-based P numbering, and retain identical required unchanged-version metadata across the stack. Correction versions are never derived from the contextual phase number.

SINGLE ROADMAP VERSION AUTHORITY
Do not solve the new grammar by scattering new `if major === 1` formulas through consumers.

`buildPlan()` or a narrow shared helper owned by the same core module must normalize enough roadmap-family metadata that downstream code can derive the correct expected semantic version without reparsing the task-folder string.

The normalized plan must make these distinctions explicit enough for consumers:
- historical pre-1.0 roadmap family -> major `0`;
- post-1.0 roadmap family -> major `1`;
- roadmap phase number -> canonical non-negative integer;
- correction mode remains a distinct fixed-version mode.

Use the smallest representation that fits the current architecture. Do not add speculative support for future major versions, aliases, or generic pluggable version schemes.

The same authoritative version derivation must own both:
1. prompt target validation during plan construction;
2. expected package-version reconstruction during Git-history resume detection.
