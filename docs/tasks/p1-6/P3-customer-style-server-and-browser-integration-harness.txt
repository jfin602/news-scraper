## Goal

Build the lightweight customer-style PHP integration/example harness required by Phase 6 and prove with real server/browser evidence that ordinary visitor rendering consumes only synchronized local state, emits direct publisher links, and behaves safely across required local states.

The target chain for this prompt is:

```text
synthetic successful Phase 5 synchronization / valid local state
-> P1 local reader
-> P2 fallback or customer-style renderer
-> real local PHP server
-> browser request
```

The ordinary browser request MUST NOT call the News Scraper API, invoke the synchronization CLI, require the bearer token/base URL, or parse cache internals.

This prompt creates a deterministic local customer-style harness suitable for Phase 7 deployment work. It does **not** claim HostGator, managed external deployment, Cloudflare, public-network, or production hosting compatibility.

## Lightweight example/customer-style integration

Add one small example integration under the PHP package, such as:

```text
integrations/php/example/
  index.php
```

plus a concise package-local usage note if needed.

Exact layout is implementation-owned, but the example must:

- require/bootstrap the generic PHP integration package;
- construct only the P1 **local read** configuration/reader from local Profile/state/freshness settings;
- render through the P2 fallback renderer or a tiny custom renderer using only the P1 result;
- send a normal `text/html; charset=UTF-8` response;
- contain no synchronization call, no `DistributionClient`, no `ProfileSynchronizer`, no bearer handling, no API fallback, and no direct manifest/generation reads;
- work when `NEWS_SCRAPER_BASE_URL` and `NEWS_SCRAPER_BEARER_TOKEN` are absent from the visitor server environment;
- remain provider-neutral and framework-free;
- use no client JavaScript for core Article content/navigation.

The example is a proof/reference integration, not a productized CMS adapter, installer, router framework, or HostGator-specific package.

## Deterministic state setup for integration proof

Build test-only setup that creates realistic local states without hand-authoring normal production cache files when a public Phase 5 boundary can create them.

Preferred approach:

- use the real `ProfileSynchronizer` with a small injected deterministic fake/scripted `DistributionPageClient` to perform at least one successful synchronization into the real `FilesystemProfileStateStore` for populated and empty LKG scenarios;
- use controlled `SynchronizationFacts` / store public operations where appropriate to establish stale or authoritative disabled state without changing production semantics;
- use a fresh temporary state root per test/scenario;
- use a deliberately corrupt/missing local state only for the unavailable scenario, and keep that corruption code test-only;
- never place real credentials or production state in fixtures;
- never contact the public internet.

The setup must not create a second persistence format or test-only production backdoor. It should prove that the example can consume state created by the existing Phase 5 machinery.

## Real PHP server process

For browser/server proof, run the example through a real PHP HTTP server process in the test environment, using the PHP CLI/built-in server or an equivalently lightweight local mechanism.

Requirements:

- bind only to loopback on an ephemeral/controlled port;
- launch with a minimal environment containing local read settings, **without upstream base URL/bearer token** for the visitor path;
- wait deterministically for readiness with a bounded timeout rather than fixed arbitrary sleeps;
- capture only bounded stdout/stderr useful for failures and never print secrets/state payloads;
- terminate/cleanup the child process on success, assertion failure, timeout, and test teardown;
- isolate state roots/ports between concurrently executable browser tests, or serialize the PHP-specific integration file if that is the safer bounded choice;
- fail clearly when PHP CLI/server prerequisites are unavailable rather than silently skipping an explicitly invoked required suite.

Do not alter production PHP code merely to make process tests easier if a test helper can own the orchestration.

## Browser/server evidence scenarios

Add substantive browser tests that cover the Phase 6 exit gate using a real browser against the real local PHP server.

### Populated usable state

Observe that:

- Publication/Profile context appears;
- ordered Articles render in the synchronized order;
- core headline anchors are present in server-rendered output;
- anchors point directly to the exact stored publisher `originalUrl` values;
- there is no News Scraper redirect/tracking URL;
- no JavaScript is required for those links/content;
- escaped Source-derived strings remain text, not executable markup.

Use a browser context/page with JavaScript disabled for at least one core-content assertion, or an equivalent browser observation proving the HTML does not depend on JS.

### Empty usable state

Observe a valid empty state distinct from unavailable/never-synced.

### Stale usable state

Observe that retained Articles still render with the bounded stale indicator and no live refresh attempt.

### Never synced

Observe safe fallback content and no Article anchors.

### Stale cutoff

Observe safe fallback content and no retained Article anchors.

### Authoritative disabled

Observe safe disabled content and no retained Article anchors even though the local store may still retain the active generation.

### Unavailable/corrupt local state

Observe bounded safe fallback content with no raw filesystem/error details and no partial Article output.

## Proving no visitor-path News Scraper request

Browser request inspection alone is insufficient to prove absence of a hidden server-side API call. Prove the server-side boundary too.

Required evidence combination:

1. the example/customer visitor server starts and serves successfully with `NEWS_SCRAPER_BASE_URL` and `NEWS_SCRAPER_BEARER_TOKEN` absent;
2. production visitor composition imports/constructs only the P1 local reader and P2 presentation boundary, not sync/upstream client objects;
3. after a test performs one successful synchronization to create valid LKG, the customer server continues to render that LKG while no upstream client configuration is present and no synchronization process runs;
4. browser network observation shows no browser-direct request to News Scraper or tracking endpoint.

If useful, add a deterministic trap/spied dependency around test setup, but do not create a production network abstraction solely for this assertion. The strongest claim should come from the visitor process not possessing upstream configuration/credentials and still rendering correctly.

## Customer presentation override proof

Use at least one server/component test showing the example can swap the fallback renderer for a tiny customer-owned renderer that consumes only P1 data.

The custom example must not:

- reach into cache internals;
- call synchronization;
- change Article order/eligibility;
- rewrite `originalUrl`;
- require News Scraper-specific HTML structure.

Do not turn this into a design system. A minimal override proves the extension boundary.

## Security and output assertions

Include controlled malicious values in synchronized test data to prove:

- headline/Source/Profile/Publication/author/summary/category markup is escaped;
- quoted/query-bearing publisher URLs remain direct logical destinations after HTML attribute escaping;
- no script executes from Source-derived content;
- no raw PHP exception/local path appears in safe fallback states;
- no bearer placeholder/Authorization string appears in served HTML/log output;
- no visitor analytics/tracking beacon is emitted by the example.

Do not claim arbitrary CSP/security-hardening coverage beyond what is actually tested.
