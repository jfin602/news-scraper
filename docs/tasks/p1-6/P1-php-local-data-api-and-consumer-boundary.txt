## Goal

Create the stable normalized local PHP consumption surface for Phase 6 over the already-implemented Phase 5 local LKG/read producer.

P1 must leave one customer-facing read boundary that can be used by either News Scraper's optional fallback renderer or customer-owned PHP presentation without reading cache paths, manifests, generation JSON, lock files, bearer credentials, or the News Scraper API.

Conceptually:

```text
state root + Profile key + local freshness settings
-> Phase 5 readForPhase6()/LocalProfileRead
-> normalized customer-facing Profile/Article/state/health DTOs
```

P1 owns only local consumer configuration, mapping, immutable normalized read DTOs, and the narrow reader/service composition. It does not own HTML rendering, customer-site routing, browser behavior, synchronization, retries, locking, cache activation, or upstream transport.

## Customer-facing local configuration

Separate visitor/read configuration from synchronization configuration.

The local reader needs only the locally relevant values:

- Profile key;
- absolute local state root;
- cadence/freshness interval used to classify stale data, defaulting consistently with the existing 900-second integration cadence;
- optional maximum stale age.

Requirements:

- ordinary customer rendering MUST NOT require `NEWS_SCRAPER_BASE_URL` or `NEWS_SCRAPER_BEARER_TOKEN`;
- reuse existing validation/bounds where practical instead of forking Profile-key, state-root, cadence, or stale-age rules;
- if an environment factory is provided, require only local-read variables and optional freshness values; do not silently load transport credentials merely because the sync runtime uses them;
- no local reader object/result may contain bearer plaintext, Authorization headers, upstream request state, cursor values, or cache paths;
- do not add customer/site/provider/topic-specific configuration.

A focused read-only configuration class/factory is appropriate if it keeps the visitor path independent from the synchronization runtime. Do not weaken the existing sync configuration to make fields optional if that would make the sync CLI ambiguous.

## Stable normalized local data model

Expose an immutable customer-readable model independent of Phase 5 persistence internals.

Exact class/file names are implementation-owned, but the public local model must provide at least:

- Profile `configKey` and `displayName` when renderable active data exists;
- Publication `name` when renderable active data exists;
- ordered Articles containing:
  - `articleId`;
  - `headline`;
  - exact stored `originalUrl`;
  - `effectiveFeedDate`;
  - `feedDateSource`;
  - nullable `publishedAt`;
  - nullable `author`;
  - nullable `summary`;
  - nullable `imageUrl`;
  - Source `configKey` / `displayName`;
  - ordered Categories with `configKey` / `displayName`;
- one explicit local availability/usability state;
- nullable stale age where applicable;
- bounded local sync/cache health sufficient for integrator/operator diagnostics.

The local model MAY internally map from the existing Phase 5 typed objects, but customers must not need to understand `ActiveProfileSnapshot`, manifest/generation structures, filesystem paths, or synchronization state-machine classes to consume ordinary data.

Do not add local filtering, sorting, deduplication, ranking, Source inference, Category interpretation, or URL rewriting. Preserve Article order and exact `originalUrl` values from the validated active snapshot.

## State and data-exposure semantics

Map Phase 5 usability exactly and distinguish renderable from non-renderable retained state.

Required states:

- `usable`;
- `stale_usable`;
- `never_synced`;
- `stale_cutoff`;
- `disabled`;
- `unavailable`.

Requirements:

- `usable` with zero items is a valid **empty** Profile result, not unavailable;
- `stale_usable` remains renderable by default and exposes the same active data plus stale-age facts;
- `never_synced` exposes no Profile/Article payload;
- `stale_cutoff` exposes no renderable Profile/Article payload even though Phase 5 may retain an active generation internally;
- `disabled` exposes no renderable Profile/Article payload even though Phase 5 deliberately retains active data for recovery;
- `unavailable` exposes no partial/corrupt payload;
- no local state should be inferred from Article dates, Source names, domains, missing nullable metadata, or upstream content;
- health facts remain diagnostics and MUST NOT override usability state.

The customer-facing surface must make it difficult for later presentation code to accidentally render retained disabled/cutoff bytes. Prefer a result shape where renderable Profile/Articles are absent for non-renderable states rather than requiring every renderer to remember a second suppression rule.

## Bounded local health

Expose only already-governed non-secret local diagnostics useful to an integrator/operator, such as:

- Profile key;
- last attempt;
- last successful sync;
- sync result;
- duration;
- item/page counts;
- unchanged flag;
- active revision/ETag only if already intentionally part of local health and useful to integrators;
- failure category;
- disabled flag;
- adapter version;
- stale age/usability.

Do not expose local filesystem paths, generation names, lock state, bearer credentials, Authorization headers, raw upstream bodies, cursors, or exceptions. Do not turn operational health into visitor/click analytics.

## Composition boundary

Leave one simple read operation suitable for later presentation, for example conceptually:

```php
$result = $reader->read();
```

or an equivalent operation where the Profile key is supplied explicitly.

The composition must call the existing `FilesystemProfileStateStore::readForPhase6()` with the governed resolver/clock. It must not call `load()`/`health()` separately in a way that recreates or weakens the Phase 5 combined read behavior unless source inspection proves an atomicity/correctness reason and the change remains inside the existing producer contract.

Keep the production read path synchronous and local. No HTTP client, DNS, News Scraper route, synchronization command, lock acquisition, or network fallback belongs in this reader.

## Focused proof

Extend the deterministic PHP suite with tests covering at minimum:

- local read configuration succeeds with state root/Profile/freshness settings and no upstream base URL/bearer credential;
- invalid Profile/state-root/freshness settings fail boundedly without leaking local paths/secrets unnecessarily;
- a valid populated active snapshot maps every governed Profile/Publication/Article/Source/Category field, preserves item/category order, nulls, and exact `originalUrl`;
- a valid active zero-item snapshot is an empty renderable result;
- `usable` exposes active data;
- `stale_usable` exposes active data plus positive stale age;
- `never_synced` exposes no renderable data;
- configured `stale_cutoff` exposes no renderable data despite retained active state;
- authoritative `disabled` exposes no renderable data despite retained active state;
- corrupt/missing committed state maps to `unavailable` with no partial data;
- bounded health facts are available and contain no bearer/API/cache-path state;
- the customer-facing reader does not parse manifest/generation JSON or require a `DistributionPageClient`/HTTP transport;
- upstream ordering/eligibility is not reinterpreted.

Use the existing PHP test harness and fail clearly if PHP CLI is unavailable. Do not introduce public-internet tests.

## Preserved behavior and non-goals

Preserve without semantic change:

- Phase 5 v1 client, synchronization retries/restarts, locking, atomic LKG activation, cadence, disable/re-enable transitions, stale policy, and local store validation;

Do not implement in P1:

- a renderer interface or fallback renderer;
- customer-site public routing/server files;
- Playwright/browser tests;
