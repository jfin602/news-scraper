## Goal

Implement the optional safe server-rendered fallback presentation over the P1 local data API, while preserving a clean customer-owned presentation escape hatch.

Conceptually:

```text
P1 local result
-> renderer interface / customer replacement point
-> default safe server-rendered HTML
```

The fallback is a functional reference, not mandatory customer markup. Customer code must be able to consume P1 directly or supply its own renderer without parsing Phase 5 cache internals or reimplementing upstream business rules.

## Renderer ownership boundary

Provide a narrow presentation contract suitable for replacement by customer code.

Exact names are implementation-owned, but prefer a shape conceptually like:

```php
interface LocalProfileRenderer {
    public function render(LocalProfileResult $result): string;
}

final class FallbackHtmlRenderer implements LocalProfileRenderer { ... }
```

or an equivalent small interface.

Requirements:

- the renderer accepts only the P1 customer-facing local result/model;
- no renderer receives filesystem paths, bearer credentials, API clients, synchronization stores, manifests, or generation data;
- customer presentation can replace the fallback implementation without replacing the local reader or changing Article selection semantics;
- the fallback renderer is optional: customers may consume the P1 data API directly;
- do not introduce a template engine/framework/Composer dependency for this bounded output;
- do not make the renderer a controller/router/server framework.

## Safe HTML rules

Treat all Source-derived/editorial strings as untrusted output data.

Requirements:

- use one explicit UTF-8 HTML escaping helper or native equivalent appropriate for text and quoted attributes;
- escape headline, Profile/Publication/Source/Category names, author, summary, dates when rendered as text, and every attribute value;
- invalid UTF-8 or substitution-worthy input must fail safely or render with bounded substitution rather than becoming executable markup;
- never render publisher-supplied HTML as trusted markup;
- do not evaluate Source content, URLs, summaries, or Category names as PHP/template code;
- avoid inline JavaScript and do not require client JavaScript for core content;
- no News Scraper tracking redirect, onclick tracking, data beacon, external script, or visitor analytics;
- do not add `nofollow`, `ugc`, `sponsored`, or tracking parameters merely because a publisher link is external;
- do not promise SEO/backlink benefit.

The renderer may use simple semantic HTML/classes and modest fallback styling only if useful. Do not turn this prompt into a design/UI-polish project.

## Direct publisher anchors

For every rendered Article headline:

- emit an ordinary `<a>` anchor;
- use the exact P1 `originalUrl` value as the logical destination;
- HTML-escape it for attribute context without canonicalizing, redirecting, shortening, reordering query parameters, appending tracking, or substituting a News Scraper URL;
- use the escaped headline as visible anchor text;
- do not require JavaScript to navigate;
- do not infer a different destination from Source domain/name, canonical identity, or image URL.

Do not add `target="_blank"` or relationship attributes as a hidden policy decision unless the existing contract explicitly requires them. The safe default should remain an ordinary direct editorial link.

## Renderable states

The fallback renderer must handle every P1 local state deterministically.

### `usable`

- populated data renders Publication/Profile context plus ordered Articles;
- zero Articles renders a safe explicit empty state rather than an error/unavailable message.

### `stale_usable`

- render the same active Article content;
- expose a bounded stale/freshness indicator useful to an integrator/reader without implying the data is invalid;
- never trigger a live refresh from the visitor path.

### `never_synced`

- render a safe unavailable/initializing fallback with no Article content.

### `stale_cutoff`

- render a safe stale-expired/unavailable fallback with no retained Article content.

### `disabled`

- render a safe disabled/unavailable fallback with no retained Article content.

### `unavailable`

- render a safe bounded unavailable fallback with no partial/corrupt Article content or raw exception details.

Do not infer state from empty Articles: a valid empty `usable` result is distinct from never-synced/unavailable.

## Nullable metadata

Handle nullable Article fields without placeholder junk or malformed HTML.

At minimum:

- headline and direct link always render for a renderable Article;
- nullable author/summary/publishedAt/imageUrl must not produce literal `null`, `undefined`, broken markup, or unsafe raw values;
- optional values MAY be omitted cleanly when absent;
- if image rendering is added at all, it must remain optional, safely escaped, and cannot become a requirement for core Article navigation. Omitting images from the fallback renderer is acceptable and preferred unless there is a clear reason to include them;
- categories may be rendered as escaped text in existing order or omitted; do not use them to filter/reorder Articles.

## Local health visibility

Where useful, the fallback may expose a small non-sensitive status block derived only from P1 health/freshness data, such as last successful sync, stale age, or adapter version.

Requirements:

- never show bearer/API/cache paths, raw failure payloads, cursor values, or internal generation/lock state;
- do not expose secrets in HTML comments, data attributes, or hidden elements;
- do not make health facts control Article eligibility beyond the P1 state already decided.

A minimal bounded indicator is enough; do not build an admin dashboard.

## Customer-owned presentation escape hatch

Prove both supported use modes:

1. use the provided fallback renderer;
2. consume P1 local data with a custom renderer implementing the narrow presentation interface or bypassing the fallback entirely.

The customer replacement must not need to subclass/modify filesystem store internals, copy cache JSON, or duplicate synchronization code.

Do not add a free-form callback that receives production service internals. The extension point should receive only normalized P1 data and return/emit presentation.

## Focused proof

Extend the deterministic PHP suite with tests covering at minimum:

- malicious HTML/script-like headline/Profile/Publication/Source/Category/author/summary strings are escaped and never executable markup;
- quote/ampersand characters in exact `originalUrl` are attribute-escaped while the logical destination remains unchanged;
- no News Scraper redirect/tracking URL is introduced;
- no script is required for core Article anchors;
- ordinary external anchors do not gain automatic tracking/nofollow policy;
- Article ordering is unchanged;
- valid populated `usable` state renders all expected anchors/content;
- valid empty `usable` state renders a distinct empty state;
- `stale_usable` retains Articles and exposes a bounded stale indicator;
- `never_synced`, `stale_cutoff`, `disabled`, and `unavailable` render no Article anchors/content from retained state;
- nullable author/summary/publishedAt/imageUrl are handled cleanly;
- health rendering, if present, is bounded and secret/cache-internal free;
- a custom renderer can replace the fallback using only the P1 local result;
- fallback rendering does not instantiate an upstream client/sync runtime or access the filesystem store directly.

Use explicit string/DOM-oriented assertions in PHP where sufficient. Browser proof belongs to P3.

## Preserved behavior and non-goals

Preserve without semantic change:

- all P1 local data/state/health semantics;
- all Phase 5 synchronization/LKG/locking/cadence behavior;
- exact upstream `originalUrl`, item order, Source/Category values, and eligibility;
- Node Web/API/Worker/admin/reference surfaces and production database state;
- machine/admin separation, topic independence, and one-Publication deployment model.

Do not implement in P2:

- public customer-site server/router/example harness;
- Playwright/browser process orchestration;
- upstream/network synchronization or visitor fallback;
- Source/Profile/category filtering, sorting, ranking, deduplication, or moderation;
- bespoke customer branding/design system;
- HostGator/provider-specific behavior;
- WordPress, RSS/Atom, widgets, analytics, advanced SEO tooling, or self-host packaging.
