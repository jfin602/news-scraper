GOAL
Create the complete relational foundation needed by Phase 11 Categories and configurable Relevance while leaving runtime behavior on the existing default-include evaluator until later prompts.

GOVERNING INVARIANTS
- Categories and Relevance rules are installation-wide singleton Publication configuration and MUST NOT introduce a Publication ID/slug/foreign-key tenancy dimension.
- Category and Relevance-rule `config_key` values are immutable installation-wide identities.
- Relevance predicates are only `title_contains`, `summary_contains`, and `source_category_equals`.
- Relevance actions are only `include`, `exclude`, and `categorize`.
- A `categorize` rule requires exactly one valid Category target; include/exclude rules must not carry a Category target.
- A rule may be installation-wide or scoped to one Source.
- Source default Category and endpoint default Category are optional references to installation-wide Categories.
- Article/Category membership is unique per Article + Category.
- `created`, `updated`, and `unchanged` observations continue to require Article identity; pre-identity `excluded` observations may have no Article ID.
- Article identity, Source/endpoint/run provenance, approval/network-safety behavior, scheduler/jobs, and public-feed behavior are unchanged by P1.

REQUIRED SCHEMA SHAPE
Add one normal additive Phase 11 migration, expected to be `migrations/0005_categories_and_relevance.sql` if the current chain still ends at `0004`. Do not rewrite/squash the accepted Phase 10 migration lineage merely because development databases are disposable.

The migration should introduce the smallest canonical relational model for:

1. `categories`
- UUID primary key;
- immutable installation-wide `config_key` using the same canonical lowercase underscore-delimited key shape already used by Sources;
- mutable trimmed bounded display label/name;
- created/updated timestamps where consistent with current configuration tables;
- unique `config_key`.

2. `relevance_rules`
- UUID primary key;
- immutable installation-wide `config_key`;
- nullable `source_id` FK for Source-scoped rules;
- predicate type constrained to `title_contains`, `summary_contains`, `source_category_equals`;
- one trimmed, bounded, non-empty literal pattern;
- action constrained to `include`, `exclude`, `categorize`;
- nullable Category target FK with a database CHECK enforcing target presence exactly for `categorize` and target absence for `include`/`exclude`;
- explicit integer priority;
- enabled boolean;
- trimmed bounded explanatory reason/label;
- timestamps;
- unique `config_key`.

3. Source and endpoint default Category references
- add nullable `default_category_id` to `sources`;
- add nullable `default_category_id` to `source_endpoints`;
- both reference `categories` and preserve existing ownership/identity relationships.

4. `article_categories`
- Article FK;
- Category FK;
- uniqueness per Article + Category;
- this table represents current automatically derived Phase 11 Category membership, not historical reasoning.

5. Article-observation include/exclude reason reference
- add a nullable Relevance-rule FK to `article_observations` for the selected include/exclude rule;
- retain/reuse the existing bounded observation `reason_code` and `detail` fields rather than inventing another include/exclude-reason table.

6. observation-level Category reasons
Add a relation, expected name `article_observation_category_reasons`, that can preserve every applied Category rule/default reason for one included observation, including multiple rule reasons that target the same deduplicated Category membership.

It must contain enough data to enforce and later persist:
- Article-observation FK;
- Category FK;
- nullable Relevance-rule FK for rule-driven reasons;
- deterministic reason position/order;
- constrained reason kind capable of distinguishing rule-driven, endpoint-default, and Source-default reasons;
- bounded snapshot detail/reason text;
- uniqueness sufficient to prevent duplicate reason positions for one observation while still allowing two distinct rules to explain the same Category.

Do not over-model later moderation/manual-category/admin/change-history behavior in P1.
