GOAL
Extend the existing per-candidate Article transaction so included Relevance/Category decisions are durably recorded atomically, and add a separate pre-identity excluded-observation persistence path that never resolves or mutates an Article.

CRITICAL DOMAIN SEPARATION
Keep these concepts distinct:

1. Source-derived Article content/identity outcome
- existing `created`, `updated`, `unchanged` semantics remain based on Article identity and Source-derived material fields.

2. Current Article Category state
- `article_categories` represents the Article's current automatically derived Phase 11 Category membership as of its latest ordinary included observation.

3. Historical observation reasons
- each Article observation records the winning include/exclude reason;
- observation-level Category-reason rows preserve every applied rule/default explanation in deterministic order for that observation.

Do not conflate a Category-only editorial change with a Source-content `updated` outcome.

INCLUDED CANDIDATE TRANSACTION
The existing `persistIncludedArticle`-style transaction currently owns Article identity + successful observation. Extend the same transaction to persist the P3 decision data.

The logical transaction must be:

1. validate candidate + observation time + supplied Relevance decision/persistence input;
2. acquire existing Source-scoped Article identity locks;
3. validate Source/endpoint/run provenance;
4. resolve Article identity using the existing strong-external-ID/canonical-fallback rules;
5. insert/update/touch Article exactly as current identity/content semantics require;
6. insert the successful Article observation;
7. persist the observation's winning inclusion reason/rule reference;
8. reconcile the Article's current automatic Category membership to exactly the evaluator's unique Category assignment set;
9. persist every ordered Category reason for this observation;
10. commit atomically.

A failure in steps 6-9 MUST roll back the Article change/touch and the entire candidate transaction, just like a failure in existing successful-observation persistence.

CATEGORY MEMBERSHIP RECONCILIATION
On every ordinary included observation:
- the evaluator's unique Category assignment set is authoritative current automatic membership for that Article;
- replace/remove stale Phase 11 automatic memberships not present in the new set;
- insert missing memberships from the new set;
- duplicate Category assignments from multiple rules remain one membership;
- an empty Category set clears previous automatic memberships;
- do not accumulate old automatic Categories forever.

This reconciliation happens only after Article identity resolves in an included candidate transaction.

IMPORTANT OUTCOME RULE
If Source-derived Article fields are materially unchanged, the persistence result remains `unchanged` even when Category membership or observation reasons change.

Existing `updated` classification remains reserved for existing Article Source-derived material changes / fallback promotion exactly as the current Article repository defines it.

HISTORICAL CATEGORY REASONS
For the successful observation:
- persist all P3 ordered Category reasons, even if multiple reasons target one Category;
- retain deterministic reason position/order;
- retain Category identity/reference;
- retain nullable Relevance-rule identity for rule-driven reasons;
- retain reason kind distinguishing rule vs endpoint default vs Source fallback;
- persist a bounded explanatory snapshot consistent with P1 schema;
- do not derive/re-run matching in the repository.

WINNING INCLUDE REASON
For an included observation:
- `default_include` has no Relevance-rule reference;
- rule-driven include retains the selected Relevance-rule reference plus canonical stable reason code and bounded snapshot detail;
- persistence consumes the P3 decision; it must not independently choose a winner.

EXCLUDED CANDIDATE PERSISTENCE
Add a dedicated repository/service operation for a P3 exclusion decision.

It must:
1. validate candidate, observation timestamp, and exclusion decision input;
2. validate candidate Source/endpoint/run provenance against persisted relationships;
3. insert an `article_observations` row with `processing_outcome='excluded'`;
4. leave `article_id` NULL;
5. persist selected exclusion Relevance-rule reference/reason code/bounded detail;
6. persist ordered Category reasons for the excluded candidate if the evaluator also produced categorize matches/defaults;
7. commit atomically.

It MUST NOT:
- acquire Article identity locks;
- query Article identity by external ID/canonical URL;
- insert/update/touch/hide/archive an Article;
- modify `article_categories`;
- infer whether this candidate corresponds to a previously stored Article.

This is a hard prospective-behavior invariant, not an optimization.

DEFAULT / REASON CODES
Use bounded stable machine-readable reason codes consistent with existing observation rules. Prefer a small vocabulary such as:
- `default_include`;
- `relevance_rule_include`;
- `relevance_rule_exclude`;
with detailed rule/category explanations stored separately/snapshotted as planned.

Do not embed mutable free-form rule text into machine reason codes.

VALIDATION / REFERENTIAL SAFETY
- Supplied rule IDs/config identities must correspond to the persisted rules represented by the P2/P3 configuration decision; reject malformed/mismatched input rather than storing impossible provenance.
- Supplied Category assignments/reasons must reference existing Categories.
- A rule-driven Category reason should reference the rule that actually targets that Category according to persisted configuration, where practical without re-running matching.
- Default reasons have no rule reference and must identify the expected Category/default kind.
- Existing Source/endpoint/run/Article ownership checks remain authoritative.

Avoid creating an expensive generic cross-check that duplicates the evaluator; validate persistence relationships and structural consistency, not matching semantics a second time.

REAL POSTGRESQL FOCUSED TESTS — MANDATORY
Prove at least:

Included create/update/unchanged
1. new included Article + Category/reasons commits Article, observation, membership, reasons atomically and returns `created`;
2. existing Article Source fields materially change and returns `updated`, while Category/reason persistence succeeds;
3. existing Article Source fields unchanged returns `unchanged` with a new observation;
4. Category-only changes on that unchanged Article still return `unchanged`;
5. empty new Category set clears old current automatic memberships while outcome remains based on Source content;
6. multiple rule reasons targeting one Category yield one membership but all reason rows.

Reason persistence
7. default include stores no selected rule reference and stable reason code;
8. rule include stores the selected rule reference/reason snapshot;
9. ordered Category reasons preserve P3 order exactly;
10. endpoint-default vs Source-default reasons remain distinguishable.

Atomic rollback
11. synthetic observation insertion failure rolls back Article insert/update/touch;
12. synthetic Category membership failure rolls back Article + observation;
13. synthetic Category-reason insertion failure rolls back Article + observation + membership;
14. no partial candidate state remains after transaction failure.

Prospective behavior
15. first observation includes Article into Category A;
16. after operator configuration changes, later ordinary included observation of the same Source Article evaluates Category B: Article cardinality remains one, Source-content outcome is `unchanged` when fields match, current membership becomes B rather than A+B, and historical first observation/reasons remain intact;
17. after configuration changes to exclusion, persist an exclusion observation for the same candidate with NULL Article ID, no Article mutation, no identity lookup/lock, and existing Article/membership left untouched;
18. after configuration changes back to inclusion, the same Article identity resolves normally and current Category membership can update through the included path.

Excluded path
19. exclusion observation validates real Source/endpoint/run provenance;
20. orphan/mismatched provenance rejects and inserts nothing;
21. exclusion persists ordered Category reasons if supplied;
22. exclusion never creates an Article or Article membership.

Identity regression
23. strong external-ID resolution, canonical fallback, fallback promotion, contradictory strong identities, digest collision handling, and existing concurrency locks remain correct;
24. Article identity cardinality remains Source-scoped.
