GOAL
Activate Phase 11 persisted Categories and configurable Relevance in the single canonical manual/scheduled endpoint collection path, producing durable exclusions/reasons and exact existing Collection-run accounting without changing Article identity, network safety, or Phase 10 job semantics.

ONE CANONICAL EXECUTION PATH
Manual and scheduled execution MUST continue to converge through the same production endpoint-execution composition.

Do not:
- add a second collection service for configurable Relevance;
- put Relevance configuration loading in Web/API request handlers;
- create a special scheduled-only evaluator path;
- bypass the existing endpoint lock/capacity/network-safety chain;
- fetch Source configuration once per candidate through ad hoc queries.

RUNTIME CONFIGURATION SNAPSHOT
Load the effective P2 Relevance configuration exactly once per endpoint execution/run before candidate Relevance processing begins.

The same immutable snapshot applies to the bounded candidate batch for that endpoint execution. A concurrent operator edit may affect a subsequent run, not half of the current run.

Prefer composition in `endpoint-collection-service.ts` or another existing endpoint-unit boundary where both manual and scheduled triggers naturally share it. Do not introduce Publication selectors.

If the current endpoint aggregate already loads Source/endpoint defaults and a separate rule loader remains cleaner, keep them as one logical frozen snapshot before candidate processing.

CANONICAL PIPELINE ORDER
Preserve exactly:

1. normalize Raw item into candidate;
2. Article-link/domain policy gate;
3. evaluate P3 Relevance + Categories using the run snapshot;
4. if excluded, persist P5 durable excluded observation/reasons and stop that candidate before Article identity;
5. if included, persist P5 included Article/observation/current Categories/reasons;
6. map persistence result to canonical candidate outcome;
7. continue unrelated candidates when item-level outcomes permit;
8. finalize Collection-run counters after the bounded batch.

Article-link rejection remains before Relevance and maps to `rejected`, not `excluded`.

OBSERVATION TIME
For every link-accepted candidate that reaches a durable Phase 11 persistence operation, obtain one bounded observation timestamp through the existing observation-clock dependency.

- included candidate uses that timestamp for Article/observation persistence;
- excluded candidate uses that timestamp for exclusion observation persistence;
- do not call Article persistence for excluded candidates;
- if the observation clock fails, preserve the existing fatal processing-stage accounting contract rather than fabricating timestamps.

EXCLUSION ACCOUNTING
Today the collection loop already has an `excludedCount` outcome branch. P6 makes it durable.

After P6:
- increment `excludedCount` only after the P5 exclusion persistence operation succeeds;
- a successfully excluded candidate creates one durable exclusion observation;
- an exclusion persistence failure is not counted as a successful exclusion;
- map that failure into truthful processing failure accounting and a stable bounded error reason without leaking raw DB/config secrets;
- remaining unattempted normalized candidates must be accounted consistently with existing fatal-stage rules if the failure is stage-fatal.

Prefer a stable failure code such as `relevance_exclusion_persistence_execution_failed` if the current error vocabulary has no better governed equivalent. Do not create free-form machine codes from exception messages.

CANONICAL RUN ARITHMETIC
Continue enforcing the existing equation:

`created + updated + unchanged + rejected + excluded + failed = normalized_candidate_count`.

Do not create a second exclusion metric or reinterpret `article_link_rejection_count`.

Normalization failures remain outside post-normalization processing outcomes.

INCLUDED PERSISTENCE INTEGRATION
Pass the P3 decision directly into the P5 included persistence operation so:
- Article content outcome remains created/updated/unchanged;
- winning inclusion reason persists;
- current Category reconciliation occurs transactionally;
- every ordered Category reason persists;
- Category-only changes still map to `unchanged` when Source fields do not change.

Do not re-run Relevance inside Article persistence or collection after P3 has decided.

EXCLUDED PERSISTENCE INTEGRATION
Pass the P3 exclusion decision directly into the P5 excluded persistence operation.

Verify the integration never calls the included Article persistence/identity path for exclusions.

MANUAL / SCHEDULED PARITY
Both trigger kinds must use:
- the same effective Relevance snapshot loader;
- the same P3 evaluator;
- the same P5 included/excluded persistence operations;
- the same candidate loop/accounting;
- the same endpoint lock, capacity, network safety, conditional-fetch, run and runtime-state behavior.

Phase 10 job retry/recovery behavior must remain based on truthful collection result classification; do not reclassify deterministic editorial exclusion as transport/parser failure or transient retry.

FAILURE ISOLATION
Preserve existing behavior where ordinary candidate-level identity/persistence failures can be isolated and unrelated candidates continue when integrity permits.

A fatal execution failure in a shared dependency (configuration snapshot load, evaluator implementation failure, observation clock, persistence infrastructure) must use bounded stage failure behavior and correctly account remaining candidates according to the existing processing-stage contract.

A malformed/invalid persisted Relevance configuration should fail safely rather than silently default-including. Configuration persistence should normally prevent this; runtime must not convert corruption into permissive behavior.
