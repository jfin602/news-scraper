GOAL
Provide the smallest explicit, topic-independent operator mechanism needed before Phase 15 to deliberately create/update Categories and Relevance rules and set/clear Source/endpoint default Categories, while preserving ordinary bootstrap semantics and never triggering automatic Article reprocessing.

BOUNDARY
This is an operator command/configuration-file capability, not an admin Web/API feature.

Expected shape:
- `config/editorial.json` as the first-deployment operator document;
- `scripts/apply-editorial-configuration.ts` as the explicit command entry point;
- `npm run editorial:apply` as the command surface;
- a focused Phase 11 parser/apply service under `src/collection/relevance/`, expected name `operator-configuration.ts` or equivalent.

If the final P2 module layout suggests a slightly different narrow name, keep ownership under Relevance/configuration. Do not put topic-specific vocabulary into shared engine modules.

ORDINARY BOOTSTRAP MUST REMAIN SEPARATE
Do not turn `db:bootstrap` into an editor.

The existing bootstrap remains responsible for initial singleton Publication/Source/endpoint creation and continues to:
- run only when explicitly invoked;
- create-if-absent;
- leave existing Publication/Source/endpoint state unchanged;
- avoid silently changing approval, lifecycle, operational state, domains, endpoint URLs, or poll intervals.

P4's editorial command is deliberately different because editing Category/Relevance/default configuration is its purpose. Do not weaken bootstrap to achieve P4.

EDITORIAL DOCUMENT SHAPE
Use one strict JSON object with explicit top-level arrays/sections equivalent to:
- `categories`;
- `rules`;
- `sourceDefaults`;
- `endpointDefaults`.

Use exact-key validation consistent with existing bootstrap/operator parsing style. Reject unknown fields rather than silently ignoring them.

Category entry fields should be equivalent to:
- `configKey`;
- mutable display label/name.

Rule entry fields should be equivalent to:
- `configKey`;
- optional `sourceConfigKey`;
- predicate type;
- literal pattern;
- action;
- optional `categoryConfigKey` only when categorizing;
- integer priority;
- `enabled` boolean;
- bounded reason.

Source default entries should identify:
- `sourceConfigKey`;
- `categoryConfigKey`, allowing explicit `null` to clear the default.

Endpoint default entries should identify:
- `sourceConfigKey`;
- `endpointConfigKey` within that Source;
- `categoryConfigKey`, allowing explicit `null` to clear the default.

Do not require or accept Publication IDs/slugs.

APPLY SEMANTICS
The whole requested document is one transactional edit.

Before commit:
1. parse/normalize the complete document;
2. reject duplicate Category/rule config keys within the request;
3. reject duplicate default-target entries that would make requested intent ambiguous;
4. resolve every referenced existing Source/endpoint and every referenced Category identity required by rules/defaults;
5. ensure endpoint references actually belong to the named Source;
6. enforce all P2 rule/category validation invariants.

Then atomically:
- create a listed Category when its config key is absent;
- otherwise update only its mutable fields while preserving identity;
- create a listed rule when its config key is absent;
- otherwise update its mutable fields while preserving identity;
- explicitly enable/disable from the document's `enabled` field;
- set, replace, or clear each listed Source/endpoint default;
- leave every omitted existing Category/rule/default unchanged.

No implicit deletion.
No implicit disable.
No inference from collected content.
No Article scan/re-evaluation.

IDEMPOTENCY
Applying the same valid document twice should converge without duplicate Categories/rules and should retain the same stable database identities.

An invalid edit must leave all requested edits unapplied.

SCRIPT / COMMAND BEHAVIOR
`apply-editorial-configuration.ts` should:
- require exactly one explicit document path argument unless the package script supplies the canonical path;
- read/parse the file;
- connect using the existing database config/environment conventions;
- invoke the transactional editorial apply service;
- print a bounded deterministic summary of created/updated/default-edit counts without secrets;
- close the database reliably on success/failure;
- map known configuration/database/filesystem failures to safe useful messages;
- return non-zero exit status on failure.

Preferred package script:
`editorial:apply`: `node --env-file-if-exists=.env scripts/apply-editorial-configuration.ts config/editorial.json`

If current project command conventions materially differ, follow them while preserving explicit invocation.
