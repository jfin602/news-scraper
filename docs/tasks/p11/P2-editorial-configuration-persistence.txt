CONFIGURATION DOMAIN TYPES
Define topic-independent canonical types for at least:
- Category identity/configuration;
- Relevance predicate type;
- Relevance action;
- installation-wide vs Source-scoped rule scope;
- Relevance rule configuration/persisted record;
- Category target identity;
- Source default Category;
- endpoint default Category;
- effective Relevance configuration snapshot for a concrete Source/endpoint execution.

Use the immutable database `config_key` as configuration identity. Mutable labels, patterns, reasons, priorities, enabled state, Source scope, and Category target are not identity.

NORMALIZATION CONTRACT
Reuse the repository's existing canonical config-key grammar/helper rather than inventing a slightly different one.

At minimum validate:
- Category display label: trimmed, non-empty, bounded (planned maximum 200 unless P1 establishes another governed bound);
- rule predicate: exactly `title_contains`, `summary_contains`, `source_category_equals`;
- rule action: exactly `include`, `exclude`, `categorize`;
- rule pattern: trimmed, non-empty, bounded (planned maximum 2048 unless P1 establishes another governed bound);
- rule reason: trimmed, non-empty, bounded to fit the observation snapshot detail boundary (planned maximum 160 unless P1 establishes another governed bound);
- priority: finite integer within any P1 DB bound;
- enabled: boolean;
- Source scope: optional existing Source identity/config key resolved explicitly;
- Category target: required only for `categorize` and absent for include/exclude.

Do not add regex/glob/fuzzy/stemming/AI/general-expression semantics.

REPOSITORY OPERATIONS
Provide the smallest composable repository API needed by P4/P5/P6. It should support deliberate caller-owned transactions and include operations equivalent to:

Categories
- create Category by immutable config key;
- find/read Category by config key;
- update mutable Category fields while retaining identity;
- list Categories deterministically where needed.

Relevance rules
- create rule by immutable config key;
- find/read rule by config key;
- update mutable rule fields while retaining identity;
- enable/disable through mutable `enabled` state;
- list/load rules deterministically.

Defaults
- set or clear Source default Category;
- set or clear endpoint default Category;
- reject real relationship mismatches/orphans.

Effective runtime snapshot
Provide one read operation for a concrete Source/endpoint execution that returns a frozen/immutable logical snapshot containing only:
- enabled installation-wide rules;
- enabled rules scoped to that Source;
- Category identities/labels required by those rules/defaults;
- Source default Category if any;
- endpoint default Category if any.

Rules scoped to another Source MUST NOT appear in the effective snapshot.

The snapshot may be loaded by Source/endpoint persisted IDs or from the existing endpoint configuration aggregate, whichever produces the smallest safe P6 integration. Do not add Publication selector parameters.

- P3 remains the behavioral precedence authority; repository ordering must not accidentally encode a competing precedence algorithm.
- Stable config-key ordering is preferred when no behaviorally stronger order is needed.

TRANSACTION OWNERSHIP
