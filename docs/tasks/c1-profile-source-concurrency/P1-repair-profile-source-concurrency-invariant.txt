OBSERVED DEFECT
Current Source invalidation resolves a Source ID without a write lock, discovers and locks only Profiles that are already `active` and currently reference that Source, then locks relevant Source rows and validates before mutation.

That leaves this race:
1. Source invalidation discovers no active Profile while a referencing Profile is still draft/disabled;
2. Profile activation locks that Profile and Source, validates the Source as usable, and commits `active`;
3. Source invalidation later obtains the Source lock but retains its stale empty Profile set;
4. Source invalidation commits unapproved/archived state;
5. committed state contains an active Profile with zero approved+active associated Sources.

The existing `Promise.allSettled()` race test is not deterministic proof because scheduler order may never exercise the stale-discovery interleaving.

GOVERNED INVARIANT
Preserve the existing Phase 1 semantics exactly:
- a usable Profile Source is `approval_state = 'approved' AND lifecycle_state = 'active'`;
- Source operational state is not part of Profile usability;
- draft/disabled Profiles may be incomplete;
- activation/reactivation requires at least one usable associated Source;
- an active Profile must never be committed with zero usable associated Sources;
- Source unapproval/archive must fail when it would remove the final usable Source from any active Profile;
- active Source-association removal must fail when it would remove the final usable Source;
- failed mutations and their success audit rows roll back atomically.

CORRECTION ARCHITECTURE
Use a narrowly scoped per-Source PostgreSQL transaction advisory lock as a predicate/synchronization boundary for "this Source may participate in Profile activation validity".

The repository already uses namespaced PostgreSQL advisory locks for correctness-sensitive identities. Follow that pattern instead of adding a process mutex, global lock, queue, schema table, or distributed lock service.

Add a Profile-owned lock module, expected near:

`src/distribution/profiles/source-validity-lock.ts`

Names may adapt to current conventions, but ownership and semantics must remain narrow.

The module should expose conceptually:
- deterministic Source-UUID -> signed 64-bit advisory key derivation under a dedicated versioned namespace;
- acquisition of one Source validity transaction lock;
- acquisition of multiple Source validity transaction locks after validating, deduplicating, and sorting stable Source UUIDs deterministically.

Use:

`SELECT pg_advisory_xact_lock($1::bigint)`

Transaction locks must release automatically on commit/rollback. Do not use session advisory locks or try-lock/retry behavior for this invariant.

Lock-key derivation should follow the existing SHA-256 -> signed bigint convention used by other repository lock namespaces, while using a distinct Profile Source-validity namespace so unrelated lock domains do not intentionally share keys.

SOURCE INVALIDATION PROTOCOL
For Source mutations capable of decreasing Profile usability (`approval -> unapproved` and/or target approval `unapproved`; `lifecycle -> archived` and/or target lifecycle `archived` as appropriate to current command semantics):

1. resolve the stable Source UUID without taking a conflicting Source row write lock;
2. acquire that Source's Profile-validity transaction advisory lock BEFORE discovering active Profiles;
3. discover and lock every currently active Profile referencing the Source in deterministic Profile-ID order;
4. lock the Sources belonging to those locked Profiles using the existing stable Source-ID row-lock order;
5. if the target Source was not included in those rows, lock/re-read it explicitly;
6. validate the proposed Source state against the locked current Profile/association/Source state;
7. reject with existing `source_required_by_active_profile` when required;
8. otherwise mutate and commit.

The critical requirement is that Source invalidation cannot perform active-Profile discovery before it owns the Source validity advisory guard.

Do not reverse the established Profile→Source ROW lock order. The advisory guard is an additional predicate synchronization boundary, not permission to acquire Source rows first.

Non-invalidating Source changes such as operational-state changes and ordinary mutable configuration must preserve existing behavior and need no new Profile-validity synchronization. Approval/lifecycle transitions that only improve usability should not be broadened unnecessarily; a harmless advisory acquisition for a no-op target may be tolerated only if it keeps the implementation materially simpler and tests prove no behavior change.

PROFILE ACTIVATION / REACTIVATION PROTOCOL
Only lifecycle transitions whose requested target is `active` need the new predicate synchronization.

Inside the existing Profile transaction:
1. lock the target Profile row using the current application authority;
2. establish that the requested transition is activation/reactivation under the existing lifecycle state machine;
3. obtain the stable Source UUIDs currently associated with that already-locked Profile WITHOUT taking Source row locks;
4. acquire Profile-validity advisory locks for those Source UUIDs in deterministic Source-ID order;
5. lock/re-read the actual associated Source rows using the existing stable Source-ID row-lock helper;
6. validate that at least one Source is currently approved+active;
7. perform lifecycle mutation and audit in the same transaction.

Because Profile association create/replace/remove operations already serialize through the Profile row, the association set read under that Profile row lock must remain stable for this activation transaction.

Add one narrow repository read if needed, conceptually:

`listDistributionProfileSourceIds(executor, profileId)`

It should:
- return stable Source UUIDs only;
- order deterministically by Source ID;
- not interpret Source usability;
- not lock Source rows;
- keep `distribution_profile_sources` topology inside the repository rather than moving SQL into admin services.

CRITICAL LOCK-GRAPH RESTRICTION
Do NOT hide the new advisory lock inside the generic `lockDistributionProfileSources()` helper or apply it indiscriminately to active association-removal paths.

Reason: Source invalidation must acquire `Source-validity advisory -> active Profile row`; activation is safe with `inactive Profile row -> Source-validity advisory` because the Source invalidation discovery predicate does not lock inactive Profiles. If active association removal also acquired `active Profile row -> Source-validity advisory`, it could form a real deadlock cycle with Source invalidation.

Keep association removal on its current Profile-row/Source-row serialization unless source inspection proves a specific additional guard is required. Do not broaden the advisory protocol speculatively.

ASSOCIATION ADDITION / FILTER REPLACEMENT
Do not add advisory locking merely because a Profile association is created or its filters change.

Adding an association cannot invalidate an already-valid active Profile. A draft/disabled Profile still must cross the guarded activation/reactivation boundary before becoming active. Filter-only changes do not affect Source usability.

If source inspection identifies a concrete association mutation that can invalidate the invariant despite these facts, stop and report the exact counterexample rather than silently widening lock ownership.

OVERLAPPING CONCURRENCY EXPECTATIONS
The final protocol must remain deadlock-safe for at least:
- two activations with overlapping Source sets;
- two Source invalidations against different Sources used by the same active Profile;
- Source invalidation racing activation/reactivation of an inactive Profile referencing that Source;
- Source invalidation racing active association removal on the same/another Profile Source;
- Source invalidation while unrelated draft/disabled association edits occur.

Multiple advisory locks must be acquired in one globally deterministic Source-ID order so overlapping activation sets cannot deadlock each other.

Do not add automatic deadlock retries that hide a broken lock graph.

DETERMINISTIC RACE A — ACTIVATION VS SOURCE UNAPPROVAL
Use real disposable PostgreSQL and two independently pooled database handles.

Force the exact previously vulnerable interleaving:
1. seed approved+active Source `alpha`;
2. create draft Profile `racing_draft` associated only with `alpha`;
3. start Source `alpha` unapproval;
4. allow invalidation to acquire the new Source-validity advisory lock;
5. allow its active-Profile discovery query to execute and return empty while `racing_draft` is still draft;
6. pause invalidation after that discovery but before it can commit Source unapproval;
7. start Profile activation through the other database handle;
8. observe that activation reaches/attempts the same Source-validity advisory lock and cannot pass it while invalidation owns it;
9. release invalidation;
10. invalidation commits `alpha` unapproved;
11. activation resumes, re-reads Source state, and fails with `profile_requires_usable_source`;
12. assert Profile remains draft and final SQL shows zero invalid active Profiles.

The test must prove serialization, not merely assert that `Promise.allSettled()` returned two outcomes.

Use a bounded test timeout so deadlock/hang fails clearly. Avoid arbitrary wall-clock sleeps as correctness evidence.

DETERMINISTIC RACE B — ACTIVE MEMBERSHIP REMOVAL VS OTHER SOURCE ARCHIVE
Keep/provide deterministic proof for the second transaction family too.

Recommended setup:
- active Profile `racing_active` associated with usable `alpha` and usable `beta`;
- removal targets `alpha`;
- concurrent Source invalidation archives `beta`.

Force:
1. association-removal transaction locks the active Profile and pauses before completing removal;
2. Source `beta` archival starts, acquires its Source-validity advisory guard, then attempts the active Profile lock and waits;
3. release the removal transaction;
4. removal validates that `beta` is still usable and commits removal of `alpha`;
5. archival resumes, re-reads the now-current Profile associations/Sources, detects that archiving `beta` would leave zero usable Sources, and rejects with `source_required_by_active_profile`;
6. final Profile remains active with usable `beta` and no invalid state.

This case is important evidence that the advisory guard does not introduce a deadlock with existing Profile-row association-removal serialization.

If current query structure makes a slightly different deterministic checkpoint cleaner, preserve the same logical interleaving and outcome.
