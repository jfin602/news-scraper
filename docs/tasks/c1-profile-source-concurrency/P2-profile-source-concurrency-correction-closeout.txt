PASS 1 — CONTRACT / EVIDENCE REVIEW
Review P1 against contracts, original Phase 1 intent, actual source, and executed evidence.

A. PRODUCT / DOMAIN SEMANTICS
Verify:
- usable Profile Source remains exactly approved + active;
- Source operational state remains irrelevant to Profile usability;
- drafts/disabled Profiles may be incomplete;
- activation/reactivation requires at least one usable Source;
- active Profile final usable association removal still rejects;
- Source unapproval/archive still rejects only when it would invalidate an active Profile;
- Profile filtering, collection trust, Article identity/provenance, Relevance, Categories, moderation, duplicates, and existing outward behavior are untouched.

B. ADVISORY LOCK OWNERSHIP
Verify the new lock helper:
- is owned by the Profile/distribution domain rather than HTTP/UI or collection code;
- uses a dedicated stable namespace distinct from Article identity and endpoint-run lock namespaces;
- derives PostgreSQL signed-bigint-compatible keys deterministically from normalized Source UUIDs;
- validates Source UUIDs rather than accepting arbitrary unbounded values;
- uses `pg_advisory_xact_lock` transaction locks;
- does not manually unlock transaction locks;
- does not use session locks, `pg_try_advisory_lock`, polling, retries, process mutexes, or one installation-global key;
- deduplicates and orders multiple Source IDs deterministically before acquisition.

C. SOURCE INVALIDATION ORDER
For Source transitions capable of making the Source unusable, prove actual order is:

`resolve stable Source identity -> acquire Source validity advisory guard -> discover/lock active Profiles -> lock/re-read relevant Source rows -> validate -> mutate`

Verify there is no path that performs active-Profile discovery before the guard and then trusts that pre-guard set.

Verify the target Source state is re-read under the transaction's real locking/synchronization rather than using an earlier stale approval/lifecycle snapshot.

D. ACTIVATION / REACTIVATION ORDER
For requested target lifecycle `active`, prove actual order is conceptually:

`lock inactive Profile -> resolve its current associated Source IDs under that Profile lock -> acquire Source validity advisory guards in deterministic order -> lock/re-read associated Source rows -> validate usable Source -> lifecycle mutation + audit`

Verify disabling does not unnecessarily acquire the validity predicate locks.

Verify the Profile association set cannot mutate behind activation while it is deriving/advising/locking Sources under the Profile row lock.

E. ASSOCIATION REMOVAL ORDER
Verify active association removal preserves its existing Profile-row/Source-row serialization and does NOT accidentally acquire the Source-validity advisory lock after owning an active Profile row.

Explicitly reason about this potential cycle:

`Source invalidation: advisory Source -> active Profile row`

versus a prohibited implementation:

`active association removal: active Profile row -> advisory Source`

The final implementation must not contain that cycle.

F. REPOSITORY / MODULE BOUNDARY
Verify:
- any new Profile-association Source-ID read lives in the Profile repository rather than raw SQL in admin routes/services;
- the repository read returns stable identity only and does not become another Source-usability authority;
- business validation remains in the application services;
- the advisory helper is not hidden inside a generic Source-row lock helper whose consumers have incompatible lock order;
- no Phase 2 consumer is forced to understand this correction's table topology or lock details.

G. TRANSACTION / AUDIT ATOMICITY
Verify:
- advisory locks are acquired inside the same real PostgreSQL transactions as the protected mutations;
- rollback releases transaction locks automatically;
- failed activation/reactivation does not write a success lifecycle audit event;
- failed active association removal does not write a success removal audit event;
- Source invalidation failures leave Source state unchanged;
- no error path manually commits partial work.

H. DETERMINISTIC LEVEL-4 PROOF
Inspect the test implementation, not just names.

Require real disposable PostgreSQL proof that deliberately controls the vulnerable ordering. The primary activation/invalidation regression must show:
1. Source invalidation owns the Source-validity guard;
2. active-Profile discovery executes while target Profile is still inactive;
3. invalidation is paused after that discovery;
4. activation starts and reaches the same guard;
5. activation cannot pass the guard before invalidation is released;
6. invalidation commits Source unusable;
7. activation resumes and rejects from current Source state;
8. final SQL shows no invalid active Profile.

A test that only starts two promises concurrently, repeats a race, sleeps, or asserts final state without controlling this ordering is insufficient.

Also require deterministic membership-removal vs other-Source invalidation proof demonstrating termination and no advisory/Profile-row deadlock.

I. TEST ISOLATION
Verify test-only barriers/wrappers:
- remain outside production source;
- preserve real Database transactions and PostgreSQL locks;
- do not mock away advisory/row locking;
- use bounded completion timeouts;
- do not rely on arbitrary sleeps as proof;
- close pools/clients/transactions before database test scope reset;
- fail clearly if PostgreSQL prerequisites are unavailable.

PASS 2 — ERROR / EDGE-CASE ADVERSARIAL REVIEW
Independently derive failure hypotheses from the final correction source. Do not satisfy this pass by listing existing tests.

At minimum challenge and disposition:
- Source invalidation obtains Source identity, then another Source state change commits before validity guard acquisition;
- activation obtains Profile row while invalidation already owns the Source advisory guard;
- invalidation owns the advisory guard while activation owns the inactive Profile row;
- activation has multiple associated Sources and another activation acquires the same Sources in opposite input order;
- duplicate Source IDs appear in lock input;
- two Source invalidations target different Sources associated to the same active Profile;
- an active Profile has exactly two usable Sources and both are concurrently invalidated;
- Source archive vs Source unapproval of the same Source;
- Source invalidation races active association removal of that Source;
- Source invalidation races active association removal of a different usable Source;
- Source invalidation races association addition to an already-active Profile;
- Source invalidation races association edits on a draft/disabled Profile;
- disabled -> active reactivation uses exactly the same predicate boundary as draft -> active;
- active -> disabled lifecycle mutation does not create an advisory/Profile cycle;
- a Source is already unapproved/archived and an equivalent no-op/invalid request occurs;
- advisory lock helper accepts malformed/non-UUID identities;
- advisory key namespace accidentally duplicates another lock domain implementation;
- multiple advisory keys are sorted by derived key in one caller and Source UUID in another;
- generic Source-row helper acquires advisory locks implicitly and changes another consumer's lock graph;
- transaction error occurs after advisory acquisition but before row locks;
- validation/audit error occurs after row locks;
- test barrier resolves too early and only appears deterministic;
- test timeout hides PostgreSQL deadlock by converting it into a generic failure without proving the lock graph;
- correction changes an API/UI/error contract even though none was required.

For each plausible concern classify it as:
- protected by source + meaningful executed evidence;
- one small bounded closeout repair/test strengthening;
- Terra High structural-refactor handoff required;
- deeper concurrency replanning/correction required.

Do not declare GREEN with an unresolved stale-discovery or deadlock concern.
