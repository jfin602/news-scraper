## Goal

Build the provider-neutral Phase 7 qualification tooling needed to exercise the existing generic PHP integration and the managed News Scraper deployment from the local Windows runner while preserving a strict remote-access boundary.

The owner has already provisioned this base transport outside the repository:

```text
Windows OpenSSH client / ssh-agent
-> SSH config alias: news-scraper-phase7
-> dedicated key identity
-> managed VPS account: news-scraper-validator
-> no password auth
-> no PTY
-> no forwarding
-> root-owned ForceCommand: /usr/local/sbin/news-scraper-phase7-validator
```

The currently installed bootstrap forced command accepts only:

```text
preflight
```

and rejects arbitrary commands. This operator-owned SSH configuration is a prerequisite, not product code.

P1 must preserve that model. It may build the repository-side client, server-helper bundle, deterministic tests, HostGator-like/shared-PHP qualification plane, and operator installation/arming instructions. It MUST NOT give Codex general SSH shell access and MUST NOT silently weaken the existing VPS hardening.

P1 is release/test tooling, not a new adapter, production API, self-host package, remote-administration feature, or customer deployment product.

## Mandatory SSH transport contract

All Codex/runner access to the managed VPS in Phase 7 must go through the configured alias:

```text
news-scraper-phase7
```

Never hard-code or fall back to the VPS IP, hostname, `deploy`, `root`, or another account.

The local client/orchestrator must invoke the transport non-interactively, equivalent to:

```text
ssh -o BatchMode=yes -o ConnectTimeout=10 -o ConnectionAttempts=1 news-scraper-phase7 <named-operation>
```

The SSH config/host-key pin remains operator-owned. P1 MUST NOT:

- run `ssh-keyscan` or modify `known_hosts`;
- modify Windows `~/.ssh/config`;
- add/remove keys from `ssh-agent`;
- use `StrictHostKeyChecking=no` or `accept-new`;
- use `ssh -t`, interactive shells, `bash`, `sh`, arbitrary quoted shell strings, `ProxyCommand`, agent forwarding, local/remote/dynamic port forwarding;
- use `scp`, `sftp`, `rsync`, or another file-transfer bypass;
- use `ssh -F NUL deploy@...`, direct IP fallback, root SSH, or the normal deployment identity;
- automatically retry SSH authentication, host-key, or connection failures.

One failed transport/preflight attempt is enough. Report the bounded failure and stop rather than triggering abuse controls such as Fail2ban.

Run exactly one bootstrap observation early:

```text
ssh -o BatchMode=yes -o ConnectTimeout=10 -o ConnectionAttempts=1 news-scraper-phase7 preflight
```

Require bounded JSON indicating the `news-scraper-validator` identity. If it fails, do not troubleshoot by weakening SSH from Codex; stop with `OPERATOR ACTION REQUIRED` and report the safe local error class.

## Build a versioned remote-validation protocol

Create the smallest repository-owned Phase 7 remote-validation client + installable server-helper bundle needed by P2/P3/P4.

The protocol must be intentionally narrower than shell access:

- every remote operation has an exact stable name;
- prefer no caller-supplied arguments. Environment/resource details should come from operator-owned server-side Phase 7 configuration rather than arbitrary SSH command text;
- if a bounded identifier argument is unavoidable, parse it as data with a strict allowlist/length grammar and never interpolate it into shell;
- never use `eval`, `bash -c "$SSH_ORIGINAL_COMMAND"`, `sh -c`, command substitution from remote input, caller-selected executable paths, arbitrary npm script names, arbitrary filesystem paths, or arbitrary SQL;
- stdout is one bounded machine-readable JSON result per invocation; stderr is bounded diagnostics only;
- neither stream may contain bearer values, Authorization headers, database URLs, environment dumps, cookies, raw response bodies, private backup contents, or secret-bearing paths;
- every result includes protocol version, operation name, outcome, and enough candidate/environment identity to prevent evidence from being attributed to the wrong deployment;
- the client rejects malformed/non-JSON/oversized remote output rather than trusting it.

Include an operation such as `capabilities` after operator installation that reports only safe protocol metadata and supported operation names. It must not expose secrets or server configuration contents.

The installed bundle must have an auditable version/hash identity derived from the P1 committed artifact. P2/P4 must be able to compare the installed protocol/bundle identity with the expected P1 handoff before trusting evidence.

## Server privilege boundary

The repository may contain installable helper scripts/config templates, but Codex must not install them through the restricted validator connection.

The intended installed shape is:

```text
sshd ForceCommand running as news-scraper-validator
-> exact operation dispatcher
-> optional exact delegated helper
-> existing News Scraper operator/runtime command
-> bounded JSON evidence
```

The operator, not Codex, installs or updates `/usr/local/sbin`, `/usr/local/libexec`, `/etc/ssh`, `/etc/sudoers.d`, private Phase 7 config, and arming state.

If delegation to the `deploy` identity is needed for an existing application command, design the narrowest possible operator-installed rule. Prefer exact helper executables/operations with no arbitrary command/path argument. Explicitly forbid:

- `sudo ALL`, `(ALL)`, a general shell, editor, interpreter REPL, package manager, service manager wildcard, or unrestricted `sudo -u deploy`;
- caller-selected commands or arbitrary executable arguments;
- environment preservation that could inject `PATH`, loader, Node/PHP config, or secret values;
- executing uncommitted/local-agent-controlled repository code on the managed VPS as a privilege shortcut.

Remote helpers may invoke only reviewed existing product/operator commands and narrow P1 qualification helpers. If a later required admin mutation cannot be performed without inventing an admin bypass or raw SQL path, report it as `operator_required`; do not smuggle admin authority into this SSH account.

## Operator-owned private configuration

Design the server-helper bundle so deployment-specific values remain outside source control.

The operator-owned configuration may identify only the resources needed for Phase 7, such as:

- expected managed repository path;
- public managed base URL;
- dedicated validation Profile key;
- approved validation Source/endpoint keys;
- paths/references to private deployment validator configuration;
- references to dedicated/disposable machine credentials without returning their plaintext;
- recovery target naming constraints;
- external qualification/fault-origin settings when appropriate.

Do not require the validator account to read the production `.env` wholesale. Prefer a narrow helper running under the existing operator identity to consume only the private values required by the exact operation and return redacted results.

No private Phase 7 config, token, key, database URL, backup, generated LKG, or arming file may be committed.

## Explicit arming for state-changing managed operations

Read-only observations and mutating qualification operations must be distinct.

Any operation capable of changing the managed deployment, database/recovery target, validation Profile, validation credential, collection state, process state, or rate-limit state must fail unless an **operator-created short-lived arm** authorizes it.

The arm must be outside the repository and unwritable by `news-scraper-validator`. At minimum it binds:

- expiration/TTL;
- exact expected committed candidate SHA;
- exact dedicated validation Profile key;
- exact disposable credential identities where implicated;
- exact approved Source/endpoint identifiers where implicated;
- explicit allowed mutation operation names.

The validator may inspect only a bounded arm status/classification. It MUST NOT create, renew, broaden, or edit the arm.

Every mutating helper must:

1. verify arm presence, expiry, candidate identity, resource identity, and allowed operation;
2. reject ordinary customer Profile/credential/Source identifiers;
3. record safe before-state;
4. perform only the named bounded action through the existing owning product/operator boundary;
5. execute deterministic cleanup/restore where the scenario owns temporary state;
6. return bounded after-state and restoration classification;
7. fail closed when cleanup cannot be proven.

The operator must always retain a separate normal `deploy`/provider-console recovery path; the validator account is never the recovery authority.

Inspect current implementation and implement only the safe operations actually needed downstream. The eventual protocol should support bounded equivalents of these capabilities where current product/operator boundaries make them safe:

### Armed managed qualification actions

Where safely possible through existing owners:

- deploy/verify a committed candidate using the existing runbook boundary;
- current backup + fresh disposable restore check;
- canonical collection of the configured approved validation endpoint;
- bounded disposable-credential rate-limit exercise;
- bounded disposable credential lifecycle/revocation check;
- legitimate validation-Profile snapshot-change exercise;
- validation-Profile disable/re-enable exercise;
- final restore-to-normal verification.

Do not implement an operation merely because it appears in this list. If the only implementation is broad shell/sudo, raw SQL, direct repository/service internals that bypass the protected control plane, or a new product debug route, mark that capability `operator_required` for P2/P4 instead.

## Qualification-only fault origin

Preserve the isolated P1 fault responder needed by later PHP failure tests.

It may provide only deterministic contract-shaped scenarios such as:

- valid bounded initial/multi-page response;
- malformed/incomplete continuation;
- `409 snapshot_changed`;
- bounded `429 rate_limited` + `Retry-After`;
- bounded `503`/transport failure.

It MUST NOT be imported/mounted into production Web/API and MUST NOT recreate Profile filtering, eligibility, duplicate handling, machine-auth policy, cursor generation, or revision algorithms.

It does not need a real bearer token and must never log/echo Authorization values. HTTPS termination remains deployment-specific; do not weaken the PHP client's HTTPS requirement.
