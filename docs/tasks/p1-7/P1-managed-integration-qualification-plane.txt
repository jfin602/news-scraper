## Goal

Build the provider-neutral Phase 7 qualification tooling needed to exercise the existing generic PHP integration as if it were installed on ordinary shared PHP hosting, including a constrained HostGator-like plane that can be run on a Linux VPS and a qualification-only fault origin for controlled downstream failure tests.

P1 is **release/test tooling**, not a new product adapter and not self-host packaging. It must not change canonical Article/Profile semantics, the v1 contract, machine authentication, synchronization/LKG behavior, local usability, or rendering behavior.

The intended qualification shape is:

```text
operator/test orchestrator
-> shared-host-like public root + separate private state/config
-> real integrations/php/bin/sync.php scheduled process
-> real FilesystemProfileStateStore / LocalProfileReader
-> real customer-style server-rendered page

and, only for controlled failure scenarios:
qualification-only fault origin
-> existing PHP DistributionClient/ProfileSynchronizer
-> existing candidate/LKG rules
```

The fault origin is never mounted into the News Scraper Web/API process and never becomes a supported distribution endpoint.

## Provider-neutral shared-PHP hosting plane

Create the smallest test/release-support implementation that can be run from a repository checkout on a Linux VPS configured to approximate ordinary shared PHP hosting.

The plane must model these constraints rather than a vendor brand:

- one public document root used by visitor HTTP requests;
- one distinct non-public state root outside that document root;
- synchronization secrets/configuration available only to the scheduled sync process;
- visitor rendering configured only with Profile key, state root, cadence, and optional stale cutoff;
- real PHP CLI execution of `integrations/php/bin/sync.php` for synchronization;
- real customer-style server rendering through the implemented local-read/presentation boundary;
- cron-like/scheduled invocation semantics separate from visitor requests;
- host-local/same-filesystem LKG assumptions rather than distributed locking;
- filesystem ownership/permission checks sufficient to detect obviously public/unwritable state placement;
- no Composer/vendor install requirement;
- no Node dependency in the visitor PHP request path. Node MAY orchestrate the qualification procedure on the VPS because this is test tooling, but the customer-facing PHP runtime itself must remain independently usable.

Prefer release/test support under `scripts/` and `test/support/` rather than adding a second production adapter. If a reusable validation module is justified, keep it under the existing operations/testing boundary and do not make it a Web route.

The qualification entrypoint must fail clearly when required prerequisites are absent. Do not silently skip because PHP, filesystem capabilities, a requested HTTPS fault origin, or another explicitly requested prerequisite is unavailable.

## Public/private and secret boundary

The plane must prove and enforce at least:

- state root is not the public document root and is not nested beneath it;
- bearer token and upstream base URL are not written into public files, generated HTML, LKG payloads, test reports, or normal visitor logs;
- visitor process execution remains valid after removing `NEWS_SCRAPER_BASE_URL` and `NEWS_SCRAPER_BEARER_TOKEN`;
- synchronization process receives the upstream settings only through private runtime configuration/environment;
- qualification output reports bounded classifications, not raw environment dumps, Authorization headers, token values, response bodies, filesystem contents, cookies, or query-bearing URLs;
- temporary probe files/directories are removed after a run;
- no qualification helper remains reachable from the ordinary customer public page unless it is explicitly running as an isolated test-only origin.

Do not solve secret handling by committing example real tokens or private deployment configuration.

## Qualification-only fault origin

Add the minimum controlled fault origin needed for P3 to exercise the real external PHP synchronizer/LKG path without corrupting or teaching fault behavior to the production News Scraper API.

The origin belongs only under test/release-support code. It MUST NOT be imported, mounted, or reachable from `src/app/web/` or the deployed News Scraper Web process.

It may use synthetic Profile/Publication/Article values and contract-shaped v1 fixtures. It should support only the bounded scenarios later required by Phase 7, for example:

- a valid bounded initial/multi-page response useful for establishing controlled traversal state;
- malformed or incomplete candidate response after a valid page;
- `409 snapshot_changed` during traversal;
- bounded `429 rate_limited` with `Retry-After` followed by a configured recovery response when useful;
- bounded `503 service_unavailable` / transport-unavailable simulation when useful.

Do not recreate the entire production API or implement Profile filtering, canonical eligibility, duplicate handling, authentication policy, cursor generation, or snapshot-revision algorithms in this fixture. It is a scripted responder used to challenge the existing PHP client/synchronizer.

The fault origin must not need a real production bearer token. If it observes an Authorization header, never log or echo it. Scenario control must be explicit, deterministic, non-secret, and incapable of affecting the real managed Web/API.

If serving it externally requires TLS termination, keep certificate/proxy provisioning deployment-specific; do not weaken `ClientConfiguration` to accept HTTP and do not add TLS/private-key material to the repository.

## Deterministic proof

Add focused deterministic tests for the qualification tooling itself. At minimum prove:

- accepted public-root/private-state layouts are classified correctly;
- state roots inside/below the public document root are rejected;
- missing PHP/required host prerequisites fail clearly rather than becoming a skip;
- visitor configuration can be constructed without upstream URL/token and does not gain them from the sync environment accidentally;
- qualification output cannot echo sentinel bearer values, Authorization headers, private config values, or raw fault-response bodies;
- the controlled fault origin produces only the explicitly supported scripted statuses/shapes and never follows/forwards to arbitrary destinations;
- malformed/second-page and snapshot-change scenarios are deterministic rather than timing-dependent;
- no production Web/API module imports the fault origin/test support;
- cleanup leaves no generated state/config probe files behind the deterministic harness;
- the existing Phase 5/6 PHP and browser regressions remain unchanged in meaning.

Use local/injected servers and temporary directories for deterministic tests. Ordinary `npm test`/`npm run check` must not require the public internet, a managed deployment, HostGator, a real external site, or real bearer credentials.

## Preserved behavior and non-goals

Preserve without semantic change:

- approved-Source collection/network-safety/normalization/idempotency/provenance behavior;
- canonical outward eligibility, Profile filtering/order/Categories/duplicate/moderation semantics;
- Phase 3 machine credential/authentication/rate behavior;
- Phase 4 v1 route/schema/cursor/revision/HTTPS/trusted-proxy behavior;
- Phase 5 PHP client, retries/restarts, per-Profile lock, candidate validation, atomic LKG activation, disable/re-enable and stale policy;
- Phase 6 `LocalProfileReader` / `LocalReadResult`, fallback renderer, escaping, direct exact `originalUrl`, and local-only visitor behavior;
- `/`, `/api/feed`, admin, Worker, migration, database, backup/recovery, and topic-independent behavior.

Do not implement:

- a new distribution API or proxy product;
- debug/fault endpoints in production;
- HostGator/cPanel-specific application branches;
- SSH/SFTP credential management as a product feature;
- Docker/Compose/self-host packaging;
- WordPress, RSS/Atom, widgets, visitor analytics, SEO tooling, delta sync, or additional adapters;
- new database schema/migrations;
- governing documentation/ADR changes.

1. a provider-neutral shared-PHP qualification plane can exercise the existing sync/read/render boundaries with public/private state separation;
