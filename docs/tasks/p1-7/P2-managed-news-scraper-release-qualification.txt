TASK: Phase 7 / P2 — Managed News Scraper release qualification

- Recommended configuration: `Terra High`.
- Task-shape classification: `Cross-cutting`.
- Specification clarity: `Explicit`.
- State coupling: `High`.
- Integrity risk: `High`.
- Concurrency: `Cross-process`.
- Security: `Sensitive`.
- Novel inference: `Moderate`.
- Model-family basis: P2 qualifies the real managed Web/Worker/PostgreSQL/distribution chain through the P1 restricted SSH validation protocol. The task spans production data, live Sources, Profiles, credentials, rate limits, snapshot pagination, recovery, perimeter behavior, and a deliberately narrow remote privilege boundary.
- Reasoning basis: High reasoning is warranted because evidence must remain tied to the actual deployed committed candidate, mutating operations must be scoped by an operator-created arm, remote failures must not trigger unsafe SSH fallbacks/retry loops, and any release blocker must be diagnosed without widening the validation account into general production authority.
- Complexity / quality floor: `High`.
- Estimated usage: `High`.
- Lower-cost alternative considered: `Terra Medium`; rejected because production-upgrade/recovery/security/live-deployment evidence now also depends on remote-operation capability/version/arming correctness and exact candidate identity.
- Escalation trigger: managed qualification would require unrestricted shell/deploy access, raw SQL/admin bypass, broad sudo, uncertain production-data mutation, a difficult credential/rate/concurrency defect, or a release blocker whose repair is not explicit from current contracts.
- Escalation target: `Terra Ultra` for explicit deeper transaction/recovery/security reasoning; higher-effort Sol only for ambiguous cross-system contract/architecture reconciliation; return `Planning needed` for material new product capability.
- Estimate confidence: `High`.
- Efficiency rationale: use one already-reviewed restricted SSH protocol to perform real managed observations, keep secrets/config server-side, stop on privilege gaps instead of improvising shell access, and leave exact final-tree Level 7/8 rerun to P4 after the runner-created P1-P3 commits are deployable.

The assigned project version is `1.7.2`.

## Goal

Qualify the real managed News Scraper side of the 2.0 release path from the local Windows runner through the P1 restricted remote-validation interface, fixing only bounded release blockers already inside the governing contract.

P2 must establish real managed evidence for:

```text
supported production state
-> current migration/schema
-> real approved Source collection
-> canonical outward/Profile state
-> machine authentication
-> real v1 pagination/revision/status behavior
-> operational telemetry + reference/perimeter behavior
```

P2 does not grant Codex normal VPS shell access and does not claim the genuinely external PHP customer-site gate. P3 owns the external-host preparation/proof; P4 independently reruns the final exact committed candidate.

## Required local-to-managed transport

The only Codex-accessible managed SSH target is the operator-provisioned Windows SSH alias:

```text
news-scraper-phase7
```

It authenticates as the dedicated `news-scraper-validator` account and is constrained by the operator-owned root-owned forced-command boundary.

P2 MUST NOT:

- use the raw VPS IP/hostname as an SSH target;
- use `deploy`, `root`, or another SSH account;
- use `ssh -F NUL` as a bypass;
- use PTY/interactive shell, `bash`, `sh`, `scp`, `sftp`, `rsync`, forwarding, ProxyCommand, agent forwarding, or arbitrary remote commands;
- alter Windows SSH config/known-hosts/ssh-agent/key material;
- alter `/etc/ssh`, `authorized_keys`, `sudoers`, user/group membership, or the installed validator bundle remotely;
- use `StrictHostKeyChecking=no`/`accept-new`;
- repeatedly retry failed SSH authentication/host-key/network attempts.

Every remote call must use the P1 local client or the equivalent non-interactive transport:

```text
ssh -o BatchMode=yes -o ConnectTimeout=10 -o ConnectionAttempts=1 news-scraper-phase7 <named-operation>
```

A failed SSH/preflight/capability call is attempted once. Then stop with `OPERATOR ACTION REQUIRED` and a bounded failure class. Do not trigger Fail2ban or weaken the SSH perimeter while troubleshooting.

## Operator-created mutation arm

Read-only observations may execute without mutation authority where the P1 protocol permits.

Every operation capable of changing deployment/process/database/recovery/Profile/credential/collection/rate state must require the operator-created short-lived arm defined by P1.

Before each mutating operation, require bounded remote proof that the arm:

- is present and unexpired;
- binds the exact currently deployed committed candidate SHA;
- binds only the dedicated Phase 7 validation Profile;
- binds only explicitly approved validation Source/endpoint identifiers;
- binds only disposable validation credential identities where implicated;
- explicitly names the requested operation.

If any identity/expiry/operation mismatches, do not attempt the action.

The validator account must never create, renew, broaden, or rewrite the arm. An expired arm is an operator gate, not permission to fall back to normal `deploy` SSH.

## Real v1 observations

Use reviewed named operations whose server-side private configuration holds required tokens. Windows/Codex must never receive bearer plaintext.

### Normal multi-page traversal

Require real managed HTTPS observations for:

- first `200` with non-null continuation;
- continuation `200`;
- requested Profile key preserved;
- stable `snapshotRevision` across unchanged traversal;
- stable ordering/no duplicate-or-missing boundary item;
- exact stored `originalUrl` values;
- governed conditional/ETag behavior where applicable;
- bounded item/page counts in returned evidence.

The helper may validate the wire shape but must not reimplement Profile filtering, cursor decoding, ordering, or eligibility.

### Invalid and revoked authentication

Using only validation resources:

- deliberately invalid credential -> bounded `401`;
- disposable valid credential works before revoke;
- revoke through the existing authorized lifecycle only;
- same credential -> bounded `401` after revoke;
- machine credential still cannot perform admin operations.

If safe revoke automation does not exist without an admin bypass, this step is `operator_required` and must be performed through the protected control plane. The remote helper can observe before/after status but cannot invent admin authority.

### Rate limit / Retry-After

Using only a disposable credential identity explicitly armed for this test, execute a bounded sequential request plan derived from the current policy.

Require:

- real `429 rate_limited`;
- positive `Retry-After`;
- bounded request count/time;
- unrelated credentials unaffected;
- no token/verifier/internal limiter state in output/log evidence.

No high-concurrency flood and no production rate-policy weakening.

### Real snapshot change

Require the legitimate sequence:

1. obtain page 1/cursor;
2. bounded authorized mutation of the dedicated validation Profile through the existing protected admin lifecycle;
3. retained cursor -> real `409 snapshot_changed`;
4. exact Profile restoration;
5. fresh traversal succeeds.

The SSH validation layer must not mutate Profile tables directly. If no safe armed helper can invoke the existing admin lifecycle without bypass, the operator performs the mutation and the remote helper observes the surrounding API statuses.

### Disabled Profile

Temporarily disable only the validation Profile through the existing admin lifecycle and require authenticated real `409 profile_disabled`, then restore/re-enable and require fresh success.

Again, operator action is required if automation would otherwise create a second admin authority.
