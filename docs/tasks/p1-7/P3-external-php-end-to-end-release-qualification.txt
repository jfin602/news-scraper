- Recommended configuration: `Terra High`.
- Task-shape classification: `Cross-cutting`.
- Specification clarity: `Explicit`.
- State coupling: `High`.
- Integrity risk: `High`.
- Concurrency: `Cross-process`.
- Security: `Sensitive`.
- Novel inference: `Moderate`.
- Model-family basis: P3 composes the real managed upstream reached through the P1 restricted SSH protocol with a genuinely external PHP sync/LKG/SSR consumer. Correctness depends on cross-host separation, secret handling, candidate/LKG atomicity, retries, browser behavior, failure recovery, and never confusing the managed VPS transport with external-host proof.

- Estimate confidence: `High`.

## Goal

Exercise and harden the complete customer integration path using the real managed News Scraper instance from P2 plus a genuinely external customer-style PHP hosting boundary, while preserving the owner-required restricted remote-access model.

Normal path:

```text
real approved Sources
-> managed collection/persistence
-> canonical eligibility / validation Profile
-> real authenticated multi-page v1 API
-> external PHP scheduled synchronization
-> complete validated atomic LKG
-> LocalProfileReader / LocalReadResult
-> customer server-rendered HTML
-> exact direct stored publisher originalUrl links
```

P3 prepares and, where the external environment is already operator-provisioned, executes this path. The final release claim still belongs to P4 against the exact committed P3 candidate after deployment.

## Managed transport is fixed

All Codex interaction with the managed News Scraper VPS continues through:

```text
news-scraper-phase7
```

using the P1 named-operation protocol only.

P3 MUST NOT use the managed VPS IP/hostname directly, `deploy`, `root`, PTY, shell, SCP/SFTP/rsync, forwarding, arbitrary remote commands, or SSH configuration/key changes. One failed SSH auth/host-key/connect attempt is enough; stop rather than retrying into Fail2ban.

The managed alias may provide upstream status, Profile lifecycle observation, fault-origin lifecycle if explicitly implemented as a P1 test helper, and bounded telemetry. It can never satisfy the **external customer host** requirement by itself.

A different directory, user, vhost, container, or PHP process on the same managed VPS is P1 preflight only, not final external evidence.

## External-host access model

The preferred automated external-host transport is a separately operator-provisioned restricted SSH alias:

```text
news-scraper-phase7-php
```

If used, it must follow the same security principles as the managed channel:

- dedicated key/account;
- pinned host key;
- public-key only;
- no PTY/forwarding;
- root/operator-owned forced command;
- named operations only;
- bounded JSON output;
- no arbitrary shell, SCP/SFTP/rsync, or caller-selected command/path;
- no automatic auth/host-key/connect retries;
- no secrets returned to Windows.

Do not reuse `news-scraper-phase7` as the external alias and do not point the external alias at the managed News Scraper host.

If the real external PHP provider does not support a safely restricted automation channel, P3 must produce an operator-run installation/qualification/evidence procedure instead. Codex MUST NOT accept unrestricted customer-host SSH merely to automate the gate.

The absence of automated external SSH is not permission to downgrade the final evidence. P4 remains BLOCKED until the real external procedure has actually been observed, either through the restricted alias or operator-produced evidence that P4 can validate.

- visitor composition uses `LocalReadConfiguration` / `LocalProfileReader` and customer/fallback renderer only;

- P1 shared-host checks pass where applicable.

Customer-owned markup may vary but must consume local-read results and preserve upstream authority/destinations.

## Required failure matrix

Every case starts from a known valid real LKG unless explicitly never-synced. Capture bounded before/after state; never edit active manifests/generation JSON manually merely to manufacture a state.

### 1. Upstream/API/sync failure

Use an isolated qualification network/origin failure where possible rather than taking the managed service down.

Require failed bounded sync, unchanged valid LKG, local visitor rendering governed by stale policy, no live visitor fallback, then successful real managed recovery sync.

If managed Web is intentionally stopped, only an explicitly armed/operator-controlled managed operation may do so, with bounded window and required restoration. Never use unrestricted SSH/service commands.

### 2. Malformed/incomplete candidate

Point only external sync process at isolated P1 fault origin returning valid initial page then malformed/incomplete continuation.

Require existing PHP validation rejection, no partial activation, exact prior real LKG preservation, no body/secret leak, continued visitor rendering, then real managed sync recovery.

### 3. Snapshot revision change

P2/managed evidence proves production API emits real `409 snapshot_changed` after legitimate Profile mutation.

P3 proves external PHP handling using either deterministic real coordinated mutation or P1 fault origin. Require candidate discard, bounded restart/retry, prior LKG preservation, and eventual real sync.

Never claim the fault origin alone proves production revision behavior.

### 4. Stale valid / configured cutoff

Use short test-specific freshness settings through supported config, not manifest timestamp editing.

Prove stale valid remains `stale_usable` and renders with no hard cutoff; configured max stale age suppresses after strict cutoff while state remains recoverable; restored settings + fresh sync recover; no stale/cutoff visitor API fallback.

### 5. Authoritative Profile disable/re-enable

Use real managed admin lifecycle, with managed observation through `news-scraper-phase7` and operator action where admin automation is intentionally unavailable:

1. active Profile + valid external LKG;
2. legitimate disable of dedicated validation Profile;
3. external sync receives real `409 profile_disabled` and local disabled state becomes authoritative;
4. page suppresses cached Articles;
5. legitimate re-enable/restore;
6. real sync succeeds;
7. rendering returns.

No adapter-side disable inference or raw DB mutation.

### 6. Invalid/revoked authentication

Use only disposable/invalid validation credential material in sync process. Require bounded `401` failure, prior LKG preserved under stale policy, not marked disabled, visitor never sees token, valid replacement recovers, no secret leak.

### 7. Rate-limit / Retry-After

P2 proves real managed `429` + `Retry-After`. P3 proves PHP retry behavior using P1 isolated short deterministic `Retry-After` sequence rather than hammering production again.

Require bounded retry timing/classification and active-state preservation.

### 8. Never-synced/unavailable

Use separate fresh external test state root. Require safe initializing/unavailable fallback with no stale Articles and no live visitor request. Do not destroy primary validation LKG.
