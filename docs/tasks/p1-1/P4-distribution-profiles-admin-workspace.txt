TASK: Phase 1 / P4 — Distribution Profiles admin workspace

PHASE SCOPE
This is Phase 1 P4. P1 owns persistence, P2 owns Profile application semantics, and P3 owns the protected Profile admin HTTP surface. This prompt adds the required administrator presentation so an authorized operator can safely create, configure, activate, disable, reactivate, and reload Distribution Profiles without changing the underlying business rules.

This is roadmap-required control-plane functionality on `main`, not an isolated `ui-polish` visual-polish task. Keep the implementation functionally complete but visually conservative and consistent with the current administration shell.

MODEL / REASONING / USAGE
- Recommended configuration: `Terra High`.
- Model-family basis: the task is a bounded but multi-state browser UI that must coordinate Profile lifecycle, nested Source associations, three filter dimensions, authoritative server errors, shared Source/Category catalog state, accessibility, responsive behavior, and existing admin workspaces; the owner explicitly raised the planned Luna configuration to the equivalent Terra tier.
- Reasoning basis: High is appropriate because browser state must remain synchronized with persisted authoritative state across create/save/association/lifecycle failures and reloads without reimplementing backend rules or breaking the existing modular admin shell.
- Complexity / quality floor: `Elevated`.
- Estimated usage: `High`.
- Lower-cost alternative considered: `Luna High`; rejected solely because the repository owner requested all planned Luna prompts in this stack be bumped to the equivalent Terra model.
- Escalation trigger: source inspection shows the existing admin shell cannot host another isolated workspace without a broader structural redesign, or the P3 API is insufficient and would require new product/application semantics.
- Escalation target: `Sol Medium`.
- Estimate confidence: `High`.
- Efficiency rationale: reuse the current modular workspace pattern, shared `api()` helper, shared Source/Category catalog, existing form/status components and CSS conventions; do not introduce a client framework, state library, design-system rewrite, or duplicate catalog/API layer.

GOAL
Add a first-class **Profiles** administration workspace that is a thin browser client over P3:

`operator interaction -> existing admin api() helper -> P3 -> P2 -> persisted authoritative Profile -> reload/render`

The UI may provide helpful local affordances, but server validation remains authoritative for all lifecycle and relationship rules.

ADMIN NAVIGATION / SHELL
Add a Profiles tab/workspace to the existing single-Publication admin navigation.

Likely files:
- `src/app/web/admin-page.ts` for workspace markup/tab/panel shell;
- `src/app/web/admin/admin.js` to register/activate the workspace;
- new `src/app/web/admin/profiles.js` for Profile behavior;
- `src/app/web/admin/admin.css` only for the minimum layout/state rules required;
- admin asset allowlisting/serving code if the current shell requires explicit asset registration.

Do not add a Publication/topic switcher.

Keep current Publication, Sources, Editorial, Articles, Operations, and other existing workspaces intact and reachable.

SHARED CATALOG
Reuse `src/app/web/admin/catalog.js` Source and Category data. Do not create a second Source/Category fetch/cache implementation for Profiles.

The Profile workspace may subscribe to or refresh the shared catalog as needed so it has current:
- Source config key;
- Source display name;
- Source approval/lifecycle status if already present in the shared Source models;
- Category config key;
- Category display name.

If the existing catalog lacks a field needed only for helpful local presentation, prefer reading it from the Profile read model or minimally extending the shared catalog from existing admin responses rather than adding a Profile-specific duplicate endpoint.

PROFILE LIST / SELECTION
The workspace must:
- load the Profile list from `GET /admin/api/distribution-profiles`;
- clearly show config key, display name, and lifecycle;
- allow selecting one Profile for editing;
- preserve selection where practical across a successful refresh;
- clear/adjust selection safely if the selected Profile is no longer returned;
- represent loading, empty, ready, and bounded error states explicitly.

Do not use database UUIDs as browser identity.

CREATE DRAFT
Provide a bounded create form with:
- immutable `configKey`;
- `displayName`;
- result limit prefilled/defaulted to 100.

Submit to `POST /admin/api/distribution-profiles` through the existing shared `api()` helper so the request-integrity header is automatic.

On success:
- add/update authoritative list state;
- select the created Profile;
- render lifecycle `draft`;
- do not allow editing the config key afterward.

On server rejection:
- show a bounded useful error near the create workflow;
- preserve entered values where practical;
- do not pretend the Profile exists.

PROFILE CONFIGURATION
For the selected Profile provide editable:
- display name;
- result limit.

Save through `PUT /admin/api/distribution-profiles/:profileKey/configuration`.

After success, replace local state with the returned authoritative Profile object rather than mutating only the fields the UI expected to change.

Do not include `configKey` in the configuration payload.

SOURCE ASSOCIATION EDITOR
For the selected Profile, show existing Source associations and allow the operator to:
- choose an unassociated Source by immutable Source config key;
- add an association;
- edit an existing association;
- remove an association.

For each association expose all three Phase 1 filter dimensions:
- `includeAnyPhrases`;
- `excludeAnyPhrases`;
- `categoryConfigKeys`.

Phrase UX may use one phrase per line or another simple bounded editor that serializes deterministically to arrays. Do not introduce a query-language/expression editor.

Category filters should use the shared Category catalog with accessible checkbox/multi-select controls. Store/send immutable Category config keys only.

Source identity must come from the association path/selected immutable Source key, not an editable hidden UUID.

Association save uses:

`PUT /admin/api/distribution-profiles/:profileKey/sources/:sourceKey`

Association removal uses:

`DELETE /admin/api/distribution-profiles/:profileKey/sources/:sourceKey`

After every successful association mutation, replace the selected local Profile from the returned authoritative Profile response.

FILTER HELP / SEMANTIC CLARITY
Make the UI text concise but accurate:
- include phrases mean match any configured include phrase;
- exclude phrases mean exclusion wins;
- Category choices restrict by configured Categories;
- empty dimensions impose no restriction;
- these are distribution Profile filters, not Source RSS/Atom collection admission filters.

Do not expose regex/fuzzy/semantic/AI/ranking terminology as available controls.

LIFECYCLE CONTROLS
Render current lifecycle prominently and expose only actions that make sense for that state:
- draft: `Activate`;
- active: `Disable`;
- disabled: `Reactivate`.

Use `PUT /admin/api/distribution-profiles/:profileKey/lifecycle` with the exact P3/P2 request shape.

The UI may disable the Activate button when it locally sees no currently approved+active associated Source, but this is advisory only. It must still render/handle the authoritative `profile_requires_usable_source` server conflict because Source state can change concurrently.

Do not expose `active -> draft`, `disabled -> draft`, `draft -> disabled`, or Profile deletion.

SERVER ERROR HANDLING
Handle bounded P3 errors without losing the operator's entire workspace context.

At minimum provide useful messages for:
- invalid request/input;
- Profile key conflict;
- missing Profile/Source/association/Category;
- invalid lifecycle transition;
- Profile requires usable Source;
- generic dependency/unexpected failure.

If a mutation fails because state changed concurrently, keep the current context visible and provide an obvious Refresh/reload action. Do not silently overwrite local edits with guessed state.

Do not expose raw JSON errors, SQLSTATE, constraints, stack traces, or request headers to the operator.

REFRESH / RELOAD
The workspace must provide an explicit refresh and participate correctly in the shell's global refresh behavior.

A fresh load/reload of `/admin` followed by Profiles activation must reproduce exact persisted state returned by the server:
- Profile fields;
- lifecycle;
- Source associations;
- phrase order/content;
- Category filters.

Do not rely on unsaved browser local storage for Profile configuration.

ACCESSIBILITY / RESPONSIVE BASELINE
Use existing admin patterns for labels, headings, focus, status, and controls.

At minimum:
- every input/select/textarea/button has an accessible name;
- grouped association/filter controls have clear headings/labels;
- keyboard-only navigation can create/select/edit/save/activate/disable without pointer-only behavior;
- mutation/result/error status is available in meaningful text;
- visible focus behavior from existing CSS is preserved;
- narrow/mobile viewport does not force unusable horizontal overflow for the core Profile form/association editor;
- long Profile/Source/Category labels and phrases wrap safely;
- destructive-looking association removal/disable actions are visually distinguishable but do not require a broad design redesign.

ADMIN ASSET / CSP SAFETY
Continue using external same-origin module files and the existing CSP. Do not introduce inline executable script, `unsafe-inline`, external client dependencies, remote assets, or runtime eval/template execution.

All operator-visible text from Profile/Source/Category state must be inserted through safe DOM text/value APIs following current admin code patterns, not interpolated into unsafe HTML.

`Profiles tab -> createProfilesWorkspace() -> admin workspace activation -> browser proof`

`shared Source/Category catalog -> association editor choices -> no duplicate catalog/API proof`

`create draft form -> P3 POST -> returned Profile -> selected authoritative state -> browser proof`
