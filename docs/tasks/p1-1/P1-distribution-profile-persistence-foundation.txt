TASK: Phase 1 / P1 — Distribution Profile persistence foundation

PHASE SCOPE
This is Phase 1 P1 for the active post-1.0 / 2.0 roadmap. The accepted development baseline is `1.1.0`. Establish the permanent persisted Distribution Profile configuration boundary that later Phase 1 administration and Phase 2 distribution-read work can consume without knowing SQL/table topology.

This prompt owns schema, validation vocabulary, repository persistence/readback, production-forward migration proof, and backup/restore coverage. It does not own Profile lifecycle commands, admin HTTP/UI, Article selection, canonical distribution eligibility, or the permanent distribution API.

- Estimate confidence: `High`.
- Efficiency rationale: add one narrow Profile persistence module and one additive migration; reuse established UUID/config-key/category/source conventions and existing database/recovery harnesses rather than introducing ORM, generic configuration storage, JSON expression engines, or tenancy abstractions.

GOAL
Create one topic-independent, installation-owned Profile persistence boundary:

`validated Profile configuration -> additive relational persistence -> complete Profile aggregate by immutable config_key -> later application/read consumers`

A later consumer must be able to load a Profile and every Source association/filter it owns without selecting child tables directly or reconstructing Profile persistence rules.

PERSISTED MODEL
Add one additive production migration named exactly:

`migrations/0015_distribution_profiles.sql`

Do not modify migrations `0001` through `0014`.

Implement the following logical schema with ordinary relational tables rather than a generic JSON configuration blob:

1. `distribution_profiles`
- UUID primary key;
- immutable installation-wide `config_key`;
- bounded mutable `display_name`;
- lifecycle constrained to `draft`, `active`, or `disabled`;
- bounded integer result/history limit;
- created/updated timestamps.

2. `distribution_profile_sources`
- first-class Profile↔Source association;
- one row per Profile/Source pair;
- real FKs to `distribution_profiles` and `sources`;
- no duplicated Source display/site/approval/configuration columns;
- no Publication/customer/tenant key.

3. `distribution_profile_source_phrases`
- association-owned phrase rows;
- distinguish `include` and `exclude` kinds with a bounded enum/check;
- deterministic zero-based or one-based position owned by the association;
- ordered uniqueness appropriate to the chosen representation;
- real FK to the association.

4. `distribution_profile_source_categories`
- association-owned Category references;
- real FK to `categories`;
- deterministic persisted position so round-trip ordering is stable;
- one Category at most once per association.

Use restrictive relationship behavior where retained configuration should block destructive removal. Do not cascade-delete Sources or Categories from Profile operations. Child Profile-owned rows may cascade from their Profile/association owner where that does not destroy peer domain resources.

PROFILE FIELD BOUNDS
Use the existing config-key convention:
- `config_key`: 1–100 characters and the established lowercase underscore-delimited shape;
- enforce immutability in PostgreSQL with a Profile-specific trigger/function or a safely shared trigger design that does not alter existing semantics.

Use these Phase 1 implementation bounds:
- `display_name`: trimmed 1–200 characters;
- result/history limit: integer 1–1000;
- default result/history limit: exactly 100;
- include phrase count: 0–64;
- exclude phrase count: 0–64;
- each phrase: trimmed 1–512 characters and no Unicode control characters;
- Category key count: 0–64;
- duplicate phrases inside the same list are invalid case-insensitively;
- duplicate Category config keys are invalid;
- the same literal phrase MAY appear in both include and exclude lists because later filtering semantics explicitly say exclusion wins;
- empty arrays mean no restriction for that dimension.

These are deterministic configuration bounds only. Do not implement matching against Articles here.

CONFIGURATION MODULE
Add the narrow topic-independent configuration module under:

`src/distribution/profiles/configuration.ts`

It should own exported types/constants/normalizers needed by the repository and later administration layer, including at minimum:
- Profile lifecycle type/values;
- default and maximum result limit constants;
- Profile create/configuration normalization primitives;
- association filter normalization;
- deterministic duplicate detection and trimming/bounds;
- standard immutable config-key normalization by reuse of the existing source/config-key authority rather than a conflicting second shape.

Do not make this module depend on Express, the admin UI, Article SQL, public feed logic, Source collection admission filtering, or Phase 2 read-model semantics.

REPOSITORY BOUNDARY
Add:

`src/distribution/profiles/repository.ts`

Expose the smallest complete persistence boundary required by P2 and Phase 2. Naming may adapt to established repository conventions, but there MUST be one obvious public read such as:

`findDistributionProfileByConfigKey(executor, configKey)`

returning one complete aggregate containing:
- Profile UUID;
- immutable `configKey`;
- mutable `displayName`;
- lifecycle;
- result limit;
- created/updated timestamps;
- every Source association in deterministic order;
- associated Source stable UUID/config key/display name;
- associated Source approval state and lifecycle state needed by later activation/read validation;
- ordered `includeAnyPhrases`;
- ordered `excludeAnyPhrases`;
- ordered `categoryConfigKeys`.

Also expose narrowly scoped repository mutation primitives sufficient for P2 to create a draft, update mutable Profile state, replace/remove Source associations/filters, lock Profiles/Sources, and persist lifecycle transitions transactionally without embedding business rules here. Keep application validation in P2.

Repository functions must:
- use parameterized SQL;
- map database rows defensively;
- return immutable/read-only aggregate values following current repository style;
- keep Profile table topology private from HTTP/UI/Phase 2;
- not implement Article matching or canonical outward eligibility.

PERSISTENCE SEMANTICS
Prove at database level:
- Profile `config_key` is unique and immutable;
- multiple Profiles can exist without implying multiple Publications;
- multiple Profiles may reference the same Source;
- one Profile cannot associate the same Source twice;
- a Source association cannot reference a missing Source;
- a Category filter cannot reference a missing Category;
- deleting a Category referenced by a Profile remains prevented by FK integrity;
- Source and Category records are never duplicated into Profile-owned rows;
- exact phrase/category ordering survives create/read/reload;
- replacing association filters cannot leave partial child state if a statement/constraint fails inside a transaction;
- no Article, observation, duplicate, Relevance, Source collection, endpoint, or Publication row is mutated by Profile repository operations.
