PHASE CLOSEOUT SCOPE
This is the sole final closeout prompt for Phase 1 — Distribution Profile foundation. P1–P4 should have established production-safe Profile persistence, transactional lifecycle/application authority, protected admin HTTP controls, and the Profiles admin workspace.

This prompt is an independent final review and evidence gate. It may repair only a genuinely bounded unambiguous Phase 1 defect/test gap under the rule below. It must not become a fifth feature implementation task, a broad refactor phase, or an excuse to pull Phase 2 distribution-read behavior forward.

A GREEN P5 does not perform the roadmap `/closeout` transition to `1.2.0`. After human review accepts this closeout and its durable validation artifact, the normal conversational `/closeout` owns the package-version-only transition to the Phase 2 baseline.

- Escalation target: deeper explicit issues use the minimum adequate Terra High/Terra Ultra or higher-effort Sol according to repository policy; meaningful behavior-preserving structural refactors use the mandatory Terra High remediation handoff below.
- Estimate confidence: `High`.

PASS 1 — CONTRACT / EVIDENCE REVIEW
Review the implementation against every governing Phase 1 requirement and explicitly record each disposition.

A. PRODUCT / DOMAIN BOUNDARY
Verify:
- Profiles are installation-owned peer resources to Sources, not Publications/customers/tenants;
- no Publication UUID/slug/FK/scope was introduced for Profiles;
- Profile filtering remains configuration only in Phase 1 and does not alter Source trust, collection, Article identity, provenance, Relevance, Categories, moderation, duplicate state, or existing outward behavior;
- no indie-author/client-specific behavior entered shared engine/UI code;
- Source configuration/collection remains singular rather than duplicated into Profile state.

B. PERSISTENCE / MIGRATION
Verify:
- exactly one justified additive Profile migration follows `0014`;
- supported migrations `0001`–`0014` were not rewritten/squashed/reordered;
- Profile config key is unique and database-enforced immutable;
- display/lifecycle/result/filter bounds are deterministic and consistent between application normalization and PostgreSQL where applicable;
- Profile↔Source and Profile↔Category relationships use real peer FKs and safe delete behavior;
- ordered phrases/Category filters reload deterministically;
- P1 repository exposes one complete Profile aggregate by immutable config key containing every field Phase 2 needs to interpret Profile configuration without child-table SQL.

C. LIFECYCLE / RELATIONSHIP AUTHORITY
Verify:
- creation always yields draft;
- supported transition matrix is draft→active, active→disabled, disabled→active;
- activation requires at least one associated Source with approval=`approved` and lifecycle=`active`;
- Source operational state is not Profile usability;
- active association removal cannot remove the final usable Source;
- Source unapproval/archive cannot leave any active Profile without another usable Source;
- draft/disabled Profiles may be incomplete;
- all multi-resource changes are transactional;
- Category deletion uses retained FK integrity and existing `category_in_use` semantics;
- Profile deletion was not introduced.

D. CONCURRENCY
Inspect the actual lock order and race tests. Prove:
- one global Profile→Source row-lock ordering is consistently observed wherever both resources participate;
- Source-side invalidation checks re-read state under locks rather than trusting stale pre-lock state;
- activation/removal and Source unapproval/archive races terminate without deadlock in real PostgreSQL evidence;
- committed state never contains an active Profile with zero approved+active associated Sources.

E. AUDIT HISTORY
Verify:
- Profile audit records reuse governed append-only audit storage rather than a parallel history subsystem;
- target type/actions are bounded and stable;
- material Profile commands commit audit + mutation atomically;
- failed/rolled-back commands produce no success audit row;
- prior/new JSON remains bounded and does not dump arbitrary secrets/unbounded state.

F. ADMIN HTTP
Verify:
- only the approved `/admin/api/distribution-profiles` control-plane routes exist;
- no Profile business logic or SQL exists in Express routes;
- existing admin enablement/request-integrity/JSON/no-store/security middleware applies;
- known application failures map to bounded 400/404/409 classes;
- unknown errors do not leak SQL/stack/secrets;
- no `/api/v1/distribution/...` route or machine auth was introduced.

G. ADMIN WORKSPACE
Verify through source and browser evidence:
- Profiles workspace is reachable without breaking existing workspaces;
- create/configure/association/filter/lifecycle flows use only P3 plus shared Source/Category catalog;
- server responses replace local state authoritatively;
- server conflicts remain visible without corrupting workspace state;
- refresh/hard reload reconstructs exact configured state;
- accessible names/keyboard/narrow-viewport behavior is meaningful;
- no Article selection preview/query logic was smuggled into JavaScript.
