TASK: Phase 1 / P3 — Protected Distribution Profile administration API

PHASE SCOPE
This is Phase 1 P3. P1 owns Profile persistence; P2 owns Profile lifecycle, cross-resource validation, transaction boundaries, concurrency protection, and audit semantics. This prompt exposes that already-complete application authority through the existing protected administrator HTTP perimeter.

Keep the HTTP layer thin. Do not add Profile SQL, lifecycle logic, Source usability rules, Category validation, audit logic, or concurrency handling to Express routes.

MODEL / REASONING / USAGE
- Recommended configuration: `Terra Medium`.
- Model-family basis: the task is bounded and explicit but touches a security-sensitive admin perimeter, nested resource routing, bounded error translation, production composition, and preserved request-integrity behavior; the owner explicitly raised the planned Luna configuration to the equivalent Terra tier.
- Reasoning basis: Medium is sufficient because P2 must already own all business rules and transaction semantics, while this prompt should remain a conventional adapter over established middleware and route-registration patterns.
- Complexity / quality floor: `Elevated`.
- Estimated usage: `Moderate`.
- Lower-cost alternative considered: `Luna Medium`; technically adequate by source inspection, but intentionally not used because the repository owner requested all planned Luna prompts in this stack be bumped to the equivalent Terra model.
- Escalation trigger: source inspection reveals Profile HTTP must make new security-boundary decisions, duplicate application logic because P2 is incomplete, or alter the existing Cloudflare/request-integrity architecture rather than simply register routes behind it.
- Escalation target: `Terra High`.
- Estimate confidence: `High`.
- Efficiency rationale: follow the existing Source/Editorial route registrar and centralized admin security middleware; add one router plus production composition and focused HTTP tests without introducing a new API framework or security layer.

GOAL
Expose one stable protected administrator HTTP surface for Distribution Profiles:

`admin request -> existing admin perimeter/request integrity -> thin Profile route -> P2 service -> bounded JSON response`

The route layer owns HTTP parsing/status/serialization only.

ROUTE SURFACE
Add:

`src/app/web/distribution-profile-administration-router.ts`

Register exactly this Phase 1 control-plane surface, adapting parameter helper names only as needed:

`GET /admin/api/distribution-profiles`

`POST /admin/api/distribution-profiles`

`GET /admin/api/distribution-profiles/:profileKey`

`PUT /admin/api/distribution-profiles/:profileKey/configuration`

`PUT /admin/api/distribution-profiles/:profileKey/lifecycle`

`PUT /admin/api/distribution-profiles/:profileKey/sources/:sourceKey`

`DELETE /admin/api/distribution-profiles/:profileKey/sources/:sourceKey`

Do not add `DELETE /admin/api/distribution-profiles/:profileKey`.

Do not add any `/api/v1/distribution/...` route in this prompt.

HTTP METHOD / RESPONSE SEMANTICS
Use established admin conventions:
- list/get reads: `200`;
- Profile creation: `201`;
- successful configuration/lifecycle/association mutation: `200` with the resulting complete Profile read model;
- association removal: prefer `200` with the resulting complete Profile read model so P4 can immediately render authoritative state; do not invent a separate partial representation solely for DELETE.

Use JSON envelopes consistently, such as:
- `{ profiles: [...] }`;
- `{ profile: ... }`.

Do not expose internal UUIDs if P2's admin read model intentionally omits them.

ERROR TRANSLATION
Translate the P2 bounded error vocabulary consistently. At minimum:
- `invalid_request` -> `400`;
- `category_not_found` -> `400`;
- `profile_not_found` -> `404`;
- `source_not_found` -> `404`;
- `profile_association_not_found` -> `404`;
- `profile_config_key_conflict` -> `409`;
- `profile_invalid_lifecycle_transition` -> `409`;
- `profile_requires_usable_source` -> `409`.

If P2 finalized slightly different stable error-code names, use those exact names and preserve the same semantic status classes.

Do not translate unknown programming/database errors into a misleading `400`. Let the established bounded dependency/error middleware or route convention handle unexpected failures without leaking SQL, stack traces, connection details, constraint names, or secrets.

ADMIN PERIMETER
Reuse the current centralized admin route/middleware stack. Do not build another CSRF/session/auth middleware for Profiles.

Prove:
- when admin is disabled, the Profile page/API surface is not registered/exposed and returns the same generic unavailable behavior as other admin routes;
- safe GET reads follow existing admin route behavior;
- POST/PUT/DELETE mutations require the existing `X-News-Scraper-Admin-Request` integrity header/value;
- mutation JSON content type/body size/invalid JSON behavior remains centralized and unchanged;
- Profile routes inherit current no-store/security headers;
- no Cloudflare identity or native login/session logic is introduced in the application;
- machine distribution authentication remains completely separate and unimplemented.

REQUEST PARSING
Pass `request.body` and path keys directly to the P2 service after only the minimal path extraction used by existing route modules. P2 remains responsible for exact body shape/field validation.

Do not duplicate P2's config-key normalization or filter validation in the router.

Do not accept query-string mutation semantics or Source/Category selectors that bypass the P2 command shapes.

PRODUCTION COMPOSITION
Wire the P2 service into the Web process using the same dependency composition style as existing admin services:
- instantiate with the application database in `src/app/web/main.ts` or the current production composition owner;
- register the new router through the existing admin route registrar mechanism;
- preserve Web/API rule that Source collection never runs inline.

Avoid growing `create-app.ts` with Profile-specific business logic. If the current composition uses an array/list of admin route registrars, extend it narrowly.
