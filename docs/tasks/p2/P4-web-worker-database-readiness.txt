CURRENT PROCESS CONTRACTS TO PRESERVE
Web currently:
- parses Web config;
- starts an Express listener;
- emits `web.listening`;
- exposes `/health/live` and `/health/ready`;
- performs idempotent signal-triggered server shutdown;
- emits `web.stopped` on clean shutdown.

Worker currently:
- parses common runtime config;
- starts an importable runtime with an explicit keepalive/lifecycle;
- emits `worker.ready` after startup;
- remains alive until shutdown;
- performs idempotent shutdown;
- emits `worker.stopped` on clean termination;
- does not expose a Worker HTTP health server.

P4 must extend these contracts rather than replace them with a second architecture.

LOCKED / PRESERVED BEHAVIOR
- Web/API and Worker remain independently runnable process roles.
- Web/API must not perform Source collection inline.
- Worker must not require Web/API to be running.
- Do not add a Worker HTTP health server.
- Shared DB behavior must be consumed through the canonical P2 `src/database` boundary; do not create Web-specific or Worker-specific pools/transaction wrappers.
- Process startup must not run migrations automatically.
- Shared engine/process code remains topic independent.
- Do not add domain schema/persistence, collection, jobs, scheduler, Sources, Articles, or admin behavior.
- Secrets/raw PostgreSQL errors/credential-bearing connection strings must not appear in process output.

DATABASE READINESS DEFINITION
A process database dependency is ready only when:
1. `NEWS_SCRAPER_DATABASE_URL` is valid;
2. PostgreSQL is reachable through the shared database boundary;
3. the database migration/schema status from P3 is current and compatible with the repository migration set.

Reachability alone is not enough. A reachable database with an uninitialized ledger, pending migration, checksum mismatch, or missing-local/applied migration history must not be advertised as current/ready.

The readiness check itself must be non-mutating. It must not create the migration ledger, apply migrations, alter schema, or repair history.

WEB APP DEPENDENCY INJECTION
Refactor `createWebApp` (or introduce the smallest equivalent app construction boundary) so readiness is injected rather than imported from process-global mutable database state.

The app-level readiness abstraction should be narrow enough for deterministic tests to supply a fake ready/unready dependency without PostgreSQL.

Do not make ordinary Web component tests spin up PostgreSQL merely to exercise HTTP semantics.

WEB `/health/live`
Preserve liveness as process/server health:
- no database ping or migration query;
- HTTP 200 when the Web process/listener is responsive;
- deterministic safe JSON body retaining the established `role: 'web'` identity;
- `Cache-Control: no-store`;
- database outage must not make this endpoint fail merely because the DB is down.

WEB `/health/ready`
Make readiness dependency-aware.

Success:
- database ping succeeds;
- schema/migration compatibility is current;
- HTTP 200;
- deterministic bounded JSON indicating ready and Web role.

Failure:
- database unreachable OR schema not current/compatible;
- HTTP 503;
- deterministic bounded non-ready body;
- no raw PostgreSQL error, stack trace, database URL, credentials, migration SQL, or sensitive environment data.

The exact JSON shape can evolve minimally, but existing consumers/tests for successful `status: 'ready', role: 'web'` should be preserved if practical rather than changed gratuitously.

WEB PROCESS STARTUP / SHUTDOWN
Startup behavior:
- parse Web + required DB configuration before listener startup;
- malformed/missing DB configuration fails predictably before listening and emits only safe startup failure output;
- a syntactically valid DB URL whose server/database is temporarily unavailable should still allow the Web HTTP listener to start so `/health/live` remains operational and `/health/ready` can report 503;
- do not require DB connectivity as a pre-listen gate for Web.

Shutdown ownership:
1. stop accepting/drain Web server using existing lifecycle boundary;
2. close the owned database pool;
3. emit clean `web.stopped` only after owned resources are closed;
4. repeated/concurrent shutdown signals remain idempotent;
5. startup failure after a DB object has been created must close it before process completion.

Do not add retry loops/backoff.

WORKER STARTUP READINESS
Worker readiness is different from Web liveness/readiness because Worker has no health HTTP server.

Before `worker.ready`, the real Worker entrypoint/runtime must prove:
- application DB config valid;
- PostgreSQL ping succeeds;
- migration/schema state is current.

If any dependency validation fails:
- never emit `worker.ready`;
- emit bounded safe `worker.start_failed` or equivalent established failure event;
- exit nonzero;
- close any DB/runtime resources already created;
- do not expose raw PostgreSQL details or credentials.

Worker must still start without Web host/port configuration and without a Web process running.

WORKER RUNTIME / SHUTDOWN
Extend the importable Worker runtime/bootstrap so it owns the DB lifecycle explicitly.

Requirements:
- preserve existing keepalive behavior after readiness;
- preserve idempotent `shutdown()` contract;
- close database pool as part of shutdown;
- close keepalive resources;
- resolve `stopped` only after owned shutdown work completes;
- repeated/concurrent shutdown requests return/share the same logical shutdown work;
- do not introduce a second Worker lifecycle path.

DETERMINISTIC UNIT / INTEGRATION TEST STRATEGY
After P4, real process success with full dependencies genuinely requires PostgreSQL. Do not add `NODE_ENV=test`, special environment switches, or production safety bypasses that skip database readiness just to keep old tests green.

Instead:
- inject fake readiness/database dependencies into app/runtime component tests;
- keep ordinary Web HTTP tests deterministic without PostgreSQL;
- keep ordinary Worker runtime lifecycle tests deterministic with an injected fake dependency where appropriate;
- preserve malformed configuration process-negative tests that fail before DB contact when they remain meaningful;
- move/add true DB-backed real-entrypoint success/failure behavior under `test:db`.

ORDINARY WEB TESTS

ORDINARY WORKER TESTS

- Worker remains independent of Web-specific config.

REAL POSTGRESQL / PROCESS TESTS
Use P1 disposable databases and P3 migrations to establish Level 4 evidence.

Web real-process cases:
- migrated/current disposable DB: real Web entrypoint listens; `/health/live` 200; `/health/ready` 200; clean signal shutdown closes resources and exits zero;
- syntactically valid but unavailable/nonexistent application DB: real Web still listens; `/health/live` 200; `/health/ready` 503; clean shutdown remains possible;
- reachable but uninitialized/pending/incompatible DB: liveness 200; readiness 503;
- synthetic credential-bearing DB URL in failure scenario is not printed to stdout/stderr.

Worker real-process cases:
- migrated/current disposable DB: real Worker emits `worker.ready`, remains running, and shuts down cleanly;
- malformed/missing DB config: no ready event, safe startup failure, nonzero exit;
- unreachable/nonexistent DB: no ready event, safe startup failure, nonzero exit;
- reachable but uninitialized/pending/incompatible DB: no ready event, safe startup failure, nonzero exit;
- synthetic credential-bearing connection failure does not leak the secret;
- Worker starts successfully without Web process and without Web host/port variables when its DB is ready.

Avoid arbitrary sleeps; reuse/better-factor the existing process line/exit waiting helpers or introduce test-only helpers if needed. Keep process-test helpers out of production source.
