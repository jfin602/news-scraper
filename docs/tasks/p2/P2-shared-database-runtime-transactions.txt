DATABASE RUNTIME BOUNDARY
Recommended ownership:
- `src/database/database.ts`

Use one pool-backed database object per application process. Avoid exposing global mutable pool state.

The public boundary should remain narrow and future-consumer-friendly. It should support at least:
- parameterized query execution;
- `ping()` / connectivity probe using a tiny real query such as `SELECT 1`;
- `transaction(work)`;
- idempotent `close()` / pool shutdown.

The exact TypeScript interface names may differ, but future repositories/services should not need to own pool construction or transaction boilerplate themselves.

Pool requirements:
- create the pool from the validated application database configuration;
- handle idle-pool/client errors so they do not become unhandled EventEmitter failures;
- any surfaced/loggable database error representation must be safe and bounded;
- `close()` must drain/end the pool and be safe under repeated or concurrent calls;
- ownership should be explicit enough for P4 to close resources on process shutdown/startup failure.

Do not add retries/backoff in Phase 2. A failed query/ping should fail truthfully.

TRANSACTION CONTRACT
Implement one canonical transaction helper using one checked-out PostgreSQL client for the entire transaction.

Required sequence:
1. acquire a client from the pool;
2. execute `BEGIN`;
3. execute the supplied callback using that same client's query interface;
4. `COMMIT` when the callback succeeds;
5. on callback/query failure, attempt `ROLLBACK`;
6. preserve/rethrow the original failure unless a more severe rollback/connection failure must be represented safely;
7. release the client in `finally` in all cases.

Do not implement transactions with `pool.query()` for BEGIN/COMMIT/ROLLBACK because transaction state is connection-scoped.

Expose only the smallest transaction-scoped query surface needed by future persistence code rather than leaking arbitrary pool lifecycle operations into the callback.

FAILURE HANDLING
Tests and implementation must consider:
- connection acquisition failure;
- callback/query failure;
- rollback path;
- client release after success and failure;
- pool shutdown with no leaked clients;
- operations after close failing predictably according to the chosen boundary;
- safe handling of credential-bearing URLs in configuration/error tests.

Do not catch-and-ignore PostgreSQL failures merely to keep the application apparently healthy.
