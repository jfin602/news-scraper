CURRENT OBSERVED DEFECT / HIGH-CONFIDENCE SOURCE DIAGNOSIS
A Windows invocation of `npm run test:db` was observed to execute the database runtime, disposable-database, and migration tests successfully and then stop producing results before the DB-backed process-readiness tests completed.

Inspect the current implementation rather than assuming the diagnosis is automatically correct, but note the current source discrepancy:
- `test/database/process-readiness.test.ts` uses a Windows-only IPC channel to emulate signal delivery to real Web/Worker child entrypoints;
- that test currently waits for child exit after sending its synthetic termination signal without releasing the Windows IPC channel;
- the older Phase 1 Web/Worker process integration tests explicitly disconnect IPC before awaiting final exit;
- current `waitForExit` helpers are unbounded, so a leaked IPC/resource handle can freeze the selected suite indefinitely rather than fail clearly.

Treat the missing IPC release as the primary suspected regression introduced at the P4 DB-process test boundary. Confirm by tracing and, where possible, reproducing the focused test before finalizing the fix. If another cause is discovered, fix the smallest correct owning boundary and report why the planned diagnosis differed.

WINDOWS PROCESS-TEST SUPPORT BOUNDARY
Prefer a small shared TEST-ONLY child-process helper rather than maintaining three nearly identical copies of Windows IPC/signal/wait logic.

Expected ownership:
- create a shared helper under `test/support/` (for example `test/support/process.ts`, exact name may adapt to current conventions);
- consume it from the existing real Web/Worker process integration tests and the DB-backed process-readiness tests;
- keep all Windows IPC emulation and process-test-only lifecycle mechanics outside production `src/`.

The shared helper should provide the smallest useful primitives for current consumers, such as:
- spawning a Node Web/Worker entrypoint with controlled environment;
- Windows IPC signal bridging while retaining real POSIX signal behavior on non-Windows platforms;
- waiting for one structured stdout/stderr JSON event with a bounded timeout;
- sending the established graceful termination action;
- disconnecting the Windows IPC channel at the correct lifecycle point;
- waiting for process exit with a bounded timeout;
- final cleanup that can force-kill only after a test is already failing/finishing cleanup.

Do not invent a generic subprocess framework beyond these current needs.

GRACEFUL SHUTDOWN PROOF MUST REMAIN REAL
Do NOT 'fix' the hang by simply killing the Web/Worker process after sending termination.

For a successful graceful-shutdown case, the test must still prove the actual application lifecycle:
1. child reaches expected ready/listening state;
2. register/await the expected `web.stopped` / `worker.stopped` lifecycle evidence where applicable;
3. deliver the graceful termination action using the established cross-platform mechanism;
4. observe the real stopped event;
5. release Windows test IPC where applicable;
6. observe actual child process exit within a bounded timeout;
7. assert the expected zero exit.

For startup-failure cases:
1. observe the safe `*.start_failed` event;
2. prove no forbidden ready event where applicable;
3. release Windows IPC where applicable;
4. observe actual nonzero process exit within a bounded timeout.

If a child does not stop/exit within the bound, reject/fail with a useful lifecycle-specific error. A timeout may trigger cleanup in `finally`, but cleanup must never turn the failed graceful-shutdown assertion into a passing test.

NO ARBITRARY SLEEPS
Do not add fixed sleeps to work around lifecycle races. Use emitted events, exit events, IPC state, bounded timers, and explicit cleanup.

CONTROLLED CHILD ENVIRONMENT
Current process tests often start from `...process.env`. Preserve legitimate inherited environment where useful, but make per-test removals deterministic.

The shared spawn/environment helper must support explicit removal semantics, e.g. when a test passes `NEWS_SCRAPER_DATABASE_URL: undefined` or another explicitly absent variable, that key must be deleted from the child environment rather than accidentally inherited from the developer's PowerShell session.

This is important after local `.env` support because developers may also have database values exported in their parent shell. Tests that claim a variable is missing must create a child where it is genuinely missing.

Do not globally scrub unrelated environment variables unless required. Make explicit test overrides/removals authoritative.

OPTIONAL LOCAL .ENV COMMAND CONTRACT
The project already requires a Node 24.12+ runtime. Use Node's native optional env-file CLI support; do not add `dotenv` or another dependency solely for this behavior.

For environment-requiring local/runtime commands, make root `.env` optional using the equivalent of:
- `node --env-file-if-exists=.env ...`

Apply this to the command boundary for:
- `npm run test:db`
- `npm run db:migrate`
- `npm run start:web`
- `npm run start:worker`

The exact package script strings should remain simple and cross-platform.

Node's env-file behavior must preserve this precedence:
1. explicit process/shell environment value wins;
2. otherwise optional `.env` supplies the value when present;
3. then the existing typed configuration parser validates `process.env`.

Do not add application-level dotenv imports or a second configuration path inside Web, Worker, migration, or database modules.

ORDINARY DETERMINISTIC SUITES MUST NOT AUTO-LOAD .ENV
Do NOT add automatic `.env` loading to:
- `npm test`
- `npm run test:unit`
- `npm run test:integration`
- `npm run check`
- format/lint/typecheck commands.

Those commands may naturally inherit variables already present in the caller's process environment, but they must not become coupled to the presence/content of the repository-local `.env` file.

The specialized `test:db` suite is the correct place to consume the local test-admin prerequisite.
