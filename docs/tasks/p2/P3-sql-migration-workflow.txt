ARCHITECTURAL RULES
- Use repository-owned SQL migrations rather than introducing an ORM or migration framework.
- Database migrations are explicit deployment/development operations; Web/API and Worker must not auto-migrate on startup.
- Migration state is part of schema compatibility/readiness, but P3 itself does not wire that status into process startup.
- Migrations must be deterministic, immutable after application, and forward-safe.
- Schema mutations and their migration-ledger record must succeed atomically per migration.
- Shared engine code remains topic independent.
- Do not create placeholder domain tables, fake Source/Article schemas, seed/bootstrap data, or compatibility bridges.

MIGRATION FILE FORMAT
Use a strict deterministic filename convention for repository SQL migrations, for example:
- `0001_<short_name>.sql`
- `0002_<short_name>.sql`

Requirements:
- filenames/ids must be sortable and unique;
- invalid/duplicate migration identifiers fail before execution;
- discovered migrations are sorted deterministically;
- migration contents are treated as immutable after application;
- compute a cryptographic checksum such as SHA-256 from the exact migration content;
- do not depend on filesystem enumeration order.

A production migration directory should exist only when substantive production SQL migrations exist. If Phase 2 requires no application schema migration beyond migration bookkeeping, do not create meaningless no-op or fake-domain SQL files merely to populate the directory. Tests may create temporary migration fixtures/directories to prove real DDL behavior.

MIGRATION LEDGER
The migration runner should own a small PostgreSQL ledger table, recommended conceptually as:
- `news_scraper_schema_migrations`

Record at minimum:
- migration identifier / filename;
- checksum;
- applied timestamp.

The ledger itself is infrastructure, not a domain model.

The system must detect and fail safely when:
- an already-applied migration's repository checksum no longer matches the stored checksum;
- PostgreSQL reports an applied migration that no longer exists in the current repository migration set;
- duplicate migration ids/files exist locally;
- a migration fails midway.

Do not silently rewrite stored checksums or accept modified migration history.

MIGRATION EXECUTION
Add an explicit root command, recommended:
- `npm run db:migrate`

It must use the ordinary validated `NEWS_SCRAPER_DATABASE_URL` production/application boundary. It must not use `NEWS_SCRAPER_TEST_DATABASE_ADMIN_URL`, create/drop databases, or infer test administration behavior.

Recommended production ownership:
- `src/database/migrations.ts`
- `scripts/migrate-database.ts`

Use a dedicated checked-out PostgreSQL client for a migration run.

Concurrency protection:
- acquire a PostgreSQL advisory migration lock before inspecting/applying migration state;
- hold the lock for the migration operation/status mutation window;
- release it in `finally` where the session remains usable;
- session loss naturally releases PostgreSQL advisory locks;
- choose a stable application-specific lock key and document it in code without topic-specific values.

Per pending migration:
1. begin transaction;
2. execute the SQL migration content;
3. insert the corresponding ledger row/checksum in the same transaction;
4. commit;
5. rollback if either schema SQL or ledger insert fails;
6. surface the failure safely and stop later migrations from executing.

Do not partially record a failed migration as applied.

SCHEMA STATUS / COMPATIBILITY API
Expose a reusable non-mutating status inspection function for P4.

It should distinguish enough state to make readiness truthful, including at minimum:
- uninitialized migration ledger/schema;
- current / repository and database migration state match;
- pending local migrations;
- checksum mismatch / modified applied migration;
- applied migration missing from repository / incompatible history.

The exact type names may vary, but P4 should be able to ask a single database boundary for schema compatibility without duplicating migration-ledger queries.

The status check must not apply migrations or otherwise mutate application schema as a side effect. If initializing the ledger itself is a mutation, keep that behavior in the explicit migration path; a readiness/status inspection against an untouched database should report uninitialized rather than silently initializing it.

REAL POSTGRESQL MIGRATION TESTS
Using P1's disposable DB helper, prove at Level 4:
- untouched disposable database can be migrated from zero;
- migration infrastructure/ledger is created reproducibly;
- temporary fixture SQL can perform real DDL/data changes;
- multiple fixture migrations run in deterministic order;
- rerunning against a current DB produces no duplicate ledger rows and no repeated schema effects;
- a failing migration rolls back its own schema/data changes;
- a failed migration is not recorded as applied;
- later migrations are not run after an earlier failure;
- after correcting/replacing the test fixture in a new fresh scenario, migration can proceed normally;
- modifying an already-applied migration produces checksum incompatibility;
- a database ledger row whose migration is missing locally is reported incompatible;
- pending migrations are reported as pending;
- current migration state is reported as current;
- an untouched/uninitialized DB is reported as uninitialized by the non-mutating status path;
- the explicit migrate path can move that database to current.

If technically stable without arbitrary sleeps, add a real advisory-lock test showing two migration attempts serialize rather than corrupt migration state. Do not add a flaky timing-heavy test merely to check a box; if not implemented, retain the advisory lock in source and explain the evidence limitation.
