STATIC DESTINATION MODULE
Create a focused substantive module, recommended:
- `src/collection/safety/static-destination.ts`

It should expose immutable types/results suitable for reuse by P3 and Phase 5.

Recommended concepts:
- `DestinationContext` such as `initial` / `redirect` where useful for diagnostics;
- `StaticValidatedDestination` containing the normalized request URL, protocol (`http:` or `https:`), normalized hostname, and effective numeric port;
- a blocked result using P1's stable reason vocabulary and `stage: 'network_safety'` (or the exact stable stage name established in P1).

Do not expose mutable `URL` instances as the durable security decision. Internally using `URL` is expected; return immutable plain data.

INITIAL / REDIRECT URL RESOLUTION
Support two uses through one policy path:
1. initial endpoint destination, which is already an absolute configured URL;
2. redirect candidate destination resolved against the current URL.

A redirect candidate may be relative. Resolve it with standards-compliant URL semantics, then run the exact same request-shape/scheme/domain/port policy as an initial destination.

P2 does not follow redirects and does not enforce redirect-count limits; Phase 5 transport owns actual following/counting.

REQUEST-SAFE URL SHAPE
Reject a destination before DNS when any of these apply:
- URL cannot be parsed/resolved;
- no hostname exists;
- username or password/userinfo is present;
- scheme is not `http:` or `https:`;
- effective hostname cannot be normalized by the canonical domain-hostname rules.

Use stable machine-readable outcomes. The contract requires `unsupported_scheme`, `domain_not_approved`, and `port_not_allowed`; a bounded `invalid_destination_url` reason is appropriate for malformed/userinfo/hostless request destinations if P1 included it or P2 adds it to the central P1 reason union.

URL fragments are not part of an HTTP request target. For a valid initial/redirect destination that otherwise passes policy, ensure the normalized request URL/result does not cause a fragment to be transmitted/used as destination identity. Do not reinterpret fragments as host/path data.

SCHEME / PORT POLICY
Enforce exactly the MVP policy:
- `http:` effective port must be 80;
- `https:` effective port must be 443;
- omitted/default ports are interpreted by scheme;
- explicit default ports are allowed even if WHATWG URL serialization removes them;
- all non-default explicit/effective ports are blocked with `port_not_allowed`.

Do not add a configuration knob for extra ports in P2.

DOMAIN POLICY
For each candidate:
1. normalize the hostname using the existing canonical Source hostname normalization behavior;
2. derive the endpoint's effective domain policy from Source maximum rules + endpoint narrowing using existing helpers;
3. require at least one effective rule to match the normalized hostname;
4. otherwise return `domain_not_approved`.

Do not create a second wildcard implementation, regex-domain engine, or DNS suffix helper that disagrees with `src/sources/configuration.ts`.

If repository inspection shows the P2 module needs a small exported pure helper from `src/sources/configuration.ts`, prefer exposing/reusing the existing canonical behavior rather than copying it. Do not change its established semantics.

NO DNS / NETWORK SIDE EFFECTS
P2 must not import or call:
- `node:dns` / resolver functions;
- `fetch` / HTTP(S) clients;
- PostgreSQL for safety decisions;
- Worker runtime execution.

The static validator must be synchronously/purely testable unless a concrete codebase convention requires Promise wrapping; do not introduce async solely for future phases.

FOCUSED UNIT TESTS
Create substantive tests, recommended:
- `test/unit/static-destination-safety.test.ts`

Use synthetic generic domains. Cover at least:
- HTTPS omitted port -> effective 443 and allowed;
- HTTPS explicit 443 -> allowed;
- HTTP omitted port -> effective 80 and allowed;
- HTTP explicit 80 -> allowed;
- HTTPS 80 rejected `port_not_allowed`;
- HTTP 443 rejected `port_not_allowed`;
- arbitrary non-default ports rejected;
- FTP and another unsupported scheme rejected `unsupported_scheme`;
- malformed URL rejected with stable invalid-destination reason;
- credential-bearing/userinfo URL rejected before DNS;
- exact-host allow success/failure;
- subdomain-enabled rule permits DNS-label descendants;
- exact rule does not permit subdomain;
- `evil-example.com` and `example.com.evil.test` are rejected;
- case/trailing-dot/IDN normalization follows canonical existing behavior where valid URL parsing permits it;
- endpoint narrowing overrides inherited Source breadth without widening it;
- empty endpoint narrowing inherits Source policy;
- relative redirect resolves against current destination and is revalidated;
- scheme-relative redirect is revalidated;
- redirect outside effective domain returns `domain_not_approved`;
- redirect to disallowed port returns `port_not_allowed`;
- URL fragment does not survive as request-destination data;
- blocked result contains stable machine-readable reason/stage/context rather than requiring message parsing.

Include boundary tests immediately around important port policy where meaningful.
