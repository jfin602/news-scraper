P5 must make steps 2-3 and step 5 composable so Phase 5 can insert step 4 naturally without replacing the Phase 4 execution API.

PRODUCTION BOUNDARY A — ELIGIBLE LOCKED EXECUTION
Create a small collection execution module, recommended:
- `src/collection/execution.ts`

It should expose a callback-scoped boundary conceptually equivalent to `withEligibleEndpointExecution(...)`.

Responsibilities ONLY:
1. accept an already-loaded endpoint aggregate;
2. run P1 state eligibility;
3. if blocked, return that decision without attempting lock acquisition;
4. acquire the P4 endpoint lock for `aggregate.endpoint.id`;
5. if contended, return `endpoint_locked` without invoking caller work;
6. while ownership is held, invoke caller-supplied work;
7. rely on P4 to release safely on success/failure.

It must know nothing about DNS, URLs, HTTP, Collection runs, parsing, or scheduler jobs.

DESIGN FOR TESTABILITY
Do not hard-code an unmockable global database singleton. Prefer a narrow injected lock-runner dependency or a small production factory binding the P4 lock helper to a `Database`, while keeping the execution function easy to test without PostgreSQL.

Do not duplicate lock implementation in P5.

Normal eligibility/lock-contention outcomes should use stable decisions. Infrastructure/database errors and caller-work errors should remain errors rather than being misreported as an endpoint state reason.

PRODUCTION BOUNDARY B — VALIDATED OUTBOUND ENTRY
Create a focused safety/outbound composition module, recommended:
- `src/collection/safety/outbound-boundary.ts`

It should expose a function that:
1. accepts the endpoint aggregate/policy context plus initial or redirect destination input;
2. runs the exact P2 + P3 safety pipeline through injected/production resolver dependency;
3. if blocked, returns the stable safety decision WITHOUT invoking outbound work;
4. if safe, invokes an injected outbound-boundary callback exactly once with the immutable `ValidatedDestination`;
5. returns the callback result or propagates its error.

The outbound callback is NOT an HTTP client in Phase 4. It is a controlled integration seam proving that future transport receives only validated concrete addresses.

Do not add `fetch`, `http.request`, `https.request`, undici, Axios, or a fake production fetcher in P5.

INITIAL / REDIRECT SUPPORT
Boundary B should support the same initial and redirect-candidate safety APIs already established in P3 without copying logic.

For redirects:
- P5 only invokes the P3 redirect revalidation primitive with a controlled candidate;
- it does not follow the redirect;
- there is no response object/status-code handling or redirect-count loop in Phase 4.

COMPOSITION DEMONSTRATION
The production pieces must be composable as:

`withEligibleEndpointExecution(aggregate, lockRunner, async () => reachValidatedOutboundBoundary(...))`

This is a Phase 4 demonstration, not the only allowed future composition.

Phase 5 must be able to evolve it as:

`withEligibleEndpointExecution(aggregate, lockRunner, async () => { createCollectionRun(); return reachValidatedOutboundBoundary(...real transport callback...); })`

Do not add an empty `createCollectionRun` hook/callback today just to model future work. The callback boundary itself is the insertion point.

NO AUTOMATIC CONFIGURATION LOAD INSIDE EXECUTION CORE
Keep aggregate loading separate from execution. P5 may add a tiny composition helper only if there is a concrete need, but the core should not accept publication/source/endpoint config keys and silently query configuration inside a broad helper.

Reason:
- persisted configuration loading is already owned by `src/sources/repository.ts`;
- later scheduler/manual commands may identify endpoints differently;
- the execution contract should operate on one explicit aggregate snapshot.
