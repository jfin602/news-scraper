## Goal

Add the Phase 1 digest to the permanent `/api/v1/distribution/{profile_key}` **complete Profile snapshot** so every successful page contains one top-level `digest` field whose value is either the P3-normalized active digest or `null`.

Conceptually:

```text
P1 canonical Article Profile snapshot
+ P3 semantic active digest/null
-> one coherent outward distribution representation snapshot
-> snapshotRevision / ETag
-> every paginated v1 page
```

P4 owns the Node outward representation, revision participation, page consistency, and HTTP serialization. It does not own digest generation/freshness, provider calls, PHP persistence, or admin UI.

## Preserve the Article-only AI input producer

The existing/P1 canonical Profile Article snapshot is also the producer used to construct Gemini input. **Do not simply add the active digest into that same conceptual input and then have P3 call it recursively.**

Create or preserve a clear distinction between:

1. **canonical Profile Article snapshot/input producer** — Profile + Publication + ordered governed Articles; no active digest dependency; used by P1/P3;
2. **outward distribution representation snapshot** — the same captured Profile/Publication/Articles plus normalized P3 active digest/null; used by v1 page/revision consumers.

Exact type/file names are implementation-owned, but dependency direction must remain acyclic:

```text
canonical Article/Profile producer
-> P1 digest input
-> P3 digest lifecycle/read authority

canonical Article/Profile producer + P3 normalized digest state
-> outward v1 representation snapshot
```

P4 may refactor P1/P3 internals narrowly to expose a transaction-aware or caller-snapshot-aware read seam needed for coherence, but MUST NOT change their business rules.

## One coherent revision

The outward `snapshotRevision` must identify **Articles + active digest representation together**.

Requirements:

- digest object -> replacement digest changes revision even when Articles are unchanged;
- digest object -> `null` suppression changes revision;
- `null` -> digest object activation changes revision;
- semantic `current` -> `older` change changes revision even if digest prose is unchanged;
- unchanged Articles + unchanged normalized digest produce the same deterministic revision;
- no internal attempt/provider error/config/secret field participates merely because it exists;
- no request-time `generatedAt` value participates in the revision.

Use deterministic serialization/hashing of the normalized digest representation, including ordered highlights/supporting Article references and the exact governed outward support metadata that the API exposes.

Do not use `digestInputIdentity` as the outward revision. It is internal provenance only.

## Snapshot transaction/race behavior

Avoid a response that captures Articles from one logical state and a digest classified against a different current Profile state.

Use the smallest coherent approach that captures the Article snapshot and active digest classification under one stable database view or an equivalent P1/P3 snapshot-aware composition. Prefer one read-only `REPEATABLE READ` transaction for the outward representation if the existing database abstraction supports it.

Important constraints:

- fix the application clock once for the representation read where lookback/freshness classification needs `now`;
- P3 remains the authority for `current | older | null`;
- do not hold transactions over Gemini/provider calls — P4 performs no provider call;
- invalid/malformed persisted optional AI state must degrade to `digest: null` while a valid Article snapshot still returns;
- a database/dependency failure that prevents reading the required Article/Profile snapshot remains the existing service failure path;
- do not catch arbitrary Article/database failure and pretend it is only an AI-null condition.

If the active digest switches after the captured representation is complete, that is simply a later revision. Existing continuation revision checks handle it.

## Normalized v1 digest shape

Every successful active Profile page MUST contain `digest` as a top-level key. It is never omitted.

When present, serialize only:

```text
digest.generatedAt
digest.freshness              # current | older
digest.inputArticleCount      # 1..20
digest.provider
digest.model
digest.overview
digest.highlights[]
  .title
  .explanation
  .supportingArticles[]
    .articleId
    .headline
    .source.displayName
    .effectiveFeedDate
    .originalUrl
```

Use the exact field naming locked by the current distribution/AI contracts; if the current contract names differ slightly, follow the contract rather than this illustrative indentation.

Supporting metadata must be application-resolved governed data. Do not expose:

- `digestInputIdentity`;
- internal digest UUIDs;
- attempt IDs/outcomes/failure categories;
- Profile AI settings;
- prompts/system instructions;
- URL Context statuses unless specifically contract-exposed (they are operator diagnostics, not v1 digest data);
- token counts/raw usage;
- Gemini key;
- raw provider URLs/citations/errors;
- stored historical digest list.

Provider/model are bounded operational provenance and are safe outward fields per the contract; no credentials or request details accompany them.

## Supporting Article resolution

Visible support destinations always use exact stored governed `originalUrl` from the generation's validated input/canonical Article authority, never model-generated URLs.

P4 must consume P3/P1 normalized support data rather than asking the model/provider again.

If a persisted support reference cannot be validated/resolved through the P3 read authority, treat the optional digest as invalid/null. Do not emit a partially trusted support object while retaining the prose as “valid.”

Preserve supporting-Article order and highlight order.

## Page consistency

The same normalized `digest` value must appear on **every page** traversed under one `snapshotRevision`, including pages with zero items if such a page shape is possible under current pagination behavior.

Requirements:

- initial and continuation pages for one revision serialize byte-equivalent logical digest data;
- cursor still binds to the same `snapshotRevision`;
- if digest changes between continuation requests, existing `409 snapshot_changed` behavior applies;
- do not put digest state into the cursor separately;
- do not invent a second digest cursor/revision/ETag;
- `304` on an unchanged initial request includes digest state through the shared revision identity — if digest changes, old ETag must no longer yield 304.

## HTTP serialization and compatibility

Update `DistributionProfilePageOutcome` / router serialization so the active outcome carries the normalized digest/null from the outward representation snapshot.

The response remains:

```json
{
  "apiVersion": "v1",
  "generatedAt": "...request time...",
  "snapshotRevision": "...",
  "profile": { ... },
  "publication": { ... },
  "digest": null,
  "items": [ ... ],
  "nextCursor": null
}
```

or the same with a structured digest object.

Existing required Article fields/semantics, authentication, rate limiting, error classes, CORS stance, cache headers, and direct publisher destinations remain unchanged.

`distribution:read` still authorizes only distribution reads. This additive digest output does **not** grant interactive AI spending authority.

## Failure isolation

Required fail-open behavior:

```text
valid Profile + Publication + Articles
+ absent/disabled/invalid optional digest
-> HTTP 200 normal Article snapshot
-> digest: null
```

Do not convert a provider failure or invalid optional digest into `503` after P3 has already determined that Articles are valid.

Do not swallow genuine database failure required to establish canonical Profile/Article state.

The v1 route must never call Gemini or trigger generation. It is a read-only consumer of persisted normalized digest state.

## Focused proof

Extend unit/integration/database/security coverage to prove at minimum:

### Revision and pagination

- article-identical null->digest, digest->replacement, digest->null, current->older each change revision;
- identical normalized outward state gives stable revision;
- request-time `generatedAt`, attempt state, failure category, and internal input identity do not affect revision;
- every continuation page carries the same digest for one revision;
- digest change between page requests yields `snapshot_changed` rather than a mixed traversal;
- ETag/304 changes exactly with the shared revision.

### Serialization

- `digest` always exists on successful active pages;
- null is represented as JSON null;
- valid current/older objects contain only allowed bounded fields;
- generatedAt is exact digest generation time;
- support Article metadata/order/exact `originalUrl` are preserved;
- internal IDs/config/attempt/errors/prompts/provider raw state are absent;
- invalid optional digest becomes null while Articles remain 200.

### Transaction/producer boundary

- outward representation uses P1/P3 producers rather than direct duplicate Article/freshness SQL;
- canonical Article-only snapshot remains usable by P1/P3 without recursive digest dependency;
- a race/activation change cannot create one page with a digest classified against another Article revision;
- Article read failures still fail as existing dependency failures and are not mislabeled as optional-AI null.

### Regression/topic independence

- existing draft/disabled/not-found/auth/rate/error behavior is unchanged;
- Article-only consumers/tests preserve order and exact fields;
- at least two materially different Profile fixtures serialize the same generic digest schema with no topic logic.

Use real PostgreSQL where the coherent-read/race claim depends on actual transaction isolation.
