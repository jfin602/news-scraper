## Goal

Propagate the P4 v1 `digest` object/null through the existing generic PHP complete-snapshot synchronization, atomic last-known-good state, and normalized `LocalProfileReader` boundary while preserving Article delivery even when optional AI data is missing, malformed, or inconsistent.

Conceptually:

```text
P4 v1 pages: Articles + digest object/null
-> DistributionClient core page parse + optional digest parse
-> complete multi-page candidate
-> optional digest coherence validation
-> one atomic Profile LKG generation
-> LocalProfileReader
   articles + digest object/null
```

P5 owns only PHP client/sync/state/local-read support for digest data. It does **not** own Gemini, digest lifecycle/freshness calculation, customer markup, renderer cleanup, config/launcher redesign, or production package deployment.

## PHP normalized digest DTOs

Add immutable typed PHP DTOs for the v1/local digest shape, including at minimum:

- digest `generatedAt`;
- `freshness` exactly `current | older`;
- `inputArticleCount` 1..20;
- bounded provider/model strings;
- overview;
- ordered highlights;
- each highlight title/explanation;
- ordered supporting Articles containing:
  - `articleId`;
  - headline;
  - Source display name;
  - `effectiveFeedDate`;
  - exact stored `originalUrl`.

Do not include internal digest UUID, `digestInputIdentity`, attempt/failure/config data, raw provider annotations, prompt, page bodies, or credentials.

Use one shared PHP validation/mapping path for upstream page data and local state rehydration where practical so the two paths cannot silently accept different digest shapes.

## Optional digest parser fail-open boundary

Required Profile/Publication/Article fields retain the existing strict validation behavior. Optional AI is different.

For a `200` page:

- missing `digest`, explicit `digest: null`, or a malformed/oversized digest MUST NOT by itself make otherwise valid required Article/Profile data an `INVALID_RESPONSE`;
- normalize optional AI for that page to a state capable of distinguishing a valid digest from absent/invalid AI while preserving core page success;
- never expose a partially parsed digest;
- do not truncate/repair arbitrary malformed provider text in PHP; invalid optional digest becomes null at the candidate boundary;
- exact support `originalUrl` is accepted only as a bounded valid string carried by the validated server response; PHP does not replace it with provider citations or derive another destination.

Keep parser bounds substantially tighter than the existing generic 65k string ceiling where the Phase 1 digest contract provides explicit smaller bounds. Validate array counts, timestamps, freshness enum, input count, and nested support shape.

Unknown future additive fields may continue to be ignored where v1 compatibility permits; do not reject a valid digest solely because an additive unknown key exists unless current PHP policy explicitly rejects unknown keys elsewhere.

## Multi-page candidate digest coherence

The complete Profile snapshot contract says every page of one revision carries the same logical digest.

Extend `ProfileCandidate` / traversal so:

- the initial page establishes the candidate's optional digest state;
- every continuation page's valid digest is compared structurally with the initial valid digest;
- `null`/absent/invalid optional AI on any page or contradictory digest values across pages degrades the **candidate digest** to null;
- required candidate identity still checks Profile, Publication, API version, and `snapshotRevision` exactly as before;
- a real core identity/revision mismatch still fails/restarts the candidate under existing rules;
- optional digest inconsistency does not discard valid Articles merely to preserve AI.

After traversal:

```text
valid required complete candidate
+ all pages same valid digest -> activate Articles + digest

valid required complete candidate
+ digest null/missing/malformed/conflicting -> activate Articles + digest null
```

Do not preserve a previous local digest when a newer valid Article snapshot explicitly normalizes its digest to null. The digest belongs to the new complete revision.

## Atomic LKG state

Extend the existing active Profile snapshot/local generation to carry one nullable digest inside the **same** committed Profile generation.

Requirements:

- no second digest state directory/file/manifest/lock;
- no separate digest activation transaction;
- Article + normalized digest state for one upstream `snapshotRevision` become visible atomically under the existing filesystem activation model;
- previous active generation remains recoverable under existing failure behavior when core activation fails;
- candidate with invalid optional digest still activates valid Articles with null digest;
- candidate core corruption still fails and preserves prior LKG as before;
- credentials and upstream request state remain outside cache payloads.

### Pre-digest local-state compatibility

Local state created before P5 that has no digest member remains valid and reads as `digest = null`. Do not require customers to delete/rebuild `ns-private` or active state merely because this feature is added.

Write the new optional representation additively enough that Phase 2 can validate immediate package rollback. Do not intentionally redesign the state format or add incompatible version gates in P5.

If current old-package parsing would reject the smallest additive digest field and that cannot be solved without a broader rollback/package decision, report the exact issue for Phase 2 rather than silently weakening current-state validation.

## LocalProfileReader digest boundary

Extend the existing normalized customer-facing local read result with nullable digest data.

Requirements:

- customer code reads `$result->digest` or the equivalent stable normalized property; it never parses cache JSON;
- digest is present only when the Profile result is otherwise renderable under existing local usability semantics;
- non-renderable `disabled`, `stale_cutoff`, `never_synced`, or `unavailable` states must not leak retained digest data merely because bytes exist;
- valid empty Article result may still carry a digest only if the upstream complete snapshot validly did so; do not invent one locally;
- preserve exact `generatedAt` and P3-provided `freshness`; PHP never recomputes semantic freshness;
- existing `staleAgeSeconds` keeps meaning **local synchronized Profile/LKG age**, not digest age;
- digest age is derivable from `digest.generatedAt` by customer code if desired but is not substituted for local stale-age policy;
- support Article links remain exact stored `originalUrl` from normalized upstream data.

Do not expose provider failure category or latest attempt through public/customer local read. Those are protected admin/operator concerns.
