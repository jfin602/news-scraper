## Goal

Implement the durable, topic-independent Profile AI data foundation and deterministic digest-input producer required by Phase 1, without calling Gemini or exposing digest data through the v1/PHP/admin surfaces yet.

Conceptually:

```text
existing active Distribution Profile
+ canonical Profile snapshot Articles
+ Profile AI settings
-> bounded deterministic digest input
-> digestInputIdentity

Profile AI settings
+ immutable successful digest records
+ separate active-digest reference

It must not implement provider transport, generation orchestration, scheduling loops, v1 serialization, PHP parsing, or browser/admin UI.

## Implementation decisions locked by this prompt

These are implementation-level choices explicitly left open by the contracts and are now fixed for Phase 1 unless current source makes one unsafe:

- Profile digest lookback is integer days in the bounded range **1–30**, default **7**.
- Maximum digest input Article count is **1–20**, default and hard Phase 1 ceiling **20**.
- Rolling-window inclusion is `effectiveFeedDate >= now - lookbackDays * 24 hours`, using an injected/explicit clock for deterministic tests.
- `digestInputIdentity` is a versioned SHA-256 identity over the Profile key, relevant AI settings, and the exact ordered bounded Article-ID set. Do not use or include outward `snapshotRevision`; do not use model output or provider state. The representation must be deterministic and documented in code/tests so equivalent inputs hash identically.
- Same Article IDs in a different canonical order are a different input identity.
- Zero qualifying Articles is a valid resolved input with zero Articles but is not a successful digest generation.
- Successful digest generations may repeat the same input identity because manual force generation is explicitly allowed later; therefore do **not** make `(profile, digestInputIdentity)` unique.

## Additive supported-production migration

Add the next migration as `migrations/0018_profile_ai_digest_foundation.sql`. Do not rewrite migrations `0001`–`0017`.

Use the smallest normalized schema that directly represents the contract. Exact SQL names may vary only if the resulting ownership is clearer, but the logical state must include:

### Profile AI settings

One Profile-owned settings row with at least:

- Profile foreign key/primary ownership;
- digest enabled boolean, default `false`;
- lookback days, default `7`, database-constrained to `1..30`;
- maximum Article count, default `20`, database-constrained to `1..20`;
- useful created/updated timestamps.

Existing Profiles must receive safe disabled defaults during forward migration. New Profile creation must establish the same default settings transactionally or otherwise guarantee the row exists before any AI operation. AI settings are Profile configuration, not Publication/topic configuration and not provider-secret storage.

### Immutable successful digest generations

Persist one immutable Profile-owned generation record per successfully validated digest with at least:

- stable UUID identity;
- Profile identity;
- bounded `digestInputIdentity`;
- generation timestamp;
- bounded provider and model identifiers;
- input Article count constrained to `1..20`;
- overview text constrained to the Phase 1 2,000-character limit;
- timestamps useful for provenance.

Represent the exact ordered input Article IDs with real Article foreign keys and deterministic positions rather than an unbounded opaque corpus. Preserve enough immutable provenance to determine overlap/current-input membership later.

Represent highlights and their supporting Article references in a bounded relational or equivalently integrity-safe form. Prefer explicit child rows with deterministic positions over large opaque JSON when doing so gives clearer foreign-key, count, ordering, and Article-reference integrity. At minimum the schema/application boundary must be able to guarantee:

- no more than 3 highlights;
- no more than 3 supporting Articles per highlight;
- supporting Articles belong to the generation input;
- no duplicate supporting Article within one highlight;
- deterministic ordering;
- title/explanation bounds required by the AI contract.

Do not persist provider-generated URLs as Article destinations.

### Active digest reference

Persist one separate Profile-owned active-digest reference pointing to one successful digest belonging to that same Profile. Activation/replacement semantics are implemented in P3, but the database representation must make cross-Profile pointers impossible or transactionally rejectable.

Do not mutate the successful digest record to mean “active.” Historical successful generations remain immutable records.

### Evaluation/generation attempts

Persist separate bounded attempt/evaluation records containing only operational state needed by the contract, including at least:

- stable identity;
- Profile identity;
- trigger kind `scheduled | manual`;
- nullable scheduled slot timestamp for scheduled work;
- bounded outcome category;
- started/completed timestamps;
- nullable input identity and bounded input count;
- nullable bounded failure category;
- nullable bounded provider/model identity;
- bounded URL Context outcome counts or an explicitly extensible safe place for them without raw page/provider payloads.

Scheduled work needs a database-enforced idempotency seam so multiple Worker processes cannot execute the same Profile evaluation slot twice. A partial unique constraint/index over `(profile, scheduled_slot)` for scheduled attempts or an equally strong representation is appropriate. Manual attempts are not deduplicated by input identity.

Attempts MUST NOT contain API keys, Authorization headers, full prompts, full Gemini responses, retrieved publisher-page bodies, arbitrary exceptions, or unbounded provider payloads.

## Repository/application ownership

Create a focused topic-independent AI/digest module boundary rather than scattering SQL through Web/API/Worker controllers. Exact directories are implementation-owned, but the boundary should make these concepts explicit:

- validated Profile AI settings read/update model;
- digest input read model;
- successful immutable digest repository model;
- active digest read/reference model;
- attempt repository model;
- transactional primitives needed by P3 for attempt claiming and atomic successful digest activation.

Do not expose raw database row shapes as the public application contract where doing so forces later prompts to know table layout.

The repository layer must validate returned database state fail closed. An invalid/cross-Profile active pointer or malformed persisted AI structure must not be silently accepted as valid digest state.

## Canonical digest input producer

Create one deterministic service that consumes the **existing canonical Profile snapshot/read-model authority** from `src/distribution/profile-snapshot.ts`. It MUST NOT reconstruct Profile eligibility or issue its own Article-selection SQL.

For one active Profile and an explicit clock:

1. obtain the current canonical Profile snapshot;
2. read the Profile AI settings;
3. preserve the snapshot's canonical Article order;
4. filter by the configured rolling lookback using `effectiveFeedDate`;
5. take at most the configured maximum Article count from the front;
6. project only the Phase 1 safe AI fields:
   - `articleId`;
   - headline;
   - Source display name;
   - `effectiveFeedDate`;
   - nullable `publishedAt`;
   - nullable author;
   - accepted bounded persisted summary;
   - effective outward Categories;
   - exact stored `originalUrl`;
7. calculate the versioned `digestInputIdentity` from Profile key + relevant AI settings + ordered Article IDs.

Do not include image URLs, Source/endpoint configuration, Collection-run state, duplicate internals, moderation/Relevance internals, persistence IDs other than the governed outward `articleId`, credentials, unrelated Profiles, or outward `snapshotRevision`.

N6WD is already authoritative for persisted summary bounds. Do not add a second summary truncator in the AI module.

Expose enough explicit input/provenance information for P3 to determine:

- current ordered Article IDs;
- whether any Article newly entered relative to a previous successful digest input;
- overlap with a previous digest input;
- current input identity;
- zero-input behavior;
- whether configuration changed because the identity contains relevant settings.

Do not decide `current | older | null` in this input producer; P3 owns lifecycle semantics.

## Profile creation/settings compatibility

Existing Profile creation and reads must remain backward compatible for non-AI consumers. If the Profile repository/service must establish default AI settings when creating a Profile, keep that transaction coherent and do not add provider/model/secrets to ordinary Profile configuration.

Do not make AI enabled by default for existing or new Profiles.

A disabled AI setting must not disable the Distribution Profile itself, suppress Articles, or change canonical Profile selection.

## Focused proof

Add focused unit/database tests that prove at least:

- migration from zero creates the new AI schema and constraints;
- supported production-forward upgrade from the accepted production baseline through `0015`–`0018` preserves existing Articles, Sources/endpoints, observations, moderation, Categories, duplicates, Profiles/source associations, credentials, jobs/audit state, and the N6WD summary invariant;
- existing Profiles receive disabled 7-day/20-Article settings without altering Profile lifecycle/result/filter behavior;
- new Profiles receive the same defaults transactionally;
- invalid lookback/count values are rejected by application validation and database constraints;
- Profile deletion/cascade behavior, if any supported draft deletion exists, cannot leave orphaned AI state;
- immutable digest history cannot be rewritten through ordinary repository APIs;
- active digest references cannot cross Profile ownership;
- scheduled-slot uniqueness prevents two scheduled attempt claims for one Profile/slot while manual attempts remain allowed;
- attempt text/provider fields remain bounded and secret/raw-payload fields do not exist;
- digest input uses canonical Profile order and filters exactly at the rolling cutoff;
- 0, 1, 20, and >20 qualifying Article behavior;
- result-limit and Profile/source/category filters continue to be inherited from canonical Profile output rather than bypassed;
- summaries are consumed as already-bounded values without an AI-specific alternate truncator;
- deterministic identity stability for equal inputs and change for Profile key/settings/ordered Article-ID changes;
- materially different subject fixtures produce the same generic input shape with no topic branches.

Use real disposable PostgreSQL for migration/constraint/transaction claims.
