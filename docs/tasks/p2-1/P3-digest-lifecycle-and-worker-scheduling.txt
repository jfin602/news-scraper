## Goal

Implement the complete Profile digest evaluation/generation lifecycle and host its twice-daily scheduled evaluations in the existing Worker process as a **separate Profile-owned work concern**, not as endpoint collection jobs.

Conceptually:

```text
scheduled UTC half-day slot OR manual Generate now
-> claim one Profile evaluation safely
-> P1 current bounded digest input
-> lifecycle decision
   skip / suppress / generate
-> P2 provider-neutral Gemini call when required
-> validate candidate already guaranteed by P2
-> persist immutable success + atomically activate
-> complete bounded attempt
-> expose current/older/null read state for later consumers
```

P3 is the sole application authority for:

- when Gemini is called;
- unchanged-input skip behavior;
- manual force semantics;
- canonical invalidation/suppression;
- `current | older | null` determination;
- provider failure retention;
- one-in-flight-generation-per-Profile behavior;
- scheduled evaluation slot ownership;
- atomic successful activation;
- digest scheduler integration with Worker runtime.

P4/P5/P6 must consume this state; they must not reimplement it.

## Scheduling policy

Implement exactly two scheduled evaluation opportunities per UTC day using deterministic **12-hour UTC slots**:

```text
00:00:00Z <= time < 12:00:00Z -> slot beginning 00:00:00Z
12:00:00Z <= time < next 00:00:00Z -> slot beginning 12:00:00Z
```

The scheduled-slot timestamp is the idempotency identity already anticipated by P1. Do not create customer/local-time scheduler semantics, a Publication timezone dependency, or Source-collection synchronization.

Requirements:

- one Profile may execute at most one scheduled attempt for one UTC slot across all Worker processes;
- a Worker starting late in a slot may evaluate the **current** slot once; do not replay every historical missed slot after downtime;
- scheduled attempts are independent per Profile;
- a disabled Profile digest does not call Gemini;
- no global “all Sources have finished” barrier exists;
- a failing Profile/provider call must not fail endpoint scheduler/dispatcher/recovery loops or another Profile's evaluation;
- ordinary endpoint collection scheduling remains unchanged.

Use a separate digest scheduler/evaluation loop in `startWorkerRuntime()` or an equivalently isolated Worker-owned loop. Do not make a slow Gemini call block the existing endpoint scheduler loop. Keep digest execution concurrency deliberately small/bounded; Phase 1 does not need speculative high-throughput AI execution.

Extend Worker timing/config only as needed for a bounded periodic check of the current UTC slot. The interval is operational timing, not an editorial rule. It should be short enough to notice a new slot/restart reasonably (for example around one minute) without polling the provider; the provider is called only after the lifecycle decision says generation is required.

## In-progress generation concurrency and crash recovery

P1 must expose a durable per-Profile claim that prevents two scheduled/manual executions from making concurrent Gemini calls for the same Profile. Use that producer seam; do not hold a PostgreSQL transaction or row lock open while awaiting Gemini.

Required behavior:

1. transactionally create/claim one `running` attempt for the Profile and trigger;
2. commit the claim before external provider I/O;
3. perform P1 input resolution and, only when required, the P2 provider call outside a long-lived DB transaction;
4. finalize the attempt and any activation in a later bounded transaction;
5. reject/defer another manual/scheduled execution while one non-stale running attempt exists.

A crashed process must not leave a Profile permanently locked. Use P1's bounded stale-running-attempt recovery seam. A running attempt older than the application-owned provider-attempt timeout plus a small recovery margin may be atomically classified as abandoned/failed before a later evaluation claims the Profile. Do not blindly retry an uncertain request in a tight loop. Recovery must be observable and bounded.

If P1 lacks a database-enforced one-running-attempt-per-Profile invariant plus stale recovery capability, **stop and return Planning needed** rather than adding consumer SQL in P3.

## Scheduled lifecycle decision

For each successfully claimed scheduled evaluation:

1. read current Profile AI settings and current P1 bounded input;
2. read the current active digest plus its immutable generation settings/input Article IDs/supporting references;
3. if digest AI is disabled:
   - do not call Gemini;
   - suppress/remove any active digest through the P1 active-reference transaction boundary;
   - complete attempt as a bounded disabled/skip outcome;
4. if current bounded input has zero Articles:
   - do not call Gemini;
   - suppress any active digest because there is no current digestable Profile input;
   - record a bounded no-input outcome;
5. if no active digest exists and input is non-empty: generate;
6. otherwise evaluate canonical validity, overlap, settings change, and newly entering Article IDs as below.

### Canonical invalidation

An old digest must be suppressed before/independent of provider success when its supporting Article state is no longer permitted by the current canonical Profile result.

Use P1/current canonical Profile producer data to validate the active digest's governed support/input membership. Do not query moderation/duplicate/Source tables independently.

Canonical invalidation includes the contract cases such as moderation, duplicate/Primary change, Profile Source/filter change, Source trust/lifecycle change, or another canonical eligibility change that removes governed support. When detected:

```text
suppress active digest atomically
-> if current bounded input is non-empty, attempt replacement through the same evaluator
-> replacement failure leaves digest null
```

Do not preserve an invalid digest merely as `older`.

### New-content threshold

If the active digest remains canonically valid:

- compare current bounded ordered Article IDs with the active generation's input Article IDs;
- if at least one current bounded Article ID was not in the prior input, generation is required;
- if relevant AI settings differ from the settings snapshot used by the active digest, generation is required;
- otherwise a scheduled evaluation does **not** call Gemini merely because time passed or an old Article naturally aged out of the lookback.

This preserves the worksheet rule that no newly entering Article means no routine Gemini call while still allowing the digest's semantic freshness to change from `current` to `older` when the bounded set drifts through natural aging.

Do not treat any newly persisted Article elsewhere in the database as a trigger unless it actually enters this current bounded Profile input.

## Manual force generation

Expose a server-side application operation for P6 such as conceptually:

```text
forceGenerate(profileKey)
```

or equivalent.

Manual force:

- is protected-admin application behavior; P6 owns HTTP/UI authorization routing;
- uses the same per-Profile in-progress claim, P1 input service, P2 provider, output validation, persistence, activation, failure handling, and redaction path;
- may bypass the scheduled unchanged-input/new-entry skip optimization;
- still requires digest enabled and at least one current bounded Article unless the contract clearly says manual generation may override enablement (it does not);
- cannot expand lookback/count/URL set;
- cannot use arbitrary prompt/user text;
- cannot create concurrent duplicate provider calls for the Profile.

Manual calls receive a bounded typed result suitable for admin status, not raw provider output/errors.

## Provider call and atomic success

When generation is required:

- call exactly one P2 provider operation for the claimed attempt;
- do not add transparent automatic provider retries in P3;
- do not hold a DB transaction open across the provider call;
- if P2 returns a validated candidate, open a bounded transaction that:
  1. persists the complete immutable digest generation and ordered input/support provenance;
  2. switches the Profile active-digest reference to that complete digest;
  3. completes the attempt as success with bounded provider/retrieval facts;
- consumers must never observe the new active reference before its complete immutable content exists;
- if persistence/activation transaction fails, the previous valid active digest remains unless it had already been canonically suppressed for safety; do not fabricate success.

The successful generation timestamp is the actual generation/validation time from an injected clock. A later failed attempt never rewrites it.

## Failure and retained prior digest behavior

Provider unconfigured/timeout/rate/safety/transport/invalid-output failures:

- complete the attempt with the bounded P2 category;
- never break collection, Web/API, ordinary Profile Article reads, Worker endpoint job loops, or another Profile;
- never create/activate a partial digest;
- preserve the previous active digest only if it remains canonically valid under current state;
- if current bounded input changed but still overlaps the previous digest input, the read state becomes `older`;
- if no previous input Article remains in current bounded input, the active digest must be suppressed to `null`;
- if canonical invalidation already required suppression, failure leaves `null`.

An individual URL Context paywall/error/unsafe result is not itself a failed generation when P2 returns a valid structured candidate using bounded fallback context.

## `current | older | null` read authority

Expose one provider-neutral application read operation for P4/P6 that returns either:

- validated active digest + `freshness: current`;
- validated active digest + `freshness: older`;
- `null`.

This operation owns semantic freshness. P4/P5/P6 must not recompute it.

Rules:

### `current`

Return `current` when the active digest remains canonically valid and its `digestInputIdentity` matches the currently resolved bounded input/settings identity.

### `older`

Return `older` when:

- the active digest remains canonically valid;
- current identity differs;
- at least one Article from the active digest input remains in the current bounded input; and
- no canonical invalidation rule requires suppression.

Age alone is irrelevant. Preserve original `generatedAt`.

### `null`

Return/sustain null when:

- digest disabled;
- no valid active digest;
- zero current input requires suppression;
- canonical invalidation makes old support unsafe;
- no Article from the previous digest input overlaps the current bounded input;
- persisted active AI state fails validation.

Do not expose provider failure categories in this outward read model.

## Worker integration

Extend `WorkerRuntimeDependencies` with a narrow digest scheduler/evaluation dependency so unit tests can control it without constructing Gemini or PostgreSQL internals.

Production dependency wiring should compose:

- current database;
- P1 repositories/input service;
- P2 Gemini provider configured from server-side environment;
- digest evaluation/scheduler service.

Worker startup must remain possible with no Gemini key when AI is unused. A missing key for an enabled generation becomes a bounded attempt failure; it must not make the entire Worker fail readiness or stop endpoint collection.

Add distinct bounded diagnostics such as digest scheduler pass completed/failed and digest attempt success/failure/skip counts. Do not log prompts, response text, page bodies, API keys, Article corpora, or raw provider errors.

Worker shutdown must stop the digest scheduler loop and wait for any owned in-flight digest evaluation according to the same truthful resource-ownership principles used elsewhere. Do not abandon unresolved local promises silently.

## Focused proof

Add deterministic unit/database/recovery tests covering at minimum:

### Scheduling/concurrency

- UTC slot calculation at boundaries and exactly two slots/day;
- multiple scheduler polls in one slot claim at most one scheduled attempt/Profile;
- two Worker/process-like concurrent claims cannot both call provider for the same Profile/slot;
- scheduled and manual attempts cannot concurrently call provider for one Profile;
- different Profiles remain independent;
- stale running attempt recovery releases a permanently stuck Profile without tight automatic provider retry;
- one digest/provider failure does not break endpoint scheduler/dispatcher/recovery loops.

### Generation threshold

- no active + 1 current Article generates;
- zero current Articles skips provider and suppresses active state;
- unchanged input/config skips provider;
- one newly entering current bounded Article generates;
- multiple new Articles in one slot produce one provider call;
- new Article outside Profile/lookback/max-20 input does not trigger;
- config lookback/count change triggers at the next evaluation even without new Article;
- natural age-out with remaining overlap does not itself force a scheduled provider call;
- manual force generates unchanged non-empty enabled input.

### Lifecycle

- successful candidate persists immutable generation before active switch;
- previous generation remains immutable/history after replacement;
- activation transaction failure cannot expose partial new digest;
- provider failure preserves prior valid overlapping digest as `older`;
- provider failure with unchanged identity leaves prior digest `current`;
- provider failure after canonical invalidation leaves null;
- no-overlap current input suppresses old digest/null;
- age alone never changes `current` to `older`;
- original `generatedAt` survives failed attempts;
- invalid persisted active state fails closed to null without breaking Articles.

### Canonical invalidation/topic independence

- a supporting Article removed by canonical Profile state suppresses active digest even with no newly entering Article;
- Source/Profile/duplicate/moderation changes are observed only through canonical Profile producer output, not direct P3 table logic;
- materially different subject fixtures follow the same lifecycle and prompt-provider path with no topic branch.

### Security/telemetry

- missing Gemini key for enabled generation records bounded `provider_unconfigured` and endpoint collection remains operable;
- attempts/Worker diagnostics exclude key, prompt, response/page bodies, and raw provider error text.

Use real PostgreSQL for claim uniqueness, atomic activation, migration interaction, concurrency, and recovery claims.
