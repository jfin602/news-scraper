TASK: Phase 1 / P6 — Profile AI admin controls and manual generation

- Recommended configuration: `Terra High`.
- Task-shape classification: `Bounded`.
- Specification clarity: `Explicit`.
- State coupling: `High`.
- Integrity risk: `High`.
- Concurrency: `Moderate`.
- Security: `High`.
- Novel inference: `Moderate`.
- Model-family basis: P1-P5 already own configuration persistence, generation lifecycle, v1, and PHP. P6 is the protected administrator application/API/browser surface over those producers, not another AI state machine.
- Reasoning basis: Terra High is warranted because manual Generate now creates an external side effect from the Web/Admin process, AI settings alter outward digest state, and status/error rendering must expose useful bounded diagnostics without leaking Gemini credentials/provider payloads or granting machine credentials admin authority.
- Complexity / quality floor: `High`.
- Estimated usage: `High`.
- Lower-cost alternative considered: `Luna High`; rejected because the task spans protected admin service/router, Web provider wiring, browser state, manual side effects, concurrency conflict handling, audit/change history, and security tests.
- Escalation trigger: P3 manual generation/status cannot be safely composed in the Web process without duplicating Worker/provider logic, or P1 settings changes cannot participate in existing admin audit/transaction rules without a producer change.
- Escalation target: `Terra Ultra` for bounded Web/Worker service-composition or transactional admin ambiguity; return `Planning needed` rather than embedding lifecycle logic in browser/routes.
- Estimate confidence: `High`.
- Efficiency rationale: make the admin a thin consumer of P1/P3 services and keep provider/lifecycle semantics centralized, while giving operators exactly the controls/status needed to operate Phase 1.

The assigned project version is `2.1.6`.

- digest enable/disable;
- lookback days;
- maximum input Article count;

- current active digest status;

## Dedicated server-side admin application boundary

Prefer a focused Profile AI administration service rather than adding provider/lifecycle logic directly to the existing generic Profile configuration service.

Conceptual operations:

```text
getProfileAi(profileKey)
updateProfileAiConfiguration(profileKey, input)
forceGenerateProfileDigest(profileKey)
```

Exact names may differ, but each operation must use P1/P3 producer APIs.

### Read model

Expose only bounded protected-admin data needed by the UI:

```text
profileKey
configuration:
  digestEnabled
  lookbackDays
  maxArticles
cadence:
  kind = twice_daily
  slots = 00:00Z / 12:00Z (or equivalent bounded display fact)
activeDigest: null OR
```

The admin status does not need raw digest prose to satisfy Phase 1; showing it is optional only if it reuses the normalized P3 digest and remains bounded/escaped. Prefer operational status over duplicating the customer presentation surface.

Never expose:

- Gemini API key;
- Authorization headers;
- prompt/system instructions;
- raw model response;
- retrieved publisher-page bodies;
- arbitrary provider exception strings;
- database/internal digest UUIDs unless genuinely necessary for operator diagnostics (they are not required by the contract);

- unrelated Profile context.

## Configuration mutation

Accept only explicit bounded JSON fields:

- `digestEnabled: boolean`;
- `lookbackDays: integer 1..30`;
- `maxArticles: integer 1..20`.

Reject unknown/wrong-type/out-of-range input under current admin validation conventions. Do not coerce strings such as `"20"` into integers if current admin APIs fail closed on type mismatches.

Changing these values:

- is Profile configuration, not Publication/topic configuration;
- does not alter Profile lifecycle/source associations/result limit;
- does not enable/disable collection;
- does not modify Articles;
- does not call Gemini synchronously merely because a setting changed;
- is observed by P3 at the next scheduled evaluation;
- immediately affects P3 outward digest classification: disabling means outward digest is null even if immutable historical generations remain; lookback/count change may make the retained digest `older`/null according to P3;
- does not rewrite prior successful digest records.

Use the existing audit/change-history mechanism or an equivalent current admin audit boundary to record successful material Profile AI configuration changes with bounded prior/new state and reason/action identity. Failed validation/mutation must not emit a successful audit event.

Do not store provider/model/key in Profile settings.

## Manual `Generate now`

Add a protected admin command route invoking **only** P3's manual force service.

Recommended HTTP shape:

```text
POST /admin/api/distribution-profiles/:profileKey/ai/generate
```

or a consistent equivalent under the existing protected admin router.

The route performs one bounded server-side operation and may await the P3 provider attempt. It must not make the browser call Gemini directly and must not pass arbitrary prompt/URL/user text.

Map P3 results into a small stable admin response. Suggested semantics:

- successful generation -> `200`, refreshed AI admin read model with latest attempt/active state;
- provider generation failure -> `200` or a bounded non-5xx application result that clearly says the attempt completed unsuccessfully and includes only the protected bounded failure category; provider outage is not an admin-Web dependency crash;
- digest disabled / no current input -> `409` with bounded application error such as `digest_disabled` / `digest_no_input`, or another consistent typed conflict mapping;
- another non-stale generation already running -> `409 digest_generation_in_progress`;
- Profile missing -> `404`;
- malformed request -> `400`;
- genuine unexpected application/database dependency failure -> existing bounded `503`/admin error pattern.

Choose one exact mapping and lock it in tests. Do not expose raw provider status/body/error merely to make the UI informative.

Manual generation must use the same P3 claim/provider/validation/persistence/activation path as scheduled generation and may bypass only the unchanged-input skip rule. No separate manual Gemini client is allowed.

## Web process composition and optional key

The Web/Admin process now needs to be able to execute the same P3 manual generation application service that the Worker uses.

Compose it from shared P1/P2/P3 production factories/dependencies rather than duplicating provider construction in the router.

Requirements:

- Gemini key remains optional at Web startup;
- ordinary admin/Profile reads and all non-AI Web/API routes remain available without a key;
- clicking Generate now without a configured key yields the bounded P3 `provider_unconfigured` attempt/result, not startup failure or key exposure;
- the public `/api/v1` read route still never invokes this generation service;
- machine `distribution:read` routes cannot call admin generation endpoints;
- Cloudflare Access/admin perimeter and current request-integrity/CSRF rules remain unchanged and must cover the new mutation routes through the same protected router.

## Admin API routes

Add a focused route family such as:

```text
GET  /admin/api/distribution-profiles/:profileKey/ai
PUT  /admin/api/distribution-profiles/:profileKey/ai/configuration
POST /admin/api/distribution-profiles/:profileKey/ai/generate
```

Use the existing admin router registration/auth perimeter. Do not create a public AI admin route or reuse `/api/v1/distribution` machine credentials for mutation.

The GET/read route is operator diagnostics and may expose bounded failure categories that P4/P5 intentionally do not expose publicly.

## Profiles UI

Extend the existing Profiles editor with a clearly separated **AI** fieldset/section for the selected Profile.

Required controls/status:

- checkbox/toggle: digest enabled;
- integer/lookback control: days, min 1, max 30, default 7 from server state;
- integer/max Articles control: min 1, max 20, default 20 from server state;
- text explaining evaluations occur twice daily and the current implementation uses 00:00/12:00 UTC slots;
- Save AI settings action;
- **Generate now** action;
- active digest status: no digest/current/older, generated time, input count, provider/model when present;
- latest attempt: scheduled/manual, outcome, attempt/completion time, bounded failure category;
- clear loading/saving/generating/error states using existing admin accessibility/status patterns.

Do not show or request the Gemini API key in Profile UI. Provider secret configuration remains deployment/operator environment configuration.

Do not render fetched Article bodies, prompts, raw model output, or customer-facing digest layout in this admin section.

### Browser behavior

- selecting/changing Profiles loads the corresponding AI state only;
- stale responses from a previously selected Profile must not overwrite the new Profile's AI panel;
- Save controls disable/busy appropriately during mutation;
- Generate now cannot be double-submitted accidentally from one browser interaction;
- server remains the real concurrency authority — UI disablement does not replace P3 claim protection;
- bounded failure text is human-readable without exposing internals;
- the section works generically for any Profile subject.

## Audit/change history

Record successful AI configuration changes through the existing append-only audit mechanism with a bounded generic action such as Profile AI configuration update. Do not log API keys (they are not part of input), provider responses, prompts, or attempt bodies.

Manual generation attempts already belong to P3 attempt history. Do not duplicate a full provider response into audit events. A small admin-command audit entry is optional only if current admin mutation policy requires it; avoid duplicating operational attempt state unnecessarily.
