TASK: Phase 0 / P1 — Server-rendered root and progressive enhancement

PHASE SCOPE
This is the sole implementation prompt for post-1.0 Phase 0 — Server-rendered public feed. The accepted baseline is `1.0.0`; the runner-compatibility gate is GREEN. Implement the Phase 0 ownership transition in one coherent change: `GET /` becomes the server-rendered canonical first public-feed page, and the existing browser client becomes progressive enhancement of that already-rendered state.

Do not split this into a server-only intermediate state or a client-only intermediate state. The current client unconditionally clears/refetches the first page, so SSR and client adoption must land together to keep the tree coherent.

MODEL / REASONING / USAGE
- Recommended configuration: `Terra High`.
- Model-family basis: this is bounded but cross-cutting Web/UI work spanning request parsing, HTTP outcome mapping, server-side output safety, SSR/client state ownership, browser history, and no-JavaScript behavior; Terra is the appropriate balanced engineering tier.
- Reasoning basis: High is warranted by interacting security and state invariants: root-form normalization must not weaken API parsing, CSP must allow only the required same-origin form navigation, server rendering must fail closed on unsafe data, and JavaScript must hydrate rather than erase/refetch correct server state while preserving stale-request and cursor behavior.
- Complexity / quality floor: `High`.
- Estimated usage: `High`.
- Lower-cost alternative considered: `Terra Medium`; rejected because the SSR/client ownership transition plus output-context safety, form/API parsing differences, history restoration, and continuation state create enough coupled edge cases to justify deeper reasoning.
- Escalation trigger: source inspection reveals a genuinely new shared read-model/security architecture decision, a required persistence/schema change, or a materially different hydration/state architecture than the governed bounded transition below.
- Escalation target: `Sol Medium`.
- Estimate confidence: `High`.
- Efficiency rationale: reuse the existing canonical `PublicFeedDependency.read()` boundary and existing DOM/CSS/client machinery; do not add another repository/query path, templating framework, hydration framework, or speculative abstraction.

ROOT-SPECIFIC DISCOVERY PARSING
The canonical API parser currently supports `q`, `source`, `category`, and `cursor`, keeps cursor criteria-bound, and intentionally rejects blank Source/Category config keys. Preserve those `/api/feed` semantics exactly.

Add the smallest sibling root parsing boundary, for example `parsePublicRootDiscoveryRequest(rawQuery)`, by reusing the existing raw decoding, duplicate detection, bounds, keyword normalization, config-key validation, and `PublicDiscoveryInputError` ownership rather than writing a second independent parser.

For root first-page navigation only:
- supported dimensions are `q`, `source`, and `category`;
- one blank `q=`, `source=`, or `category=` produced by an ordinary HTML form means that criterion is inactive after normalization;
- duplicate/repeated forms remain invalid even if one value is blank;
- unknown keys, malformed percent encoding, invalid config keys, and out-of-bound values remain invalid;
- any `cursor` parameter on `/` is bounded generic `400` in Phase 0, including a syntactically valid cursor; crawlable/server-rendered cursor continuation belongs to Phase 1;
- do not make plain root forms capable of weakening API cursor validation or changing API acceptance of blank Source/Category values.

Add focused unit tests that prove the root/API distinction explicitly. Do not expose decoder internals merely for testing if the public parser boundaries provide sufficient proof.

ROOT HTTP ORCHESTRATION
Convert the current static root handler into an async handler that:
1. obtains the raw query string through the same bounded request extraction style used by the API;
2. parses it through the root-specific first-page parser;
3. calls `dependencies.publicFeed.read(discoveryRequest)` exactly once for a valid request;
4. passes only the resulting canonical public feed plus normalized criteria/outcome class into the page renderer;
5. maps errors without leaking backend detail.

Required root status mapping:
- valid populated result -> `200` HTML;
- valid empty result -> `200` HTML;
- malformed/repeated/unknown/out-of-bound/root-cursor input -> `400` generic invalid-discovery HTML without calling the feed dependency;
- canonical `unsupported_discovery_filter` from Source/Category validation -> `400` generic invalid-discovery HTML;
- absent singleton Publication or non-public Publication -> generic `404` HTML;
- dependency/read/invalid-row/render-safety failure -> generic `503` HTML.

Retain `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, and a strict same-origin CSP. Do not expose SQL, stack traces, connection strings, private Publication state, internal IDs, normalized titles, summaries, authors, cursor internals, or other non-public fields in error or success HTML.

SERVER RENDERER
Evolve `src/app/web/public-feed-page.ts` from a constant loading shell into the narrow renderer for the root page. Do not introduce a general template engine or a new rendering framework for this one route.

For a successful public read, initial HTML must directly contain:
- configured Publication name;
- optional configured description;
- optional configured same-origin logo path;
- configured accent presentation where safe under the existing style approach;
- normalized active `q`/Source/Category controls;
- bounded public Source/Category choices from the canonical feed model;
- the canonical first Article page;
- effective feed date presentation using configured valid IANA `presentationTimezone`, falling back to UTC;
- Article headline;
- Source display name;
- exact stored `original_url` as the same-context headline anchor;
- populated or empty state/status markup;
- a configured, non-loading document title consistent with existing presentation behavior.

Keep the SSR row/list/control structure semantically compatible with the existing client-generated DOM so desktop/mobile CSS, accessibility, selectors, and later client transitions do not become parallel presentation implementations.

For `400`, `404`, and `503`, render bounded useful HTML with the same restrained public-page presentation. Do not manufacture Publication branding for unavailable/error states from private or failed data.

SERVER-SIDE CONTENT SAFETY
SSR is now an output security boundary. Treat dependency-fed Publication/Article/Source/discovery data as untrusted even though ordinary production persistence validates it earlier.

At minimum:
- escape every text node for HTML text context;
- escape every attribute value for HTML attribute context;
- validate Publication presentation values to the same bounded public contract before emitting them;
- logo path remains bounded same-origin path data, not arbitrary remote markup/content;
- accent remains the canonical safe color representation already governed by Publication configuration; do not emit arbitrary CSS text;
- effective feed dates must be valid before formatting/emission;
- `original_url` must be valid absolute HTTP/HTTPS and must contain no username/password credentials before it is emitted as an `href`;
- hostile values such as `<script>`, quote-breaking strings, event-handler-looking text, and markup-looking Source/headline labels must remain inert;
- if an injected/malformed dependency object violates required public render invariants, fail closed to generic `503` rather than emit unsafe/partial success HTML.

Keep existing client validation as defense in depth for API-driven enhanced transitions. Do not weaken it merely because the server now validates initial data.

NO-JAVASCRIPT DISCOVERY AND RESET
Make the SSR controls genuinely functional without JavaScript:
- discovery form must explicitly use same-origin root GET navigation, e.g. `method="get" action="/"`;
- allow only the necessary same-origin form destination by changing CSP `form-action 'none'` to `form-action 'self'`; do not add `unsafe-inline`, wildcard form targets, or other unrelated CSP relaxation;
- keep empty `All sources` / `All categories` options compatible with root-form normalization;
- provide Reset as a real same-origin `/` navigation that works with JavaScript disabled, preferably semantic `<a href="/" data-discovery-reset>` styled as the existing quiet secondary action;
- JavaScript may intercept/enhance Search and Reset when available, but no-JS behavior must remain the same first-page semantics.

Preserve native semantics, keyboard order, visible focus, target sizing, responsive reflow, and theme styling. This is not a redesign.

PROGRESSIVE CLIENT HYDRATION
The current client unconditionally calls `loadFirstPage(...)` on startup, clears the shell, and fetches `/api/feed`. Remove that initial ownership.

On a successful SSR page, `public-feed.js` must adopt the already-rendered DOM/state without reconstructing or replacing correct server output and without issuing an initial `/api/feed` request.

Use the smallest explicit bootstrap contract. Prefer semantic DOM plus bounded `data-*` attributes containing only values already public, such as:
- normalized criteria;
- Article IDs and any item fields genuinely needed by existing client state/continuation validation;
- opaque `nextCursor`;
- Publication presentation/timezone values required for later client rendering;
- resolved view state.

Do not add inline executable JavaScript, an unsafe inline CSP exception, a client framework, or a second serialized private read model. If a small inert serialized bootstrap representation is objectively simpler than many attributes, it must still contain only the canonical public fields, be safely encoded for its output context, preserve the CSP, and not become a competing public-feed authority.

Client startup must:
- validate/adopt the SSR state;
- initialize internal criteria/items/item-ID/next-cursor state needed by later interactions;
- keep the existing SSR Article nodes in place;
- attach/re-establish any required broken-logo fallback, including a logo that failed before deferred client startup;
- preserve configured accent/theme behavior;
- initialize the existing Load More control from the SSR cursor when present;
- leave populated/empty server states stable;
- never request `/api/feed` merely to reconstruct the same initial root state.

After hydration, preserve existing enhanced behavior:
- Search/Source/Category transitions may use `/api/feed` and `history.pushState`;
- Reset may be enhanced while remaining a real `/` link without JS;
- Back/Forward restores URL-reflected criteria/results;
- first-page stale-response generation/AbortController protection remains intact;
- changing criteria discards old continuation state;
- Load More uses the existing criteria-bound opaque API cursor and stays out of canonical root URL state in Phase 0;
- continuation duplicate-ID/repeated-cursor/empty-page guards and local failure UI remain intact;
- themes remain presentation-only and do not trigger feed requests.

Do not attempt full SPA hydration of `400`/`404`/`503` into an API-driven state. Error pages must already be useful server-side; client code may safely no-op where the required successful-feed DOM/state is absent.
