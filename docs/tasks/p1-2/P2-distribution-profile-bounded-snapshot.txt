## Required service boundary

Create the smallest transport-independent distribution read service/repository boundary that accepts a Profile `config_key` and returns a typed Profile read outcome.

The boundary must distinguish at least:

- Profile not found;
- Profile exists in `draft` lifecycle;
- Profile exists in `disabled` lifecycle;
- Profile exists and is `active`, producing a bounded coherent snapshot;
- bounded read/persistence failure.

Do not assign HTTP status codes here. Phase 4 will map these producer-owned outcomes to the permanent API contract.

Only an `active` Profile produces distributable Article results. Draft and disabled Profiles must remain distinguishable so the later HTTP layer does not query Profile persistence or invent lifecycle interpretation.

## Coherent PostgreSQL snapshot

The Profile aggregate, singleton Publication name, and canonical Article selection must be read from one coherent PostgreSQL snapshot.

Use the smallest existing database mechanism that provides this, expected to be one read-only `REPEATABLE READ` transaction established before the first domain read. Do not rely on ordinary separate `READ COMMITTED` queries that may combine Profile configuration from one database state with Article selection from another.

Do not acquire write locks, advisory locks, or participate in Phase 1's Profile↔Source mutation lock protocol merely for a read. The goal is snapshot consistency, not serialization with writers.

If the current database abstraction cannot establish a read-only repeatable-read transaction without invasive redesign, stop and report the observed blocker rather than adding speculative infrastructure.

## Canonical Profile filtering

Apply Profile Source membership and filters only after canonical Article eligibility.

A Source contributes Articles only when it has a Profile association and its Articles remain canonically outward-eligible under P1. The Profile cannot resurrect an Article from an unapproved/archived Source, a hidden/archived Article, or a visible non-Primary Duplicate member.

For each associated Source:

### Include phrases

- empty list means no include restriction;
- populated list uses OR: at least one phrase must match;
- matching is deterministic case-insensitive literal substring matching;
- search only effective outward headline, author, and summary;
- do not search normalized title, hidden Source-derived title variants, Source display name, URL, Category display name, or other fields;
- nullable author/summary simply do not match.

### Exclude phrases

- empty list means no exclude restriction;
- populated list uses OR: any phrase match excludes the Article;
- matching uses the same deterministic case-insensitive literal headline/author/summary fields;
- exclusion wins even when an include phrase also matches.

### Category selectors

- empty list means no Category restriction;
- populated list uses OR: at least one configured Category must be present in the Article's effective moderated Categories from P1;
- do not inspect historical observation/category reasons;
- an active intentionally empty Article Category override therefore matches no configured Profile Category.

### Dimension composition

For a Source association, include, exclude, and Category dimensions combine with AND, with exclusion taking precedence.

Across associated Sources, qualifying Articles form one union and then use the canonical global ordering from P1.

## Result/history bound and query strategy

The final active Profile snapshot contains at most `profile.resultLimit` Articles.

Filtering must happen before the Profile limit. Do not read a prematurely truncated unfiltered canonical window and then filter it in application code.

Prefer a fixed parameterized bounded query strategy. A safe shape is:

1. read the complete Profile aggregate inside the read-only repeatable-read transaction;
2. for each associated Source, execute a fixed canonical selection over P1's shared eligibility projection using that Source's Profile filters;
3. bound each Source candidate set to at most `profile.resultLimit` after that Source's filters;
4. merge the already canonically ordered per-Source candidate sets;
5. globally order by the shared canonical tuple;
6. retain only the first `profile.resultLimit` Articles.

This per-Source bound is complete because an Article below position `resultLimit` within one Source cannot appear in the first `resultLimit` rows of the union.

A single equally bounded fixed SQL query is acceptable if it is simpler and still consumes/reuses the canonical eligibility authority rather than restating it.

Do not:

- build SQL syntax from phrase text or config values;
- introduce regex/glob/fuzzy/semantic/expression behavior;
- scan an unbounded corpus in application memory;
- let Profile filtering mutate Article, Relevance, Category, Duplicate, or Source state.

## Active snapshot read model

The active snapshot must expose consumer-safe state needed by the later v1 API:

- Profile `configKey`;
- Profile `displayName`;
- Publication `name` only;
- complete bounded ordered Article set;
- for each Article: `articleId`, effective `headline`, exact stored `originalUrl`, `effectiveFeedDate`, `feedDateSource`, nullable persisted `publishedAt`, nullable `author`, nullable `summary`, nullable `imageUrl`, Source `{ configKey, displayName }`, and effective `categories[]` as `{ configKey, displayName }`.

Collections must be represented deterministically, including an empty Category collection when appropriate. Nullable Article metadata must remain genuinely nullable rather than replaced with invented defaults.

The active snapshot must also retain internal state P3 needs to derive a revision and continuation positions without rereading persistence or exposing those internals to the later transport. At minimum retain exact microsecond canonical order positions per item and the already-read semantic Profile/Source/filter state needed to detect meaningful snapshot change.

Do not add `apiVersion`, `generatedAt`, HTTP ETag values, or encoded cursors in this task.
