GOAL
Add the minimum durable, topic-independent persistence/configuration foundation required by later Phase 14 prompts:
- Source priority;
- optional Source RSS/Atom item admission phrases;
- `source_item_filtered_count` on Collection runs;
- aggregate/repository mapping so later collection/admin code can consume those values.

P1 owns durable representation, normalization, bootstrap initialization/no-overwrite compatibility, repository mapping, accounting validation, and focused real-PostgreSQL proof. P1 does NOT perform Raw-item matching and does NOT add admin routes.

MIGRATION
Add exactly one new forward migration after the current `0008_publication_presentation.sql`:

`migrations/0009_source_administration_foundation.sql`

Do not edit previously tracked migration SQL. Migration checksums are current behavior and must remain meaningful.

The migration must canonically add:

1. `sources.priority`
   - PostgreSQL integer;
   - NOT NULL;
   - existing/current Sources receive `0`;
   - CHECK non-negative;
   - priority is persisted/operator-managed configuration only in P1; do not alter feed/scheduler ordering yet.

2. Source RSS/Atom admission phrase persistence
   - use a normalized child table rather than JSON/JSONB or an array column;
   - each row belongs to exactly one Source through a real FK;
   - preserve deterministic operator ordering with an integer position/ordinal unique within one Source;
   - phrase must be trimmed, non-empty, control-character-free, and at most 512 characters;
   - support at most 64 phrases per Source through the application normalization boundary; database constraints must protect individual row shape/order integrity without inventing trigger-heavy machinery merely to enforce the aggregate count;
   - zero rows is the canonical no-filter/collect-all representation;
   - no exclude-phrase storage and no separate enabled flag.

3. `collection_runs.source_item_filtered_count`
   - NOT NULL non-negative integer with default zero for existing/new runs;
   - replace the old pre-normalization accounting constraint so, when parser/normalization accounting is applicable, the canonical equation is:
     `raw_item_count = source_item_filtered_count + normalized_candidate_count + normalization_failure_count`;
   - preserve `source_item_filtered_count <= raw_item_count` and existing Article-link/downstream outcome invariants;
   - do not change the downstream processing equation:
     `created + updated + unchanged + rejected + excluded + failed = normalized_candidate_count`.

- `priority: number`;
- `rssAtomAdmissionPhrases: readonly string[]`.

Normalization requirements:
- missing priority in bootstrap-compatible input normalizes to `0`;
- priority must be a safe integer, non-negative, and within PostgreSQL integer range;
- missing admission phrases normalizes to an immutable empty array;

- normalized results remain immutable/frozen as current configuration boundaries do.
