GOAL
Add the protected endpoint-administration command/read API under a real Source relationship.

P5 owns endpoint list/detail/create/update/state operations, polling configuration, endpoint-approved-domain narrowing, existing default Category assignment, and provenance-safe retirement semantics. It does NOT own durable check-now, health/run history, or final browser workflows.

RESOURCE IDENTITY / RELATIONSHIP
Admin endpoint operations are Source-scoped.

Use:
- Source immutable `config_key` in the parent URL;
- endpoint immutable `config_key` inside that Source.

Every endpoint operation MUST first resolve the Source and then resolve the endpoint as owned by that Source. An endpoint key that exists under another Source must behave as not found for the requested Source path.

Do not accept an endpoint UUID independently from the Source path as authority, and do not add Publication tenant identifiers.

ENDPOINT CREATE
Support creation under an existing Source with:
- immutable endpoint `configKey`;
- `endpointUrl`;
- endpoint type, currently only canonical `rss_atom` unless current contracts have explicitly promoted another type;
- approval state;
- operational state;
- positive bounded `pollIntervalSeconds`;
- optional endpoint domain narrowing rules;
- optional existing default Category config key.

New endpoints are created with lifecycle `active`.

Required validation before commit:
- Source exists and is not archived for ordinary create operations;
- endpoint config key is unique within that Source;
- endpoint URL/type/poll interval normalize through canonical Source configuration helpers;
- endpoint narrowing is equal to or narrower than Source approved-domain maximum;
- if the endpoint is created approved, its configured hostname is allowed by the effective Source/endpoint domain policy;
- default Category exists when specified;
- no endpoint may widen Source policy;
- no fetch/DNS/contact occurs during admin creation.

Create endpoint row, narrowing rules, and default Category relationship atomically.

ENDPOINT CONFIGURATION UPDATE
Provide one deterministic replacement-style configuration command for mutable endpoint-owned fields excluding immutable config key and explicit state/lifecycle commands.

At minimum mutable configuration includes:
- endpoint URL;
- endpoint type;
- poll interval;
- endpoint narrowing rules;
- optional existing default Category.

Use exact-key validation.

When updating an endpoint:
- lock/read Source first and endpoint second using the same global order as P4;
- validate proposed narrowing against current Source maximum;
- if endpoint is currently approved, reject a URL/narrowing change that would place the configured endpoint host outside effective approved policy;
- do not silently change Source domains or approval merely to accept an endpoint edit;
- preserve runtime telemetry/ETag/Last-Modified/history unless a governing contract explicitly requires a particular configuration change to clear a value; do not reset runtime state speculatively;
- do not contact the endpoint during validation.

DEFAULT CATEGORY
Reuse the existing Phase 11 endpoint default Category relationship.

Resolve Category by immutable config key, reject missing references, permit clearing according to the canonical request representation, and reuse `setEndpointDefaultCategory()` or a transactionally equivalent canonical repository operation.

Do not add Category CRUD.

ENDPOINT STATE COMMANDS
Keep approval, operational state, and lifecycle explicit/orthogonal.

Required operations:
- set approval `approved` / `unapproved`;
- set operational state `enabled` / `paused` / `disabled` while active;
- archive;
- restore to active.

Approval to `approved` MUST validate the configured endpoint host against current effective Source/endpoint approved-domain policy in the same transaction.

Archive semantics:
- lifecycle becomes `archived`;
- operational state becomes `disabled` atomically;
- retain approval, Collection runs, Article observations, job relationships, runtime history, and endpoint identity.

Restore semantics:
- lifecycle becomes `active`;
- operational state remains `disabled`;
- no implicit approval or re-enable;
- a later explicit enable is required to resume collection.

Operational state changes on archived endpoints fail rather than implicitly restore.

PHYSICAL DELETION
Do NOT add general endpoint `DELETE` in Phase 14.

The contract permits physical removal only when no retained dependent provenance exists, but it does not require destructive CRUD. Archive/retirement is the canonical operator-facing removal behavior for this phase and preserves Source endpoint → Collection run → observation/job history.

Do not create special orphan-cleanup logic solely to support deletion.

RECOMMENDED HTTP API
Use the P4/P3 conventions. Canonical intent:

`GET  /api/admin/sources/:sourceKey/endpoints`
`POST /api/admin/sources/:sourceKey/endpoints`
`GET  /api/admin/sources/:sourceKey/endpoints/:endpointKey`
`PUT  /api/admin/sources/:sourceKey/endpoints/:endpointKey/configuration`
`PUT  /api/admin/sources/:sourceKey/endpoints/:endpointKey/approval`
`PUT  /api/admin/sources/:sourceKey/endpoints/:endpointKey/operational-state`
`PUT  /api/admin/sources/:sourceKey/endpoints/:endpointKey/lifecycle`

All unsafe requests inherit P3 JSON/custom-header/body-size request-integrity controls.

READ MODELS
Endpoint list/detail should expose bounded operator-relevant configuration without leaking internal implementation details:
- Source config key and endpoint config key;
- endpoint URL/type;
- approval/lifecycle/operational state separately;
- poll interval;
- endpoint narrowing rules/inherited-policy indication;
- default Category identity when configured;
- runtime timing/health may be omitted or kept minimal here because P6 owns the canonical operational read model.

Do not expose raw response validators/secrets unless they are explicitly useful and governed for admin display. Avoid leaking internal UUIDs in normal API responses.

TRANSACTION / RACE SAFETY
Use real database transaction boundaries for mutations that depend on Source policy/current endpoint state.

At minimum protect against:
- concurrent Source approved-domain update versus endpoint URL/narrowing/approval update;
- concurrent archive/state update versus configuration mutation;
- wrong-Source endpoint mutation.

Reuse Source-first then endpoint locking/order rather than inventing an opposite lock order.

Do not weaken the separate Phase 4 per-endpoint collection run lock. Admin configuration locking and collection execution locking solve different problems.

- config key immutable;
- approval transitions;
- enabled/paused/disabled transitions;

- restore remains disabled;

Use disposable PostgreSQL for relationship, FK, locking/transaction, and provenance claims.
