TEXT NORMALIZATION FOR MATCHING
The parser's Raw-item `content` may contain Source markup. Admission matching must compare human editorial text rather than matching HTML tag names, attributes, script/style content, or entity spelling.

Extract/refactor the current pure plain-text conversion used by Article normalization into the smallest shared collection helper appropriate for both normalization and Source admission matching.

The helper must preserve existing normalization behavior:
- strip CDATA wrappers where applicable;
- remove script/style executable content;
- remove markup/comments;
- decode the existing bounded entity forms safely;
- collapse whitespace and trim;
- remain deterministic and side-effect free.

Do not move canonical Article-candidate normalization earlier in the pipeline. This helper is only text preparation for safe deterministic comparison and existing normalization reuse.

SOURCE ADMISSION EVALUATOR
Add one focused module under a suitable collection ownership path, for example:

`src/collection/admission/source-rss-atom-item-filter.ts`

The evaluator consumes:
- one `RawItem`;
- the Source-owned normalized admission phrase list.

Required semantics:
- empty phrase list => admit;
- one or more phrases => admit when ANY phrase matches ANY permitted editorial field;
- fields are Raw-item title, summary/content text, and Source-provided category labels only;
- missing fields simply do not match;
- comparisons are case-insensitive deterministic literal substring comparisons;
- normalize both phrase and field comparison text consistently with Unicode NFKC plus lowercase/case normalization suitable to the existing runtime;
- phrase characters that have regex/glob meaning remain ordinary literal characters;
- do not perform regex, glob, fuzzy, stemming, tokenization, semantic/AI, or general-expression evaluation;
- do not fetch or inspect the Article page/full body;
- do not inspect URL, author, date, diagnostics, language, image URL, or external ID as matching surfaces.

Keep the production evaluator small and pure. Do not create a second Relevance engine or generic policy framework.

PIPELINE INTEGRATION
Insert admission evaluation after successful RSS/Atom parsing and before the call to `normalizeArticleCandidate()`.

For each mismatching Raw item:
- increment `source_item_filtered_count` exactly once;
- do not call candidate normalization;
- do not call Article-link policy;
- do not load/evaluate Relevance for that item;
- do not call Article identity/persistence;
- do not create an Article observation.

For each admitted Raw item, preserve the existing downstream path unchanged.

All Raw items are already parser-bounded. Preserve the parser's item/field bounds and do not add a competing unbounded text source.

ACCOUNTING
Every successful parsed batch must satisfy:

`raw_item_count = source_item_filtered_count + normalized_candidate_count + normalization_failure_count`

Preserve:
- `source_item_filtered_count <= raw_item_count`;
- `article_link_rejection_count <= normalized_candidate_count`;
- `created + updated + unchanged + rejected + excluded + failed = normalized_candidate_count`.

A filter mismatch is NOT:
- a normalization failure;
- an Article-link rejection;
- a Relevance `excluded` outcome;
- a processing `failed` outcome.

Propagate the filtered count consistently through collection attempt results, Collection-run finalization, failure/result helper drafts that represent already-parsed batches, and persisted run mapping.

ALL-ITEMS-FILTERED BEHAVIOR
A parsed feed in which every Raw item is filtered is a successful content Collection run unless another stage-level failure occurs.

Required result:
- parser status succeeded;
- normalization stage completed successfully with zero candidates;
- `source_item_filtered_count = raw_item_count`;
- `normalized_candidate_count = 0`;
- all downstream candidate processing counters zero;
- no Article observations;
- do not load Relevance configuration merely because the existing processing helper historically loads it before iterating candidates.

Refactor the candidate-processing helper so an empty accepted-candidate batch does not require a Relevance snapshot. Preserve current behavior for non-empty batches.
