COLLECTION-RUN PROVENANCE
A durable job's Collection run must use the same trigger kind as the job.

Generalize the current scheduled run-store/attachment path so:
- claimed `scheduled` job => Collection run trigger `scheduled`;
- claimed `manual` job => Collection run trigger `manual`;
- Collection run is transactionally attached to the exact claimed job as today;
- attachment rejects a run whose endpoint, execution ID/job ID, claim ownership, or trigger kind does not match the job;
- recovery validates the same endpoint/execution/trigger relationship before reconciling an interrupted run;
- no durable manual job falls back to the separate direct-manual run-store path merely because its Collection run trigger is `manual`.

The existing direct Worker manual command remains different in orchestration: it is explicit immediate Worker invocation and not a durable queued job. It still records Collection run trigger `manual` and remains supported.

ADMIN CHECK-NOW COMMAND
Add protected admin API behavior:

`POST /api/admin/sources/:sourceKey/endpoints/:endpointKey/check-now`

Use P4/P5 real Source→endpoint resolution. Wrong-Source endpoint paths must not enqueue work.

Before enqueue:
- Source and endpoint must exist under the requested relationship;
- current Source/endpoint approval must be approved;
- lifecycle must be active;
- operational state must be enabled;
- singleton Publication collection must be active;
- perform no publisher network contact;
- do not acquire the collection run lock inside the Web process merely to enqueue.

If current state is non-collectable, return a bounded conflict/unprocessable result with stable safe reason rather than enqueueing work that is already known to be invalid. Execution still rechecks eligibility later to handle races.

When accepted:
- enqueue an immediately available attempt-1 job with trigger `manual`;
- never call `executeEndpointCollection()` from the HTTP request;
- never wait for the Worker to finish;
- return a bounded accepted/queued representation.

If one queued/running job already owns the endpoint outstanding slot:
- do not create a second overlapping job;
- return a deterministic non-error/accepted-conflict representation of the existing outstanding job so repeated button presses are idempotent from the operator perspective;
- preserve the existing unique index as the race authority.

Do not cancel/replace an already scheduled job just because a manual check-now is requested. The existing outstanding job owns the slot and will collect the endpoint through the same canonical path.
