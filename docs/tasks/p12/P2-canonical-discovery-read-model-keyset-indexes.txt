CANONICAL PATH LAW
Do NOT create a second feed/search eligibility implementation.

The item query that answers discovery requests must continue to apply the ordinary public-feed gates:
- singleton Publication must be public;
- Source must be approved;
- Source lifecycle must be active;
- Source operational state must NOT hide retained otherwise-eligible Articles;
- Article visibility must be `visible`;
- duplicate role remains logically ungrouped before duplicate grouping exists;
- endpoint operational/approval/lifecycle state and Collection-run success/failure are not public-row suppression gates;
- Article headline destination remains stored `original_url`.

Discovery criteria only narrow that eligible chronological stream.

REPOSITORY INPUT / OUTPUT
Change the canonical reader to accept the immutable normalized P1 discovery request, with a safe default equivalent for callers that need the unfiltered first page during the P2->P3 transition.

Extend the returned read model with the semantic equivalents of:
- existing `publication`;
- bounded public Source choices;
- bounded public Category choices;
- existing safe `items`;
- nullable opaque `nextCursor`.

A public discovery choice must contain only:
- `configKey`;
- `displayName`.

Do not expose Source/Category UUIDs, internal state fields, rule internals, observation reasons, Article normalized title/summary/author merely because search uses them, or cursor ordering internals.

PUBLIC PAGE SIZE
Retain the existing server page size of 100 Articles for Phase 12 unless the current contract/source now establishes another value before execution.

Implement continuation detection by selecting at most page-size + 1 matching rows internally, returning at most 100, and issuing `nextCursor` from the last returned row only when another matching row exists.

Do not add a public `limit`, offset, page number, total-count query, or count-before-fetch requirement.

PUBLICATION / INVALID-FILTER PRECEDENCE
Preserve indistinguishability of absent/private singleton Publication state.

A structurally valid but nonexistent/non-publicly-selectable Source or nonexistent Category is a discovery-input failure only after the repository has established that the singleton Publication is public. A private/absent Publication must not reveal whether a supplied Source/Category key exists through a different result/error.

Return/throw bounded typed repository/domain outcomes suitable for P3 to distinguish:
- no public Publication -> existing `undefined` semantics;
- unsupported Source/Category on a public Publication -> generic-discovery-400 category for the later HTTP layer;
- malformed DB row -> bounded repository invalid-row failure;
- database failure -> bounded repository read failure.

Do not put raw SQL, connection details, internal UUIDs, or full attacker input in exposed errors.

SOURCE FILTER
Source filtering uses immutable `sources.config_key` only.

A returned Article under a Source filter must still satisfy the ordinary Source approval/lifecycle gates.

A Source key is publicly selectable only when that Source is:
- `approval_state = 'approved'`;
- `lifecycle_state = 'active'`.

`operational_state = paused/disabled` does not make an otherwise approved active Source invalid for public discovery because operational state governs collection, not retained-feed visibility.

Public Source option metadata must never expose unapproved or archived Sources.

CATEGORY FILTER
Category filtering uses immutable `categories.config_key` and the Article's CURRENT `article_categories` membership.

Use `EXISTS` or another non-row-multiplying shape when practical. Do not join historical `article_observation_category_reasons` to decide current membership.

Historical observation/category evidence for a Category without current `article_categories` membership MUST NOT make the Article match.

Categories have no Phase 12 public lifecycle state; public metadata may expose configured Category stable identity/display name but no rule/default/reason internals.

COMBINED FILTERS
When supplied, `q`, Source, and Category compose with logical AND in addition to ordinary feed eligibility.

Do not build OR behavior between discovery dimensions and do not rerank based on number of matches.

KEYWORD SEARCH
Implement deterministic case-insensitive LITERAL substring filtering over only:
- `article.display_title`;
- `article.normalized_title`;
- `article.author` when present;
- `article.summary` when present.

Missing optional author/summary simply does not match.

Do not search:
- URLs;
- Source display/configuration fields;
- Category labels;
- observation reasons;
- arbitrary metadata;
- image/language/date fields unless a governing contract changed before execution.

The P1 normalized query is a SQL parameter. Never interpolate it into SQL.

Do not use unescaped `LIKE '%q%'`/`ILIKE '%q%'` in a way that treats `%` or `_` as wildcards. Prefer an explicit literal substring operation such as `strpos(lower(field), lower($n)) > 0` or an equally clear parameterized equivalent. Add focused tests proving `%`, `_`, backslash, and regex/glob-looking text are data, not search syntax.

Do not add PostgreSQL full-text ranking, `pg_trgm`, regex, fuzzy matching, stemming, semantic search, boost scoring, or query-language parsing.

ORDERING / KEYSET LAW
Matching rows retain exactly:
1. effective feed date DESC, where parsed `published_at` is used and otherwise `first_seen_at`;
2. `first_seen_at` DESC;
3. stable Article UUID ASC.

The cursor continuation predicate must be logically equivalent to "strictly after the last returned row" under that MIXED-DIRECTION tuple.

For cursor keys `(effective, firstSeen, id)`, later-page rows are those where:
- effective date is lower; OR
- effective date equals cursor effective and `first_seen_at` is lower; OR
- effective date and `first_seen_at` both equal cursor values and Article ID is GREATER, because the final key sorts ASC.

Do not accidentally use `id < cursorId` for the final tie.

HIGH-PRECISION TIMESTAMP LAW
P1 intentionally preserved cursor ordering timestamps beyond JavaScript millisecond precision.

The P2 SQL/result mapping must preserve the exact PostgreSQL ordering values used to create the cursor. Do not create a cursor from a JavaScript `Date` that may have truncated database microseconds.

A valid approach is to select dedicated canonical UTC microsecond timestamp strings for the two cursor keys, for example via explicit PostgreSQL formatting, while continuing to map the public `effectiveFeedDate` field to `Date` for the existing API response.

The cursor predicate must round-trip those exact canonical timestamp strings back to PostgreSQL comparison values without dropping precision.

Add a real-PostgreSQL test with timestamps that differ only below the millisecond boundary so the pagination proof would fail if JavaScript `Date` truncation controlled the cursor.

NO FROZEN SNAPSHOT PROMISE
Pagination does not hold a database transaction/snapshot across HTTP requests. Newly arriving Articles may appear on a later fresh first-page request.

P2 must guarantee deterministic keyset walking over a static result set; do not add server-side cursor sessions, snapshot IDs, temporary tables, or persistence solely to freeze pagination.

Order each list deterministically by a user-meaningful stable shape such as case-insensitive display name with immutable `config_key` as final tie-break. Do not let database physical order leak into response behavior.

If an active valid Source/Category filter would otherwise fall just outside the normal metadata cap, keep total metadata bounded but ensure the actively selected choice is present so a valid direct URL can be represented by P4.

An empty public Publication may still expose valid public discovery choices.
