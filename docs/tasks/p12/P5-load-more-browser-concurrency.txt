GOAL
Complete Phase 12 browser discovery by consuming server-issued opaque `nextCursor` values through an explicit Load more action. Preserve canonical URL criteria, append continuation rows exactly once, handle concurrent/stale requests safely, preserve already rendered rows on continuation failure, and reset continuation whenever URL-reflected discovery state changes.

CONTINUATION URL LAW
Load-more cursor depth is NOT canonical shareable URL state.

The root URL continues to contain only non-empty:
- `q`;
- `source`;
- `category`.

Do not push/replace browser history when Load more succeeds or fails.

Do not add:
- `cursor` to root URL;
- page number;
- offset;
- `limit`;
- loaded-row count;
- internal request-generation IDs.

CLIENT STATE MODEL
Extend the P4 state into one explicit coherent model containing the semantic equivalents of:
- active normalized discovery criteria;
- currently rendered Article items/IDs;
- current nullable opaque `nextCursor`;
- current first-page request ownership/generation;
- current continuation request ownership/generation;
- whether continuation is loading;
- bounded continuation-error state.

Do not scatter independent mutable cursor/criteria flags across unrelated event handlers if a small central state object/reducer-like helper is clearer.

The browser must never decode or infer ordering from the cursor.

LOAD MORE CONTROL
Render/show an accessible Load more button only when:
- the current successful feed state contains rendered Articles; and
- `nextCursor` is non-null.

During a continuation request:
- disable the button or otherwise guarantee one active continuation request at a time;
- expose a bounded loading status accessible to assistive technology;
- keep already rendered Articles visible.

When the final response returns `nextCursor = null`, remove/disable continuation affordance so another page cannot be requested accidentally.

Do not implement automatic infinite scroll, intersection observers, or background prefetching. One explicit user action is the Phase 12 requirement.

CONTINUATION REQUEST
Construct continuation API requests from the CURRENT normalized successful criteria plus the CURRENT opaque cursor.

The API request must include:
- `q` when active;
- `source` when active;
- `category` when active;
- exactly one `cursor`.

Use deterministic parameter order `q`, `source`, `category`, `cursor` for client-generated requests.

Do not send stale control DOM values that have not been applied to the current URL/result state.

APPEND SEMANTICS
On a currently owned successful continuation response:
- validate the complete P3 response before mutating DOM/state;
- confirm the response normalized `discovery.query` is semantically the same active criteria;
- append response items in server order;
- preserve existing rows before the appended rows;
- update stored `nextCursor` from the response;
- preserve Publication name/title and filter metadata unless the response provides compatible refreshed values;
- update status copy to reflect the total currently displayed Articles without implying total result count.

Do not re-sort continuation rows client-side. Server canonical order is authoritative.

DUPLICATE DEFENSE
The server's P2 keyset tests are the primary guarantee against duplicates/omissions, but browser concurrency must not create duplicates independently.

Before committing an appended page, detect an Article ID already present in the currently rendered set. If the response would append a duplicate Article ID:
- treat that continuation page as invalid/bounded pagination failure;
- preserve already rendered rows;
- do not silently deduplicate and pretend the page was valid;
- do not advance `nextCursor` from that invalid page.

This catches double-application/stale-page bugs without masking a backend contract violation.

CONTINUATION OWNERSHIP / RACES
At most one continuation request belongs to the current active criteria/result state.

Use explicit abort/generation ownership integrated with P4's first-page request ownership.

Required cases:

1. Double activation
- a second click/Enter while the same continuation is loading must not issue/apply a duplicate page.

2. Apply while continuation in flight
- changing criteria invalidates/aborts the continuation;
- old continuation response cannot append to new first-page results;
- new criteria start at page one.

3. Reset while continuation in flight
- old continuation becomes irrelevant;
- reset loads unfiltered first page;
- old continuation cannot append afterward.

4. Back/Forward while continuation in flight
- history navigation invalidates continuation;
- URL-reflected state loads first page only;
- old continuation cannot mutate restored history state.

5. New first-page request
- any existing continuation ownership is cleared before first-page state commits.

6. Stale callback/error
- stale/aborted continuation success or failure must not change current loading/error/button/result state.

FIRST-PAGE VS CONTINUATION ERROR POLICY
Keep P4 first-page errors unchanged.

A continuation failure is different because valid rows are already displayed.

For continuation:
- network failure, API 400/404/503, malformed payload, criteria mismatch, duplicate ID, or another invalid page must preserve currently rendered Articles;
- show one bounded pagination-specific error/status near the continuation control;
- do not replace the whole feed with initial `error`, `invalid`, or `unavailable` state solely because a later page failed;
- do not advance/clear the cursor merely because the request failed;
- re-enable Load more so the same current cursor can be retried when safe.

A 404/400 on continuation is still an unexpected later-page failure for the already rendered view; preserve rows and expose generic retryable pagination failure rather than leaking details.

A successful retry must append the page once and clear the continuation error.

CRITERIA / HISTORY RESET LAW
Any transition to a different URL-reflected first-page discovery state MUST discard:
- all appended rows from the previous criteria/history entry;
- old `nextCursor`;
- continuation loading/error state;
- continuation ownership;
- rendered-ID set from the old result.

This applies to:
- Apply/Search;
- Reset;
- Back;
- Forward;
- direct page refresh/reload naturally reconstructing first page.

Browser history restoration intentionally returns the URL's FIRST page, not the previous in-memory load-more depth. Do not invent cursor/history snapshot restoration.

METADATA CONSISTENCY
Continuation responses may carry the P3 discovery metadata again.

Do not let a stale continuation overwrite filter options for newer criteria.

For a current valid continuation, it is acceptable either to:
- leave current Source/Category options unchanged after validating compatible response shape; or
- replace them with the new bounded metadata if selected criteria remain representable.

Choose one deterministic simple behavior and test it. Do not create a second metadata cache keyed by cursor unless necessary.

PUBLIC STATUS COPY
Keep status messages bounded and truthful.

For populated pages, copy may say the number currently displayed, for example `100 headlines shown.` / `150 headlines shown.` Do not call that number a total result count because the API does not provide totals.

Continuation loading/error should use a separate live/status region or otherwise avoid destroying the main feed status/rows.
