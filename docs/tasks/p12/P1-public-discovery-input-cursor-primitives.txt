GOAL
Create one pure, topic-independent public discovery input and continuation-cursor module that later Phase 12 repository/API/browser prompts can reuse. P1 must define strict normalization, bounds, duplicate/unknown-input rejection, opaque/versioned cursor encoding/decoding, and cursor/query binding without changing the current public feed query, HTTP route, or browser behavior.

ARCHITECTURAL BOUNDARY
The P1 discovery module MUST remain:
- database-free;
- Express-free;
- DOM/browser-free;
- network-free;
- filesystem-free;
- clock-free;
- randomness-free;
- topic-independent.

It may use deterministic standard-library helpers such as `node:crypto` for a criteria fingerprint.

The later stack must have one canonical logical discovery-request shape. Do not create separate SQL-specific and HTTP-specific interpretations of `q`, `source`, `category`, or `cursor`.

PUBLIC DISCOVERY PARAMETERS
Support exactly these optional public query parameters:
- `q`;
- `source`;
- `category`;
- `cursor`.

No `limit`, offset/page number, ranking, sort, Publication selector, slug, or arbitrary query parameter is introduced.

Each supported key represents at most one logical value. Reject repeated forms even when repeated values are identical. Reject unknown parameter names rather than silently ignoring them.

RAW QUERY PARSING
Provide a pure parser that can consume the raw query-string representation available from the HTTP request before framework coercion loses ambiguity.

Requirements:
- preserve the ability to detect repeated parameters;
- reject malformed percent escapes;
- reject invalid UTF-8 percent-encoded sequences rather than silently replacing them;
- handle ordinary query `+` space semantics deterministically;
- reject a raw query string beyond a conservative documented bound before expensive decoding;
- decode names and values exactly once;
- do not allow malformed encoding to become a different normalized valid request.

A small manual pair decoder using `decodeURIComponent` with caught URI errors is acceptable if it remains simple and fully tested. Do not build a general-purpose URL parser.

NORMALIZED CRITERIA
Produce an immutable/frozen logical request shape containing the semantic equivalents of:
- optional normalized keyword query;
- optional Source `config_key`;
- optional Category `config_key`;
- optional validated continuation position.

Use deterministic normalization:
- trim `q` at the input boundary;
- a post-trim empty `q` is equivalent to no keyword criterion;
- bind cursor identity to a deterministic case-normalized representation of `q` because Phase 12 search is case-insensitive;
- Source/Category identities are not case-repaired; they must already satisfy the persisted immutable `config_key` grammar;
- `source` and `category` empty values are invalid rather than meaning no filter.

PUBLIC BOUNDS
Use small explicit constants with tests. Unless current source/contracts already establish stricter compatible limits, use:
- raw query string: maximum 8192 characters;
- normalized `q`: maximum 200 Unicode code points;
- Source `config_key`: persisted maximum 100 ASCII characters and grammar `^[a-z0-9]+(_[a-z0-9]+)*$`;
- Category `config_key`: same persisted maximum/grammar;
- encoded cursor: maximum 2048 ASCII characters before decode.

Do not duplicate these numeric/grammar limits in unrelated modules later; export/narrowly reuse the P1 helpers where appropriate.

CURSOR CONTRACT
Implement a small opaque base64url-encoded versioned cursor. JSON inside base64url is acceptable because opacity means callers must not depend on its representation; encryption is not required.

The cursor must contain only the semantic equivalents of:
- cursor format version `1`;
- deterministic fingerprint/digest of normalized `q`/`source`/`category` criteria;
- exact effective-feed-date ordering key;
- exact `first_seen_at` ordering key;
- stable Article UUID ordering key.

Use a stable criteria representation with explicit field order and null/absent treatment before hashing. SHA-256 hex/base64url is acceptable. Do not use process-random secrets or signatures; the token is validated state, not an authentication credential.

TIMESTAMP PRECISION
Do NOT define cursor timestamp keys as JavaScript millisecond epoch numbers or ordinary `Date` values only. PostgreSQL `timestamptz` can preserve finer precision than JavaScript `Date`, and losing that precision can create pagination omission/repetition around ties.

Define cursor ordering timestamp keys as a canonical UTC textual representation that can preserve PostgreSQL microseconds, for example exactly `YYYY-MM-DDTHH:mm:ss.ffffffZ`, or another equally precise deterministic representation that P2 can round-trip through PostgreSQL without precision loss.

The pure P1 validator must reject malformed/non-canonical timestamp keys. It may use `Date` only as one validation aid for calendar/range sanity; it must not truncate the stored cursor key to milliseconds.

CURSOR VALIDATION
Decoder must fail closed on:
- malformed/non-base64url token;
- token beyond bound;
- invalid UTF-8/JSON;
- non-object or array payload;
- missing/extra fields when exact shape is expected;
- unsupported version;
- invalid criteria fingerprint shape;
- invalid canonical timestamp keys;
- invalid Article UUID;
- cursor fingerprint that does not match the normalized criteria supplied with the request.

All malformed/unsupported discovery-input failures should use one bounded application error type/reason family suitable for P3 to map to a generic public `400`. Do not include attacker-controlled full input or secrets in public-facing error messages.

IMMUTABILITY / DETERMINISM
- Freeze returned discovery request/cursor position structures consistent with current project conventions.
- Do not mutate caller-provided data.
- Repeated parse/encode/decode of equivalent inputs must produce the same semantic result.
- Cursor encode -> decode -> encode should be deterministic for the same canonical position/criteria.
- Do not read locale, environment, time, random state, Publication topic, Source display name, or Category display name.
