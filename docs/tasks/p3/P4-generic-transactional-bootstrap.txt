LOCKED BOOTSTRAP CONTRACT
Bootstrap is explicit initialization input, not competing runtime authority.

Stable identities:
- Publication: slug;
- Source: `(publication_id, config_key)`;
- Source endpoint: `(source_id, config_key)`.

Ordinary bootstrap behavior:
- create an absent record from validated bootstrap input;
- when the stable identity already exists, use the existing record and leave the entire record unchanged;
- do not update existing name/site URL/state/domain/URL/type/polling/narrowing/timestamps merely because seed input differs;
- do not recreate an obsolete endpoint merely because an operator changed its URL after initial bootstrap;
- no Source/endpoint discovery;
- no auto-approval outside explicit bootstrap data;
- no approval inferred from successful fetch;
- no domain widening;
- no Web/API or Worker startup mutation;
- no network access.

A bootstrap document MAY explicitly request `approved / active / enabled` Source/endpoint state. That is deliberate operator input, not an approval bypass. P4 tests should use synthetic approved data to prove the generic path.

BOOTSTRAP DOCUMENT
Define one explicit JSON document shape for one Publication tree.

It should contain only Phase 3 fields, conceptually:
- Publication name/slug/collection/public state;
- Sources array;
- each Source: config key, display name, site URL, approval/lifecycle/operational state, approved-domain rules;
- each endpoint: config key, URL, type, approval/lifecycle/operational state, polling interval, optional narrowing rules.

Use P2 validators to normalize/validate leaf values. Add only the small document-level validation needed for:
- required object/array shape;
- exactly one Publication document per invocation;
- duplicate Source config keys inside the document rejected;
- duplicate endpoint config keys inside one Source rejected;
- duplicate normalized domain rules rejected through P2;
- malformed/unknown required field values rejected predictably.

Do not add future Phase fields.

INPUT VALIDATION ORDER
Before starting database mutation:
- read/parse the complete JSON document;
- validate all input-intrinsic fields and internal duplicates;
- normalize all host/rule/key/state/polling values possible without database state.

Some semantic validation necessarily depends on persisted state. In particular, a new endpoint being added beneath an already-existing Source must be checked against that Source's CURRENT persisted approved-domain policy, not blindly against the seed document's stale Source policy.

TRANSACTION BOUNDARY
Bootstrap one Publication tree inside one `Database.transaction(...)` call.

If any required new record cannot be validly/persistently created, all records newly created by that bootstrap invocation must roll back.

Do not open independent nested transactions for each Source/endpoint.

CREATE-IF-ABSENT ALGORITHM
Within the transaction:

PUBLICATION
1. lookup by slug;
2. if present, use the persisted Publication unchanged;
3. if absent, race-safely insert from the validated bootstrap Publication input;
4. if another concurrent bootstrap wins the insert race, resolve to the now-existing row rather than failing or creating a duplicate.

SOURCE
For each configured Source under the resolved Publication:
1. lookup by Publication ID + Source config key;
2. if present, use the persisted Source and persisted Source-domain rules unchanged;
3. if absent, race-safely insert the Source plus complete validated Source-domain policy;
4. never update an existing Source to match seed data.

ENDPOINT
For each configured endpoint under the resolved Source:
1. lookup by Source ID + endpoint config key;
2. if present, use the existing endpoint unchanged and do not compare mutable fields as a reason to create/update anything;
3. if absent, validate the new endpoint and its narrowing against the CURRENT persisted Source maximum policy;
4. race-safely insert the endpoint plus narrowing;
5. if another concurrent invocation wins, resolve to the existing endpoint without mutation.

The config key is the stable identity. Endpoint URL is not bootstrap identity.

CRITICAL NO-OVERWRITE CASES
A rerun must preserve operator-managed changes to any existing record, including:
- Publication name;
- Publication collection/public state;
- Source display name/site URL;
- Source approval state;
- Source lifecycle state;
- Source operational state;
- Source approved-domain rules;
- endpoint URL;
- endpoint type/state/polling;
- endpoint narrowing.

If an operator changed endpoint URL from seed URL A to B but kept the endpoint config key, rerunning the original seed MUST leave B in place and MUST NOT recreate URL A as another endpoint.

CURRENT-PERSISTED-POLICY CASE
If Source stable identity already exists and its approved-domain policy differs from the seed:
- bootstrap must not restore/widen the Source policy;
- an already-existing endpoint is left unchanged even if seed values now differ;
- a seed endpoint that is genuinely absent may be created only if the endpoint's current proposed configuration is valid against the persisted Source policy;
- if it is not valid, fail the Publication-tree bootstrap transaction rather than widening the Source policy.

This case is required proof that bootstrap yields to later operator authority.

RACE / CONCURRENCY SAFETY
Do not rely on a check-then-insert sequence that can fail under concurrent invocations.

Use a race-safe PostgreSQL pattern, for example an explicit repository primitive using `INSERT ... ON CONFLICT DO NOTHING RETURNING ...` followed by stable-key lookup when necessary. The exact implementation may differ, but it must:
- rely on P1 uniqueness constraints;
- converge on one logical Publication/Source/endpoint tree;
- avoid transaction-aborting uncaught unique violations in normal races;
- never convert a conflict into an update of mutable fields.

Do not add a global bootstrap lock unless a real implementation requirement justifies it. Stable uniqueness + race-safe inserts should be sufficient for this narrow create-if-absent operation.

First run:

Idempotent rerun:
- second identical bootstrap returns successfully;
- Publication/Source/endpoint logical cardinality does not increase;
- domain-rule cardinality does not increase.

Operator no-overwrite:
- mutate existing Publication fields via controlled direct SQL to simulate later admin authority, rerun seed, verify changes survive;
- mutate existing Source display/site/state/domain policy, rerun, verify every changed field/rule remains unchanged;
- mutate existing endpoint URL/state/polling/narrowing, rerun, verify every change survives;

Persisted Source policy:
- create/bootstrap Source, then change its persisted domain maximum;
- present a later seed containing an absent endpoint that would require the old/wider seed Source policy;
- rerun must reject/roll back rather than widen Source policy;
- verify existing Source policy remains untouched.

Transactional rollback:
- arrange a Publication document where an early new record can insert but a later new endpoint fails a database/semantic invariant depending on persisted state;
- verify no new records from that invocation survive;
- preserve pre-existing records unchanged.

Concurrency:
- invoke equivalent bootstrap concurrently against one disposable DB using independent Database instances/connections;
- both invocations should complete safely or one may report a well-defined non-corrupting result according to implementation, but final logical cardinality must be exactly one stable tree;
- no duplicate Source/endpoint/domain rows;
- no partial tree/corrupt state;
- avoid arbitrary sleeps; synchronize naturally through Promise concurrency/PostgreSQL constraints.
