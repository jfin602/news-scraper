## Goal

The required ownership chain is:

`cryptographic issuance -> one-time plaintext result + secure persisted verifier -> lifecycle metadata/revocation/rotation -> narrow repository/service exports`

This prompt does not authenticate HTTP requests, implement rate limiting, add admin routes/UI, or build `/api/v1/distribution/...`.

## Persisted model

Add exactly one additive migration after the current chain, normally:

`migrations/0016_distribution_credentials.sql`

Do not modify migrations `0001` through `0015`.

Create one installation-owned credential table/model with the minimum fields needed by the governing contract:

- internal UUID primary key;
- unique immutable non-secret lookup identity suitable for indexed authentication lookup;
- secure fixed-length verifier/digest bytes for the secret portion;
- bounded human-readable label;
- capability constrained to `distribution:read` for the initial 2.0 model;
- creation timestamp;
- lifecycle/update timestamp if the established repository convention requires it;
- nullable expiration timestamp;
- nullable revocation timestamp/state;
- optional self-reference or equivalent non-secret lineage metadata sufficient to identify a credential created as a rotation successor without making the predecessor invalid automatically.

Do not persist:

- plaintext bearer tokens;
- recoverable secret material;
- Authorization header values;
- a credential-to-Profile authorization relation;
- Publication/customer/tenant identity merely for scoping;
- billing/quota fields that are not required by Phase 3.

Credential ownership is the isolated News Scraper instance. Any valid future `distribution:read` credential is instance-scoped, not Profile-scoped.

Use database constraints for durable invariants where appropriate: unique lookup identity, fixed/validated capability, sane non-empty label representation, valid self-reference shape, and non-destructive relationship behavior. Do not encode current time-dependent expiry/revocation decisions in brittle database checks that depend on `now()` semantics.

## Token and verifier authority

Add the smallest coherent credential module under `src/distribution/` (a `credentials/` submodule is appropriate if it improves ownership clarity).

Use Node built-in `node:crypto`; do not add a dependency merely for API-key generation/hash comparison.

Define one versioned, bounded opaque token format that contains:

1. a non-secret lookup component that can be parsed before database access; and
2. an independently generated high-entropy secret component.

The exact prefix/separators are implementation-owned, but the format must be canonical, unambiguous, bounded, and forward-versionable. The secret must contain at least 256 bits of cryptographically secure randomness before encoding. The lookup identity must be non-secret and collision-resistant enough for its indexed identity role.

Persist only a secure fixed-length verifier/digest derived from the high-entropy secret. A straightforward cryptographic digest is acceptable because the generated secret itself has high entropy; do not weaken security with reversible encryption or plaintext storage.

Export narrow primitives needed by P2 so authentication can:

- parse the canonical token into lookup identity + secret material;
- derive the exact verifier candidate from supplied secret material;
- compare fixed-length verifier bytes safely without exposing stored verifier state to controllers/serializers.

Keep verifier representation internal. Ordinary list/read models must never contain it.

## Lifecycle service/repository boundary

Expose a topic-independent service/repository boundary sufficient for later admin and authentication consumers to:

- issue a new credential with label and optional expiration;
- list credential metadata without verifier or plaintext token;
- find verifier-bearing authentication material only through a narrow authentication-oriented lookup by non-secret lookup identity;
- revoke an existing credential;
- rotate an existing credential by issuing a new successor while leaving the predecessor unchanged/usable until it is explicitly revoked or naturally expires;
- distinguish missing credential records from persisted metadata without leaking secret state.

One-time issuance semantics are mandatory:

- the issue/rotate operation may return the new plaintext bearer token to its immediate caller exactly as transient application data;
- no later repository/service read can reconstruct or return that plaintext token;
- no verifier/digest may appear in ordinary admin metadata.

Rotation is overlapping by design. Creating the successor MUST NOT silently revoke the predecessor. Revocation must be an explicit separate lifecycle action.

Make revocation safe under repeated operator intent. Prefer an idempotent result or another clearly bounded deterministic outcome rather than producing ambiguous partially-mutated state.

Do not invent credential deletion. Retain lifecycle/audit metadata so revocation history remains observable.

## Audit and secret-safety requirements

Follow established `audit_events` conventions for lifecycle mutations if current architecture treats administrative configuration/lifecycle changes as audited state.

Any credential audit state MUST contain only non-secret metadata such as lookup identity, label, capability, expiry, revocation state, and rotation lineage. It MUST NOT contain:

- plaintext token;
- secret component;
- verifier/digest;
- Authorization header;
- another recoverable credential representation.

Likewise, errors and implementation reports must never print generated real credential plaintext except where an explicit synthetic test value is necessary and clearly test-only.

If transactional audit ownership would be cleaner in P3 because current audit conventions are strictly administration-owned, keep the persistence service capable of transactional composition and document the handoff. Do not duplicate lifecycle mutation logic merely to write an audit row.

## Input and metadata bounds

Centralize deterministic credential metadata validation rather than scattering it across HTTP/UI layers.

At minimum:

- label is trimmed, required, bounded, and rejects control characters;
- optional expiration is represented unambiguously as an absolute timestamp and round-trips exactly enough for lifecycle decisions;
- capability is not caller-selectable beyond the single governed `distribution:read` capability;
- lookup/token encoded lengths are bounded;
- malformed persisted verifier/token-version state is treated as a bounded credential-layer failure rather than silently accepted.

Do not create an extensible arbitrary capability/role framework for hypothetical future authorization.

## Real-PostgreSQL and production migration proof

Add focused database tests for the new persisted boundary. Prove at minimum:

- migration from zero includes `0016` after the existing chain;
- supported upgrade from the accepted production migration history through `0015` to `0016` preserves all representative existing governed state;
- a credential can be issued after that forward upgrade and its verifier/lifecycle metadata persists correctly;
- plaintext token bytes are absent from the credential row and ordinary audit/read-model state;
- lookup identity uniqueness and capability constraints are enforced;
- label/expiry metadata round-trips;
- revocation persists without deleting the record;
- rotation creates a distinct successor and leaves the predecessor unchanged until explicit revocation;
- multiple independent credentials may coexist in one instance;
- no Profile association or Publication tenancy is introduced.

Extend migration assertions rather than weakening existing Phase 1 production-upgrade coverage.

Because this phase introduces governed credential-verifier state, extend the native backup/restore representative-state test so at least one credential record with non-secret metadata and verifier bytes survives backup/restore exactly. The test must not need or persist the original plaintext token to prove verifier preservation.

## Unit proof

Add focused unit tests for token/metadata primitives. At minimum cover:

- cryptographic generation produces the canonical versioned shape;
- generated secrets meet the required entropy byte length before encoding;
- two issues produce distinct lookup IDs/secrets;
- parser rejects malformed, wrong-version, truncated, extra-component, and oversized tokens;
- verifier derivation is deterministic and fixed-length;
- metadata validation bounds and optional expiration normalization;
- public/read metadata never includes secret/verifier fields by construction.

Use deterministic injected/random test seams only where necessary for assertions. Production generation must always use a cryptographically secure source.

## Downstream handoff

Before P1 is complete, prove this producer matrix:

`plaintext credential creation -> issuance service -> one-time returned token + persisted verifier -> unit + PostgreSQL proof`

`non-secret lookup identity -> indexed repository auth lookup -> verifier-bearing internal auth record -> PostgreSQL proof`

`credential metadata -> redacted list/read model -> no secret/verifier -> unit/PostgreSQL proof`

`revoke -> persisted revocation state -> authentication-consumable record -> PostgreSQL proof`

`rotate -> new successor + unchanged predecessor -> overlapping validity-capable persisted state -> PostgreSQL proof`

`supported production baseline -> additive 0016 -> preserved existing governed data -> production-forward PostgreSQL proof`

`credential verifier state -> native backup/restore -> exact persisted verifier/metadata -> recovery proof`

P2 must not need to query credential tables directly except through the narrow repository export, invent token parsing, recreate verifier derivation, or infer lifecycle columns from raw SQL.
