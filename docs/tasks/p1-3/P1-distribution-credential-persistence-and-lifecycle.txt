TASK: Phase 3 / P1 — Distribution credential persistence and lifecycle

- Recommended configuration: `Terra High`.
- Model-family basis: bounded security-sensitive work crosses production schema evolution, cryptographic secret handling, lifecycle persistence, and downstream authentication completeness.
- Reasoning basis: high reasoning is justified by the need to preserve supported customer data while ensuring plaintext credentials never enter persistence, audit, logs, or ordinary read models.
- Complexity / quality floor: `High`.
- Estimated usage: `High`.
- Lower-cost alternative considered: `Terra Medium`; rejected because production-forward migration integrity and secret-lifecycle ownership create enough combined data/security risk to justify deeper reasoning.
- Escalation trigger: current schema cannot represent the required lifecycle without rewriting supported migration history, or secure one-time issuance would require a materially different credential architecture.
- Escalation target: `Sol Medium`.
- Estimate confidence: `High`.
- Efficiency rationale: use Node built-in cryptography, one additive relational migration, and a narrow credential module; do not add an auth framework, ORM, generic secrets store, tenancy layer, or external credential service.

The assigned project version is `1.3.1`.

## Goal

Create the permanent instance-local persisted machine-credential and lifecycle authority that later Phase 3 authentication and protected administration consumers can use without knowing credential table topology or ever receiving stored plaintext secrets.

Required ownership:

`cryptographic issuance -> one-time plaintext result + secure persisted verifier -> lifecycle metadata/revocation/rotation -> narrow transaction-composable repository/service exports`

This prompt does not authenticate HTTP requests, implement rate limiting, add admin routes/UI, or build `/api/v1/distribution/...`.

Read current `BOOT.md`, `AGENTS.md`, the Project Contract, distribution API/integration contracts, domain/data contract, testing contract, security/operations guidance, production-data compatibility ADR, backup/restore guidance, Phase 3 roadmap entry, the migration chain through `0015_distribution_profiles.sql`, database/repository conventions, current administration audit patterns, migration/production-upgrade tests, and recovery helpers.

## Additive persisted model

Add exactly one migration after the current supported chain, normally:

`migrations/0016_distribution_credentials.sql`

Do not modify migrations `0001` through `0015`.

Persist one installation-owned credential record with the minimum governed fields:

- internal UUID primary key;
- unique immutable non-secret lookup identity suitable for indexed auth lookup;
- secure fixed-length verifier/digest bytes for the secret portion;
- bounded human-readable label;
- capability constrained to `distribution:read`;
- creation timestamp and any ordinary lifecycle/update timestamp justified by current conventions;
- nullable expiration timestamp;
- nullable revocation timestamp/state;
- optional non-secret rotation-predecessor lineage sufficient to identify a successor without invalidating the predecessor automatically.

Do not persist plaintext bearer tokens, recoverable secret material, Authorization values, Profile authorization relations, tenant/customer keys, or billing quota state.

Use database constraints for durable invariants such as lookup uniqueness, fixed capability, required bounded stored representation, and valid self-reference. Do not encode time-dependent expiry decisions in brittle `now()` check constraints.

Credential scope is the isolated News Scraper instance. Multiple credentials may coexist and every valid future credential has only `distribution:read`; there is no credential-to-Profile matrix.

## Token and verifier authority

Create the smallest coherent credential module under `src/distribution/`, using a `credentials/` submodule if that best matches ownership.

Use `node:crypto`; do not add a dependency.

Define one canonical, bounded, versioned opaque token format containing:

1. a non-secret lookup component parseable before database access; and
2. an independently generated secret containing at least 256 bits of cryptographically secure randomness before encoding.

The exact prefix/separators are implementation-owned but must be unambiguous and forward-versionable.

Persist only a secure fixed-length verifier/digest derived from the high-entropy secret. Do not use reversible encryption or plaintext storage.

Export narrow primitives P2 can reuse to:

- parse canonical token -> lookup identity + supplied secret material;
- derive the candidate verifier;
- perform/enable fixed-length safe verifier comparison without exposing stored verifier state to controllers/serializers.

Ordinary metadata must not contain verifier bytes.

## Transaction-composable lifecycle boundary

Expose narrow repository/service primitives that accept the existing database executor/transaction abstraction where appropriate so P3 can compose a lifecycle mutation and sanitized admin audit row in one transaction.

P1 owns credential semantics; P3 owns human-administration audit composition.

P1 must support:

- issue new credential from validated label + optional expiry;
- list redacted credential metadata;
- authentication-only lookup by non-secret lookup identity returning the minimum internal verifier/lifecycle material P2 needs;
- revoke an existing credential;
- rotate an existing credential by issuing a distinct successor while leaving the predecessor unchanged until separately revoked/expired;
- deterministic missing/repeated-revocation outcomes.

One-time issuance is mandatory:

- issue/rotate may return the newly generated plaintext token only to their immediate caller as transient application data;
- no later read can reconstruct it;
- no ordinary metadata contains it or the verifier.

Do not implement deletion. Retain lifecycle metadata.

## Audit ownership and secret safety

Do **not** write `audit_events` in P1. Current repository convention places administrative audit composition in the administration service. P1 must instead expose transaction-composable lifecycle primitives so P3 can atomically write sanitized audit events without duplicating credential business rules.

Credential row timestamps are the persisted lifecycle/audit metadata owned here.

P1 must guarantee its returned ordinary metadata is safe for P3 audit state. Safe audit fields may include lookup identity, label, capability, expiry, revocation state, and non-secret rotation lineage. Never return plaintext token or verifier as part of that ordinary metadata.

Errors/implementation reports must not print generated real bearer plaintext. Synthetic test-only tokens are allowed only when explicitly test data.

## Validation and bounds

Centralize deterministic metadata/token validation. At minimum:

- label is trimmed, required, bounded, and rejects control characters;
- optional expiry is an unambiguous absolute timestamp and round-trips reliably;
- capability is server-fixed, not caller-extensible;
- token/lookup encoded lengths are bounded;
- malformed token versions/verifier persistence fail boundedly rather than authorizing.

Do not create a generic role/capability framework.

## Unit proof

- malformed/wrong-version/truncated/extra-component/oversized tokens are rejected;

- ordinary public/admin metadata types cannot contain token/verifier fields.

Use deterministic test seams only where needed; production generation must use CSPRNG output.
