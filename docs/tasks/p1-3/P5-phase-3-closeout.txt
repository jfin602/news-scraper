## Pass 1 — Contract and evidence review

Review the integrated implementation against every Phase 3 roadmap exit condition and governing machine-security contract.

### Credential generation and persisted state

Verify from source and evidence that:

- bearer secrets are generated with strong cryptographic randomness and at least the planned entropy floor;
- the token format is canonical, bounded, versioned/forward-versionable, and supports indexed non-secret lookup without scanning verifier rows;
- plaintext bearer tokens are returned only at issue/rotation time and are never persisted;
- PostgreSQL stores only non-secret lookup identity, secure verifier/digest, fixed `distribution:read` capability, label, lifecycle/audit timestamps, optional expiry, revocation state, and bounded non-secret rotation lineage where implemented;
- ordinary repository/admin read models cannot expose verifier bytes;
- audit records, error objects, logs, test snapshots, and browser persistence do not contain bearer plaintext or verifier bytes;
- multiple credentials may coexist in one instance without creating tenancy or a credential↔Profile authorization matrix.

### Production schema compatibility

Verify:

- migration `0016` (or the actual planned additive Phase 3 migration) follows the existing supported chain without rewriting `0001`–`0015`;
- migration from zero succeeds;
- a real supported production-forward upgrade preserves pre-existing governed customer state;
- credential verifier/lifecycle state created on the new schema round-trips and survives native backup/restore;
- migration/recovery tests do not use plaintext persistence as their proof mechanism;
- rollback/restore assumptions remain compatible with the production-data ADR.

### Lifecycle and rotation

Verify:

- issue/list/revoke/rotate semantics have one owning service/repository path;
- revocation retains the record and blocks later machine authentication;
- expiration is optional and evaluated predictably at the exact boundary;
- rotation creates a distinct new credential and leaves the predecessor usable until explicit revocation/expiry;
- no operation silently recovers or copies predecessor plaintext;
- repeated revocation is deterministic/bounded and cannot corrupt lifecycle state;
- rotation/revocation audit state contains only redacted metadata.

### Machine authentication

Verify:

- machine credentials are accepted only as caller-supplied Authorization Bearer values through the canonical auth boundary;
- token query-string/body/cookie credential acceptance has not been introduced;
- P2 reuses P1 parsing, verifier derivation, and indexed auth lookup rather than duplicating them;
- unknown lookup IDs still execute fixed verifier-comparison work against a dummy verifier rather than trivially skipping comparison;
- stored/candidate verifier comparison uses appropriate fixed-length timing-safe comparison;
- malformed, unknown, wrong-secret, revoked, expired, capability-invalid, and unusable/corrupt credentials collapse to one outward unauthenticated result without credential-state leakage;
- successful principals contain only redacted non-secret identity plus `distribution:read`;
- no Profile key is required to authenticate and no Profile-specific permission/403 model exists.

Do not require flaky wall-clock timing equality. Require structural boundedness and absence of obvious existence/state shortcuts.

### Rate/abuse foundation

Verify:

- authenticated rate limiting is keyed by non-secret credential identity;
- invalid-auth abuse limiting is separately keyed by bounded caller-provided network identity;
- future HTTP/proxy code, not this security core, owns trusted client-network extraction;
- limiter state is memory/cardinality bounded and cleans/evicts stale attacker-controlled keys safely;
- bearer plaintext is never a limiter key;
- exact limit/time boundaries produce deterministic positive `retryAfterSeconds`;
- failed authentication does not consume a guessed valid credential's authenticated quota;
- successful authentication does not consume invalid-auth failure quota;
- current process-local semantics are represented honestly and are not documented/tested as cross-process distributed enforcement.

### Human admin controls

Verify:

- create/list/revoke/rotate admin operations are protected by the existing admin surface and mutation-integrity middleware;
- the admin API is a thin consumer of P1 lifecycle and does not reconstruct verifier/lifecycle logic;
- list/revoke responses contain only safe metadata;
- create/rotate expose only the newly generated plaintext token as explicit transient response data;
- no route exists to reveal an old token;
- machine bearer credentials are never interpreted as human administrator authority;
- current Cloudflare Access perimeter assumptions remain unchanged and local tests do not falsely claim to validate Cloudflare itself.

### Browser workspace

Verify:

- the credential workspace consumes only P3 protected routes;
- one-time token display is transient and cleared on dismissal/navigation/replacement/reload as implemented;
- plaintext is absent from URL/localStorage/sessionStorage/cookies/long-lived global state/console/error text;
- rotate UX clearly states predecessor overlap until explicit revoke/expiry;
- revoke retains historical metadata;
- verifier/digest fields are never rendered;
- accessibility, narrow-viewport usability, and existing admin workspace behavior remain intact.

### Phase 4 producer readiness

Audit this exact handoff:

`downstream-required capability -> owning implementation/export -> focused proof`

Require a concrete owner/proof for:

- strict Authorization Bearer parsing;
- token version/shape validation;
- indexed non-secret lookup;
- verifier candidate derivation + timing-safe comparison;
- dummy verifier path for unknown identity;
- revocation/expiration/capability authorization decision;
- redacted authenticated machine principal;
- generic unauthenticated outcome;
- per-credential limit decision;
- invalid-auth network abuse decision;
- positive `retryAfterSeconds` on rate-limited outcomes;
- strict absence of admin authority;
- instance scope/no Profile permission matrix.

Phase 4 must be able to compose the Phase 2 Profile page producer with the Phase 3 security guard without inventing credential SQL, token parsing, lifecycle interpretation, verifier checks, quota counters, or authorization semantics.

## Pass 2 — Error and edge-case adversarial review

Independently derive realistic attacks/failures from the final implementation. Do not merely confirm test names.

At minimum inspect applicable cases involving:

### Token/verifier attacks

- absent header;
- multiple/combined Authorization header values as represented by Express/Node;
- wrong scheme;
- case/whitespace edge cases according to the chosen strict grammar;
- empty token;
- wrong version/prefix;
- too many/few token components;
- malformed base64url/UUID/lookup encoding;
- control characters;
- embedded delimiters;
- huge header/token inputs;
- unknown lookup identity;
- valid lookup with random wrong secret;
- truncated/extended secret;
- verifier length corruption;
- persisted malformed capability/verifier state;
- accidental string comparison instead of fixed-byte safe comparison;
- different work path for unknown identity that creates an obvious lookup-existence oracle;
- token or verifier values entering thrown errors/logs.

### Lifecycle/race/state combinations

- revocation immediately before/after authentication lookup;
- expiry exactly at `now`;
- clock injection/timezone conversion errors;
- rotate then authenticate old/new;
- rotate then revoke predecessor;
- revoke then repeated revoke;
- attempts to rotate a missing/revoked/expired predecessor according to the final documented service semantics;
- concurrent-ish repeated admin rotate submissions producing multiple successors;
- transaction/audit failure after mutation begins;
- duplicate/colliding lookup identity retry behavior;
- dependency failure during issue/rotate without leaking transient secret into persistence/audit;
- database restart/service reconstruction using verifier-only state.

Where current architecture is single-process and operations are short transactions, do not invent unsupported distributed guarantees; still ensure failure/transaction boundaries are coherent.

### Rate/abuse attacks

- exact quota boundary;
- window/refill rollover;
- very large/invalid policy values;
- empty/oversized network keys;
- flood of unique invalid-auth keys;
- stale-key cleanup and hard-cap behavior;
- eviction strategy enabling trivial unlimited bypass;
- one credential starving another;
- invalid attempt with a guessed valid lookup identity debiting that valid credential;
- blocked invalid network path continuing to hit PostgreSQL unnecessarily;
- retryAfter zero/negative/NaN/overflow;
- wall-clock changes if implementation incorrectly depends on non-monotonic assumptions;
- limiter object recreated per request, accidentally disabling enforcement.

### Admin/browser secret leakage

- one-time token included in ordinary list state after create/rotate;
- token copied into audit event JSON;
- token in browser URL/history;
- token retained after dismiss or workspace navigation;
- token redisplayed after hard reload;
- previous token remaining when a rotation returns a new token;
- token in thrown fetch error/console diagnostics;
- verifier field accidentally serialized because a repository object is spread into JSON;
- machine bearer token bypassing admin mutation integrity;
- admin disabled but credential routes accidentally mounted;
- CSP weakened to support the new UI.

For each plausible issue classify it as:

1. already protected by source structure + executed evidence;
2. bounded Phase 3 bug/test gap that can be repaired inside closeout;
3. meaningful behavior-preserving refactor requiring the Terra High handoff below; or
4. contract/architecture/new-scope problem requiring stop/escalation/replanning.

A bounded closeout repair is permitted only when behavior is already unambiguous under Phase 3 contracts and all invalidated evidence can be rerun.
