- Recommended configuration: `Terra High`.
- Model-family basis: the task is a bounded but security-critical producer covering bearer parsing, verifier comparison, revoked/expired handling, abuse resistance, and a Phase 4 reusable authorization result.
- Reasoning basis: high reasoning is warranted by generic-failure requirements, timing/state-leak risk, limiter ordering, bounded attacker-controlled state, and the need to keep HTTP response policy out of the producer.
- Complexity / quality floor: `High`.
- Estimated usage: `High`.
- Lower-cost alternative considered: `Terra Medium`; rejected because authentication correctness and abuse-boundary mistakes can become externally exploitable once Phase 4 mounts the producer.

- Estimate confidence: `High`.
- Efficiency rationale: compose the P1 token/verifier/repository authority with small deterministic authentication and in-process limiter primitives; do not introduce Passport, sessions, Redis, a distributed quota service, or the Phase 4 route.

## Bearer authentication contract

Implement one canonical machine authentication function/service under the distribution credential/security boundary.

It must accept only an Authorization-header value supplied by its caller. It MUST NOT inspect query-string parameters or accept tokens from cookies/body/path values.

Parsing requirements:

- only the `Bearer` scheme is accepted;
- require exactly one non-empty bearer credential with no trailing credential components;
- reject malformed, wrong-scheme, oversized, non-canonical, wrong token-version, and otherwise invalid token shapes boundedly;
- do not echo supplied tokens in errors;
- do not log Authorization values or token fragments.

Use the P1 parser/verifier/repository exports. Do not introduce another token syntax, digest function, or credential SQL path.

## Verification and lifecycle behavior

For a syntactically valid token:

1. parse the non-secret lookup identity and secret using P1;
2. perform one indexed lookup through P1's authentication repository boundary;
3. derive the candidate verifier using the P1 authority;
4. perform a fixed-length timing-safe comparison against either the persisted verifier or a fixed dummy verifier when the lookup identity is unknown;
5. only after verifier comparison evaluate persisted capability/revocation/expiry for authorization success.

The goal is constant/bounded authentication structure, not a mathematically identical wall-clock duration across PostgreSQL cache/network conditions. Unknown lookup IDs must not skip verifier work in a way that creates an obvious credential-existence oracle.

All of these states must collapse to the same public authentication outcome with no reason exposed to Phase 4's external error serializer:

- malformed/unsupported bearer token;
- unknown lookup identity;
- wrong secret;
- revoked credential;
- expired credential;
- missing/invalid `distribution:read` capability;
- malformed persisted credential state that cannot safely authorize.

Internally, narrowly scoped non-secret telemetry categories MAY distinguish failure classes if existing observability conventions support that without leaking secrets. Do not expose those distinctions through the returned external-auth reason.

A successful principal should expose only what downstream code needs, such as:

- stable internal/non-secret credential identity;
- non-secret lookup identity if operationally useful;
- label if useful for telemetry;
- fixed `distribution:read` capability.

It must never expose verifier bytes or plaintext token material.

Credential authentication is instance-scoped. Do not accept a Profile key or create a credential↔Profile authorization check.

## Rate-limit and invalid-auth abuse foundation

Add a deterministic bounded request-guard/limiter foundation that Phase 4 can compose around the authentication result.

Two independently keyed protections are required:

1. authenticated requests: primary limit keyed by the authenticated credential's non-secret identity;
2. failed/invalid authentication: separate abuse limit keyed by a bounded network identity supplied by the future HTTP caller.

The future caller owns extraction of the network identity from trusted request/proxy context. This prompt MUST NOT invent `X-Forwarded-For` trust policy or parse arbitrary forwarding headers.

A small process-local limiter is acceptable for the current single Web/API process architecture. It is a Phase 3 foundation, not a claim of cross-process/global quota enforcement. If current runtime architecture already contains a better shared limiter primitive, reuse it.

The limiter must:

- use injected/testable monotonic or controlled clock semantics;
- have explicit bounded policy inputs/central defaults rather than magic values scattered through callers;
- return an allowed/rate-limited decision plus integer `retryAfterSeconds` sufficient for Phase 4's `Retry-After` mapping;
- avoid an unbounded attacker-controlled key map through expiry/cleanup and a hard cardinality bound or equivalent bounded strategy;
- avoid retaining bearer secrets as keys;
- keep authenticated-credential and invalid-network buckets logically separate;
- handle exact window/refill boundaries deterministically;
- fail closed or boundedly when policy/input state is invalid.

Do not implement billing quotas or persistent quota counters.

## Combined Phase 4-facing guard

Expose one obvious producer interface that Phase 4 can call with:

- Authorization header value (or absence);
- bounded caller-provided invalid-auth network key;
- configured/constructed limiter policy/dependencies.

It should return a typed result equivalent to:

- `authenticated` with redacted machine principal;
- `unauthenticated` with no credential-state reason;
- `rate_limited` with `retryAfterSeconds` and only the non-secret classification needed for internal telemetry.

The exact type names are implementation-owned.

Ordering must protect both resources and semantics:

- if an invalid-auth network key is already blocked, the guard may reject before database verification;
- otherwise authenticate through the bounded path;
- failed authentication consumes/updates only the invalid-auth bucket;
- successful authentication is evaluated against the per-credential limiter;
- an invalid-auth attempt must never consume another valid credential's quota merely because an attacker guessed its lookup identity.

Do not return HTTP status codes or Express responses from the transport-independent core. A very thin adapter/helper may be added under `src/app/web/` only if necessary to normalize a raw Authorization header into the core call, but no distribution route is authorized.

## Security proof

Add focused security/unit tests covering at minimum:

- absent Authorization;
- wrong scheme/casing/shape according to the chosen strict parser;
- empty, malformed, oversized, wrong-version, truncated bearer values;
- unknown lookup identity;
- valid lookup + wrong secret;
- valid active non-expired credential succeeds;
- revoked credential fails generically;
- expired credential fails generically at the exact boundary;
- future expiry succeeds before the boundary;
- capability mismatch/corrupt persisted capability cannot authorize;
- unknown lookup executes fixed verifier-comparison work through the dummy verifier path;
- returned principal contains no token/verifier;
- returned unauthenticated result does not reveal unknown/wrong/revoked/expired distinctions;
- no Profile key is needed for authentication;
- generated machine principal has no administrator role/capability.

Do not attempt flaky microbenchmark timing assertions. Test structural constant/bounded behavior with injected/spied verifier/lookup seams where appropriate.

## Limiter proof

Add deterministic unit/security tests proving:

- authenticated requests are isolated by credential identity;
- invalid-auth attempts are isolated by supplied network key;
- reaching a limit returns stable positive `retryAfterSeconds`;
- allowance resumes after the governed time boundary;
- failed auth does not debit an authenticated credential bucket;
- successful auth does not count as an invalid-auth failure;
- attacker-controlled invalid keys cannot grow retained limiter state without bound;
- cleanup/eviction does not permit a trivially permanent bypass of the configured bound;
- malformed/empty network keys are rejected or normalized according to one explicit bounded rule;
- token plaintext is never used as a limiter key.

If limiter implementation uses mutable in-process state, cover its repeated-call and cleanup behavior thoroughly. No real PostgreSQL proof is needed for pure limiter mechanics.

## Database/integration proof

Use real disposable PostgreSQL for the credential lifecycle/authentication interaction. At minimum prove:

- a P1-issued credential authenticates from its persisted verifier;
- process/service restart represented by reconstructing the auth service from the database still authenticates without plaintext persistence;
- revocation immediately prevents later authentication;
- overlapping rotation allows old and new credentials until old is revoked;
- expiration is enforced from persisted state;
- unknown lookup and wrong-secret paths remain generic;
- ordinary list/read state remains redacted.

Do not re-test every P1 migration constraint in this prompt; preserve P1 evidence and focus on the consumer behavior.

## Machine/admin separation

Phase 3 machine auth must remain completely separate from human administrator authority.

Prove structurally and with focused integration coverage that:

- the machine principal contains only `distribution:read`;
- no admin router/middleware consumes it as administrator identity;
- presenting a machine bearer token cannot bypass the existing admin mutation-integrity requirement;
- disabling the admin surface remains independent from machine credential existence;
- this prompt does not add native administrator login/session behavior.

Remember that Cloudflare Access is the managed human perimeter outside the local Express test harness. Do not falsely claim a local test proves Cloudflare itself.
