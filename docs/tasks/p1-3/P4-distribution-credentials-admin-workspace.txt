TASK: Phase 3 / P4 — Distribution credentials admin workspace

- Recommended configuration: `Terra Medium`.
- Model-family basis: this is a bounded browser/control-plane consumer over the P3 API with a security-sensitive one-time-secret UX but no new credential semantics.
- Reasoning basis: medium reasoning is adequate because backend lifecycle rules are already explicit; the main risks are secret retention, stale UI state, and accidental duplication of server authority.
- Complexity / quality floor: `High`.
- Estimated usage: `Moderate`.
- Lower-cost alternative considered: `Luna High`; rejected because transient bearer-secret presentation and revocation/rotation UX warrant Terra's stronger security-sensitive implementation baseline.
- Escalation trigger: the current modular admin shell cannot host the credential workspace without a broader redesign, or P3 lacks an API operation/error shape necessary to implement the required workflow safely.
- Escalation target: `Terra High`.
- Estimate confidence: `High`.
- Efficiency rationale: reuse the existing admin shell, shared `api()` request-integrity helper, browser test harness, and CSS conventions; do not add a client framework, state library, or secret-storage mechanism.

The assigned project version is `1.3.4`.

## Goal

Add the minimum first-class administrator presentation needed to create, list, rotate, and revoke machine distribution credentials safely.

This is required roadmap control-plane functionality on `main`, not optional visual-polish work on `ui-polish`.

The UI must remain a thin consumer:

`operator -> existing admin api() helper -> P3 protected credential routes -> P1 authoritative lifecycle -> returned server state`

The browser must never implement token generation, verifier logic, expiry/revocation authority, machine authentication, or Profile permissions.

## Workspace and navigation

Add a dedicated admin navigation item/workspace named clearly for machine distribution credentials, for example `Credentials` or `Distribution Credentials`.

Keep existing Publication, Sources, Editorial, Profiles, Articles/Moderation, Operations, and other current workspaces intact and reachable.

Prefer a new isolated module such as:

`src/app/web/admin/credentials.js`

plus only the minimal shell/asset/CSS changes needed to register and render it.

Do not add inline executable script, external client dependencies, runtime eval, or a framework/state-manager migration. Preserve the existing CSP and safe DOM patterns.

## Credential list

Load P3's credential list and render safe metadata only:

- label;
- non-secret lookup identity;
- fixed capability `distribution:read`;
- created timestamp;
- optional expiry;
- current derived lifecycle/status such as active, expired, or revoked;
- safe rotation lineage if P3 exposes it and it materially helps the operator.

Never expect, render, request, or retain verifier/digest fields.

Provide explicit loading, empty, ready, and bounded error states. Support refresh/reload from authoritative server state.

Do not use plaintext token as browser identity or place it in URL/query/hash state.

## Create workflow

Provide a compact form for:

- required label;
- optional expiration.

Do not expose capability selection or Profile permissions. The server owns the single `distribution:read` capability.

Submit through P3's create route using the existing shared `api()` helper so the admin mutation-integrity header/body conventions remain automatic.

After success:

1. adopt the returned safe metadata as authoritative list state;
2. display the newly returned plaintext token in a dedicated **one-time secret** panel;
3. clearly state that the token cannot be shown again and should be copied to the intended consumer's secret configuration;
4. provide a simple copy action when compatible with current browser patterns;
5. provide an explicit Dismiss/Clear action.

Do not put the token into localStorage, sessionStorage, cookies, IndexedDB, URL state, form defaults, hidden elements kept after dismissal, analytics, console logging, or reusable global application state.

The token may exist in the active DOM/state only as long as necessary to show the one-time result. Dismissal, navigation away from the workspace, another secret-producing action, or a full reload must clear it.

Do not attempt to recover the token later.

## Rotate workflow

Allow rotation of an existing credential through P3.

The UI must explain the governed overlap semantics accurately:

- rotation creates a **new** credential/token;
- the predecessor remains usable until the operator explicitly revokes it or it expires;
- rotation itself is not revocation.

On success:

- refresh/adopt authoritative metadata;
- replace any previously displayed transient secret with the newly issued successor token;
- show the same one-time-copy warning;
- do not display or recover the predecessor token.

Prevent accidental double submission using normal in-flight UI state, but do not invent backend idempotency semantics the server does not provide.

## Revoke workflow

Provide an explicit revoke action for a credential that is not already revoked.

Use P3's revoke route and adopt the returned authoritative metadata. Make the effect clear: future machine authentication for that credential is disabled; the record remains for lifecycle/audit history.

Do not implement deletion.

Use a confirmation affordance consistent with current admin patterns if available, but do not introduce a new modal framework merely for this action.

Repeated/reloaded revoked state should render safely without offering misleading recovery actions.

## Expiration and status UX

Render expiration in an operator-readable way while treating server-returned timestamps/state as authoritative.

The UI may derive a visual `expired` label from a server timestamp for presentation, but it must not use browser clock state to decide whether the machine credential actually authenticates. P2 remains the security authority.

Avoid continuously running timers unless already part of the admin shell. A normal refresh is sufficient to update presentation.

## Error handling

Handle P3's bounded errors near the relevant workflow without exposing raw response bodies or destroying unrelated list state.

At minimum cover:

- invalid create/rotate input;
- missing credential;
- lifecycle/conflict result if exposed by P3;
- generic dependency failure;
- existing request-integrity failures through the shared helper.

A failed create/rotate must not fabricate a secret or credential row. A failed revoke must not mark the credential revoked locally.

When state may have changed concurrently, retain context and provide an obvious Refresh action rather than guessing authoritative state.

## Secret-handling browser safety

Use safe text/value DOM APIs. Treat the plaintext token as sensitive even though it must be visible once.

Required behavior:

- no token in `innerHTML` templates that could be retained/interpreted unsafely;
- no token in accessible labels unrelated to the one-time display;
- no token in page title/navigation/history;
- no token in console output or thrown error text;
- copying uses the exact returned token only on explicit operator action;
- after Dismiss/Clear, the token text is absent from visible DOM and application state reachable by the workspace;
- a hard reload cannot redisplay it because P3 list responses are redacted.

Do not add a "show old token" or "reveal" feature.

## Accessibility and responsive baseline

Follow existing admin conventions. At minimum:

- navigation/workspace is keyboard reachable;
- all forms/buttons have accessible names;
- list status/lifecycle text is not color-only;
- one-time-secret warning and copy result are meaningful to assistive technology;
- focus moves sensibly after create/rotate so the operator can find the newly issued secret;
- revoke/rotate controls remain usable at narrow viewport;
- long labels/lookup identities/tokens wrap or scroll safely without breaking the overall admin layout;
- existing admin workspaces retain their navigation/accessibility behavior.

This prompt is functional roadmap UI, not a broad visual redesign.

Reuse the current admin browser/service-stub harness. Do not require real PostgreSQL for browser behavior already proven by P1-P3.

2. empty/list state renders only safe metadata;

Update shared admin-page/browser assertions only where the new navigation item requires it. Do not duplicate unrelated workspace coverage.

Before P4 is complete, map and prove:

`admin nav -> credential workspace -> P3 list -> safe metadata -> browser proof`

`create form -> P3 create -> one-time token panel -> dismiss/reload clears -> browser proof`

`rotate -> P3 rotate -> successor one-time token + predecessor overlap explanation -> browser proof`

`browser state -> no verifier/plaintext persistence -> secret-safety browser proof`
