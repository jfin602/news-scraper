TASK: Phase 3 / P3 — Protected distribution credential administration

- Recommended configuration: `Terra Medium`.
- Model-family basis: this is a bounded cross-file administration/API task consuming already-governed P1 lifecycle semantics while preserving the existing managed admin perimeter and one-time-secret boundary.
- Reasoning basis: medium reasoning is adequate because the security/domain rules are explicit; the main risk is accidentally leaking transient secrets or duplicating P1 lifecycle logic in HTTP code.
- Complexity / quality floor: `High`.
- Estimated usage: `Moderate`.
- Lower-cost alternative considered: `Luna High`; rejected because one-time bearer-secret exposure and human/machine authority separation warrant Terra's stronger security-sensitive implementation baseline.
- Escalation trigger: P1 lacks a complete lifecycle service, the current admin composition cannot return a one-time secret without exposing it through shared state, or implementing the controls requires changing the human-auth perimeter.
- Escalation target: `Terra High`.
- Estimate confidence: `High`.
- Efficiency rationale: follow the existing admin service/router/registration patterns and reuse request-integrity/error handling rather than creating a second admin framework or moving credential security into controllers.

The assigned project version is `1.3.3`.

## Goal

Expose the Phase 3 credential lifecycle to an authorized human operator through the existing protected administration application/API boundary while keeping P1 as the credential authority and P2 as the machine-authentication authority.

Required chain:

`protected admin request -> credential administration service -> P1 lifecycle authority -> redacted metadata or one-time newly issued plaintext`

This prompt does not build the browser workspace yet and does not expose the permanent distribution API.

## Administration application service

Add a narrow service, preferably under `src/admin/`, that owns admin input validation and maps the P1 credential lifecycle into safe operator read models.

Required operations:

- list credentials;
- create a credential;
- revoke a credential;
- rotate a credential.

Use the non-secret immutable lookup identity as the operator/API resource key. Never use bearer plaintext as identity and never require a database UUID in browser-facing routes.

### Admin metadata read model

List/revoke results must expose only bounded non-secret fields required to operate credentials, such as:

- lookup identity;
- label;
- fixed capability `distribution:read`;
- created timestamp;
- optional expiration;
- revocation timestamp/state;
- rotation predecessor/successor identity only if P1 deliberately exposes safe lineage metadata;
- derived operator-friendly lifecycle state when useful, without creating a second persisted lifecycle authority.

The read model MUST NOT contain:

- plaintext token;
- token secret component;
- verifier/digest;
- Authorization header;
- internal data not required by the operator.

### Create

Accept a strict exact bounded input containing:

- label;
- optional expiration.

Capability is fixed by the server. Do not accept arbitrary roles/capabilities or Profile permissions.

A successful create response may contain the P1-issued plaintext bearer token exactly once together with its safe credential metadata. Treat that plaintext as a distinct transient field that is not part of the ordinary persisted/read model.

### Revoke

Revoke by non-secret lookup identity. Preserve P1's deterministic/idempotent lifecycle behavior. Return safe current metadata only.

Do not delete the credential.

### Rotate

Rotate by non-secret lookup identity using P1's overlapping-rotation primitive. Allow the operator to provide only the bounded new metadata P1 supports, such as a replacement label and optional expiry. Do not silently revoke the predecessor.

The successful rotate response may expose the new plaintext bearer token exactly once with the successor metadata. It must make no attempt to recover/display the predecessor secret.

Do not implement rotation by reading the old secret or copying verifier bytes.

## Audit ownership

If P1 already owns transactional sanitized lifecycle audit events, consume that behavior without duplicating audit rows.

If P1 deliberately left audit composition to administration, write the established `audit_events` rows transactionally with the lifecycle mutation and include only redacted metadata. Never place plaintext token or verifier bytes into `prior_state`, `new_state`, exception messages, logs, or test snapshots.

Do not introduce a second competing audit convention.

## Protected admin HTTP surface

Register a dedicated credential administration router through the existing `/admin/api` route registrar pattern.

Use a small REST-like surface. Exact verbs may follow current conventions, but the final API must provide clear bounded operations equivalent to:

```text
GET  /admin/api/distribution-credentials
POST /admin/api/distribution-credentials
POST /admin/api/distribution-credentials/:lookupId/revoke
POST /admin/api/distribution-credentials/:lookupId/rotate
```

Do not add an endpoint that returns a credential plaintext after creation/rotation.

All mutation routes must inherit the existing admin security middleware:

- admin surface enabled only by current managed configuration;
- existing `X-News-Scraper-Admin-Request` mutation-integrity requirement;
- JSON content-type/body bounds and duplicate-key rejection;
- no-store/security headers;
- existing outer Cloudflare Access deployment perimeter.

Do not add machine bearer authentication to `/admin/api` and do not treat a P2 machine principal as an administrator.

## HTTP response safety

Define compact deterministic response shapes.

Suggested shape:

- list: `{ credentials: [...] }`;
- create/rotate: `{ credential: <safe metadata>, plaintextToken: <one-time token> }` or a similarly explicit one-time field;
- revoke: `{ credential: <safe metadata> }`.

The exact one-time field name is implementation-owned, but it must be unmistakably separate from ordinary metadata.

Map expected admin validation/resource/lifecycle errors to bounded `400`/`404`/`409` classes consistent with current admin conventions. Unexpected dependency failures must flow through the existing bounded admin error handler.

Never serialize:

- verifier/digest;
- SQL/constraint/internal stack details;
- token fragments in error objects;
- a distinction between P2 invalid-auth credential states, because P2 machine authentication is not used by these routes.

## One-time-secret proof

Add focused application/integration tests proving:

1. create returns one plaintext token and safe metadata;
2. subsequent list does not return that plaintext token;
3. list never returns verifier/digest fields;
4. rotate returns a different new plaintext token once;
5. subsequent list contains successor metadata but neither old nor new plaintext;
6. predecessor remains non-revoked after rotation until revoke is requested;
7. revoke returns safe metadata and no plaintext;
8. no endpoint can fetch/recover plaintext by lookup ID;
9. API errors do not echo supplied label/token-like data unnecessarily or leak internal verifier state.

Use synthetic credentials only in tests.

## Admin security and authority-separation proof

Extend focused integration/security coverage for:

- admin-disabled deployment does not expose credential admin routes;
- list/create/revoke/rotate are mounted only under the existing admin API;
- mutation without the existing admin request-integrity header receives the established integrity failure;
- wrong/non-JSON mutation bodies retain current bounded behavior;
- a valid P2 machine bearer token alone does not bypass admin mutation integrity or cause an admin route to treat the request as machine-authorized;
- credential admin registration does not alter `/`, `/api/feed`, health, or existing admin route behavior;
- no new CORS/public route exposes admin credential controls.

Do not claim these local tests prove Cloudflare Access itself; they prove the application preserves its existing perimeter assumptions and does not create a bearer-based admin bypass.

## Downstream P4 handoff

Before P3 is complete, prove:

`list -> protected admin GET -> redacted credential metadata -> integration proof`

`create -> protected admin POST -> P1 issuance -> one-time plaintext + redacted metadata -> integration/security proof`

`rotate -> protected admin POST -> P1 overlapping successor -> one-time successor plaintext -> integration/PostgreSQL proof`

`revoke -> protected admin POST -> P1 persisted revocation -> redacted metadata -> integration/PostgreSQL proof`

`machine bearer alone -> no admin authority elevation -> admin-security proof`

P4 must not need to query P1/P2 directly, infer revocation/expiry, reconstruct rotation semantics, or know verifier/table topology. It should be a thin browser consumer of these protected routes.

## Preserved behavior

Preserve:

- P1 credential/token/verifier/lifecycle authority;
- P2 machine authentication and rate/abuse guard;
- current Cloudflare Access + request-integrity human-admin boundary;
- every existing admin workspace/API route;
- Phase 1/2 distribution behavior;
- `/`, `/api/feed`, health/readiness;
- collection/idempotency/provenance/duplicate laws;
- topic independence and single-Publication deployment.

## Non-goals

Do not implement:

- `/api/v1/distribution/...`;
- machine-auth HTTP middleware on a distribution route;
- Profile authorization or credential↔Profile mappings;
- new human login/session/authentication;
- password-reset/account behavior;
- credential deletion;
- plaintext recovery/history;
- API billing quotas;
- PHP/LKG or post-2.0 adapters;
- broad admin redesign.
