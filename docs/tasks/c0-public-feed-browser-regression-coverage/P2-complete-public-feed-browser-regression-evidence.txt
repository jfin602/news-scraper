REQUIRED PUBLIC-FEED EVIDENCE
Implement deterministic tests for every item below. If a current test already proves an item, strengthen or split it so the exact relevant assertions are obvious and the title no longer overstates coverage.

A. ENHANCED FIRST-PAGE STALE OWNERSHIP
Prove independently that after SSR startup:
- a stale successful enhanced first-page response cannot overwrite a newer owned result;
- a stale enhanced `404` cannot clear/replace a newer owned result;
- a stale enhanced network/rejected-fetch or generic error cannot overwrite a newer owned result;
- a slow Apply request cannot win after Reset has established newer ownership;
- a slow Apply/history request cannot win after newer Back/Forward/popstate ownership.

Use deterministic controlled fetch/deferred resolution. Do not rely on AbortController cancellation alone; explicitly resolve/reject abort-insensitive stale requests after the newer state is visible and assert the newer URL, controls, branding, rows, and bounded status remain unchanged.

B. CONTINUATION VALIDATION AND FAILURE ISOLATION
Prove separately or in clearly diagnostic parameterized cases:
- duplicate Article IDs in a continuation response are rejected before mutating rows, item IDs, or cursor state;
- a repeated `nextCursor` equal to the requested cursor is rejected and does not create a loop;
- an empty continuation page with non-null next cursor is rejected;
- network failure preserves existing rows and the current retry cursor;
- HTTP 400 preserves existing rows and retry cursor;
- HTTP 404 preserves existing rows and retry cursor;
- HTTP 503 preserves existing rows and retry cursor;
- malformed JSON preserves existing rows and retry cursor;
- successful JSON with mismatched discovery criteria preserves existing rows and retry cursor;
- after each retryable failure, a later valid retry uses the SAME cursor and may append safely;
- duplicate activation while continuation is in flight still produces only one owned continuation request.

Assertions must prove both visible state and requested cursor URL. A generic "shows an error" assertion is insufficient.

C. CONTINUATION DEPTH INVALIDATION / HISTORY
Starting from a page that actually loads at least one continuation row, prove:
- changing Source discards loaded depth and requests only the new first page with no cursor;
- changing Category discards loaded depth and requests only the new first page with no cursor;
- Reset discards loaded depth and restores `/` with no cursor;
- Back/Forward restores the first page represented by the URL, not previously loaded continuation depth;
- stale continuation success after a newer criteria/reset/history owner is ignored;
- stale continuation FAILURE after Reset/history is ignored and cannot surface a pagination error on the newer first page.

At least one history test must load continuation depth before navigating away and then verify Back/Forward returns only the first-page rows for the URL state.

D. APPENDED-ROW PRESENTATION PARITY
For a continuation item near a calendar-day timezone boundary, prove:
- appended row date rendering uses configured Publication `presentationTimezone`;
- viewer/browser timezone does not override configured Publication timezone;
- UTC fallback remains correct when Publication timezone is absent;
- exact appended `original_url` remains unchanged;
- hostile appended headline/Source content remains inert.

Do not infer appended-row parity from initial SSR-row coverage.

E. JAVASCRIPT-DISABLED LEVEL 6
Use real Chromium contexts with `javaScriptEnabled: false` and prove each behavior through actual navigation/form submission:
- populated `/` is useful;
- native keyword Search submits with Source and Category both left at their blank All values and returns the expected q state;
- Source-only submission works with Category inactive;
- Category-only submission works with Source inactive; explicitly ensure the preceding Source selection is not accidentally carried into the Category-only request;
- Reset is a real `/` navigation independent of JavaScript;
- clicking/following the headline exercises the exact stored publisher destination, not merely `getAttribute('href')`;
- invalid discovery returns an intelligible `400` page and exposes usable Reset/recovery navigation;
- absent/private-equivalent returns an intelligible `404` page and exposes recovery navigation;
- dependency failure returns an intelligible `503` page and exposes recovery navigation;
- a successful SSR response with a non-null cursor exposes NO Phase 1 continuation link/button/control when JavaScript is disabled.

Do not combine these into one test title unless the body genuinely exercises every named behavior. Prefer a few diagnostic tests over one oversized scenario.
