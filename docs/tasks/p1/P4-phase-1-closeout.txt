ZERO-SELECTION NEGATIVE VALIDATION
Physically invoke the repository's test-selection wrapper/command with a deliberately nonexistent pattern.

Expected result:
- zero matching tests are detected before/at runner invocation;
- command exits nonzero;
- output clearly explains that no required tests matched.

Record the command and observed nonzero result. A zero-match command that exits successfully is a Phase 1 closeout failure.

PHYSICAL WEB/API RUNTIME VALIDATION
Run the real Web/API entrypoint/package script, not only tests around an app factory.

Use a safe local host and an available port (port 0 is preferred if the package/runtime supports reporting the actual assigned port).

Observe and record:
1. startup command;
2. structured `web.listening` event or equivalent actual listener evidence;
3. actual bound host/port;
4. HTTP request to `/health/live`;
5. observed HTTP status and concise JSON body;
6. HTTP request to `/health/ready`;
7. observed HTTP status and concise JSON body;
8. SIGTERM/SIGINT graceful-shutdown action;
9. clean `web.stopped`/termination evidence;
10. successful exit after clean shutdown.

Expected Phase 1 health semantics:
- live: Web process is responsive;
- ready: initialization/current Phase 1 dependencies are usable;
- no PostgreSQL dependency exists yet.

Do not use browser evidence; curl/native HTTP is sufficient for this Phase 1 HTTP process claim.

WEB INVALID-CONFIG NEGATIVE VALIDATION
Execute the actual Web startup command with intentionally invalid Phase 1 Web configuration, such as an out-of-range/non-numeric port.

Expected result:
- listener does not become ready/listening;
- bounded configuration error is emitted;
- process exits nonzero;
- output does not dump the complete environment or secrets.

Record the exact synthetic invalid value and result. Do not use any real secret values in validation.

PHYSICAL WORKER RUNTIME VALIDATION
Run the actual Worker entrypoint/package script with valid common configuration.

Observe and record:
1. startup command;
2. `worker.ready` lifecycle event or equivalent readiness evidence;
3. confirmation the process remains running after readiness rather than immediately exiting;
4. SIGTERM/SIGINT shutdown action;
5. `worker.stopped` or equivalent clean-stop evidence;
6. successful process exit.

Confirm the Worker starts without Web/API running and without requiring Web-only host/port configuration.

WORKER INVALID-CONFIG NEGATIVE VALIDATION
Execute the actual Worker command with intentionally invalid common runtime configuration (for example unsupported NODE_ENV).

Expected result:
- no Worker ready event;
- bounded safe configuration error;
- nonzero process exit;
- no environment/secret dump.

Record the exact synthetic invalid input and observed result.

PROCESS ISOLATION CONFIRMATION
During physical validation, demonstrate:
- Web can start/serve health without Worker running;
- Worker can start/become ready without Web running.

This is runtime evidence for the required process separation.

SELF-REFERENCE / SHA TRUTHFULNESS
The validation artifact cannot truthfully contain the commit SHA of the commit that contains itself while also claiming that exact commit was runtime-tested beforehand.

Therefore use this convention:
- `VALIDATED_SOURCE_SHA` = the clean committed implementation/version tree actually tested before creating the artifact;
- the later documentation-only commit containing the validation artifact is an evidence-record commit and must not be represented as though its own SHA received the runtime validation above.

After creating the artifact, perform structural/static checks appropriate to the artifact itself (including whitespace/diff inspection). Any subsequent runtime/source/test/package change invalidates the Phase 1 runtime evidence and requires rerunning the applicable closeout matrix against the new source SHA. A documentation-only evidence-record commit does not change the authoritative package version.
