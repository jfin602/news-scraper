TECHNICAL BASELINE
Use the smallest current stable toolchain that satisfies the contracts:
- Node.js 24 LTS, with package engines requiring a version new enough for stable native TypeScript type stripping (minimum 24.12; remain on major 24).
- npm with committed package-lock.json.
- ESM (`type: module`).
- TypeScript 6.x/current stable compatible release for static type checking.
- Node's built-in `node:test` runner for Phase 1 automated tests.
- Node native TypeScript execution for erasable TypeScript syntax; do not add tsx, ts-node, Jest, or Vitest unless a verified technical blocker makes native execution impossible.
- ESLint flat configuration with TypeScript support.
- Prettier for formatting.

Node's native TypeScript runtime does not type-check and ignores tsconfig at runtime. Therefore `tsc --noEmit` remains mandatory for static correctness. Keep source syntax within Node's erasable-TypeScript boundary; do not enable experimental transformed TypeScript syntax merely for convenience.

TSCONFIG DIRECTION
Use a strict Node-native-TypeScript-compatible configuration. At minimum, account for:
- `noEmit: true`
- `target: esnext`
- `module: nodenext`
- `strict: true`
- `rewriteRelativeImportExtensions: true`
- `erasableSyntaxOnly: true`
- `verbatimModuleSyntax: true`
- explicit `.ts` relative import extensions
- TypeScript type imports using `import type` where applicable
Do not introduce `paths` aliases that Node cannot resolve natively.

ZERO-TEST-SELECTION PROTECTION
The testing contract forbids a required filtered suite from passing when zero tests are selected.

Implement a small deterministic wrapper under `scripts/run-tests.mjs` rather than relying on shell glob behavior. It should:
1. accept one or more test glob patterns;
2. discover matching files before invoking the test runner;
3. sort matched paths deterministically;
4. exit nonzero with a clear error if zero test files match;
5. otherwise invoke the current Node executable with `--test` and the selected files;
6. inherit stdout/stderr so terminal evidence is visible;
7. propagate child exit failure correctly.

Use Node standard-library capabilities available in the required Node 24 baseline; do not add a glob/test wrapper package unless genuinely necessary.

RUNTIME CONFIGURATION CONTRACT
Create a pure shared configuration boundary in `src/shared/runtime-config.ts` (or a comparably narrow path).

P0 owns common process configuration only. Recommended initial common setting:
- `NODE_ENV`: allowed values `development`, `test`, `production`; documented default `development`.

Requirements:
- parsing must accept an explicitly provided environment object rather than hard-wiring all tests to global `process.env`;
- return a typed immutable/read-only configuration object;
- use a dedicated configuration error type or equivalent deterministic error contract;
- invalid values fail predictably before process-role startup;
- error messages identify the offending variable/reason without serializing the full environment or unrelated raw values;
- do not invent database, Source, Publication, scheduler, API-key, or collection configuration just to make validation look substantial;
- design the shared parser so later Web-only configuration can compose with common configuration without forcing Worker processes to validate Web-only values.

FOCUSED AUTOMATED TESTS
Add substantive Level 2 tests covering at minimum:
- missing NODE_ENV uses the documented default;
- each supported NODE_ENV is accepted;
- unsupported NODE_ENV is rejected predictably;
- configuration result has the intended stable shape;
- errors do not expose the complete supplied environment;
- test wrapper executes a known selected test set;
- test wrapper fails nonzero when no files match;
- child test failure propagates nonzero;
- ordering/discovery behavior is deterministic where observable.

Tests should assert observable contracts rather than private implementation details.
