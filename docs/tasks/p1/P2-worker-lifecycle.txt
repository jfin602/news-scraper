GOAL
Implement the second independently runnable process role: a non-HTTP Worker bootstrap/runtime lifecycle that validates common configuration, becomes ready, remains alive until shutdown, and stops cleanly. Do not implement collection, endpoint arguments, jobs, queues, PostgreSQL, Source behavior, or a Worker HTTP health server.

Phase 10 will place the same endpoint execution unit behind durable jobs/scheduling. Phase 1 must establish the Worker lifecycle now without inventing those future stages early.

WORKER RUNTIME MODEL
The Phase 1 Worker should follow a lifecycle equivalent to:

common validated runtime config
  -> Worker bootstrap
  -> emit ready lifecycle event
  -> remain active awaiting termination
  -> initiate shutdown once
  -> emit stopped lifecycle event
  -> terminate successfully

This is a real process/lifecycle foundation, not a fake collection loop.

The importable runtime should expose a testable lifecycle boundary rather than placing all behavior in `main.ts`. Use an AbortSignal/controller, explicit shutdown primitive, or comparably deterministic approach so unit tests can start/stop the runtime without sending OS signals.

The actual process entrypoint should own process-level signal wiring.

PROCESS LIVENESS
An unresolved Promise by itself may not keep Node's event loop alive. Implement the process lifetime intentionally and minimally. It is acceptable for the process entrypoint's signal watchers or another explicit lightweight runtime handle to keep the Worker alive, but:
- do not add periodic fake work;
- do not poll anything;
- do not perform network/database I/O;
- do not create an artificial scheduler;
- ensure the handle is released during shutdown so the process exits cleanly.

READY / STOPPED LIFECYCLE OUTPUT
Emit bounded machine-readable, secret-safe lifecycle output so integration tests and manual closeout can synchronize without arbitrary sleeps.

Use event shapes equivalent to:
- ready: `{ "event": "worker.ready", "role": "worker" }`
- stopped: `{ "event": "worker.stopped", "role": "worker" }`

Do not include complete environment/config dumps. Do not introduce a heavy logging framework for this alone.

CONFIGURATION
Worker consumes P0's common validated runtime configuration only unless this task uncovers a genuine Worker-specific Phase 1 setting.

In particular:
- Worker must not require `NEWS_SCRAPER_WEB_HOST` or `NEWS_SCRAPER_WEB_PORT`;
- invalid common configuration (for example unsupported NODE_ENV) must fail before readiness;
- do not invent DB URL, Source ID, endpoint ID, polling interval, queue URL, or similar future configuration.

ENTRYPOINT / SIGNAL CONTRACT
`main.ts` should:
1. load/validate common runtime config;
2. construct/start the Worker runtime;
3. install process signal handling in the process boundary, not reusable library modules;
4. report `worker.ready` only after successful initialization;
5. on SIGINT/SIGTERM, request shutdown at most once;
6. await clean shutdown;
7. report `worker.stopped`;
8. terminate successfully after clean stop;
9. report bounded safe startup/runtime errors and terminate nonzero on failure.

Avoid direct `process.exit()` from reusable modules. Prefer setting process exit status/allowing normal termination from the entrypoint after cleanup.

FOCUSED UNIT TESTS
At minimum prove observable Worker runtime behavior:
- runtime initializes successfully with valid common configuration;
- runtime reports/enters ready state only after initialization;
- runtime remains active until shutdown is requested;
- explicit shutdown resolves cleanly;
- repeated/concurrent shutdown requests do not run shutdown twice or fail unpredictably;
- invalid common configuration prevents startup/readiness;
- Worker runtime does not require Web-specific configuration;
- resources/handles owned by the runtime are released on shutdown so tests do not hang.

Avoid asserting private implementation details when observable lifecycle results are sufficient.

FOCUSED PROCESS INTEGRATION TEST
Spawn the actual Worker command/entrypoint (`node src/app/worker/main.ts` or the substantive package script resolving to it).

The test should:
1. launch with valid common config;
2. wait for the structured `worker.ready` event rather than sleeping;
3. prove the child remains running after readiness rather than exiting immediately;
4. send SIGTERM;
5. observe `worker.stopped` and process termination;
6. require successful exit after normal shutdown.

Also spawn with intentionally invalid common configuration and require:
- no `worker.ready` event;
- bounded safe startup error output;
- nonzero exit.

Use process/lifecycle events and bounded safety timeouts, not arbitrary sleeps.

PROCESS-BOUNDARY ISOLATION TESTING
Add a meaningful assertion/test that the Worker does not depend on Web startup. Suitable proof may include:
- spawning Worker with no Web process running and no Web host/port variables and observing readiness;
- structural/import validation if needed to prevent accidental imports from `src/app/web/`.

Do not create a brittle architecture test that merely snapshots filenames; prove the important dependency boundary.

ACCEPTANCE CRITERIA
- Worker starts independently from Web/API.
- Worker does not require Web-specific environment variables.
- Worker becomes ready only after successful Phase 1 initialization.
- Worker remains alive after readiness until termination is requested.
- SIGINT/SIGTERM shutdown is handled predictably and at most once.
- Worker stops cleanly with no leaked runtime handle preventing process exit.
- invalid common configuration prevents readiness and exits nonzero.
- no Worker HTTP server exists.
- no Source fetch, DB connection, queue, scheduler, endpoint runner, or fake collection behavior exists.
- Worker source contains no indie-author-specific condition/data.
- full current deterministic regression matrix is actually executed before completion is claimed.

NON-GOALS
- Manual endpoint collection arguments or execution (Phase 5).
- Durable jobs/scheduler/queue consumption (Phase 10).
- PostgreSQL or dependency readiness beyond currently implemented Phase 1 dependencies.
- Fetchers, network safety, locks, Collection runs, parsers, normalization, Relevance, identity, Articles, deduplication, or feed behavior.
- Worker HTTP health/readiness endpoints.
- Admin functionality or native authentication.
- Hosted CI.

DELIVERY / REVIEW NOTES
Keep the Worker boundary minimal but real. Do not add fake future machinery just to make a long-running process look busy. If shared P1 lifecycle code can be reused cleanly without coupling Worker to Web, do so only when the abstraction reflects a real shared process concern. Otherwise prefer explicit small role-specific code. Report exact commands/tests actually executed and observed.
