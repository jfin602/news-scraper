TASK: Correction 1 / P1 — Expand Gemini digest execution budget

CORRECTION SCOPE
This is the sole implementation prompt in correction `c1-gemini-timeout`.

Phase 1 P1-P6 are implemented and the Phase 1 P7 closeout candidate is at package `2.1.7`. A real local invocation of `npm run test:live-gemini` reached the production Gemini provider path but returned bounded `provider_timeout` after roughly 167 seconds. Subsequent closeout repair already corrected one independent provider-boundary defect: the production Interactions wrapper now forwards the application `AbortSignal`, explicitly sets SDK `maxRetries: 0`, and passes the application timeout through the SDK request options.

The remaining owner-approved correction is narrower: the current 30-second Gemini digest budget is too aggressive for a twice-daily/background URL-Context digest workload. Phase 1 never locked 30 seconds as product behavior; it requires a bounded abort policy and no hidden duplicate provider retries. The application should allow one legitimate Gemini request substantially longer to finish while retaining a finite safety/recovery ceiling.

Change the production Gemini digest execution budget to exactly **5 minutes / 300,000 milliseconds** at unchanged package version `2.1.7`.

Do not redesign the provider, lifecycle, scheduler, admin Generate-now flow, or Phase 1 contracts. Preserve the already-landed single-request/no-retry/abort-signal fix.

CORRECTION GOAL
The final provider/lifecycle timing relationship must be conceptually:

```text
one claimed digest attempt
-> one Gemini Interactions request
   -> maxRetries = 0
   -> caller AbortSignal forwarded
   -> 300,000 ms application/provider ceiling
-> success OR one bounded provider failure

P3 stale-running recovery threshold
= same provider attempt ceiling + existing safety margin
```

A legitimate in-flight Gemini request must not become stale merely because it exceeds the old 30-second implementation choice.

Change the application-owned production digest timeout from 30,000 ms to exactly 300,000 ms.

Primary expected owner:

`src/distribution/digests/provider.ts`

P3 STALE-RECOVERY COUPLING
Do not independently hard-code a second five-minute value into lifecycle code.

Current source inspection found that `createDigestLifecycleService()` defaults `providerAttemptTimeoutMilliseconds` from `GEMINI_DIGEST_TIMEOUT_MILLISECONDS`, then computes stale recovery as:

`attempt timeout + DIGEST_STALE_RUNNING_ATTEMPT_MARGIN_MILLISECONDS`

Preserve that relationship.

With the current 5,000 ms margin, the normal production stale cutoff should therefore be approximately 305,000 ms after attempt start, not 35,000 ms.

Requirements:
- do not shorten or remove the existing stale-recovery margin;
- do not add a heartbeat/lease subsystem for this correction;
- do not modify database attempt constraints or repository claim/recovery semantics;
- a still-legitimate request inside the five-minute provider ceiling must remain `already_running` to competing scheduled/manual work rather than being recovered as stale;
- only an attempt beyond the provider ceiling plus the existing margin may enter the existing stale-recovery path;
- test-only dependency injection of shorter timeouts may remain available so deterministic lifecycle tests do not wait minutes.
