GOAL
Implement the persistence-free deterministic domain logic that P3/P4 will consume:
- canonical unordered Article-pair identity;
- strong-vs-weak duplicate evidence classification;
- bounded deterministic reasons/confidence and stable evidence fingerprinting;
- deterministic automatic Primary selection across existing Article/Source metadata.

P2 must not read/write PostgreSQL, mutate groups/review state, or alter collection/public-feed behavior.

PAIR IDENTITY
Create a small topic-independent module under `src/deduplication/` that canonicalizes two distinct Article UUIDs into stable low/high ordering.

Requirements:
- reject identical IDs and malformed IDs through the module's normal validation/error contract;
- `(A,B)` and `(B,A)` produce exactly the same canonical pair;
- pair ordering is stable and deterministic and matches the persistence ordering expected by P1;
- do not derive pair identity from Source, title, URL, Publication, or mutable metadata.

DETERMINISTIC EVIDENCE
Automatic grouping is conservative.

Implement only evidence currently available from governed persisted fields:

1. `canonical_identity_url_equal`
   - strong evidence only when two distinct persisted Articles from different Sources have exactly equal full `canonicalIdentityUrl` strings;
   - digest equality alone never counts as evidence; full persisted value equality is required;
   - this signal may authorize automatic grouping later.

2. `normalized_title_equal`
   - weak review-only evidence when two different-Source Articles have exactly equal non-empty persisted `normalizedTitle` strings;
   - it never becomes strong because author/date/summary also resemble each other;
   - it may create persisted review work later but cannot suppress public rows by itself.

Same-Source pairs are ineligible for Phase 16 true-duplicate grouping/review detection. Same-Source repeat/conflict behavior stays in Article identity and must not be routed around Source-scoped identity invariants.

Do not add fuzzy similarity, edit distance, token scores, embeddings, semantic matching, body fetching, publisher reputation heuristics, domain-name inference, or cross-Source external-ID assumptions.

FALSE-POSITIVE SAFEGUARDS
Unit behavior must make these consequences explicit:
- equal/generic/recurring titles without strong canonical evidence remain weak only;
- same topic/event with different URLs/titles remains separate;
- matching author/date/summary cannot independently promote a weak pair to strong;
- distinct canonical identity URLs do not become strong merely because titles match;
- uncertainty favors preserving separate public Articles.

EVIDENCE RESULT / CONFIDENCE
Return one immutable deterministic evidence object suitable for persistence by P3.

Use a small documented confidence scale, consistent with P1 storage. A simple deterministic baseline is acceptable:
- strong canonical equality: 100;
- weak exact normalized-title equality without strong evidence: 50;
- no governed signal: no review candidate/evidence result rather than a zero-confidence row.

If both strong and weak signals exist, preserve both reasons in deterministic order but strength remains strong and confidence remains the governed strong value. Do not accumulate weak points until they cross an automatic-grouping threshold.

EVIDENCE FINGERPRINT
Generate a stable evidence fingerprint from the canonical pair plus the exact deterministic evidence material used by P2, not from transient timestamps or database row order.

The fingerprint must change when materially used evidence changes even if the reason-code set happens to remain the same; for example, if two equal normalized titles later change together to a different equal normalized title, unchanged-dismissal logic must be able to distinguish the new evidence.

Use a deterministic bounded representation and cryptographic digest already available in Node; do not persist unbounded serialized Article objects. Signal order must not change the fingerprint.

PRIMARY SELECTION
Implement a pure deterministic comparator/selector over the current persisted Article plus Source-priority context.

The governing order is:
1. trustworthy explicit original-publisher/canonical metadata when it genuinely exists through a governed contract;
2. Source priority;
3. metadata completeness and destination quality;
4. earliest credible Source publication time;
5. persisted timing/stable identity fallback;
6. stable Article ID final tie-break.

Current repository constraint: as of the P2 handoff, there is no governed persisted trustworthy original-publisher/syndication field. Do NOT invent one or infer it from Source name/domain/reputation. Therefore current selection safely falls through to Source priority.

For current numeric Source priority consumption, use the repository's existing higher-number-wins priority convention: a larger persisted `sources.priority` value is more preferred. If current governing docs/source have explicitly established the opposite direction by execution time, treat that as planning drift and stop rather than silently diverging.

Define the remaining criteria narrowly and transparently:
- metadata completeness: prefer more present optional Source-derived metadata among `author`, `summary`, `imageUrl`, and `language`; do not count publication time here because it is a later criterion;
- destination quality: when completeness ties, prefer an HTTPS `originalUrl` over HTTP; do not replace `originalUrl` with canonical identity or infer publisher quality from hostname;
- credible publication time: a persisted `publishedAtStatus = parsed` timestamp outranks missing/invalid; when both are parsed, earlier publication time wins;
- persisted fallback: earlier `firstSeenAt`, then earlier `createdAt`;
- final tie: lexical/stable Article UUID ordering.

Do not use visibility, Category, Relevance, Source display name/config key, title similarity, last-seen time, or mutable UI labels as hidden Primary criteria.

The selector must be order-independent: selecting from the same member set in any input order produces the same Primary.
