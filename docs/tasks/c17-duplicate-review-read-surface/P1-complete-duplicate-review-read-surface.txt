OBSERVED GAP
The P3 task required bounded Duplicate-review queue/detail reads with stable continuation, ordered persisted signals, Article summaries, current group/membership/Primary context, and manual-authority blockers.

Current `src/deduplication/moderation.ts` provides `readDuplicateReviewQueue()` with only `state`, `confidence`, and `limit` inputs plus basic pair/title/manual-separation data. It does not provide:
- continuation/cursor semantics;
- a candidate-detail service;
- complete current group/member/Primary context;
- indirect manual-separation blocker context across would-be combined components;
- conflicting manual-Primary blocker context;
- an admin/service boundary that P5 can consume without inventing duplicate-domain behavior.

P2 already supplies the canonical moderated-Article read model. Reuse it rather than creating a competing Article mapping.

GOAL
Complete the missing P3 duplicate-review read surface so the later P5 HTTP task can remain a strict adapter:

request parsing -> duplicate administration service -> bounded response/error mapping

P5 must not need SQL, cursor design, topology inference, candidate-detail composition, or duplicate-policy interpretation after this correction.

SERVICE BOUNDARY
Add a bounded duplicate administration/read service, preferably `src/admin/duplicate-administration.ts`, analogous in responsibility to the existing Article administration service.

The service must expose at minimum:
- `searchReviews(input?)` — normalized bounded queue/search request returning items plus opaque continuation;
- `getReview(candidateId)` — normalized candidate-ID lookup returning the complete bounded candidate-centric detail needed by P5.

It may call narrow read helpers in `src/deduplication/moderation.ts` or another clearly owned duplicate read repository. Do not move HTTP concerns into these modules.

Do not create a generic admin patch/repository API. The service is specifically the governed duplicate-review read boundary.

QUEUE / PAGINATION CONTRACT
Complete bounded queue reads with these semantics:
- supported filters: candidate `state` and `confidence` only unless current governing source already requires another P3/P5 filter;
- bounded page size with the existing practical default/max of 50/100 unless source-level convention requires an equivalent smaller established bound;
- deterministic keyset order `candidate.updated_at DESC, candidate.id DESC`;
- read `pageSize + 1`, return at most `pageSize`, and emit continuation only when another page exists;
- use an opaque cursor owned by the duplicate administration service;
- bind the cursor to normalized search criteria so a cursor produced under one state/confidence filter cannot be silently reused under another;
- reject malformed, oversize, unsupported, or criteria-mismatched cursor/input deterministically;
- do not implement offset pagination or an unbounded export.

Queue items should preserve the useful current candidate metadata while remaining bounded and immutable.

CANDIDATE DETAIL CONTRACT
`getReview(candidateId)` must return one bounded immutable read model containing at least:
- candidate ID and canonical low/high Article IDs;
- current candidate state and origin;
- confidence and evidence fingerprint;
- manual decision timestamp/reason;
- persisted duplicate signals in canonical `signal_order`, including reason code and strength;
- both Articles using/reusing the canonical P2 moderated-Article representation or an intentionally smaller projection derived from it;
- each side's current duplicate role and group ID;
- current group Primary Article ID and `automatic`/`manual` authority when grouped;
- bounded current member summaries for every distinct group implicated by the candidate;
- total member count and an explicit truncation/has-more indication when the detail bound omits members;
- whether current automatic grouping would be blocked by active manual separation;
- whether current distinct groups are blocked from automatic merge by conflicting manual Primaries.

Do not infer new duplicate evidence, confidence, policy, or Primary rules. This task reports already-persisted/governed state.

ARTICLE READ-MODEL REUSE
The current P2 Article administration path already maps Source/effective title, visibility, Categories, duplicate role, group ID, Primary ID/origin, and Article-level review data.

Reuse `readModeratedArticle` / `readModeratedArticles` or another existing canonical Article mapping boundary where practical. Do not duplicate the complete Article SQL/mapping merely to build duplicate detail.

When listing group members, prefer the existing bounded Article repository search using its `duplicateGroupId` criterion so duplicate administration does not become a second full Article repository.

Keep any projection returned by duplicate detail explicit and bounded; do not expose observations/history for every group member unless already needed by the governed P3/P5 contract.

INDIRECT MANUAL-SEPARATION BLOCKER
The read model must mirror the actual automatic grouping policy, not merely check whether the candidate pair itself has a separation row.

For the candidate's two Articles, derive the complete current components that automatic grouping would combine:
- an ungrouped Article contributes itself;
- a grouped Article contributes every member of its current Duplicate group.

Report automatic grouping blocked by manual separation when any active `duplicate_manual_separations` pair exists wholly inside that would-be resulting member set and would therefore make the automatic topology change invalid.

Example that must be represented correctly: Article A and B are grouped, candidate evidence connects B to C, and active manual separation is A-C. The candidate is indirectly blocked even though B-C itself is not the separated pair.

Do not mutate or acquire the topology mutation lock solely to answer this read. Read a transactionally coherent bounded snapshot using normal repository/database conventions.

CONFLICTING MANUAL PRIMARY CONTEXT
For candidates whose Articles currently belong to two different Duplicate groups, report the existing governed automatic-merge blocker when both groups have different valid manual Primaries.

Do not resolve that conflict in this task. Do not choose a winner. P3 mutation semantics remain authoritative.
