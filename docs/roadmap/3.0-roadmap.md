## Product direction

3.0 builds on the proven 2.0 managed Profile → authenticated v1 API → generic PHP complete-snapshot/LKG → customer SSR path.

The immediate goals are:

1. preserve the completed topic-independent Gemini Profile digest foundation while adding the owner-approved bounded Profile digest writing-style configuration through `c1-digest-style`;
2. immediately correct the observed PHP customer-integration/package issues, rebuild the integration package, and only then push the Gemini-capable package update to the customer;
3. add Profile-grounded interactive Gemini chat;
4. prove one customer Publication can operate several materially different Distribution Profile feeds end to end, including publishing news, opportunities, and indie filmmaking; and
5. use the resulting real deployment experience to tighten remaining administrator and PHP integration workflows before the owner defines the final 3.0 release gate.

The 3.0 roadmap does **not** introduce relational multi-Publication tenancy. Under the 2026-08-27 Publication amendment, one installation hosts one customer/editorial property that may contain several subject verticals. Distribution Profiles are the supported feed/section boundary.

The governing AI behavior is `docs/contracts/ai-assistance-contract.md`. The governing Publication interpretation is `docs/decisions/single-publication-multi-vertical-editorial-property.md` and Project Contract Law 11.

- treat Source/article text and provider-retrieved publisher-page content as untrusted prompt data with no authority over system policy, secrets, Profile scope, URL selection, or output schema;

- treat inaccessible/paywalled/unsupported URL Context retrieval as bounded context degradation when normalized metadata/summary fallback is sufficient;
- never trust model-generated URLs as Article destinations.

### Profile AI administration

Each Distribution Profile gains a dedicated protected **AI** section. Phase 1 must provide at least:

- digest enable/disable independent from ordinary Profile Article distribution;
- bounded digest lookback control;
- bounded maximum digest Article count;
- operator-visible twice-daily evaluation cadence/status;
- manual **Generate now** using the same governed server-side generation path;
- active digest existence, generation time, freshness, input count, and provider/model identity where useful;
- latest evaluation/attempt time and bounded outcome/failure category.

Gemini credentials/API secrets are deployment/operator configuration and MUST NOT become Profile fields.

### Digest evaluation cadence and regeneration

Digest generation is independent of endpoint collection timing. Endpoints remain independently scheduled; Phase 1 must not invent a global "all Sources finished" moment.

For each enabled Profile digest the server performs **two scheduled evaluations per day**. An evaluation does not automatically call Gemini.

At each scheduled evaluation:

1. resolve the current bounded digest input through canonical governed Profile output;
2. derive the internal `digestInputIdentity` from that exact bounded input plus relevant Profile AI configuration;
3. compare it with the latest successful valid digest input;
4. if no Article newly entered the current bounded governed digest input and relevant configuration did not change, keep the existing digest and make no Gemini request;
5. if at least one Article newly entered that input, one new Article is sufficient to justify generation;
6. multiple arrivals naturally accumulate until the next scheduled evaluation, yielding at most one scheduled regeneration for that evaluation.

Changing lookback/count changes the governed input definition and requires reevaluation rather than waiting for a newly collected Article.

Manual **Generate now** may deliberately bypass the unchanged-input skip optimization, but it must use the same canonical input, URL restrictions, provider boundary, output validation, persistence, and activation path.

Canonical eligibility invalidation is a correctness exception: an active digest must not remain distributable merely because no new Article arrived if supporting input becomes disallowed by moderation, duplicate/Primary changes, Profile membership/filter changes, Source trust/lifecycle changes, or another canonical eligibility change.

### Digest input

The digest input is a deterministic narrowing of canonical governed Profile order. It is not AI ranking and does not introduce a second selector.

Default Profile AI configuration:

- **lookback window:** 7 days;
- **maximum input Articles:** 20.

Maximum Article count is configurable only within **1–20**, with 20 as the hard Phase 1 ceiling. Lookback is bounded Profile configuration with a 7-day default; implementation planning may choose its safe finite minimum/maximum.

For each evaluation:

1. begin with the canonical Profile result;
2. keep only Articles whose `effectiveFeedDate` falls within the configured rolling lookback;
3. take at most the configured maximum from the front of canonical Profile order;
4. preserve that canonical order.

Input cardinality:

- 0 qualifying Articles: do not generate a new digest;
- 1 qualifying Article: sufficient input;
- 2 through the configured maximum: use all;
- over the configured maximum: use only the newest bounded canonical prefix.

Per-Article Gemini context is limited to:

- `articleId`;
- headline;
- Source display name;
- `effectiveFeedDate`;
- nullable `publishedAt`;
- nullable author;
- accepted bounded persisted summary;
- effective outward Categories;
- exact stored `originalUrl`.

Do not send image URLs, Source/endpoint configuration, collection/run internals, duplicate mechanics, moderation/Relevance internals, private persistence identifiers, credentials, or unrelated Profiles merely because they exist.

Gemini URL Context may receive every exact stored `originalUrl` in the bounded input, subject to the same hard maximum of 20. The bounded persisted summary remains present as fallback context even when URL Context is attempted.

### Structured digest output

Phase 1 uses validated structured output rather than unrestricted prose.

The visible digest contains:

1. **Overview** — concise plain text, target approximately 100–200 words, hard maximum **2,000 characters**.
2. **Highlights / key developments** — up to **3** structured highlights, each with a short plain-text title and concise 1–2 sentence explanation, hard maximum **500 characters** for the explanation.
3. **Supporting Articles** — up to **3** supporting Articles per highlight, identified by Gemini only through `articleId` values from the exact bounded input.

The complete Gemini-generated textual portion of a digest is hard-bounded to approximately **4,000 characters total** across overview and highlights. Supporting Article metadata/URLs are application-resolved references rather than Gemini-generated prose.

News Scraper validates returned support IDs against the exact generation input, removes duplicates within one highlight, and resolves outward fields from governed Article data. The normalized supporting-Article shape includes at minimum:

- `articleId`;
- headline;
- Source display name;
- `effectiveFeedDate`;
- exact stored `originalUrl`.

The same Article may support more than one highlight. Model-provided URLs, Source names, dates, or replacement headlines are never trusted outward data.

All generated text is untrusted plain text. Phase 1 does not accept model-provided executable HTML or trusted Markdown. Shared prompts/schemas remain topic independent.

### Digest identity, persistence, and lifecycle

`digestInputIdentity` is internal generation provenance and MUST remain separate from outward `snapshotRevision`.

```text
bounded canonical digest input + relevant AI configuration
→ digestInputIdentity
→ Gemini generation
→ validated active digest
→ outward Profile state (Articles + active digest)
→ snapshotRevision / ETag
```

Successful digest generations, the currently active digest, and generation/evaluation attempts are distinct durable concepts.

Every successful validated generation is persisted as an immutable Profile-owned digest record containing enough bounded provenance and structured content to reconstruct the activated output, including digest/Profile identity, `digestInputIdentity`, generation timestamp, provider/model identity, bounded input count, exact bounded input Article IDs in canonical order or equivalent immutable provenance, overview, highlights, supporting references, and bounded safe provider/usage metadata where useful.

The Profile owns a separate active-digest reference. Replacement is atomic:

```text
generate
→ validate complete structured output and references
→ persist complete immutable digest
→ atomically switch Profile active-digest reference
```

Previous successful digests remain immutable history unless a later retention policy deliberately prunes them. Evaluation/generation attempts persist separately with bounded status metadata and MUST NOT store secrets, unbounded prompts, retrieved page bodies, full failed provider payloads, or unnecessary sensitive content.

### Digest freshness and invalidation

Digest freshness is semantic, not based on a fixed age threshold.

Downstream digest freshness is exactly:

- **`current`** — active digest still corresponds to the current bounded governed input/configuration;
- **`older`** — current input changed and replacement is not active, but the prior digest remains canonically valid and still meaningfully overlaps the current bounded input.

Age alone does not make an otherwise current digest stale.

A failed/pending replacement may retain a prior digest as `older` only while it remains canonically valid and at least one Article from the previous digest input remains in the current bounded input. If none remain, or any canonical invalidation condition disallows support, suppress the active digest to `null` until replacement succeeds.

```text
unchanged governed input
→ current digest remains current regardless of simple age

changed governed input
→ replacement succeeds → new current digest
→ replacement pending/fails + prior digest overlaps and remains canonically valid → older digest
→ no overlap or canonical invalidation → digest = null
```

Provider failure categories remain protected operator diagnostics and are not public/customer error text.

### v1 complete-snapshot representation

Every successful v1 Profile page gains one top-level **`digest`** field, always present as either:

- a validated structured active digest; or
- `null`.

The same normalized digest value belongs to every page of one `snapshotRevision`. Digest activation/replacement/suppression or `null` transition changes the outward `snapshotRevision`/ETag even when Articles are unchanged. Existing `snapshot_changed` continuation/restart semantics handle races; there is no second digest endpoint, digest ETag, customer digest cron, or competing synchronization protocol.

The v1 digest exposes only bounded downstream data: `generatedAt`, `freshness`, `inputArticleCount`, provider, model, overview, highlights, and application-resolved supporting Article references. Internal input identity, attempts, provider diagnostics, prompts, config, and secrets remain server-side.

Invalid optional AI state fails open relative to Articles: valid Article state is served normally with `digest: null`, not converted into an AI-caused `503`.

### PHP LKG and normalized local-read

The digest is part of the existing complete synchronized Profile snapshot/LKG under the existing customer state root. Phase 1 MUST NOT create a parallel digest cache, second sync file, separate digest state directory, visitor-time upstream request, or new customer-side digest job.

The upgraded PHP integration validates optional digest data independently from required Profile/Publication/Article state:

```text
valid Profile + valid Articles + invalid digest
→ activate new valid Article snapshot normally
→ normalize local digest to null
```

All pages in one candidate revision must agree on digest. Contradictory digest values degrade the candidate's optional AI state to `null` when required Article state remains coherent rather than causing Article LKG failure.

Pre-digest local state remains a valid upgrade starting point and reads as `digest = null` until synchronized digest data exists.

`LocalProfileReader` exposes normalized digest values containing `generatedAt`, `freshness`, `inputArticleCount`, provider, model, overview, highlights, and supporting Articles with `articleId`, headline, Source display name, `effectiveFeedDate`, and exact `originalUrl`.

Existing local `staleAgeSeconds` continues to describe synchronized Profile/LKG freshness; it is not redefined as digest age. Digest age derives from `digest.generatedAt`; semantic state comes from `digest.freshness`.

Ordinary visitor rendering remains local-only with no Gemini/News Scraper call merely to display the digest.

### Customer presentation boundary

News Scraper/PHP owns synchronization, LKG persistence, validation, normalization, and safe data exposure. The customer owns final HTML, CSS/classes, layout, placement, wording, and site-specific presentation.

Phase 1 must not expand the existing bundled/local renderer into an authoritative digest presentation layer. A minimal instructional/example snippet may demonstrate normalized digest access, but it is non-authoritative. The actual renderer/presentation cleanup and production package refresh are Phase 2 responsibilities.

AI-origin labeling must be application/customer-owned and clearly distinguish AI-generated summary content from publisher-supplied Article metadata. When `digest === null`, default integration behavior is omission of the digest block rather than an injected provider-error placeholder.

### Security and correctness requirements

- Source/article/retrieved-page text remains untrusted prompt data;
- URL Context receives only exact application-selected governed `originalUrl` values;

### Package / remote-upgrade contract

The protected admin surface supplies one version-matched package whose extraction creates the supported replaceable directory directly:

```text
news-scraper-php-integration-<version>.zip
└── ns-integration/
    ├── VERSION
    ├── integration-package.json
    ├── README.md
    ├── UPGRADE.md
    ├── run-sync.php
    ├── top-tag.php
    ├── bin/
    │   └── sync.php
    ├── src/
    ├── config/
    │   ├── sync.env.example
    │   └── local-read.env.example
    └── example/
```

The sibling `ns-private` directory is never part of the package and is never overwritten by package extraction:

```text
<customer home>/
├── ns-integration/        # replaceable versioned package
└── ns-private/            # durable customer-owned private state
    ├── local-read.env     # authoritative shared non-secret Profile/state/freshness settings
    ├── sync.env           # synchronization-only upstream/credential/transport settings
    ├── state/
    └── logs/
```

The supported configuration boundary is deliberately asymmetric: `local-read.env` contains the shared non-secret values needed by both sync and visitor read paths; `sync.env` contains synchronization-only values. Visitor rendering never needs or reads synchronization-only secrets. The sync launcher consumes both files. An upgrade may tolerate legacy duplicated shared keys in `sync.env` only when they exactly agree with `local-read.env`; mismatch must fail closed and the canonical documented layout removes those duplicates.

The protected admin download UI must visibly identify the exact offered integration package version from the same authoritative package metadata used for the ZIP filename, `VERSION`, and `integration-package.json`; no separately typed UI version label is allowed. The installed package must expose that exact version through its supported diagnostic/preflight surface as well.

The supported low-friction remote upgrade is cPanel/File-Manager friendly:

1. download the exact current integration ZIP from the protected admin surface and note its version;
2. rename existing `ns-integration` to a bounded backup name;
3. upload/extract the ZIP beside durable `ns-private`; extraction creates new `ns-integration` directly;
4. confirm `ns-integration/VERSION` matches the admin-displayed package version and the package diagnostic/preflight reports the same version;
5. confirm stable `ns-integration/run-sync.php` exists for the unchanged cron target;
6. run the supported preflight against the existing private configuration/state before customer cutover;
