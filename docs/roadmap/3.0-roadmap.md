# 3.0 Roadmap

**Status:** OWNER-APPROVED / PRE-ACTIVATION  
**Current package baseline:** `2.0.0`  
**Prior roadmap:** `docs/roadmap/post-1.0-roadmap.md` — COMPLETE at `2.0.0`  
**Planned activation baseline:** `2.1.0`  
**Planned terminal release:** `3.0.0`  
**Current blocker before activation:** roadmap-runner grammar supports the historical `0.x` and post-1.0 `1.x` families only; a bounded unchanged-`2.0.0` runner compatibility correction is required before any `2.1.x` phase prompt stack is written/executed.

## Product direction

3.0 builds on the proven 2.0 managed Profile → authenticated v1 API → generic PHP complete-snapshot/LKG → customer SSR path.

The immediate goals are:

1. add Google Gemini in a topic-independent way through scheduled Profile digests and Profile-grounded interactive chat;
2. prove one customer Publication can operate several materially different Distribution Profile feeds end to end, including publishing news, opportunities, and indie filmmaking; and
3. use that real deployment experience to tighten the administrator and PHP integration workflows before the owner defines the final 3.0 release gate.

The 3.0 roadmap does **not** introduce relational multi-Publication tenancy. Under the 2026-08-27 Publication amendment, one installation hosts one customer/editorial property that may contain several subject verticals. Distribution Profiles are the supported feed/section boundary.

The governing AI behavior is `docs/contracts/ai-assistance-contract.md`. The governing Publication interpretation is `docs/decisions/single-publication-multi-vertical-editorial-property.md` and Project Contract Law 11.

## Version lifecycle

The intended lifecycle mirrors the successful 2.0 development pattern: implementation remains in the `2.x.x` series and the final release transition alone creates `3.0.0`.

```text
current release                 2.0.0
runner compatibility correction 2.0.0 unchanged
roadmap activation              2.1.0
Phase 1 prompts                 2.1.1 ... 2.1.x
Phase 1 /closeout               2.2.0
Phase 2 prompts                 2.2.1 ... 2.2.x
Phase 2 /closeout               2.3.0
Phase 3 prompts                 2.3.1 ... 2.3.x
Phase 3 /closeout               2.4.0
Phase 4 prompts                 2.4.1 ... 2.4.x+
terminal /closeout              3.0.0 only after owner locks and satisfies final gate
```

The exact executable task-folder grammar for this roadmap is **not active yet**. The intended family is `p2-<phase>` with prompt target versions `2.<phase>.<prompt>`, but `scripts/codex-phase-core.mjs` and its focused tests must first be deliberately extended while preserving all historical `p<number>` and `p1-<phase>` behavior. Documentation must not pretend that grammar already works.

After that correction is accepted, roadmap activation may perform the version-only `2.0.0` → `2.1.0` baseline transition. No Phase 1 implementation prompt may silently perform the activation transition itself unless the workflow is explicitly amended.

## Permanent preserved behavior

Every 3.0 phase must preserve:

- topic-independent shared aggregation/distribution logic;
- one singleton Publication/editorial property per installation without relational tenancy;
- administrator-approved Source trust and network-safety boundaries;
- Source-specific normalization before public/distribution/AI use;
- Source-scoped idempotent Article identity and retained endpoint/run provenance;
- true-duplicate suppression without deleting Source Article instances;
- canonical outward eligibility, moderation, ordering, Category, and `originalUrl` authority;
- Distribution Profiles as post-eligibility selectors that can only narrow output;
- machine/admin authorization separation;
- the permanent authenticated `/api/v1/distribution/{profile_key}` compatibility contract unless an explicitly governed additive extension is used;
- PHP complete-snapshot validation, per-Profile locking, atomic LKG activation, stale/failure behavior, local-read normalization, and local-only ordinary visitor rendering;
- supported customer production-data migration/backup/restore compatibility;
- first-party/customer presentation freedom;
- ordinary non-AI operation when Gemini/AI is disabled or unavailable.

## Phase 1 — Gemini Profile digest foundation

**Planned baseline:** `2.1.0`  
**Planned prompt versions:** `2.1.x`  
**Primary goal:** generate safe, durable, Profile-scoped AI summaries of the most recent governed Articles and deliver them through the existing distribution/PHP/customer-page path without making AI a visitor-path dependency.

### Required scope

- integrate Google Gemini through a narrow server-side AI provider boundary using the Gemini Developer API, Interactions API, official `@google/genai` SDK, and stable `gemini-3.7-flash` initial model configuration;
- use low-thinking scheduled digest requests, structured JSON output validated against an application-owned schema, `store=false`, Gemini URL Context enabled, and Google Search grounding disabled for the initial provider profile;
- consume only bounded canonical Distribution Profile Article context;
- provide bounded normalized Article metadata and summary fallback context together with a bounded set of the exact stored governed Article `originalUrl` values for provider URL Context;
- never allow Source text, user text, model output, conversation history, or arbitrary destinations to expand the provider URL set beyond application-selected governed `originalUrl` values;
- implement owner-decided issue `N6WD`: normalized persisted `Article.summary` is at most 4,000 characters after plain-text normalization; oversized values truncate at the last complete word boundary that permits `...` while keeping the final value at or below 4,000 characters, with a 3,997-character hard fallback plus `...` when no usable boundary exists;
- apply the N6WD invariant to existing supported production summaries through the governed forward-upgrade/data-preservation path as well as to new normalization;
- treat inaccessible/paywalled/unsupported URL Context retrieval as bounded Article-context degradation, using normalized metadata/summary fallback where sufficient rather than automatically failing the entire digest;
- schedule digest generation approximately once or twice daily through configurable server-side job/cadence behavior rather than customer visitor requests;
- produce validated structured output tied to Profile/input snapshot identity and generation time;
- retain supporting Article IDs for bounded highlights/themes where applicable;
- persist/activate valid digest state coherently and preserve prior valid state on provider failure where appropriate;
- expose explicit absent/stale/failure-safe AI state without affecting Articles;
- add compatible outward digest propagation through the v1/PHP/LKG/local-read path when proven safe;
- support server-rendered customer display of the synchronized digest with no Gemini/News Scraper call during ordinary page rendering;
- expose operator-visible digest generation/health facts sufficient to diagnose stale/failed AI output and bounded URL-retrieval outcomes without leaking prompts, retrieved page bodies, or secrets.

### Security and correctness requirements

- Gemini keys remain server-side and secret-safe;
- Source/article text and provider-retrieved publisher-page content are untrusted prompt data and cannot issue instructions;
- URL Context receives only exact application-selected governed stored `originalUrl` values; Gemini is not given arbitrary web-search or model-selected browsing authority;
- model output is schema/size validated before persistence/distribution;
- model-generated URLs are never trusted as Article destinations;
- provider timeout/rate/failure/invalid output cannot break collection, canonical Article distribution, PHP Article LKG, or customer Article rendering;
- individual inaccessible/paywalled Article URLs do not by themselves invalidate a digest when sufficient bounded fallback context remains;
- AI output is distinguishable from publisher metadata;
- shared prompts contain no indie-author, opportunity, filmmaking, or customer-specific topic logic.

### Validation

Focused deterministic tests plus an executed Gemini integration proof must demonstrate structured-output handling, input bounds, governed URL Context selection, fallback behavior for inaccessible URLs, prompt-injection resistance across Source/user/retrieved-page content, failure isolation, digest freshness/provenance, API/PHP/local-read compatibility, and no AI call on ordinary visitor rendering.

A multi-subject fixture/Profile set should already prove that the same digest service operates without code changes across materially different Profile content.

### Phase 1 exit gate

At least one real managed Profile can generate a valid Gemini digest using bounded governed metadata/summary context plus provider URL Context for exact stored publisher URLs, synchronize it through the supported PHP integration, and server-render it on the customer side while ordinary Article delivery continues correctly when Gemini or individual Article-page retrieval is unavailable.

Green Phase 1 `/closeout` advances only to `2.2.0` after the roadmap runner supports this family and the accepted evidence is tied to the exact final tree.

## Phase 2 — Profile-grounded "Ask this feed" chatbot

**Planned baseline:** `2.2.0`  
**Planned prompt versions:** `2.2.x`  
**Primary goal:** provide an interactive Gemini assistant whose subject knowledge is determined by the selected Distribution Profile's current governed Articles rather than hard-coded deployment prompts.

### Required scope

- implement a server-side Profile-grounded chat application/service boundary;
- use a bounded current Profile Article context selected through canonical Profile semantics;
- begin with the simplest adequate bounded-context approach; embeddings/vector infrastructure is not required while current Profile limits make direct context practical;
- when URL Context is used for chat, allow only bounded exact stored `originalUrl` values from the selected governed Profile context and prohibit user/model/Source text from adding arbitrary destinations or general web search;
- bound user input and conversation history;
- require the assistant to identify when the feed does not sufficiently support an answer;
- return validated supporting Article references and resolve visible citation links from canonical stored `originalUrl` values rather than model-generated URLs;
- define a server-side customer-integration chat transport suitable for the PHP-hosted website;
- keep Gemini credentials out of browser JavaScript and public PHP configuration;
- introduce an explicit AI authorization/capability boundary so `distribution:read` does not silently authorize unrestricted billable chat;
- implement rate/request/cost-abuse limits and bounded telemetry;
- preserve strict machine/admin separation;
- provide a generic customer integration surface that can label the experience "Ask this feed" or equivalent without topic-specific shared code.

### Failure and safety behavior

Chat provider failure affects only the explicit chat request. It cannot suppress cached Article feeds or scheduled digest state.

Untrusted Source, user, and provider-retrieved publisher-page text cannot alter system policy, URL selection, or expose secrets. Model output remains untrusted rendering input. Citations are accepted only after application validation against the supplied Profile context.

### Validation

Prove authentication/capability separation, rate/request bounds, prompt/context bounds, governed URL selection where URL Context is used, unsupported-question behavior, validated citations, exact stored destination resolution, provider failure isolation, secret/log redaction, and no cross-Profile context leakage.

Executed Gemini evidence must include at least two materially different Profiles to prove topic independence.

### Phase 2 exit gate

A customer-site user can explicitly ask questions about a selected Profile and receive a bounded Gemini answer grounded in that Profile's current governed Articles with validated Article citations, while unrelated Profiles and admin authority remain inaccessible.

Green Phase 2 `/closeout` advances only to `2.3.0`.

## Phase 3 — Multi-feed customer integration proof

**Planned baseline:** `2.3.0`  
**Planned prompt versions:** `2.3.x`  
**Primary goal:** prove the singleton Publication/multi-vertical Profile model and the complete setup/display workflow on the real customer site.

### Required customer configuration

One News Scraper instance / singleton customer Publication should expose at minimum:

```text
publishing-news
opportunities
indie-filmmaking
```

The exact source lists and editorial filters remain customer configuration. The three feeds must be materially distinct enough to prove that Profile Source membership/filtering, independent snapshots, and customer rendering do not accidentally collapse into one global feed.

### Required scope

- configure/onboard the additional approved Sources/endpoints needed for opportunities and indie filmmaking without subject-specific engine changes;
- configure the three Distribution Profiles with clear immutable keys and explicit Source membership/filtering;
- prove Profile isolation across canonical API output, synchronization state, local-read results, and customer rendering;
- prove one Profile failure/disable/stale state does not corrupt the other Profile states;
- exercise multiple Profile sync jobs on the same customer host without state/lock/config collisions;
- resolve open issue `T4QP`: the supported PHP package must no longer require customers to hand-write a private sync launcher merely to load `sync.env` and call the packaged CLI;
- make the packaged multi-feed configuration/launcher path generic rather than HostGator- or customer-specific;
- keep bearer tokens/private sync configuration outside the public document root and off cron command lines where the governing integration security contract requires it;
- prove all three feeds can be rendered on the customer's website through supported local-read APIs rather than cache-file parsing;
- preserve direct stored publisher destinations and crawlable server-rendered Article links;
- exercise the operational workflow from admin Source/Profile configuration → machine credential/config → PHP sync → LKG → local-read → customer SSR;
- capture friction/issues discovered during that real setup for Phase 4 rather than hiding manual workarounds.

### AI composition

Where useful, the multi-feed proof should also demonstrate that scheduled digests and "Ask this feed" bind to the correct Profile and do not leak article context between publishing news, opportunities, and filmmaking.

### Phase 3 exit gate

The real customer integration demonstrably serves all three configured Profile feeds from one singleton Publication/editorial property. Each feed uses the canonical Profile/API/PHP/local-read chain, maintains independent local state, links directly to governed publisher destinations, and survives isolated failure/disable conditions without contaminating the others.

The installation process is documented using the shipped package rather than undocumented customer-written glue.

Green Phase 3 `/closeout` advances only to `2.4.0`.

## Phase 4 — Admin and PHP integration tightening

**Planned baseline:** `2.4.0`  
**Planned prompt versions:** `2.4.x+`  
**Goal:** remove operator/integrator friction discovered through the Gemini and real multi-feed deployments while preserving established product boundaries.

### Intentionally open scope

This phase is deliberately not decomposed into implementation tasks yet. Candidate areas include:

- Source/endpoint onboarding ergonomics;
- Profile creation and Source-membership/filter workflow;
- Gemini configuration, cadence, status, and failure visibility;
- machine credential creation/rotation and AI-capability administration;
- integration-package download/install instructions;
- private configuration generation/validation;
- multi-Profile PHP sync launcher/configuration;
- cron/scheduler setup;
- sync/digest/chat health diagnostics;
- customer local-read integration examples;
- upgrade/install/version visibility;
- safer, clearer error reporting.

Real observed friction from Phases 1–3 should outrank speculative polish.

### Boundary

Phase 4 is a hardening/experience bucket, not permission to add unrelated product families. Material new capabilities—new adapters, analytics, autonomous AI, multi-Publication tenancy, major API incompatibility, or unrelated self-host productization—require explicit owner promotion into the roadmap/contracts.

## 3.0 terminal release gate

**Status: intentionally TBD / owner-controlled.**

The owner will define the final `3.0.0` exit gate after:

1. the Gemini scheduled digest works through the real customer integration;
2. Profile-grounded chat works with appropriate safety/cost/auth controls;
3. the three-feed publishing/opportunities/filmmaking deployment is proven; and
4. enough real admin/PHP workflow experience exists to identify which remaining friction is release-blocking.

Until that explicit decision:

- there is no assumed final Phase 4 prompt count;
- there is no automatic `3.0.0` transition;
- later `2.4.x` hardening work may continue only within the governed Phase 4 boundary;
- `/closeout` must not infer a terminal gate from version number alone.

When the owner later locks the terminal gate, the roadmap must be amended before a terminal release transition. The intended terminal transition is version-only from the exact accepted final `2.x.x` candidate to `3.0.0`, but that behavior is not executable merely from this pre-activation document.

## Deferred unless explicitly promoted

The following remain outside the current 3.0 commitment unless the owner later promotes them:

- concurrent multi-Publication/multi-tenant hosting;
- AI-based Source approval, Relevance, moderation, duplicate decisions, or autonomous admin control;
- a News Scraper-owned Article-body crawler or persisted Article-body RAG corpus;
- arbitrary web browsing/search or model-selected URL retrieval beyond application-selected governed `originalUrl` URL Context;
- mandatory embeddings/vector storage;
- reader personalization/profiling;
- visitor/click/referral analytics;
- WordPress-specific productization;
- public RSS/Atom output;
- browser widgets as the primary integration path;
- Linux VPS/Docker Compose self-host packaging/productization;
- native/default self-host administrator accounts;
- advanced SEO tooling;
- delta synchronization;
- unrelated adapter families.

These may be reconsidered later, but none should be pulled into an implementation prompt merely because they were previously described as post-2.0 possibilities.
