# 2.0 Planning Questions

**Status:** Completed historical planning record  
**Authority:** Non-normative. Approved answers were promoted into `docs/contracts/distribution-and-integration-contract.md` and `docs/contracts/distribution-api-contract.md`; later owner-approved scope/roadmap changes are governed by those contracts and `docs/roadmap/post-1.0-roadmap.md`.

The final promotion refinements established bounded Profile selectors/persistence, bound cursors to `snapshotRevision` with `409 snapshot_changed`, made authenticated `409 profile_disabled` authoritatively suppress cached rendering, and removed Profile-specific `403` authorization and permissive browser-CORS requirements from initial v1.

A later owner decision during roadmap approval removed Linux VPS/Docker Compose self-host packaging from the `2.0.0` completion gate. Self-hostability remains architectural direction, but packaging/productized self-host support is post-2.0. This record reflects that final scope below.

## 1. Distribution Profile selectors

**Status:** Answered

Sources and Distribution Profiles are peer top-level resources within one News Scraper instance. Sources are configured, approved, collected, normalized, and monitored once; Profiles associate with one or more approved Sources without duplicating Source configuration, collection jobs, Article identity, or provenance.

The Profile↔Source association is first-class and may hold Source-specific distribution configuration for that Profile. An active Profile must have at least one usable approved Source association, while drafts may exist before that requirement is met.

Filtering is split deliberately:

- **Source collection filtering** is an optional protective ingestion gate.
- **Distribution Profile filtering** is the normal customer-facing selection mechanism after canonical outward eligibility.

The finalized bounded Profile filters are `include_any_phrases[]`, `exclude_any_phrases[]`, and `category_config_keys[]`: OR within each list, dimensions AND, exclusion wins, deterministic case-insensitive literal phrase matching over safe normalized outward text, effective moderated Category membership, and no regex/fuzzy/semantic/ranking/expression behavior. Profile filtering only narrows governed Articles and never alters Source approval, collection, identity/provenance, moderation, duplicate decisions, Relevance, Categories, or canonical eligibility.

## 2. Canonical outward eligibility vs reference-frontend visibility

**Status:** Answered

Canonical outward Article eligibility is independent of bundled reference-frontend exposure. Distribution Profiles operate after canonical eligibility and may only narrow it.

The Publication/reference-frontend `public_status` governs only legacy/reference public surfaces. Disabling the bundled frontend must not disable Distribution Profiles or the 2.0 machine/PHP integration.

`GET /` and `GET /api/feed` remain supported reference/legacy surfaces and are not the permanent 2.0 integration API.

## 3. Permanent 2.0 machine API

**Status:** Answered

The permanent 2.0 machine interface is a separate, explicitly versioned, read-only, Profile-addressed JSON API:

```text
GET /api/v1/distribution/{profile_key}
GET /api/v1/distribution/{profile_key}?cursor=...
```

The immutable Profile `config_key` is explicit in the path. Consumers receive the governed Profile result and may not reconstruct Profile selection with arbitrary Source/Category/keyword query parameters.

Continuation uses opaque keyset/cursor pagination bound to `snapshotRevision`. Normal JSON distribution requires machine authentication. Expected states include `200`, conditional initial `304`, `400`, `401`, `404`, `409 profile_disabled`, `409 snapshot_changed`, `429`, and `503`. Initial v1 has no credential↔Profile matrix or Profile-specific `403`.

Within `/api/v1`, required fields and documented semantics cannot be removed or incompatibly reinterpreted. Compatible additive fields are allowed; breaking changes require a new major API path such as `/api/v2`.

## 4. Guaranteed distribution fields

**Status:** Answered

The v1 schema has stable field presence. Optional metadata remains present as `null`; collections remain present as `[]` when empty.

Envelope fields:

- `apiVersion`
- `generatedAt`
- `snapshotRevision`
- `profile.configKey`
- `profile.displayName`
- `publication.name`
- `items`
- `nextCursor`

Each Article item guarantees:

- `articleId`
- `headline`
- `originalUrl`
- `effectiveFeedDate`
- `feedDateSource`
- nullable `publishedAt`
- nullable `author`
- nullable `summary`
- nullable `imageUrl`
- `source.configKey`
- `source.displayName`
- `categories[]` containing `configKey` and `displayName`

`summary` and `imageUrl` are guaranteed schema fields from v1 even when current collection cannot populate them. Category output reflects effective outward moderated state. Control-plane/persistence internals are not exposed. Downstream integrations own presentation, so Publication branding beyond name is not required initially.

## 5. Machine authentication

**Status:** Answered

The 2.0 machine API uses dedicated high-entropy bearer credentials sent only through `Authorization: Bearer ...`. Machine authentication is separate from human administrator authentication and grants only `distribution:read` capability.

Tokens are generated by News Scraper, use strong cryptographic randomness, are shown in plaintext only at creation, and are never stored plaintext in PostgreSQL. Persisted state contains non-secret lookup identity, a secure verifier/digest, label, lifecycle/audit timestamps, optional expiry, and revocation state. Tokens are never accepted in query strings or intentionally logged; production distribution requires HTTPS.

Expiration is supported but optional. Rotation allows overlapping replacement credentials before revoking the old one. Invalid/revoked/expired credentials return `401` without leaking internal state.

Rate limiting is primarily per authenticated credential, with separate network/IP protection for invalid-auth abuse. `429` responses are machine-readable and include `Retry-After`. Billing-style quotas are not required for 2.0.

## 6. Credential-to-Profile mapping

**Status:** Answered

Machine distribution credentials are owned and authenticated locally by each isolated News Scraper instance. No central credential authority or higher-level shared credential database is required.

A valid instance credential with `distribution:read` may request any active Distribution Profile on that same instance. The Profile remains explicit in the API path; the token proves machine access to the instance rather than selecting or individually authorizing a Profile.

2.0 therefore does not require a credential↔Profile permission matrix. Multiple instance credentials may exist for independent consumers, rotation, or emergency replacement. Profile and credential lifecycles remain independent.

Managed deployments may share physical infrastructure, but each customer instance retains its own state and credential verifier.

## 7. Adapter synchronization model

**Status:** Answered

PHP integrations synchronize using complete bounded Distribution Profile snapshots rather than incremental/delta synchronization. A run follows all required cursors, validates the complete snapshot/revision, and only then atomically replaces the local visible cache. Any partial, invalid, failed, or mixed-revision run leaves the previous valid snapshot untouched.

The Profile defines the bounded outward history/result set; adapters do not request unbounded history or reimplement Article selection. Incremental/delta synchronization is deferred unless later scale proves snapshots insufficient.

Synchronization cadence is customer-configurable with a **15-minute default**. Public page rendering reads local adapter state and never calls News Scraper synchronously per visitor request.

Overlapping syncs are prevented; retries are bounded and respect `429`/`Retry-After`. The API/adapters support the governed ETag/`If-None-Match`/`304` direction.

## 8. Last-known-good cache contract

**Status:** Answered

Each integration maintains an independent last-known-good cache per Distribution Profile. Rendering reads only the active local snapshot.

A sync builds a candidate separately, validates all cursor pages plus API version, Profile identity, envelope/schema, item shape, `snapshotRevision`, and storage, then activates it atomically. Partial or invalid candidates never replace the active snapshot. Syncs lock per Profile and preserve a recoverable prior valid state where practical.

Cache metadata includes Profile key, API version, upstream `generatedAt`, local last-successful-sync time, and ETag/revision when available. Machine credentials are never stored inside cache payloads.

Freshness and usability are separate. Stale-but-valid data remains renderable by default and **there is no hard stale cutoff by default**. Customers may optionally configure a maximum stale age; once exceeded, their configured empty/unavailable fallback may be used instead.

If no valid snapshot has ever existed, render a safe configured empty/unavailable state rather than exposing raw errors or making a live visitor-path API call.

Ordinary network/auth/rate/5xx/invalid-candidate failures preserve LKG under stale policy. An authenticated `409 profile_disabled` is authoritative control-plane state: cached bytes may be retained for recovery, but cached Articles are not rendered until the Profile is re-enabled and a later synchronization succeeds.

## 9. Generic PHP integration surface

**Status:** Answered

The generic PHP integration exposes three layers:

1. a synchronization/cache client;
2. normalized local Distribution Profile data access;
3. an optional safe server-rendered fallback renderer.

The sync/cache layer owns API authentication, endpoint construction, cursor traversal, conditional requests, full-snapshot validation, locking, atomic replacement, stale-state metadata, retry/backoff, and last-known-good preservation.

The local data layer exposes the cached Profile and guaranteed v1 fields without requiring customers to parse raw cache files or contact News Scraper during rendering. This is the primary extension surface for custom presentation.

The fallback renderer produces safe server-side HTML with direct stored publisher destinations and graceful handling of nullable metadata, stale snapshots, disabled/empty/unavailable states. It is thin and fully replaceable. Customer customization may change presentation but never reimplement selection, eligibility, moderation, dedupe, Relevance, Categories, ordering, or destination semantics.

## 10. WordPress/PHP sharing boundary

**Status:** Answered — planned post-2.0 feature

WordPress is not required for the `2.0.0` completion gate. When later implemented it follows the generic PHP integration model rather than becoming an independent News Scraper client.

Shared/core behavior owns authentication, API consumption, schema validation, snapshot synchronization, normalized data access, freshness/staleness semantics, cache correctness, and fallback rendering primitives. WordPress-specific code is limited to CMS settings/admin UI, credential configuration, scheduling, storage/locking adapters, health/status presentation, shortcodes/blocks/templates, and presentation hooks.

The dependency direction is generic/shared PHP core → WordPress adapter. The shared core has no WordPress dependency.

## 11. RSS/Atom distribution access

**Status:** Answered — planned post-2.0 feature

RSS/Atom is not required for `2.0.0`. When later implemented it is an optional, explicitly enabled, bare-bones per-Profile public interoperability output using the same canonical Profile/read-model authority.

It is not a second selection/query engine. Private/authenticated RSS/Atom and secret-bearing feed URLs are not part of the initial plan; authenticated machine consumers use the versioned JSON API.

## 12. SEO and link policy

**Status:** Answered

News Scraper supports technically crawlable, direct editorial links to original publishers but does not promise ranking improvements, backlink value, PageRank transfer, or other SEO performance outcomes.

The generic PHP integration and its fallback renderer should produce ordinary server-rendered HTML anchors whose `href` points directly to exact stored publisher `originalUrl`. Core links do not depend on browser JavaScript and do not route through News Scraper tracking redirects by default.

Ordinary editorial external links are unqualified by default; News Scraper does not add `nofollow` automatically merely because a destination is external. Customers remain responsible for appropriate relationship-specific `rel` treatment.

News Scraper must not require, negotiate, automate, or condition Article inclusion on reciprocal backlinks; implement backlink quotas/automatic link exchanges; keyword-stuff anchor text; or manipulate Profile selection for search rankings.

The customer website owns canonical tags, sitemaps, robots directives, page titles, surrounding copy, site architecture, and overall SEO strategy. News Scraper does not create local Article-detail copies merely to capture search traffic by default.

## 13. Exclude-self semantics

**Status:** Answered

2.0 has no dedicated `exclude self` semantic. A Profile includes only the Sources whose eligible Articles it should distribute. A customer-owned Source may remain configured and collected while being omitted from a selected Profile.

The engine must not infer ownership from domains, URLs, Source names, aliases, or heuristics. If a future feature needs formal Source ownership/organization identity, that relationship must be modeled explicitly.

## 14. Self-host deployment direction

**Status:** Answered — packaging deferred beyond 2.0

News Scraper remains self-hostable by design under Project Contract Law 12: the complete independently operable single-Publication stack must not depend on a mandatory central News Scraper service, credential authority, licensing service, or shared customer database.

The earlier planning direction considered a lightweight standard-Linux VPS/Docker Compose package. During final roadmap approval, the owner explicitly removed that packaging work from the `2.0.0` completion gate so 2.0 can validate the managed Profile/API/PHP product first.

Therefore Linux VPS/Docker Compose packaging, installer/setup UX, formal self-host production support, and deployment-specific packaging validation are post-2.0. A later roadmap may use the earlier planning assumptions—complete Web/Admin/API, Worker, scheduler/jobs, PostgreSQL, persistence, health, migrations, external-PostgreSQL compatibility, configuration/secrets, upgrades, backup/restore—as input, but they are not current 2.0 deliverables.

## 15. Self-hosted administrator authentication

**Status:** Answered — deferred beyond 2.0

Native/default News Scraper administrator authentication is not required for `2.0.0`. Managed deployments continue to use the current/planned managed admin perimeter, including Cloudflare Access where applicable. Human admin protection remains separate from machine distribution authentication.

Built-in administrator authentication or a formally supported reverse-proxy/SSO replacement contract is deferred to later self-hosting work and must eventually define bootstrap/recovery, credential/session security, authorization, abuse protection, and interaction with optional outer access gateways.

## 16. Distribution telemetry

**Status:** Answered

2.0 distribution telemetry is operational and diagnostic rather than analytical.

The News Scraper instance records bounded structured distribution outcomes including Profile key, API version, response status, duration, Article/page information, non-secret machine-credential identity, authentication/rate-limit/missing/disabled/failure categories, and adapter/client version when supplied. Plaintext credentials, Authorization headers, secrets, and sensitive payloads are never logged.

The generic PHP integration exposes local synchronization/cache health including last attempt/success, duration, items/pages, fresh/stale state and stale age, unchanged/`304` result, last failure category, and adapter version.

Click, referral, visitor, page-view, backlink-performance, reader-identity, and tracking-redirect analytics are outside 2.0. Telemetry remains locally operable; managed infrastructure may aggregate it externally without creating a runtime dependency.

## 17. Backward compatibility

**Status:** Answered

2.0 preserves supported 1.x production data and legacy/reference outward behavior while allowing internal architecture and implementation details to evolve.

The accepted `1.0.0` launch remains the first supported production schema/data baseline. `1.0.1` was the application package immediately before the active 2.0 development roadmap; roadmap activation moved the development baseline to `1.1.0` without changing runtime behavior.

Existing `GET /` and `GET /api/feed` remain supported reference/legacy surfaces through 2.0 and are not promoted into the permanent distribution API. Their supported eligibility, duplicate suppression, ordering, destination, discovery, and public-exposure behavior must not regress accidentally.

`GET /api/v1/distribution/{profile_key}` establishes a separate version-bound external compatibility contract. Compatible additive v1 fields are allowed; breaking changes require a new major API path.

Production upgrade validation preserves Articles/provenance, Sources/endpoints, collection/runtime state, Publication configuration, Categories/Relevance/moderation, duplicate state, introduced Distribution Profiles/associations, machine-credential verifier state, and other governed persisted state. Migration from zero remains required but is not production upgrade proof.

Downgrades are not guaranteed. Backup/restore is the rollback path. Compatibility does not freeze internal TypeScript APIs, repository structure, SQL implementation, undocumented helpers/admin markup, or development tooling.

## 18. `2.0.0` completion gate

**Status:** Answered — final owner-approved scope

`2.0.0` proves that News Scraper can operate as a reliable managed headless aggregation/distribution product powering an external customer-style website through a governed Distribution Profile and generic PHP integration.

Required path:

```text
approved Sources
→ collection / normalization / persistence
→ canonical outward eligibility
→ Distribution Profile
→ authenticated GET /api/v1/distribution/{profile_key}
→ scheduled generic PHP synchronization
→ validated local last-known-good snapshot
→ server-rendered customer website
→ direct stored publisher originalUrl links
```

The release requires:

- administrator-configurable Distribution Profiles with immutable keys, lifecycle, explicit Source associations, bounded result/history, and finalized filters;
- one canonical distribution read model independent of reference `public_status`;
- dedicated machine credentials with secure verifier storage, lifecycle/rotation/revocation, `distribution:read`, bearer authentication, and rate/abuse protection;
- stable v1 JSON schema, opaque keyset pagination, `snapshotRevision`, governed errors, and direct publisher destinations;
- generic PHP complete-snapshot synchronization, configurable cadence, cursor traversal, validation, locking, atomic LKG activation, normalized local data access, optional stale cutoff, and safe fallback SSR;
- operational distribution telemetry without visitor/click analytics;
- production-safe forward migration from the supported baseline plus compatibility with documented backup/restore/rollback procedures;
- real managed end-to-end external customer-site proof, including upstream failure, invalid/partial candidate, revision-change, stale-cache, authoritative-disable/re-enable, authentication/revocation, rate-limit, and no-live-visitor-path-API behavior.

Linux VPS/Docker Compose self-host packaging is **not** a `2.0.0` requirement.

Explicitly post-2.0: self-host packaging/installer/productized support, native self-host admin authentication, WordPress, RSS/Atom, SSO/multi-admin identity, click/referral/visitor/backlink analytics, advanced SEO tooling, browser widgets, Kubernetes/multi-node deployment, delta synchronization, and additional adapters.

The product milestone distinction is:

- **1.x development:** existing aggregation/reference product plus incremental implementation of the seven-phase distribution roadmap;
- **2.0:** the final validated `1.7.x` managed Profile/API/PHP integration candidate promoted by a version-only terminal closeout to `2.0.0`.

This planning record no longer gates implementation. The owner-approved seven-phase roadmap is active at `1.1.0`; normal `/prompt-ass` → `/prompt-plan` → `/prompt-write p1-1` may proceed for Phase 1.
