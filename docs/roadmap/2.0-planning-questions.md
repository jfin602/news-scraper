# 2.0 Planning Questions

**Status:** Working roadmap-planning worksheet.  
**Authority:** Non-normative. This file records unresolved 2.0 design questions and the answers reached during roadmap planning. Governing contracts/ADRs must be updated separately through the normal docs workflow before implementation resumes.

As decisions are reached, replace each `Open` entry with the agreed answer rather than keeping a parallel answer log.

## 1. Distribution Profile selectors

**Status:** Open

What exactly can a Distribution Profile select? Sources, Categories, keyword rules, limits, exclusions, combinations, or another bounded selector set?

## 2. Canonical outward eligibility vs reference-frontend visibility

**Status:** Open

How should canonical outward eligibility be separated from reference-frontend visibility? Should integrations continue working when the bundled `/` reference frontend is not publicly exposed?

## 3. Permanent 2.0 machine API

**Status:** Open

What is the permanent 2.0 machine-facing distribution API? Define path, versioning, response envelope, pagination, errors, and compatibility guarantees.

## 4. Guaranteed distribution fields

**Status:** Open

Which Article, Source, Publication, and profile fields must the 2.0 machine contract guarantee? Consider stable IDs/config keys, headline, dates, Categories, summary, image, and `original_url`.

## 5. Machine authentication

**Status:** Open

How should machine authentication work? Define credential format, scope, storage, rotation, revocation, least privilege, and rate-limit implications.

## 6. Credential-to-Profile mapping

**Status:** Open

How do machine credentials map to Distribution Profiles? One credential per Profile, one credential allowed multiple Profiles, or both?

## 7. Adapter synchronization model

**Status:** Open

How should PHP/WordPress adapters synchronize? Full bounded snapshots, incremental/delta synchronization, polling intervals, retries, and atomic replacement need to be decided.

## 8. Last-known-good cache contract

**Status:** Open

What is the local last-known-good cache contract? Define storage representation, freshness/TTL, stale-on-error behavior, locking, corruption handling, and replacement rules.

## 9. Generic PHP integration surface

**Status:** Open

What should the generic PHP integration expose? Raw normalized data access, synchronization/cache helpers, fallback rendering, extension hooks, or a combination?

## 10. WordPress/PHP sharing boundary

**Status:** Open

How much implementation should WordPress share with the generic PHP package? Determine the common client/synchronization/cache boundary and WordPress-specific responsibilities.

## 11. RSS/Atom distribution access

**Status:** Open

How should RSS/Atom distribution be exposed? Decide public vs private/authenticated access, Profile-specific endpoints, credentials/tokens if any, and supported metadata.

## 12. SEO and link policy

**Status:** Open

What is the supported SEO/link policy? Define direct publisher links, `rel` attributes, reciprocal-link behavior, canonical/sitemap ownership, and the limits of any SEO/backlink claims.

## 13. Exclude-self semantics

**Status:** Open

Does the Platform need an explicit `exclude self` Distribution Profile semantic, or should this always be represented through ordinary Source exclusion/profile configuration?

## 14. 2.0 self-hostable deployment definition

**Status:** Open

What does self-hostable mean for the 2.0 release? Decide required packaging/deployment form, supported environment assumptions, configuration/secrets, PostgreSQL expectations, upgrades, backup/restore, and operational boundaries.

## 15. Self-hosted administrator authentication

**Status:** Open

What secure administrator perimeter replaces or complements Cloudflare Access for self-hosted installations? Native application authentication, reverse-proxy/SSO contract, or both?

## 16. Distribution telemetry

**Status:** Open

What telemetry is required for distribution? Consider profile/API requests, authentication failures, adapter synchronization failures, stale caches, adapter versions, response errors, and whether referral/click analytics belong in 2.0.

## 17. Backward compatibility

**Status:** Open

What backward compatibility is promised through 2.0? Define treatment of existing `/`, `/api/feed`, `1.0.1` behavior, the new external API, adapter compatibility, and production schema/data upgrades.

## 18. 2.0.0 completion gate

**Status:** Open

What specifically must be production-ready for `2.0.0`? Define required adapters, deployment modes, control-plane/profile capabilities, security/reliability proof, and which capabilities may remain post-2.0.
