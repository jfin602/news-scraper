# 2.0 Planning Questions

**Status:** Working roadmap-planning worksheet.  
**Authority:** Non-normative. This file records unresolved 2.0 design questions and the answers reached during roadmap planning. Governing contracts/ADRs must be updated separately through the normal docs workflow before implementation resumes.

As decisions are reached, replace each `Open` entry with the agreed answer rather than keeping a parallel answer log.

## 1. Distribution Profile selectors

**Status:** Answered

Sources and Distribution Profiles are peer top-level resources within one News Scraper instance. Sources are configured, approved, collected, normalized, and monitored once; Profiles associate with one or more approved Sources without duplicating Source configuration, collection jobs, Article identity, or provenance.

The Profile↔Source association is first-class and may hold Source-specific distribution configuration for that Profile. An active Profile must have at least one usable approved Source association, while drafts may exist before that requirement is met.

Filtering is split deliberately:

- **Source collection filtering** is an optional protective ingestion gate and is expected to be unused in many ordinary deployments.
- **Distribution Profile filtering** is the normal customer-facing selection mechanism and operates after canonical outward eligibility.

Profile filtering may only narrow already-governed Articles and must not alter Source approval, collection, Article identity/provenance, moderation, duplicate decisions, or canonical eligibility. The exact bounded Profile selector/operator vocabulary remains to be designed.

## 2. Canonical outward eligibility vs reference-frontend visibility

**Status:** Answered

Canonical outward Article eligibility is independent of bundled reference-frontend exposure. Distribution Profiles operate after canonical eligibility and may only narrow it.

The Publication/reference-frontend public exposure state governs only legacy/reference public surfaces. Disabling the bundled frontend must not disable Distribution Profiles, the 2.0 machine API, RSS/Atom Profile output, or integrations.

`GET /` and `GET /api/feed` remain supported reference/legacy surfaces and are not reinterpreted as the permanent 2.0 integration API. The 2.0 distribution system uses a separate Profile-governed machine interface controlled by Profile lifecycle/state and machine authorization.

## 3. Permanent 2.0 machine API

**Status:** Answered

The permanent 2.0 machine interface is a separate, explicitly versioned, read-only, Profile-addressed JSON API:

```text
GET /api/v1/distribution/{profile_key}
GET /api/v1/distribution/{profile_key}?cursor=...
```

The immutable Profile `config_key` is explicit in the path. Consumers receive the governed Profile result and may not reconstruct Profile selection with arbitrary Source/Category/keyword query parameters.

Continuation uses opaque keyset/cursor pagination. Normal JSON distribution requires machine authentication. Expected states include `200` success/empty result, `400` malformed request or cursor, `401` failed authentication, `403` authenticated-but-forbidden access where applicable, `404` missing Profile, an explicit machine-readable disabled-Profile error, `429` rate limiting, and `503` bounded service/dependency failure.

Within `/api/v1`, required fields and documented semantics cannot be removed or incompatibly reinterpreted. Compatible additive fields are allowed; breaking changes require a new major API path such as `/api/v2`.

## 4. Guaranteed distribution fields

**Status:** Answered

The v1 schema has stable field presence. Optional metadata remains present as `null`; collections remain present as `[]` when empty.

Envelope fields:

- `apiVersion`
- `generatedAt`
- `profile.configKey`
- `profile.displayName`
- `publication.name`
- `items`
- `nextCursor`

Each Article item guarantees:

- `articleId`
- `headline`
- `originalUrl`
- `effectiveFeedDate`
- `feedDateSource`
- nullable `publishedAt`
- nullable `author`
- nullable `summary`
- nullable `imageUrl`
- `source.configKey`
- `source.displayName`
- `categories[]` containing `configKey` and `displayName`

`summary` and `imageUrl` are guaranteed schema fields from v1 even when current collection cannot populate them. Category output reflects effective outward moderated state. Control-plane/persistence internals are not exposed. Downstream integrations own presentation, so Publication branding beyond name is not required initially.

## 5. Machine authentication

**Status:** Answered

The 2.0 machine API uses dedicated high-entropy bearer credentials sent only through `Authorization: Bearer ...`. Machine authentication is separate from human administrator authentication and grants only `distribution:read` capability.

Tokens are generated by News Scraper, use strong cryptographic randomness, are shown in plaintext only at creation, and are never stored plaintext in PostgreSQL. Persisted state contains non-secret lookup identity, a secure verifier/digest, label, lifecycle/audit timestamps, optional expiry, and revocation state. Tokens are never accepted in query strings or intentionally logged; production distribution requires HTTPS.

Expiration is supported but optional. Rotation allows overlapping replacement credentials before revoking the old one. Invalid/revoked/expired credentials return `401` without leaking internal state.

Rate limiting is primarily per authenticated credential, with separate network/IP protection for invalid-auth abuse. `429` responses are machine-readable and include `Retry-After`. Billing-style quotas are not required for 2.0.

## 6. Credential-to-Profile mapping

**Status:** Answered

Machine distribution credentials are owned and authenticated locally by each isolated News Scraper instance. No central credential authority or higher-level shared credential database is required.

A valid instance credential with `distribution:read` may request any active Distribution Profile on that same instance. The Profile remains explicit in the API path; the token proves machine access to the instance rather than selecting or individually authorizing a Profile.

2.0 therefore does not require a credential↔Profile permission matrix. Multiple instance credentials may exist for production/staging separation, independent consumers, rotation, or emergency replacement. Profile and credential lifecycles remain independent.

Managed deployments may share physical/VPS infrastructure, but each customer instance retains its own state and credential verifier. Self-hosted deployments use the same complete local model.

## 7. Adapter synchronization model

**Status:** Answered

PHP integrations synchronize using complete bounded Distribution Profile snapshots rather than incremental/delta synchronization. A run follows all required cursors, validates the complete snapshot, and only then atomically replaces the local visible cache. Any partial or failed run leaves the previous valid snapshot untouched.

The Profile defines the bounded outward history/result set; adapters do not request unbounded history or reimplement Article selection. Incremental/delta synchronization is deferred unless later scale proves snapshots insufficient.

Synchronization cadence is customer-configurable with a **15-minute default**. Slower Publications may poll less frequently; faster domains may choose shorter intervals. Public page rendering reads local adapter state and never calls News Scraper synchronously per visitor request.

Overlapping syncs are prevented; retries are bounded and respect `429`/`Retry-After`. The API/adapters should support or be designed for ETag/`If-None-Match` and `304 Not Modified` as an efficiency optimization.

## 8. Last-known-good cache contract

**Status:** Answered

Each integration maintains an independent last-known-good cache per Distribution Profile. Rendering reads only the active local snapshot.

A sync builds a candidate separately, validates all cursor pages plus API version, Profile identity, envelope/schema, item shape, and storage, then activates it atomically. Partial or invalid candidates never replace the active snapshot. Syncs lock per Profile and preserve a recoverable prior valid state where practical.

Cache metadata includes Profile key, API version, upstream `generatedAt`, local last-successful-sync time, and ETag/revision when available. Machine credentials are never stored inside cache payloads.

Freshness and usability are separate. Stale-but-valid data remains renderable by default and **there is no hard stale cutoff by default**. Customers may optionally configure a maximum stale age appropriate to their use case; once exceeded, their configured empty/unavailable fallback may be used instead.

If no valid snapshot has ever existed, render a safe configured empty/unavailable state rather than exposing raw errors or making a live visitor-path API call. Physical storage may differ by adapter, but the behavioral guarantees remain the same.

## 9. Generic PHP integration surface

**Status:** Answered

The generic PHP integration exposes three layers:

1. a synchronization/cache client;
2. normalized local Distribution Profile data access;
3. an optional safe server-rendered fallback renderer.

The sync/cache layer owns API authentication, endpoint construction, cursor traversal, conditional requests, full-snapshot validation, locking, atomic replacement, stale-state metadata, retry/backoff, and last-known-good preservation.

The local data layer exposes the cached Profile and guaranteed v1 fields without requiring customers to parse raw cache files or contact News Scraper during rendering. This is the primary extension surface for custom presentation.

The fallback renderer produces safe server-side HTML with direct stored publisher destinations and graceful handling of nullable metadata, stale snapshots, and empty/unavailable states. It is thin and fully replaceable. Customer customization may change presentation but never reimplement selection, eligibility, moderation, dedupe, Relevance, Categories, ordering, or destination semantics.

## 10. WordPress/PHP sharing boundary

**Status:** Answered — planned post-2.0 feature

WordPress is not required for the 2.0.0 completion gate. It remains a planned adapter feature after the generic PHP integration is established.

When implemented, the WordPress plugin must follow the same model as the generic PHP integration rather than becoming an independent News Scraper client. Shared/core behavior should own authentication, API consumption, schema validation, snapshot synchronization, normalized data access, freshness/staleness semantics, cache correctness, and fallback rendering primitives.

WordPress-specific code should be limited to CMS concerns such as settings/admin UI, secure local credential configuration, WordPress scheduling, WordPress-native storage/locking adapters, health/status presentation, shortcodes/blocks/templates, and WordPress-specific presentation hooks.

The dependency direction is generic/shared PHP core → WordPress adapter. The shared core must have no WordPress dependency. The WordPress release may bundle a compatible copy of that maintained core so customers are not required to install Composer dependencies separately.

## 11. RSS/Atom distribution access

**Status:** Answered — planned post-2.0 feature

RSS/Atom is not required for the 2.0.0 completion gate. It is a planned interoperability fallback after the primary authenticated JSON API and generic PHP integration are established.

When implemented, RSS/Atom is an optional per-Distribution-Profile public output, disabled by default and enabled explicitly by the customer. It must remain intentionally bare-bones: a standards-compatible fallback for consumers that cannot use the JSON/PHP integration modes, not a second full-featured integration stack.

RSS/Atom serializes the same canonical Distribution Profile/read-model result as every other outward consumer and may not implement independent Source, Category, Relevance, moderation, duplicate, ordering, or selection logic. Public RSS/Atom exposure is independent of the bundled reference frontend's `public_status`.

The output should preserve stable Article identity, headline, direct stored publisher `originalUrl`, effective date, and available standard metadata such as author, summary/description, Categories, and image only where a clean standards-compatible mechanism exists.

Private/authenticated RSS/Atom and secret-bearing feed URLs are not part of the initial plan. Machine consumers requiring authenticated access use the versioned JSON API instead. Exact feed paths and secondary format details are deferred until this post-2.0 feature is planned for implementation.

## 12. SEO and link policy

**Status:** Answered

News Scraper supports technically crawlable, direct editorial links to original publishers but does not promise ranking improvements, backlink value, PageRank transfer, or other SEO performance outcomes.

The generic PHP integration and its fallback renderer should produce ordinary server-rendered HTML anchors whose `href` points directly to the exact stored publisher `originalUrl`. Core links must not depend on browser JavaScript and should not route through News Scraper tracking/redirect URLs by default.

Ordinary editorial links are unqualified by default; News Scraper does not add `nofollow` automatically merely because a destination is external. Customers remain responsible for configuring appropriate `rel` treatment when their actual relationship with a destination requires sponsored, UGC, nofollow, or other qualification.

News Scraper must not require, negotiate, automate, or condition Article inclusion on reciprocal backlinks. It must not implement backlink quotas, automatic link exchanges, keyword-stuffed anchor rewriting, or Profile-selection behavior whose purpose is manipulating search rankings. Customers may naturally link to approved Sources or partners, but reciprocal commercial/editorial arrangements remain outside the aggregation engine.

The customer website owns page-level SEO concerns including canonical tags, sitemaps, robots directives, page titles, surrounding copy, site architecture, and overall SEO strategy. News Scraper does not create local Article-detail copies merely to capture search traffic by default.

The supported product claim is limited to the technical behavior News Scraper can prove: integrations can expose server-rendered, crawlable direct outbound links to original publishers. No SEO/backlink-performance guarantee is part of the product contract.

## 13. Exclude-self semantics

**Status:** Answered

2.0 does not define a dedicated `exclude self` Distribution Profile semantic. Distribution Profiles express their outward Source set explicitly: a Profile includes the Sources whose eligible Articles should be distributed and omits Sources that should not appear.

A customer-owned Source may remain configured, approved, collected, normalized, and available to other Profiles while simply being absent from a Profile intended to show external news. No special engine-level concept of "self" is required for that use case.

The aggregation/distribution engine must not infer customer ownership from domains, URL matching, Source names, aliases, or similar heuristics merely to support exclusion. Such inference would introduce ambiguous ownership semantics and unnecessary topic/customer-specific behavior into the shared engine.

If a future feature genuinely requires formal Source ownership or organization identity, that relationship should be modeled explicitly with its own contract rather than introduced indirectly through a magic `exclude self` rule.
