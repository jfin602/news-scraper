**Status:** Working roadmap-planning worksheet.  
**Authority:** Non-normative. This file records unresolved 2.0 design questions and the answers reached during roadmap planning. Governing contracts/ADRs must be updated separately through the normal docs workflow before implementation resumes.

As decisions are reached, replace each `Open` entry with the agreed answer rather than keeping a parallel answer log.

## 1. Distribution Profile selectors

**Status:** Answered

Sources and Distribution Profiles are peer top-level resources within one News Scraper instance.

A Source is configured, approved, collected, normalized, and monitored once per instance. It owns its endpoints and collection behavior. Distribution Profiles do not own, duplicate, or recollect Sources. The same approved Source may be associated with multiple Profiles without duplicating Source configuration, endpoint configuration, collection jobs, Article identity, or provenance.

A Distribution Profile has explicit associations to one or more approved Sources. The Profile↔Source association is a first-class relationship because it may carry distribution-specific configuration for that Source in the context of that Profile. An active Profile must ultimately have at least one usable approved Source association, while draft configuration may exist before that requirement is satisfied.

Filtering is deliberately split into two stages with different purposes:

1. **Source collection filtering** is an optional protective ingestion gate. It answers whether an item should enter News Scraper at all. It is expected to be unused in many ordinary deployments and must not be treated as the primary mechanism for sorting or tailoring customer feeds.
2. **Distribution Profile filtering** is the normal customer-facing selection mechanism. It operates after governed collection/normalization and canonical outward eligibility, and decides which already-eligible Articles from each associated Source appear in that Profile.

Profile filtering must never alter Source approval, endpoint collection, stored Article identity/provenance, moderation state, duplicate decisions, or canonical outward eligibility. A Profile may only narrow the already-governed corpus.

The exact bounded selector/operator vocabulary for Profile distribution filtering remains to be designed later, but its ownership and placement are fixed by this answer: Source-global collection safety remains Source-owned; customer/feed tailoring belongs to the Distribution Profile and, where Source-specific behavior is needed, to the Profile↔Source relationship.

## 2. Canonical outward eligibility vs reference-frontend visibility

**Status:** Answered

Canonical outward Article eligibility is independent of bundled reference-frontend exposure.

The canonical eligibility boundary continues to decide which Articles are ordinarily eligible for outward use based on governed Source trust/lifecycle, Article visibility/moderation, duplicate suppression, ordering, destination semantics, and other canonical rules. Distribution Profiles operate after that boundary and may only narrow it.

The Publication/reference-frontend public exposure state governs only the legacy/reference public surfaces. Disabling the bundled public frontend must not disable Distribution Profiles, the 2.0 machine distribution API, RSS/Atom profile output, or PHP/WordPress/custom integrations.

The existing `GET /` and `GET /api/feed` remain supported reference/legacy surfaces associated with the bundled public feed and its public exposure semantics. They are not reinterpreted as the permanent 2.0 integration API.

The 2.0 distribution system therefore uses a separate Profile-governed machine interface whose availability is controlled by Profile lifecycle/state and machine authorization rather than by the reference frontend's public exposure setting.

Conceptually:

```text
canonical outward eligibility
→ Distribution Profile selection
→ 2.0 machine/RSS/adapter distribution
```

is independent from:

```text
canonical outward eligibility
→ reference-frontend public exposure gate
→ GET / and legacy/reference GET /api/feed
```

## 3. Permanent 2.0 machine API

**Status:** Answered

The permanent 2.0 machine-facing distribution interface is a separate, explicitly versioned, read-only, Profile-addressed JSON API.

The initial route shape is:

```text
GET /api/v1/distribution/{profile_key}
GET /api/v1/distribution/{profile_key}?cursor=...
```

The immutable Profile `config_key` is explicit in the resource path. Machine credentials authenticate and authorize access but do not implicitly choose the Profile. This keeps Profile identity visible, allows a credential model that may later authorize more than one Profile, and makes requests/debugging unambiguous.

The API exposes only the result of the governed Distribution Profile/read-model authority. Consumers may not reconstruct Profile selection through arbitrary Source, Category, keyword, or equivalent discovery query parameters. Profile configuration belongs to the control plane.

Continuation uses opaque keyset/cursor pagination rather than SQL offset or page-number semantics. Cursor validity remains bound to the governed request/profile criteria required for deterministic continuation.

The response uses a stable versioned JSON envelope containing API/profile metadata, an Article item collection, and an opaque next cursor or null. Exact guaranteed fields are decided under Question 4.

Normal machine JSON distribution requires machine authentication. The exact credential mechanism and credential-to-Profile mapping are decided under Questions 5 and 6. The distribution API is read-only and machine credentials must not grant administrator mutation capability.

Expected response-state semantics are:

- active Profile + authorized credential + valid request: `200`;
- active Profile with no matching Articles: `200` with an empty item collection;
- malformed request or invalid cursor: `400`;
- missing/invalid machine authentication: `401`;
- authenticated credential without authorization for the requested Profile: `403`;
- nonexistent Profile: `404`;
- disabled Profile: an explicit machine-readable disabled-Profile error rather than disguising it as nonexistent;
- bounded dependency/service failure: `503`.

The exact HTTP status/code used for the disabled-Profile error may be finalized with the API/error contract, but the response must distinguish disabled state from missing Profile state for authorized clients.

Compatibility is version-bound. Within `/api/v1`, required fields and documented semantics may not be removed or incompatibly reinterpreted. Additive optional fields may be introduced when they preserve existing consumers. Breaking external contract changes require a new major API path such as `/api/v2` rather than silently changing v1 semantics.

The existing `GET /api/feed` remains a supported reference/legacy public-feed surface and is not redefined as this permanent integration API.
