## Phase 5 boundary that documentation must preserve

Phase 5 is the reusable generic PHP synchronization and last-known-good core against the stable v1 API. Current documentation may summarize this, but must not silently redesign it.

Phase 5 scope includes:

- PHP API client using bearer authentication;
- complete bounded Profile snapshot traversal through all cursors;
- validation of the v1 envelope, item/Profile schema, API version, and `snapshotRevision` consistency;
- bounded restart after `409 snapshot_changed` while preserving current active state;
- ETag / conditional initial synchronization where available;
- customer-configurable cadence with 15-minute default;
- per-Profile locking and overlap prevention;
- bounded retries respecting `Retry-After`;
- candidate state separate from active state;
- atomic activation only after a complete valid candidate;
- independent per-Profile LKG state and preservation of prior recoverable valid state where practical;
- no bearer credential inside cache payloads;
- freshness/staleness metadata and stale-valid-by-default behavior with optional maximum stale age;
- safe never-synced behavior;
- authenticated `409 profile_disabled` as authoritative local suppression state;
- later successful synchronization restoring re-enabled output;
- local operational sync/cache health.

Phase 5 does **not** own customer HTML, a customer-facing local data API, fallback renderer, customer-style website integration, or visitor-path rendering. Those remain Phase 6. Do not pull Phase 6 behavior forward merely because the distribution contract describes the full 2.0 PHP integration.
